Chapter six

6Today and the calendar

The hub. A month of dots, a streak, today's schedule, and four tiles that each carry their own week. Every number on it comes from one local table and one local cache, and every tap opens something rather than explaining something.

6.1Intent

Working backwards

Today opens on a grid of dots, one per day this month. Filled dots are days you hit your targets, hollow dots are misses, faint dots are days with no data, and today is orange. Under it sit your schedule for the day and the week ahead, drawn from the phone's calendar, then a streak, then four tiles: steps, sleep, weight, recovery, each with the last seven days as bars. Tap a dot and the day opens in full; tap a tile and the metric opens on a page of its own with a week, a month or a year behind it; tap the calendar icon and a month you can walk through opens.

What makes a dot fill?

Meeting 3 of 4 daily goals: steps 8,000, sleep 7h, exercise 30 min, water 2,500 ml. All five values are editable in Settings (Chapter 17). The rule is deliberately explicit; a vague definition makes the entire grid meaningless.

What happens on a day with no data at all?

It renders as no-data, not as a miss, and it is excluded from streak arithmetic entirely. Leaving your watch on the charger is not a moral failure, and a system that punishes it teaches you to distrust the streak. A day with some data is judged on what it has: if steps are logged at 500 and nothing else was recorded, that is a miss.

If I change a goal, does history change?

Yes. Status is computed on read, never stored, so past dots re-evaluate against the new target immediately. The grid answers "how am I doing against my current standard".

Where does the schedule come from?

From EventKit, through a local SwiftData cache. The permission prompt fires from the agenda card's own connect button, never at launch, and the phone's calendar app remains the source of truth: Almanac reads a window of 30 days back and 90 forward, writes go straight back to EventKit, and the cache is re-synced afterwards so it shows what the provider actually stored.

Why is there a separate month screen?

Today's month grid shows how the streak has been going and cannot leave the current month. The month screen answers the other question, what is on, across any month, with day numbers and up to three event dots per day. Two questions, two grids.

6.3Model

The hub's snapshot

// LIfeOS/Features/Today/Model/TodaySnapshot.swift
struct TodaySnapshot: Equatable {
    var date: Date = .now
    var cells: [DotCell] = []
    var streak: Int = 0

    var steps: Int?
    var stepsProgress: Double?
    var sleepMinutes: Int?
    var sleepProgress: Double?
    var weightKg: Double?
    var recoveryPct: Double?

    var stepsWeek: TrendSeries = TrendSeries(points: [])
    var sleepWeek: TrendSeries = TrendSeries(points: [])
    var weightWeek: TrendSeries = TrendSeries(points: [])
    var recoveryWeek: TrendSeries = TrendSeries(points: [])
    var stepsTarget: Double?
    var sleepTargetMinutes: Double?

    var calendarAccess: CalendarAccessState = .notDetermined
    var agenda: [CalendarEventSnapshot] = []
    var upcoming: [UpcomingEvent] = []
    var scheduledWorkoutTitle: String?

    var hasNoHealthData: Bool {
        steps == nil && sleepMinutes == nil && weightKg == nil && recoveryPct == nil
            && stepsWeek.points.isEmpty && sleepWeek.points.isEmpty
    }
}

Every metric is an optional, and each one that has a goal carries its progress alongside it, already divided. The view receives numbers it can render and nothing it has to interpret: it never sees a DailyMetrics, so rendering cannot fault a SwiftData object or trigger a fetch mid-layout. Two things are new since the previous edition. Each figure carries its week as a TrendSeries with a slot for every day, so a gap stays a gap in the chart rather than closing up. And hasNoHealthData exists because the app used to seed sixty days of invented history at first launch, so an empty hub was unreachable; now that the numbers are real, an unconnected day is the normal first thing a person sees and the screen has to offer a connection rather than a grid of dashes.

One metric, described once

// LIfeOS/Features/Today/Model/TodayMetric.swift
enum TodayMetric: String, Identifiable, Hashable, CaseIterable {
    case steps, sleep, weight, recovery

    var icon: String { ... }          // figure.walk, moon.fill, scalemass.fill, bolt.heart.fill
    var hue: ModuleHue { ... }        // activity, nutrition, body, recovery
    var unit: String? { ... }         // nil, nil, "kg", "%"
    var baseline: RoundedBarChart.Baseline { self == .weight ? .windowMinimum : .zero }
    var higherIsBetter: Bool { self != .weight }

    func value(in row: DailyMetrics) -> Double? { ... }
    func goal(in targets: GoalTargets) -> Double? { ... }
    func format(_ value: Double) -> String { ... }
}

The tile and the detail page used to be able to disagree: the grid decided steps were figure.walk in the activity hue, and a second screen would have decided again. Icon, hue, unit, formatting, the reading a row yields and the goal a day is judged against all live here once, and both surfaces read them. It also gives the navigation destination something to be: a value the stack can carry, rather than four booleans. Weight is the one exception that runs through everything. It is read against its own window rather than against nought, because it moves about a percent over a week and bars measured from zero would be indistinguishable, and it has no goal, because it is not a target to hit.

The calendar event, in three shapes

@Model public final class CalendarEvent { ... var sourceRaw: String ... var lastSyncedAt: Date }

The @Model is the cache row. The snapshot is what views and assistant tools receive, and Sendable is the point: a tool result crosses into an inference engine (Chapter 15), and a CalendarEvent cannot make that trip. The draft is what a caller supplies to create or edit, with no id and no source, because routing decides those. The natural key of a row is (source, sourceID); the local id never leaves the device. For a recurring occurrence the source id is qualified with the occurrence's start, because EventKit reuses one identifier across a whole series. A qualified id never resolves through event(withIdentifier:), so a write against an occurrence fails with unknownEvent instead of silently editing the wrong one, and the sheet refuses such writes before that can happen.

The day sheet and the metric page

DayDetailSnapshot is Identifiable on its date because .sheet(item:) presents it. It lists every habit that currently exists, done or not, deliberately not filtered by creation date, which is why the sheet's header is a count and never a grade: an old day can list a habit that did not exist then. MetricDetailSnapshot carries a MetricRange of week, month or year and a MetricBar per bucket. The grain is not a separate choice: a week is seven days, a month thirty days, a year twelve months, because a year drawn as 365 bars is a smear three points wide and a week drawn as one bar is not a chart.

6.4ViewModel

TodayViewModel.load(): one pass over the rows

// LIfeOS/Features/Today/ViewModel/TodayViewModel.swift
func load() {
    guard let context else { return }
    let store = MetricsStore(context: context, calendar: calendar)
    do {
        let targets = try store.goals().targets
        let start = calendar.date(byAdding: .day, value: -400, to: .now) ?? .distantPast
        let rows = try store.metrics(from: start, to: .now)      // most recent first

        var statusByDay: [Date: DayStatus] = [:]
        var ordered: [DayStatus] = []
        for row in rows {
            let status = evaluate(row.reading, against: targets)
            statusByDay[calendar.startOfDay(for: row.date)] = status
            ordered.append(status)
        }

        let cells = MonthGridLayout.cells(monthContaining: .now, calendar: calendar, today: .now,
            status: { date in
                switch statusByDay[calendar.startOfDay(for: date)] {
                case .onTarget: .onTarget
                case .missed:   .missed
                case .noData, nil: .noData
                }
            })

        var rowByDay: [Date: DailyMetrics] = [:]
        for row in rows { rowByDay[calendar.startOfDay(for: row.date)] = row }
        let week = TrendSeries.days(endingOn: .now, count: 7, calendar: calendar)
        func series(_ value: (DailyMetrics) -> Double?) -> TrendSeries {
            TrendSeries(points: week.map { day in
                TrendPoint(date: day, value: rowByDay[day].flatMap(value))
            })
        }
        ...
        snapshot = TodaySnapshot(... streak: currentStreak(statuses: ordered), ...)
        if let detail { select(detail.date) }
    } catch {
        assertionFailure("Today load failed: \(error)")
    }
}

Inside load(), in order:

  1. Read GoalTargets from the store, which materialises defaults on first access.
  2. Fetch four hundred days ending now, most-recent-first. Bounded on purpose: the grid needs this month and the streak needs recent history, never the whole table.
  3. evaluate each row once into a date-keyed dictionary. Rebuilding that map inside the per-day closure would re-evaluate every row about thirty times per load.
  4. Ask MonthGridLayout for the cells, mapping DayStatus to DotState here because Persistence must not depend on DesignSystem.
  5. Compute currentStreak from the same ordered statuses.
  6. Build the four week series from the rows already in hand: a second dictionary and seven lookups per metric rather than a second query. The rows stay inside this method; only plain numbers reach the snapshot.
  7. Read today's agenda and the next seven days from CalendarStore, two windowed fetches.
  8. Read the title of any workout scheduled for today from the bookmark store and the catalog cache (Chapter 10). Two reads rather than a relationship: the catalog is a cache the next refresh can drop a row from, so a schedule pointing at a vanished video simply shows nothing.
  9. Publish one TodaySnapshot. A single assignment means a single render.
  10. If the day sheet is open, re-derive it, so an external write, a WHOOP sync or a habit tick, updates the sheet as well as the grid behind it.

A read failure trips an assertionFailure and leaves the previous snapshot in place rather than blanking the screen. Nothing about a failed local fetch is recoverable by the user, so the last good state is the most useful thing to keep showing.

select(date) builds the day sheet from three stores: the metrics row for that day, the habit ticks on it, and the events overlapping it. A day with no metrics row is not an early return; its habits are still worth showing and the metric rows render as blanks. toggleHabit writes through PlanStore and then does nothing else: the save fires ModelContext.didSave, RootView reloads every view model, and load() re-derives the open sheet. That is the one refresh path; calling select() again here would repeat the 400-day pass a second time per tap.

MetricDetailViewModel: its own object, on purpose

A view model of its own rather than more fields on TodayViewModel, because that one runs a 400-day pass on every save in the app, and hanging a year of bucketing off it would repeat that work for a screen nobody is looking at. load(metric) makes one fetch bounded by the range, then buckets in memory: 

// LIfeOS/Features/Today/ViewModel/MetricDetailViewModel.swift
let buckets = Self.buckets(range: range, endingOn: now, calendar: calendar)
guard let start = buckets.first else { return }
let rows = try store.metrics(from: start, to: now)     // one fetch, not one per bucket

var readingsByBucket: [Date: [Double]] = [:]
for row in rows {
    guard let value = metric.value(in: row),
          let bucket = Self.bucket(for: row.date, range: range, calendar: calendar)
    else { continue }
    readingsByBucket[bucket, default: []].append(value)
}
let bars = buckets.map { bucket in
    MetricBar(date: bucket,
              label: Self.label(for: bucket, range: range, calendar: calendar),
              value: readingsByBucket[bucket].map { $0.reduce(0, +) / Double($0.count) })
}

Every bucket is present whether or not it has a reading, for the same reason TrendSeries.days keeps gaps: compacting the buckets that do have readings draws a chart whose neighbouring bars are not a bucket apart, which is a quieter lie than a false zero but a lie. A day has at most one row, so the mean is that row's own value in the two short windows; it only averages anything in the year view, where a bucket is a month. The month view labels one bar in five, because thirty labelled bars on a phone is a grey smudge. The headline figure is the most recent actual reading in the window, which is usually but not always today: a night's sleep or a recovery score can be a day behind, and the year view's monthly aggregate must never replace it.

MonthViewModel: one fetch per month

The month screen fetches the visible month padded by a week either side, then groups with CalendarDayIndex.group so a cell asks a dictionary rather than the store. A month is up to 42 cells and every one wants a count; one fetch, not one per cell. The padding is what makes the leading and trailing cells answerable, since the first row of a month usually starts in the previous one. Stepping remembers the day number the person last picked separately from the selection, so walking from 31 March to February and back returns to the 31st rather than the 28th; MonthGridLayout.stepping clamps only for display.

The screen takes a value and a set of intents and owns nothing: no view model, no store, no context. Every tap names what was tapped and stops there. What a day opens, what a metric opens, whether the permission sheet fires, are all the shell's decisions, which is what keeps this a pure function of its inputs and a preview a single literal.

One column or two

On a phone the order is month, scheduled workout, agenda, streak, health prompt, stat grid, with layout.statColumns deciding whether tiles are one or two across. On a wide pane the month, workout, agenda and streak stand in a left column capped at 520 points, and the stats stand beside them two across. The cap is the point, not merely a column count: a dot grid divides whatever width it is given by seven, so a full-width month on a 1300 point pane draws 170 point dots and shoves every stat below the fold, the opposite of what more room should buy. There is no maxContentWidth on this screen, because both arrangements are grids and the cap exists for prose.

The pieces

  • MonthCalendarView composes DateHeadline (the day numeral at masthead size), WeekdayHeader (narrow symbols rotated to the calendar's first weekday, today's column accented) and DotGrid. Cells arrive already computed; deriving them in a body would re-run the calendar maths on every render.
  • AgendaCard always renders, because it carries the three permission states. Not determined shows "Connect calendar", denied shows "Open Settings", authorised shows up to four rows grouped by DayPart (all day, morning, afternoon, evening, each with its own icon and pastel) and a "+N more" that opens the day sheet. Upcoming is a second card, shown only with access and something to show, five rows grouped by day label. Rows are capped before grouping so the card's height budget stays the same whatever shape the day has.
  • TrendStatTile is the tile with the week: label, pastel icon bubble, the numeral, and a RoundedBarChart of seven bars at 74 points on a phone and 88 on a wide pane. A week with no readings draws the plain figure and still holds the chart's height, so a dataless tile stands as tall as its siblings. Every tile is a plain button into MetricDetailScreen, built from TodayMetric.allCases rather than written out four times.
  • The health prompt appears only when there is nothing to show and nothing attached. A connected strap that has not synced yet is a different situation, and telling that person to connect something would be wrong.
  • The scheduled workout card is informational: the library is where a workout is played, and a card that opened a video would put the player two taps from a calendar grid.

The sheets

DayDetailSheet renders past days as history with static marks and gives only today controls, so the grid can never be rewritten after the fact. A not-done habit on a past day is a dash rather than a cross, because the list may include habits that did not exist that day and a cross would read as a verdict the sheet has no standing to make. A missing metric renders as a dash rather than hiding the row, so the sheet's height does not jump between days.

EventSheet is a pure function of its EventSheetPresentation, create or edit. Every write goes out through onSave and onDelete, which is what keeps it previewable without EventKit. A recurring occurrence renders read-only, fields disabled, Save and Delete hidden, with "This repeats. Edit the series in your calendar app." Editing one occurrence needs series semantics the app does not implement, and pointing at the calendar app is honest where silently mutating the occurrence would not be. The end date is clamped on save rather than blocked: a timed event floors at fifteen minutes after its start, an all-day event only at its start, since end equals start is the normal single-day shape. A new event defaults to the next full hour today, or 9am on any other day, because "next Tuesday at 16:41" is nobody's intent.

MonthScreen carries a swipe gesture on the grid to step months, chevrons for anyone who would rather aim than swipe, a date jump sheet, and a "Today" button disabled while today is selected. On a wide enough pane ViewThatFits puts the 400 point calendar panel and the agenda side by side. It never writes: create and edit leave through the caller, which owns CalendarSync, and it re-reads on ModelContext.didSave so a write from the sheet it opened lands in its dots.

The quick log and the journal

QuickLogSheet logs water and weight, the two metrics with no automatic source, and is now reached from inside Begin Activity rather than from a bar button. Water accumulates: "add 250 ml" is the intent, not "today's total is 250 ml". JournalEntrySheet is a bare text editor with no title and no fields, because asking for either is friction on the one thing that has to stay effortless.

6.6How it works

The calendar pipeline

  1. RootView.syncCalendar() runs on the launch task, on every scene activation, and after any calendar write. It does nothing unless CalendarAccessState.current is .authorized, which requires both the system permission and the per-account opt-in flag: a device permission granted for one Almanac account does not authorise another.
  2. CalendarSync.sync() asks each source whether it is authorised, fetches the window from those that are, and skips any that throw. Partial data beats an empty screen, and errors are not surfaced because sync is ambient, never a user-visible request.
  3. CalendarMerge.merge dedups across sources on lowercased title plus start date, EventKit winning because that copy is writable offline and is what the OS shows elsewhere. Google is the second source the protocol is shaped for; today only EventKit is wired.
  4. CalendarStore.apply reconciles the fetch into the cache by natural key: an existing row is updated in place and keeps its local id, a new one adopts the snapshot's, and in-window rows absent from the fetch are deleted only when their source was authoritative this pass. Rows outside the window are never touched.
  5. The save fires didSave and the hub's agenda repaints.

Writes go the other way. EventSheet hands a draft to RootView, which calls calendarSync.create, update or delete. Sync routes the write to the source that owns the event, and then runs a full sync() so the cache reflects what the provider actually stored. Providers normalise all-day handling and time zones, so trusting the local draft would drift.

Keeping today's numbers moving

A step count climbs until midnight, and a sync at breakfast is stale by lunch. Two mechanisms keep the tiles honest while the app is open. HealthSyncWindow.days(since:) decides which days a sync re-reads: always today, plus the day of the last sync and every day since, because a night's sleep is recorded against the morning it ends and the day already covered can still gain a value. A first sync backfills thirty days, the month the dot grid shows, and no further, because Health keeps the data regardless and a longer backfill can be added the day something needs it. A last-sync stamp from the future is treated as a clock change and syncs today alone.

Then HealthConnectionViewModel.startWatching() runs an HKObserverQuery per metric for as long as the app is in front. Each change re-runs the sync, then sleeps fifteen seconds; the stream buffers one event, so a day's steps arriving in dozens of batches becomes one re-read per quarter minute rather than one per batch. The observers are torn down when the app leaves the foreground, so a phone in a pocket is not running ten queries a quarter minute. The sync writes through MetricsStore, the save reloads the hub, and the numeral moves. Nothing in the watcher knows about a screen.

6.7Performance and cost

  • Bounded fetches. The hub reads 400 days; the metric page reads only its range; the month screen reads one month plus a week either side; the agenda reads one day and the next seven. Nothing reads the whole table.
  • Evaluate once, look up many times. Status and rows are keyed by day in two dictionaries with reserved capacity; the grid, the streak and the four week series are all lookups against them.
  • Bucket in memory, not in the store. The year view is one fetch and a dictionary, not twelve round trips.
  • Reload only what is on screen. reloadAll() reloads the metric page only while it is pushed, and the money detail only while it is open.
  • Event-driven, never polled. The single didSave subscription in RootView is the whole refresh mechanism; the Health observer stream is throttled to one re-read per fifteen seconds and stopped in the background.
  • One assignment, one render. The snapshot is built whole and assigned once; no intermediate state is published mid-load.
  • The chart maths is pure and static. RoundedBarChart.fraction and MonthGridLayout.cells take values and return values, so they are tested from the terminal and never recomputed inside a body.
  • The cache means the calendar works on a plane. Reads never touch EventKit directly; a sync that fails leaves the previous rows in place.
  • Nothing leaves the device. Calendar contents and the day sheet stay local. What an escalated assistant turn sends is described in Chapter 15 and Chapter 24.

Tests

  • GoalEvaluationTests and StreakTests: three of four is on target, two is a miss, exactly at goal counts, partial data is judged not excused, no-data days are skipped without breaking the streak.
  • MonthGridLayoutTests (eleven tests): August 2026 starts with five blanks, a Sunday-first month takes six, today overrides its status, days after today are future, stepping keeps the day number, clamps to a short month, reaches a leap 29th, and crosses a year boundary backwards.
  • TrendSeriesTests and RoundedBarChartTests: the average ignores gaps, the latest reading is not the last slot, a lone reading has no delta, points keep their gaps, the window minimum baseline spreads a metric that never nears zero, a flat week draws half bars.
  • CalendarStoreTests: applying the same fetch twice does not duplicate, an existing row keeps its local id, in-window rows absent from a fetch are deleted, out-of-window rows survive, pruning only touches authoritative sources.
  • CalendarSyncTests: a throwing source does not block the others and keeps its previously synced events, an unauthorised source is skipped, create dispatches to the first authorised source and resyncs, update routes to the owner.
  • CalendarMergeTests, CalendarFreeSlotTests, CalendarDayIndexTests: the dedup rule, gap subtraction with all-day events not blocking time, and overnight and daylight-saving spans.
  • HealthSyncWindowTests (eight tests): a first sync backfills a month, today is always included, a recent sync only re-reads today, a gap is backfilled including the day before it, a future stamp still syncs today.
The one test that matters most For every screen, an empty store must produce a snapshot whose readings are all nil. The hub, the metric page and the day sheet all obey it by construction: each optional is filled from a row that may not exist, and there is no default of zero anywhere in the path.

Read in this order

  1. Features/Today/ViewModel/TodayViewModel.swift: load() top to bottom.
  2. LifeOSKit/Sources/DesignSystem/MonthGridLayout.swift: the padding and the today/future rule.
  3. Features/Today/Model/TodayMetric.swift: why one enum describes both the tile and the page.
  4. Features/Today/ViewModel/MetricDetailViewModel.swift: the bucketing.
  5. LifeOSKit/Sources/Persistence/CalendarStore.swift: apply() and freeSlots().

  7. LifeOSKit/Sources/Integrations/HealthSyncWindow.swift, then HealthConnectionViewModel.startWatching().

Check yourself

  • Why is the status map built before the grid closure and not inside it? The closure runs once per cell; building the map inside it would evaluate every row about thirty times per load.
  • Why do the week series reuse the 400-day rows? The rows are already in hand for the streak, so the week costs a dictionary and seven lookups rather than a second query.
  • What happens to a cached event whose source threw during sync? Nothing. Pruning only applies to sources that answered this pass, so the row survives.
  • Why is a recurring event's source id qualified with its start? EventKit shares one identifier across a series; qualifying it makes each occurrence a distinct cache row and makes accidental writes fail loudly.
  • Why does the metric page have its own view model? Because the hub reloads on every save in the app, and a year of bucketing must not ride along for a screen nobody is looking at.
  • Why does a Health sync re-read the day of the last sync as well as today? Sleep is attributed to the morning it ends, so a day already read can gain a value afterwards.
