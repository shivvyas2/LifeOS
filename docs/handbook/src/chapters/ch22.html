Chapter twenty-two

22Production edge cases

The register below is the difference between a demo and something you can rely on. Each row is a condition that will occur in normal use, not a theoretical one, and each names where in the code or the test suite the behaviour is pinned. The feature chapters cross-reference the rows that apply to them.

22.1How to read this register

Three columns. Condition is what happens in the world. Behaviour is what the app does about it, in the present tense, because every row here describes code on disk today. Pinned by names the test, native check or pure function that holds the behaviour in place, so that a future edit which changes it fails somewhere visible. A row marked by design has no test because the behaviour is structural: a type that cannot cross a boundary, a table with no policies. A row marked hardware is unverified in the simulator and waits on a physical device; those are listed again in Appendix A.

Two themes recur. The first is the rule from 21.1: absence is never zero, and a screen with no data shows its designed empty state rather than a number nobody earned. The second is that destructive outcomes, signing someone out, moving a sync cursor, replacing a cache, happen only on a definitive answer from the server and never on a transport failure, a rate limit or an empty response that is more likely a bug than a fact.

22.17Study notes

Read in this order

  1. LifeOSKit/Sources/Integrations/SessionRefresh.swift, the clearest statement of "destroy only on a definitive refusal".
  2. SyncStalenessPolicy.swift and SessionKeepAlive.swift, two pure clocks.
  3. MetricArbiter.swift and MetricSource.swift, then the tests beside them.
  4. PlaidSync.swift, for store-then-move-cursor.
  5. supabase/functions/lifo-agent/index.ts, for every failure path a cloud call has.
  6. supabase/functions/_shared/nudge.ts and apns.ts, for the fallback and collapse rules.
  7. LIfeOS/Features/Activity/ViewModel/ActivityRecorderChecks.swift, the native checks that stand in for tests.
  8. docs/design/watch-companion/report.md, for what is still unverified.

Check yourself

  • Which HTTP statuses sign a person out, and why not 429? 400, 401, 403 and 422 are the server refusing the credential; 429 and 5xx are the server failing to answer.
  • Why does the Plaid cursor live in UserDefaults and not the Keychain? The Keychain survives a reinstall and the database does not; a surviving cursor would replay nothing into an empty app.
  • What happens to an empty catalog response? The cache is kept; an empty answer is believed only when there was nothing to lose.
  • Why is a refused model reply still debited? It consumed real tokens; an unmetered path would let off-topic questions burn budget for free.
  • How can two cron runs not double-send? The log insert precedes the send and the primary key makes the second insert conflict.
  • What does a watch hand-off do when Health saving is off? It is never offered; the watch writes to Health, so the phone keeps the session.
