Chapter eighteen

18Widgets, Live Activities and notifications

Three surfaces outside the app: a Home and Lock Screen widget with a Watch complication behind it, a Live Activity and Dynamic Island for a running session, and a push channel that lets LIFO speak first. All three share one rule: the surface is handed a small, credential-free value and never a store, and every value is owned by exactly one account.

18.1Intent

Working backwards

Put "Your day" on the Home Screen and it shows steps against the goal, sleep and movement, refreshed after Almanac syncs and blanked after six hours or at midnight, whichever comes first. Add the circular complication to a watch face and the step gauge is there. Begin an activity and the Lock Screen carries a blue card with the timer, heart rate zone, estimated effort, calories and battery; the Dynamic Island shows the heart rate and the timer, and the zone number when minimal. Once a day, at eight in the morning your time, LIFO may send one sentence about your sleep, your steps or a streak; tap it and the conversation opens on that sentence. A notification inbox in the profile keeps the last hundred.

What does a widget actually get?

A SurfaceSnapshot: an owner id, when it was generated, when it expires, and four numbers. No token, no store, no rows. It is written as one encoded value into the App Group, so a reader can never join fields from two accounts.

Why does it expire?

Because a widget that shows yesterday's steps as today's is worse than one that says "Open Almanac to sync". Six hours is long enough to be useful between launches and short enough that a stale number does not survive a night. The timeline carries an explicit expiry entry so the blanking happens even when WidgetKit delays a refresh.

Why is the Live Activity throttled?

The heart-rate sensor streams every second and ActivityKit has an update budget. The lock screen does not need a new frame per beat; it needs one when something meaningful changed. A pure LiveActivityThrottle decides, and the timer ticks itself through Text(timerInterval:) without any update at all.

Who decides whether to send a nudge?

The server, as a pure function with tests. The device's whole job is to be reachable, to say which time zone eight in the morning is in, and to open on what arrived. The numbers are not in the payload: a phone that has been offline for days re-evaluates locally rather than opening on figures two days stale.

AppSurfaces is its own package target with no dependencies because three processes import it: the app, the widget extension and the watch app. It holds value types and pure functions only, so nothing about a store, a keychain or a network client can leak into an extension that must stay small and must launch cold in a few milliseconds.

18.3Model

The snapshot the widget reads

// LifeOSKit/Sources/AppSurfaces/SurfaceSnapshot.swift
public struct SurfaceSnapshot: Codable, Equatable, Sendable {
    public static let appGroup = "group.com.shivvyas.lifeos"
    public static let storageKey = "surface.snapshot.v1"
    public var ownerID: String?
    public var generatedAt: Date
    public var expiresAt: Date
    public var measuredAt: Date?
    public var steps: Int?
    public var stepGoal: Int
    public var sleepMinutes: Int?
    public var exerciseMinutes: Int?

    public init(ownerID: String? = nil, generatedAt: Date = .now, measuredAt: Date? = nil,
                steps: Int? = nil, stepGoal: Int = 8000, sleepMinutes: Int? = nil,
                exerciseMinutes: Int? = nil, calendar: Calendar = .current) {
        ...
        let midnight = calendar.date(byAdding: .day, value: 1, to: calendar.startOfDay(for: generatedAt))!
        expiresAt = min(midnight, generatedAt.addingTimeInterval(6 * 3600))
        self.steps = steps.flatMap { $0 >= 0 ? $0 : nil }
        self.stepGoal = max(1, stepGoal)
        ...
    }

    public func isAvailable(at date: Date = .now) -> Bool {
        ownerID != nil && date >= generatedAt.addingTimeInterval(-60) && date < expiresAt
    }
    public func supersedes(_ previous: Self?) -> Bool {
        previous.map { generatedAt > $0.generatedAt } ?? true
    }
}

The initialiser is where the rules live. A negative reading becomes nil rather than a lie, a goal of zero becomes one so progress can never divide by nothing, and the expiry is the earlier of midnight and six hours. A snapshot with no owner is a tombstone: it is what sign-out writes, and it is never available. supersedes exists because WatchConnectivity can deliver a queued older application context after a newer reply, and the watch must not replace a fresh value with a stale one. 

// LifeOSKit/Sources/AppSurfaces/SurfaceSnapshot.swift
public enum SurfaceRoute: String, CaseIterable, Sendable {
    case today, health, activity, notifications
    public var url: URL { URL(string: "almanac://\(rawValue)")! }
    public init?(url: URL) {
        guard url.scheme == "almanac", url.user == nil, url.password == nil,
              url.port == nil, url.path.isEmpty, url.query == nil, url.fragment == nil,
              let host = url.host, let route = Self(rawValue: host) else { return nil }
        self = route
    }
}

Routes are the four places a widget tap can land. The parser accepts exactly almanac://host and nothing else: no path, no query, no credentials, no port. That is deliberate, because the same scheme carries OAuth callbacks, and a widget URL must never be mistaken for one.

The readout the Live Activity renders

// LifeOSKit/Sources/AppSurfaces/LiveSessionReadout.swift
public struct LiveSessionReadout: Codable, Hashable, Sendable {
    public var elapsed: TimeInterval
    public var runningSince: Date?       // nil while paused
    public var heartRate: Int?
    public var zone: Int?
    public var effort: Double?           // WHOOP's 0 to 21 scale, rounded to a tenth
    public var calories: Int?
    public var distanceMeters: Int?
    public var batteryPercent: Int?
    public var capacitySource: String?   // "whoop" or "health"
    public var ceilingMaxZone: Int?
    public var ceilingTarget: ClosedRange<Double>?
    public var reps: Int?
    public var setIndex: Int?
    public var push: PushState

    public var timerAnchor: Date? { runningSince?.addingTimeInterval(-elapsed) }
    public var isPaused: Bool { runningSince == nil }
}

This is the one value every live surface renders: the in-app HUD, the lock screen and the Dynamic Island. Every reading is optional because a missing sensor is not a zero. WorkoutActivityAttributes.ContentState is this very type, so the app and the extension cannot disagree about its shape. timerAnchor is the trick that makes the timer free: Text(timerInterval: anchor...distantFuture) lets the system tick the clock itself, so an activity update is needed only when a reading changes, never per second. PushState carries its own headline, "Easy going", "On track", "Near your limit", "Over your target", so the words never drift between surfaces. 

// LifeOSKit/Sources/AppSurfaces/LiveSessionReadout.swift
public enum LiveActivityThrottle {
    public static let heartRateStep = 3
    public static let floor: TimeInterval = 10
    public static let readingInterval: TimeInterval = 3

    public static func shouldPublish(previous: LiveSessionReadout?, next: LiveSessionReadout,
                                     lastPublishedAt: Date?, now: Date) -> Bool {
        guard let previous, let lastPublishedAt else { return true }
        if previous == next { return false }
        if previous.isPaused != next.isPaused { return true }
        if previous.push != next.push { return true }
        if previous.reps != next.reps { return true }
        switch (previous.heartRate, next.heartRate) {
        case let (old?, new?) where abs(old - new) >= heartRateStep:
            return now.timeIntervalSince(lastPublishedAt) >= readingInterval
        case (nil, .some), (.some, nil):
            return now.timeIntervalSince(lastPublishedAt) >= readingInterval
        default: break
        }
        return now.timeIntervalSince(lastPublishedAt) >= floor
    }
}

Read it as a ranking of what deserves a frame. A pause, a push-state change or a rep always publishes at once. A heart rate that moved three beats or more, or appeared or vanished, publishes if three seconds have passed. Anything smaller waits ten. An identical readout never publishes. Because it is a pure function it is pinned by tests instead of thumbs on a device.

The inbox entry and the nudge

// LifeOSKit/Sources/AppSurfaces/InboxEntry.swift
public struct InboxEntry: Codable, Equatable, Identifiable, Sendable {
    public let id: String                 // "\(day)|\(trigger)"
    public let ownerID: String
    public let text: String
    public let trigger: String
    public let day: String
    public let receivedAt: Date
    public var isRead: Bool

    public static func inserting(_ entry: Self, into entries: [Self], ownerID: String) -> [Self] {
        guard entry.ownerID == ownerID else { return entries.filter { $0.ownerID == ownerID } }
        var result = entries.filter { $0.ownerID == ownerID }
        if !result.contains(where: { $0.id == entry.id }) { result.append(entry) }
        return Array(result.sorted { $0.receivedAt > $1.receivedAt }.prefix(100))
    }
}

The id is the day plus the trigger, which is exactly the uniqueness the server enforces in nudge_log, so a notification delivered twice, once as a banner and once as a tap-through, is one row. inserting filters to the owner, deduplicates, keeps existing read state, and caps at a hundred. NudgePayload, in Integrations, is the same three fields parsed out of a notification's userInfo, and it returns nil rather than throwing for a notification that is not ours: something to ignore, not something to report.

18.4ViewModel

SurfaceCoordinator: one writer for the App Group

// LIfeOS/App/Surfaces/SurfaceCoordinator.swift
func publish() {
    guard let ownerID, let context, sharingEnabled else { return }
    let store = MetricsStore(context: context)
    let now = Date.now
    let row = try? store.metrics(from: now, to: now).first
    let goals = try? context.fetch(FetchDescriptor<UserGoals>()).first
    let next = SurfaceSnapshot(ownerID: ownerID, measuredAt: row?.updatedAt,
        steps: row?.steps, stepGoal: goals?.stepsGoal ?? 8000,
        sleepMinutes: row?.sleepMinutes, exerciseMinutes: row?.exerciseMinutes)
    // Coalesce saves unrelated to health. Still renew the Watch lease hourly.
    if let previous = snapshot, previous.ownerID == next.ownerID,
       previous.steps == next.steps, previous.sleepMinutes == next.sleepMinutes,
       previous.exerciseMinutes == next.exerciseMinutes, previous.stepGoal == next.stepGoal,
       previous.measuredAt == next.measuredAt,
       next.generatedAt.timeIntervalSince(previous.generatedAt) < 3600 { return }
    write(next)
}

publish() is called from RootView.reloadAll(), which means on every save in the app. Most saves are notes, money or a habit tick, and none of those change the four numbers, so the coalescing guard is what stops a widget reload and a watch transfer per keystroke. The hour limit is the exception: even with nothing changed, the snapshot is rewritten hourly so its expiry keeps moving and the watch's copy stays fresh. write stores the value, asks WidgetKit to reload every timeline, and sends the same bytes to the watch as an application context (queued, survives the watch being asleep) and, if it is reachable, as a message.

adopt(ownerID:context:) is called by AccountSession whenever a store is opened. If the snapshot on disk belongs to a different owner, or there is no owner, or sharing is off, a tombstone is written before anything else, so the next account starts with missing readings and never with the previous account's values. sharingEnabled is the toggle on the Widgets & Watch page; turning it off writes the tombstone at once.

WorkoutLiveActivityController

// LIfeOS/App/Surfaces/WorkoutLiveActivityController.swift
func sync(_ readout: LiveSessionReadout, timer: ActivitySessionState, icon: String) {
    guard timer.phase != .finished else { end(); return }
    if current == nil {
        current = Activity<WorkoutActivityAttributes>.activities.first { $0.attributes.sessionID == timer.id }
    }
    let now = Date.now
    guard current == nil || LiveActivityThrottle.shouldPublish(previous: lastState, next: readout,
                                                               lastPublishedAt: lastPublishedAt, now: now) else { return }
    lastState = readout; lastPublishedAt = now
    let content = ActivityContent(state: readout, staleDate: now.addingTimeInterval(8 * 3600))
    if let current {
        let preceding = updates
        updates = Task { await preceding?.value; await current.update(content) }
    } else if ActivityAuthorizationInfo().areActivitiesEnabled {
        current = try? Activity.request(attributes: WorkoutActivityAttributes(sessionID: timer.id,
            name: timer.activity, icon: icon), content: content, pushType: nil)
    }
}

The recorder calls sync on every state change and every reading; the controller decides whether that becomes an ActivityKit call. Three details carry weight. The activity is keyed on the session id, so a relaunch, or a session the watch started whose card was requested before the phone's timer existed, adopts the activity already on screen rather than orphaning it. Updates are chained through a single Task so they land in order. And the stale date is eight hours out, which means a phone that dies mid-run leaves a card that the system will eventually grey rather than one that claims a heart rate forever. endAll() is called on every account change and sign-out so no session card outlives its owner.

PushService: registration and the inbox in one object

One object rather than two because the two halves share the state that matters: the device token. It arrives asynchronously from the system long after the sign-in that asked for it, and it is needed again at sign-out to delete the row. The service keeps the token in UserDefaults.standard (it belongs to the phone), and everything else per account.

  • Asks late, on purpose. requestAuthorization() is called from the inbox screen's button, never at launch. A permission prompt on first run, before the app has shown anyone anything worth being interrupted about, is the fastest way to a permanent no. A denied status short-circuits: registering anyway would silently succeed and produce a token that can never deliver anything.
  • Registers on every foreground. syncRegistration() upserts the token, the account id and the current time zone. The zone is what the send hour is read in, so somebody who has flown somewhere would otherwise keep being nudged at eight in the morning where they used to live. The row is keyed on the token, so a second account on the same device replaces the first account's row in one upsert.
  • Deregisters before the session goes. AppShell's sign-out captures the outgoing access token by value and deletes the row with it, because the delete needs the token of the account whose row it is, and the keychain is cleared a line later. Left behind, that row would push one person's sleep onto a phone showing somebody else's name.
  • Attaches per account. attach(ownerID:) re-reads the inbox from that account's defaults suite and clears any pending route if the owner changed. receive refuses an entry whose owner is not the attached account, and refuses an id the person has already cleared, so a delayed duplicate cannot resurrect a dismissed check-in.
  • Reads back what the system already delivered. refreshInbox() walks deliveredNotifications(), so a notification that arrived while the app was dead, and was never tapped, still lands in the inbox on the next open.

18.5View

The widget, in every family

HealthTimeline produces two entries: the snapshot now, and, if it has not already expired, a nil entry at its expiry. The policy asks for a refresh after thirty minutes. The view switches on the family. The inline accessory is a label of steps and sleep. The circular accessory is a Gauge of step progress. The rectangular accessory is the wordmark, the two figures and "Updated 7:41". The small home widget is the step numeral at 34 points against the goal with a progress bar; medium adds sleep and a movement line; large and extra large add a movement tile and a "Begin activity" link that deep-links to almanac://activity. Every figure is privacySensitive(), so a locked phone redacts it. The empty state is one sentence per family and never a zero. BeginActivityWidget is a second, accessory-only widget whose whole job is the deep link. The watch bundle ships the same HealthWidget with only the accessory families, and the watch canvas is plain black.

The Live Activity

Widget extensions cannot render materials, so the "glass" tiles on the lock screen card are translucent white at 18 percent over the live gradient with a half-point hairline. The card is the activity's icon and name, the push headline in the push tint, the timer at title size, then four tiles: heart rate with the zone as eyebrow, effort with "of 18" as unit once there is a reading, calories or, in a strength session, the set and reps, and battery with a tiny ring. The Dynamic Island's expanded view puts the name leading, the timer trailing, and four readings across the bottom with an "Open activity" link. Compact shows a heart and the beats per minute leading and either the timer or the reps trailing. Minimal is the zone number in a circle of the push tint, or a pause glyph. keylineTint follows the push state, so the island's outline goes green, amber or red with the person's effort. Every text field is privacySensitive().

The inbox and the settings page

NotificationInboxScreen is reached from the bell on the profile and from Settings. It shows the permission card first ("Enable notifications" when never asked, "Notification settings" otherwise), then either "You're all caught up" or the unread count, a "Read all" button, one panel per entry, and "Clear read notifications". Tapping an entry marks it read and opens a full-screen LifoCoachScreen seeded with the sentence, so the notification is an opening line rather than a reminder (Chapter 14). The screen refreshes from delivered notifications on appear and on every return to the foreground. SurfaceSettingsScreen is the Widgets & Watch page: the sharing toggle and four short guides for adding the widgets, the complication and the activity timer.

18.6How it works

The widget path

  1. A save anywhere fires ModelContext.didSave; RootView.reloadAll() calls SurfaceCoordinator.shared.publish() first.
  2. publish() reads today's row and the goals, builds a snapshot, and returns early unless one of the four numbers, the goal, or the measured time changed, or an hour has passed.
  3. write() encodes the snapshot into the App Group defaults under one key, reloads every WidgetKit timeline, and sends the bytes to the watch.
  4. The widget's timeline provider decodes it on the next reload, renders it if isAvailable, and schedules its own blank entry at expiresAt.
  5. The watch app decodes the context or message, keeps it only if it supersedes the copy it holds, writes it to its own App Group and reloads its complication. Its dashboard redraws on a sixty-second TimelineView, so the expiry takes effect without a message.

The Live Activity path

  1. The recorder rebuilds its readout on every state change (persist()) and every sensor reading (persistReading(at:)), then calls syncLiveActivity(). The draft is written at most every ten seconds; the readout is refreshed every time.
  2. The controller either finds the activity for this session id, or asks LiveActivityThrottle whether the change deserves an update, or requests a new activity if the person has them enabled.
  3. On finish, discard, account change or sign-out the activity is ended immediately. endStrayLiveActivities() removes any card that belongs to a different session id, because only one activity belongs on screen.

The nudge path

  1. Once an hour, pg_cron calls lifo-nudge. The job selects the rows in device_tokens whose local hour is eight, evaluates the triggers over the account's rows, claims the day in nudge_log, phrases one sentence, and sends it through APNs with a collapse id so a phone that was off for three days gets today's nudge rather than three, and a twelve-hour expiry so a morning observation never turns up stale (Chapter 20).
  2. PushDelegate.willPresent hands the notification to PushService.receive. A nudge that arrives while the app is open is still shown as a banner, because suppressing it would drop the message entirely; nothing else surfaces it.
  3. PushDelegate.didReceive is the tap. The entry is marked read and pending is set to the payload.
  4. RootView watches pending and, on the launch task and every foreground, checks it directly too, because a notification tapped from a cold launch lands before the view exists and onChange never fires for it. openNudge clears it, seeds the coach with the sentence, and presents LIFO, deferring behind any open profile or inbox cover.

18.7Performance and cost

  • A widget launch reads one defaults key. No store is opened in the extension; AppSurfaces has no dependencies, so the extension links almost nothing.
  • Publishes are coalesced. Saves unrelated to health cost no widget reload and no watch transfer; only a changed number or the hourly lease renewal does.
  • Timelines refresh themselves. Two entries and a thirty-minute policy; the blanking at expiry costs no process wake at all.
  • The timer is free. Text(timerInterval:) ticks in the widget process; an ActivityKit update is spent only on a meaningful change, and the throttle's floor of ten seconds keeps a jittery sensor from burning the budget.
  • The watch gets bytes, not rows. An application context is a few hundred bytes and is delivered whenever the watch next wakes.
  • APNs costs nothing per send, and the job sends at most once a day per person. The unique key on nudge_log is claimed before any model call, so an overlapping cron run cannot double-spend the phrasing.
  • Silence is the common path. Most hourly runs evaluate triggers and send nothing, which costs a query and no inference.
  • Dead tokens are pruned. An "unregistered" answer from Apple deletes the row, so the job does not push at a wiped phone forever.
  • The inbox is capped at a hundred, and cleared ids at two hundred.

Read in this order

  1. LifeOSKit/Sources/AppSurfaces/SurfaceSnapshot.swift: the initialiser's rules and SurfaceRoute.
  2. App/Surfaces/SurfaceCoordinator.swift: adopt, publish, write.
  3. AlmanacWidgets/HealthWidget.swift: the timeline's two entries.
  4. LifeOSKit/Sources/AppSurfaces/LiveSessionReadout.swift: the throttle.
  5. App/Surfaces/WorkoutLiveActivityController.swift, then ActivityRecorder.syncLiveActivity and endStrayLiveActivities.
  6. AlmanacWidgets/WorkoutLiveActivity.swift: which region shows what.
  7. App/PushService.swift: attach, receive, syncRegistration, then PushDelegate.
  8. App/RootView.swift: openNudge and the three places it is called.

Check yourself

  • Why is the snapshot one encoded value under one key rather than four keys? So a reader can never join fields from two accounts; a tombstone replaces everything at once.
  • What does publish() do on a notes save? Builds a snapshot, sees nothing changed within the hour, and returns without writing, reloading or sending.
  • Why does the Live Activity need no update per second? The readout carries timerAnchor, and Text(timerInterval:) ticks in the widget process.
  • What always publishes regardless of timing? A pause or resume, a push-state change, and a rep.
  • Why are the nudge's numbers absent from the payload? A phone offline for days would open on stale figures; the tap-through re-evaluates locally.
  • Why is the push row deleted before the keychain is cleared at sign-out? The delete needs the outgoing account's token; afterwards there is nothing to authenticate it with.
