Chapter eleven

11Money

Real transactions from a real bank, exact to the cent, on six pastel bands. The device holds the ledger, the server holds only the credential, and every figure on the tab is derived from rows that actually happened.

11.1Intent

The Money tab answers six questions, one per side tab: what came in and went out, where it went, what repeats every month, what is being saved towards, what hurts, and the ledger itself. It reads from a bank connected through Plaid, or from transactions typed in by hand, and it never invents a row. The sample month that used to stand in before a bank was linked is gone. An empty month shows the empty state.

Working backwards

Connect a bank once and Almanac keeps the last two years of transactions on the phone. The net for the month is the first thing on the screen with a one-word verdict under it. Budgets are buckets that claim categories, so a renamed category never silently stops counting. Tap any category, any merchant, or any row to see six months of it on a page of its own.

Why is the savings rate sometimes blank rather than 0%?

A savings rate against no income is undefined, not zero. Rendering 0% says you saved nothing when what happened is that nothing was earned. The whole app draws that distinction and this is its sharpest case.

Where do my transactions live?

On the device, in SwiftData. The Edge Functions hand each sync delta straight back to the phone and store nothing but the bank credential. A compromise of the database exposes a token, not a ledger of where you shop.

Why can Plaid never be called from the app?

Every Plaid endpoint needs a client id and a secret on the request, and an .ipa is a zip file. Any secret compiled into the binary is public the moment it ships, so the four Plaid calls run in Edge Functions and the app talks only to those, authenticated with its own Supabase session.

What happens to a pending charge?

Stored and shown, greyed, but excluded from every rollup. Plaid re-issues a pending transaction under a new id when it settles and sends the old id in removed, so counting it twice is the default failure and the rollup refusing to see pending rows is what prevents it.

11.3Model

MoneyEntry, shaped for Plaid from the first line

// LifeOSKit/Sources/Persistence/MoneyEntry.swift
@Model
public final class MoneyEntry {
    public var id: UUID
    public var externalID: String?      // Plaid transaction_id, nil for manual
    public var sourceRaw: String
    public var date: Date               // always startOfDay
    public var amount: Double           // positive = in, negative = out
    public var currencyCode: String
    public var merchant: String
    public var category: String?        // display text, never keys arithmetic
    public var categoryCode: String?    // Plaid personal_finance_category.detailed
    public var merchantID: String?      // Plaid merchant_entity_id
    public var logoURL: String?
    public var accountID: String?
    public var accountName: String?
    public var pending: Bool
    ...
    public var isSpending: Bool {
        amount < 0 && !pending && !MoneyCategoryRule.isTransferLike(categoryCode)
    }
}

Three pairs of fields look redundant and are not. category is what the row shows; categoryCode is what the rollup and the buckets key on, so renaming a label can never change a savings rate. merchant is the descriptor the bank sent; merchantID is Plaid's stable entity, so NETFLIX.COM and Netflix are one merchant where the id exists and two strings where it does not. And MoneyAccount keeps both type and subtype, because "is this money owed" reads the first and "is this a credit card" reads the second, and a mortgage is a loan with a balance and no meaningful utilisation.

Every field added since the first edition (merchantID, logoURL, subtype, mask, availableBalance, creditLimit) is optional. That is what makes each one a lightweight SwiftData migration: a row written before the field existed reads back nil, and the app never hangs on the launch spinner the way it does when a new field lacks a default.

Sign convention: positive is money in Plaid's amount is positive when money leaves the account. This app's is the opposite. PlaidMapping negates on the way in, and the rule is written on the type, on the mapping, and on the scorer, because a silent flip turns a salary into the month's largest expense and nothing crashes.

The rollup

// LifeOSKit/Sources/Persistence/MoneyEntry.swift
public func summarise(entries: [MoneyEntry], accounts: [MoneyAccount] = []) -> MoneySummary {
    var income = 0.0
    var expenses = 0.0
    for entry in entries where !entry.pending
        && !MoneyCategoryRule.isTransferLike(entry.categoryCode) {
        if entry.amount > 0 { income += entry.amount } else if entry.isSpending { expenses += -entry.amount }
    }
    return MoneySummary(
        income: income,
        expenses: expenses,
        netWorth: accounts.isEmpty ? nil : accounts.reduce(0) { $0 + $1.netWorthContribution }
    )
}

Transfers between your own accounts and credit card payments appear as a real debit and a real credit. Counting them leaves net correct but overstates both income and expenses, and the savings rate is computed from those two. MoneyCategoryRule.isTransferLike matches TRANSFER_IN_ and TRANSFER_OUT_ as underscore-delimited prefixes plus the card-payment code, and nothing else. The underscore matters: without it a code that merely starts with the same letters would be excluded as if it were a transfer, which is a test (aCategoryThatMerelyStartsLikeATransferIsStillSpending) rather than a hope.

MoneyParts, or why cents are split in the kit

// LifeOSKit/Sources/Persistence/MoneyParts.swift
public init(_ amount: Double) {
    // Round in the unit that has to carry: cents, as an integer.
    let totalCents = Int((abs(amount) * 100).rounded())
    self.isNegative = amount < 0 && totalCents > 0
    self.whole = totalCents / 100
    self.cents = totalCents % 100
}

The one rule is that rounding happens to the cent before anything is split. Splitting a Double first and rounding each half lets 19.995 render as "$19.100", and lets the float noise in 0.1 + 0.2 leak into the cents. Money that displays as the wrong number is the worst bug a finance screen can have, so the split lives where it is tested against 19.995, 999.999, thirty 19.99s, negatives and zero, and MoneyFigure in the view only draws what it is handed.

SpendBucket and the claim key

// LifeOSKit/Sources/Persistence/SpendBucket.swift
@Model
public final class SpendBucket {
    public var name: String
    public var monthlyLimit: Double     // always positive; the store rejects anything else
    public var claimedRaw: [String]     // MoneyEntry.claimKey values
    public var sortOrder: Int
    ...
}

extension MoneyEntry {
    public var claimKey: String? { categoryCode ?? category }
}

A budget is a bucket that claims one or more raw categories. This survives Plaid renaming a category, works for manual entries (which have no code and fall back to their free-form category), and lets one budget cover what Plaid calls three different things. The rejected alternatives, raw strings and merchant rules, both fail silently: a renamed category simply stops counting and the budget quietly reads as under. A budget that silently stops counting is worse than no budget.

The snapshot

MoneySnapshot carries everything the six sections render: the summary figures, the budget and unclaimed bands, categories with a precomputed share, recurring charges, the seven-day week, the donut slices, a goal, and four connection flags. Two of those flags exist because a bank linked seconds ago has no transactions yet: hasConnectedBank keeps the screen out of the empty state, and isFetchingHistory keeps it out of "you spent nothing this month" while Plaid is still assembling the history.

11.4ViewModel

MoneyViewModel.load(connection:) fetches the calendar month to date plus the accounts, calls summarise, assesses the buckets through BudgetPeriod, and then derives every list and series from the same entries. It is called from RootView.reloadAll() on every store save in the app, and again after the Plaid sync that reloadAll kicks off. 

// LIfeOS/Features/Money/ViewModel/MoneyViewModel.swift
let logos = Self.logoMap(from: entries)
let rows = Self.rows(from: entries, logos: logos)
let categories = Self.categories(from: entries, expenses: summary.expenses)

snapshot = MoneySnapshot(
    income: summary.income, expenses: summary.expenses, net: summary.net,
    savingsRate: summary.savingsRate, netWorth: summary.netWorth,
    recent: rows, budgets: budgetRows, unclaimed: unclaimedRows,
    categories: categories,
    recurring: Self.recurring(from: entries, calendar: calendar, logos: logos),
    week: Self.week(from: entries, now: .now, calendar: calendar),
    slices: Self.slices(from: categories),
    spendCount: entries.filter(\.isSpending).count,
    goal: Self.goal(saved: summary.net),
    monthLabel: Date.now.formatted(.dateTime.month(.wide).year()),
    isConnected: !entries.isEmpty || !accounts.isEmpty || !bankNames.isEmpty,
    hasConnectedBank: !bankNames.isEmpty,
    isFetchingHistory: connection?.isFetchingHistory ?? false,
    reconnectPrompt: reconnect,
    lastSyncedAt: connection?.lastSyncedAt
)

Four derivations are worth reading closely.

  • Categories are grouped from isSpending rows only, the same predicate summarise uses, so the list sums to the "Spent" figure above it. Uncategorised spend is kept rather than dropped, because the gap is exactly the spend nobody labelled.
  • Logos are mapped twice, by merchantID where Plaid gave one and by lowercased merchant name always. A row Plaid sent without a logo borrows from any sibling that has one, and a manual "Netflix" picks up the mark from the Plaid rows. A borrowed logo never changes grouping. It is a picture beside a name, not an identity.
  • Slices fold the categories to the five largest plus "Other" through SpendSeries.fold, then assign each an opacity step. Shares are of the full month, so the slices still sum to one.
  • The goal reads a target and a name from the account's UserDefaults suite and reports this month's net as progress, clamped at zero. There is no account history to total, so a lifetime figure would be invented. As of this revision nothing in the app writes those two keys: the "Set a goal" button opens the bucket editor, so the goal band always shows "No goal set" until a setter is built.

Bucket editing goes through the store. saveBucket creates or updates, then reconciles claims by unclaiming what was dropped and claiming what was added. The store owns the single-holder rule: claim removes the key from whichever bucket held it and returns that bucket's name so the sheet can say "Held by Groceries, saving moves it here". Nothing resolves collisions at read time, because by then the same transaction has already counted twice.

MoneyDetailViewModel is a second view model rather than more fields on the first. Six months of rows for a page nobody is looking at, re-run on every save in the app, is the kind of work that makes a tab feel slow. RootView reloads it only while its page is up.

11.5View

The Money tab is the one screen in the app that is not cards on the warm canvas. It is full-bleed pastel bands on pure white, because money is mostly figures and a figure wants a block of colour behind it. MoneyPalette is therefore its own palette, not LifeOSTokens: paper, one near-black ink, and six pastels (sage, butter, clay, mint, mist, stone) stepped a little darker and more saturated than the reference screens because the paler versions washed out to grey on a real phone at real brightness.

The rail, two ways

On a phone the app's own nav bar is a floating pill along the bottom, so the side is free and MoneySectionRail is a 62-point vertical rail with a glyph and a short word per section. On iPad the nav bar stands on end against the left edge, and a second vertical rail beside it would be two parallel bars of chrome doing unrelated jobs. So on a regular width the rail lies down into a row of chips above the content, carrying the full titles ("Where it went" rather than "Spend") because a horizontal chip has the room. One matchedGeometryEffect id makes the selection block slide between sections instead of cross-fading.

Bands, cards and the grid

// LIfeOS/Features/Money/View/MoneySections.swift

Every section is a MoneyBandStack of MoneyBands. Stacked on a phone, the section is clipped as one rounded block and the bands have square corners; in the iPad grid each band is its own card with its own corners, because a single 340-point column down the middle of an iPad is most of the screen saying nothing.

A band that holds a chart or a list is a MoneyCard. Its header keeps the eyebrow and the figure, so a collapsed card still says its number; what folds is the chart or the list under it. Nothing is dropped by collapsing, and every card starts open. The handful of chart cards with a stable identity remember their state in UserDefaults under money.card.collapsed.<id>; a day of transactions uses transient state, since a key per calendar day forever is not a preference anyone set.

Rows that never wrap

Every row is one line. The amount is fixedSize and drawn first; the name takes what is left, scales to 0.8, then trails off. This replaced layoutPriority(1) on the name column, which starved the amount into "+…00" and stacked "PENDING" letter by letter. A word cut in half reads as a different category, so names scale before they truncate.

Charts

Three charts, all Swift Charts, all one ink at stepped opacity with no y-axis and no grid. The figure above each chart is the number; the marks are the shape. The week chart draws an empty track for every day so a day still to come is visibly a slot and not a gap, and labels only today. The donut uses SectorMark with a 1.5-point angular inset so two adjacent steps of the same ink read as two slices rather than a gradient, and chartAngleSelection turns a tap into a category page. The six-month chart adds a dashed RuleMark at the average of the completed months. The money pastels were run through the dataviz validator as a categorical palette and failed every check, which is the long way of saying what the one-ink rule already said.

The merchant tile

Plaid's logos come as 100 by 100 PNGs on whatever background the merchant chose. Bare, a row of them is a row of mixed squares that breaks the band. MerchantTile puts the mark in a paper-white circle with a hairline, and gives the category-glyph fallback the same footprint, so a list with and without logos lines up. AsyncImage loads it; a failed load shows the glyph.

11.6How it works

Connect

  1. PlaidConnectionViewModel.connect() asks plaid-link-token for a token. The function calls /link/token/create with the Supabase user id as client_user_id and returns only the link token.
  2. PlaidLinkPresenter.present opens Plaid's LinkKit sheet. The presenter is the only file in the app that imports LinkKit, and it holds the live Handler statically because a bank using OAuth sends the user out to Safari; a handler released while they are away has nothing to hand the redirect back to, and the connection dies silently at the last step.
  3. LinkKit returns a public_token. The app posts it to plaid-exchange, which refuses a second connection to the same institution (two Items with overlapping transactions under different ids cannot be deduplicated on the device), calls /item/public_token/exchange, and writes the access token into plaid_items. The response carries the item id and the institution name, never the token.
  4. The view model records the item with a nil cursor, sets isFetchingHistory, and runs a sync straight away.

The OAuth banks are the reason web/ exists. Plaid sends the browser to almanac.shivvyas.com/plaid-oauth when the bank is done. The apple-app-site-association file claims exactly that path, so iOS hands the URL to the app and the HTML page is never rendered. It renders only when the handoff fails, and its whole job is to tell a stranded person to open the app without claiming the connection failed, because by then Plaid has usually already succeeded. The link token that session was built with is kept in UserDefaults rather than memory, so a process killed during the round trip can resume the same Link session on relaunch, and the view model re-registers the completion closure on attach because the original one died with the old process.

Sync

// LifeOSKit/Sources/Integrations/PlaidSync.swift
let rows = try PlaidMapping.ingestRows(from: delta.added + delta.modified,
                                       accounts: delta.accounts)
try money.ingest(rows)
try money.remove(externalIDs: delta.removed.map(\.transaction_id))
try money.upsertAccounts(PlaidMapping.accountRows(from: delta.accounts))

// Only now. Every throw above leaves the cursor where it was, and
// the next run replays this page into an idempotent upsert.
if let cursor = delta.next_cursor {
    items.setCursor(cursor, for: delta.item_id)
}

This ordering is the whole design in three lines. A cursor advanced before a successful ingest is a page of transactions Plaid will never send again. That is also why the cursor lives on the device, per Item, in UserDefaults rather than on the server or in the Keychain: a server-advanced cursor would permanently lose a page to an app that crashed mid-ingest, and a Keychain cursor would survive a reinstall that the SwiftData database does not, leaving Plaid replaying nothing into an empty app. The cursor must die with the data it describes.

The function fetches at most three pages per invocation to stay inside its wall clock and reports has_more; the view model loops up to twenty times, so an initial pull of years of history finishes across several runs rather than stopping part-way and looking complete. Balances are fetched opportunistically after the transactions, and a failure there travels separately as balance_error: /transactions/sync serves cached data and succeeds even with an expired bank login, while /accounts/balance/get does a live fetch and is the call that actually throws ITEM_LOGIN_REQUIRED. That is what raises the reconnect banner without discarding the transaction pages already fetched.

Sync is triggered by reloadAll through syncIfDue, which applies the shared SyncStalenessPolicy: stale after an hour, or across a day boundary, or when the recorded time is in the future because the clock moved backwards. Before it checks staleness it runs replayHistoryOnce, which clears every cursor exactly once under a versioned flag so rows synced before the logo field existed gain their logo on the next pass. A replay on every launch would pull years of rows daily; a replay once is free, because Plaid bills per connected Item, not per call.

Disconnect

plaid-disconnect calls /item/remove and deletes the row. A connected Item bills monthly, so this is not optional polish. The client discards the response body and succeeds on the status alone, because reading a field that carries no further information only creates a way for a disconnect that worked to be reported as a failure. Local history is kept by default; deleting that Item's entries is a separate, explicit choice.

11.7Performance and cost

  • Batched ingest. externalID has no index and ingest runs on the main actor. A per-row fetch inside the loop would be an unindexed table scan per row, thousands of times on an initial pull. MoneyStore.ingest fetches every id the page touches once, builds a dictionary, keeps it current as rows are inserted so a duplicate id within the page still upserts, and saves once for the whole page. remove and upsertAccounts do the same.
  • Three pages per function call, twenty calls per sync. Bounded work on both sides, with has_more carrying the continuation.
  • Sync only when stale. One rule, shared with Whoop and Fitbit, keeps the sync off every save and every foreground.
  • One month loaded per save; six months only while the detail page is up. The tab view model is cheap because it reads the calendar month to date. The detail view model is separate so its six-month fetch runs only when its page is open.
  • No per-row lookups in the view. Category shares, logo URLs, slice opacities and day groupings are computed once on the snapshot. Views divide nothing and look nothing up.
  • Reads and writes serialised. UserDefaultsPlaidItemStore is Sendable and wraps every read-modify-write in an NSLock, so a cursor set from one task cannot lose an update from another. The test concurrentCursorSetsDoNotLoseUpdates pins it.
  • Private by construction. The server holds one row per bank containing the access token and an institution name. Transactions, merchants, categories and logos never touch Postgres. Nothing about spending is sent to a logo service either: the logo URL is Plaid's own, in a response already being paid for.
  • Cost. No new Plaid products since the first connection: Transactions and Accounts only, no /transactions/recurring (a separately billed product that RecurringSpend replaces for free from history). Plaid bills per connected Item per month, which scales with the number of banks a person links. The app targets one user on the free tier today; the pricing question is deferred, not answered, and must be answered before a second person connects a bank. See Chapter 24.
  • Offline. Every band renders from SwiftData. A sync failure leaves the previous snapshot on screen with its own timestamp, which is honest, rather than replacing it with zeros. A network outage never disconnects a saved bank.

Tests

All in LifeOSKit, all passing, all without a network or a Plaid account:

  • PersistenceTests/MoneyTests: the sign convention, the undefined savings rate, pending exclusion, transfer and card-payment exclusion, the underscore-prefix rule, upsert on the provider id, removal of a settled pending charge, merchant entity and logo round trips, and that isSpending matches what the summary counts.
  • PersistenceTests/MoneyPartsTests: the carry at 19.995 and 999.999, float noise, zero-padded cents, a zero that is never negative, grouping of large balances.
  • PersistenceTests/SpendBucketTests: a key moves rather than being held twice, deleting a bucket frees its keys, the claim key prefers the code over the label.
  • SectorsTests/BudgetPeriodTests: refunds net within a bucket, income never appears as unclaimed, adherence is 1.0 at the limit and decays linearly to 0 at double it.
  • InsightsTests/SpendSeriesTests and RecurringSpendTests: week boundaries, an empty month at zero in the middle of a run, fold leaving a list at or under keep plus one alone, the median resisting a single price rise.
  • IntegrationsTests/Plaid*: the client's error mapping through a stub URLProtocol, a missing session never reaching the network, disconnect succeeding on status alone, the mapping's negation and time-zone behaviour, the wire format's optional fields, and PlaidSyncTests pinning that a failed ingest leaves the cursor where it was and a balance login failure raises reconnect without losing the transactions.

11.9Study notes

Read in this order

  1. LifeOSKit/Sources/Persistence/MoneyEntry.swift, for the sign rule and summarise.
  2. LifeOSKit/Sources/Integrations/PlaidMapping.swift, the negation and the date parsing.
  3. LifeOSKit/Sources/Integrations/PlaidSync.swift, the ingest-then-cursor ordering.
  4. LifeOSKit/Sources/Persistence/MoneyStore.swift, the batched upsert and the claim rule.
  5. LifeOSKit/Sources/Sectors/BudgetPeriod.swift, the pure budget assessment.
  6. LIfeOS/Features/Money/ViewModel/MoneyViewModel.swift, how the snapshot is derived.
  7. LIfeOS/Features/Money/View/MoneySections.swift, bands, cards and the grid.
  8. supabase/functions/plaid-sync/index.ts, the server half of a sync.

Check yourself

  • Why does the cursor live in UserDefaults and not the Keychain? The Keychain survives a reinstall and the database does not; a cursor that outlived its data would make Plaid replay nothing into an empty app.
  • What would go wrong if the cursor advanced before ingest? A page that failed to save would never be sent again, and the total would be silently short.
  • Why is a card payment excluded from spending? The purchases on the card were already spending; the payment is the same money moving, and counting it inflates expenses and lowers the savings rate.
  • Why does a budget claim a category code rather than a merchant or a label? A label can be renamed and a merchant can be spelled three ways; a silently non-counting budget is worse than none.
  • Why is a missing credit limit stored as nil rather than zero? Zero renders as 100% utilised and looks like a fact; nil renders as nothing, which is the truth.
  • Why is the donut one ink at stepped opacity? The six pastels fail as a categorical palette; a sequential encoding of one hue passes, and identity is carried by the legend and the matching swatches on the bands, never by colour alone.
