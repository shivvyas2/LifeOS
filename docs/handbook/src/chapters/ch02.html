Chapter two

2MVVM and project structure

Every screen in Almanac is built the same way: a Model of value types, a ViewModel that owns all state and every decision, and a View that renders and forwards intent. The folder layout mirrors that exactly, one folder per screen, so a file's path tells you its layer before you open it.

The first edition described nine view models and four tabs. There are now thirty-three observable classes, most of them view models, across sixteen feature folders and five tabs, plus a composition root that has grown to 844 lines because it is the one place every feature is wired to every other. The shape did not change. This chapter explains why it held, and adds the two things that were not in the first edition: the composition root itself, and the preview and checks harness that lets a screen be captured and verified without an account.

2.1Why MVVM here

SwiftUI will happily let a view query the database. @Query in a View is one line and works immediately, and it is the reason this app does not do it. Three specific things break:

  1. Nothing is testable without a simulator. Goal evaluation, streak arithmetic, sector scoring and the arbiter are the parts most likely to be wrong, and they would live inside a view body that only a running device can exercise.
  2. Derivation gets re-run per render. Status-per-day, the month grid, the streak, the money rollup: computed in body, they recompute on every state change, including ones that have nothing to do with them.
  3. Persistence types leak into layout code. Once a view knows what a @Model class is, changing the schema means editing views. The schema has changed many times since Revision D.

MVVM fixes all three for the price of one extra file per screen. The ViewModel does the fetching and all derivation once, hands the View a plain value type, and can be exercised in a unit test with an in-memory container in milliseconds.

The rule that makes it work A ViewModel never imports SwiftUI, and a View never imports SwiftData. Both are checkable by reading the first ten lines of a file, and between them they force everything else into place. grep -rn "import SwiftData" LIfeOS/Features/*/View returns nothing today, and it should stay that way.

Where are the view controllers?

There are none, and that is not an omission. UIViewController is UIKit's unit of screen ownership: it manages a view hierarchy's lifecycle by hand. SwiftUI replaces that whole job with declarative views that re-render from state, so the controller's two remaining responsibilities split cleanly: owning state and making decisions went to the ViewModel, and describing what is on screen went to the View struct. The one place UIKit still appears is PushDelegate, because APNs registration and the orientation query have no SwiftUI entry point, and the note editor's UITextView, because block editing needs a text view SwiftUI does not offer.

Every feature folder has a View/; most have all three. Health/ and Life/ have no Model/ because their snapshots are assembled from other features' snapshots or from package types. Notifications/ is a single file because the inbox's state lives in PushService. A folder with fewer than three subfolders is not a violation; it is a screen that did not need the layer.

Why this works without touching the project file The app target uses a PBXFileSystemSynchronizedRootGroup. Any folder created under LIfeOS/ is picked up by Xcode automatically, because the directory structure is the project structure. Moving a screen between folders is a git mv. The corollary still holds: do not put documentation in these folders, because every file is a build input and a README.md is copied into the bundle as a resource.

2.4Anatomy of a feature folder

Every feature folder answers the same questions in the same order. Chapters 5 to 18 are each one instance of this template.

FolderContainsTest
Model/One snapshot struct per screen, plus any small enums it needs. Value types only. No methods that fetch, no dates computed from .now.Compiles without SwiftUI or SwiftData
ViewModel/One class per screen. Holds private(set) var snapshot, the context, and the funcs the view calls.Instantiable in a test with an in-memory container

The ViewModel shape is identical everywhere, which is the point:

// LIfeOS/Features/Today/ViewModel/TodayViewModel.swift
@MainActor @Observable
final class TodayViewModel {
    private(set) var snapshot = TodaySnapshot()
    private(set) var detail: DayDetailSnapshot?

    private var context: ModelContext?
    private let calendar: Calendar

    init(calendar: Calendar = .current) { self.calendar = calendar }

    func attach(_ context: ModelContext) { self.context = context }

    /// One pass over the day rows: the day-to-status map is built once and used
    /// for both the grid and the streak.
    func load() {
        guard let context else { return }
        let store = MetricsStore(context: context, calendar: calendar)
        // Bounded: the grid needs this month and the streak needs recent
        // history, never the whole table.
        let start = calendar.date(byAdding: .day, value: -400, to: .now) ?? .distantPast
        ...
    }
}

The context arrives through attach rather than the initialiser because RootView constructs every view model as @State before the environment is available, and a snapshot with its empty default is a valid thing to render in the meantime. Two view models break the pattern for a reason each states in a comment: AssistantViewModel takes its context in init because it builds a ChatStore immediately, so RootView holds it as an optional and creates it in attachAll(); and ActivityRecorder takes a UserDefaults suite so the design preview and the checks harness can run it against disposable defaults.

A calendar is injected everywhere a date is normalised. It defaults to .current and a test passes a fixed UTC calendar, which is what makes "which day does 23:30 belong to" a deterministic question in PersistenceTests.

Injection is by context, not by protocol Every view model builds a concrete store from a ModelContext, so testing one means standing up an in-memory ModelContainer rather than passing a stub. The consequence the first edition named is still true: the package has 1,298 tests across 130 suites and the app target has none. What changed is the mitigation. Everything that can be decided by arithmetic now lives in the package where a test can reach it (SessionKeepAlive, LiveEffort, HUDPlacement, CodeDigits), and the view models that cannot be unit tested are driven by the checks harness in 2.7 instead.

2.5The composition root

RootView is where every feature is wired to every other, and it is the one file in the app that may know about all of them. Five tabs, stated rather than inferred from ordering: 

// LIfeOS/App/RootView.swift
private enum AppTab: Hashable { case today, health, money, notes, life }

@State private var tab: AppTab = .today   // deliberately not persisted: a cold launch lands on Today

private var navItems: [PillNavItem<AppTab>] {
    [
        PillNavItem(value: .today,  systemImage: "circle.grid.3x3.fill",  label: "Today"),
        PillNavItem(value: .health, systemImage: "heart.fill",             label: "Health"),
        PillNavItem(value: .money,  systemImage: "dollarsign",            label: "Money"),
        PillNavItem(value: .notes,  systemImage: "text.book.closed.fill",  label: "Notes"),
        PillNavItem(value: .life,   systemImage: "square.grid.3x3.fill",   label: "Life"),
    ]
}

Health absorbed activity, weight, recovery and wellness so the bar stays free for the other life domains. Plan lost its tab to Notes, where habits now live as a section. Settings sits behind the profile avatar on Today rather than spending a slot. The Life board maps three of its nine sectors back onto tabs, and LifeSector.ownsTab in the Sectors package is the one decision about which three; RootView reads it and asserts if the switch ever drifts.

The root does five jobs, and each is one mechanism:

  1. Owns every view model as @State, nineteen of its own plus the four connection view models the shell hands it, and attaches the context to all of them in attachAll() from a single .task. Cross-feature wiring happens here and only here: the recorder's onSaved triggers a Health sync, the coach's bundleExtras closure reads the money and life snapshots, notes get their sync client.
  2. Reloads on save, never on a timer. One .task listens for ModelContext.didSave and calls reloadAll(). A save is the only thing that can change what a screen shows while the app is running, so nothing polls. Detail pages reload only while open, because off screen they are six months of rows nobody is looking at.
  3. Draws two shells over one set of screens. A compact width gets the pill bar floating over the content; a regular width gets the same bar stood on end as a rail. The screens are identical in both; 4.9 has the rail's behaviour.
  4. Presents every sheet and cover from one place, keyed on optionals rather than parallel booleans where the sheet has content: today.detail is the only source of truth for the day sheet, openMetric is a value rather than four flags, eventSheet is an enum of create or edit.
  5. Routes what arrives from outside: a widget deep link through SurfaceCoordinator.pendingRoute, a tapped nudge through PushService.pending, a scene activation that syncs the calendar and restarts the Health watcher.

The three quick actions (calendar assistant, LIFO, begin activity) are defined once in RootView and injected through EnvironmentValues.quickActions. Notes and Life own their own NavigationStacks several levels down, and a toolbar has to be attached inside the stack it belongs to; threading an array through both would put the same three buttons in four call sites, which is how a set drifts apart.

A component earns its place in Components/ the second time it is needed, not the first. SessionHUD and ActivityControls are the recent example: they were private to Begin Activity until the video player needed them, and they were moved rather than copied.

Where the dash rule lives "A missing metric renders as a dash, never as 0" is the single most repeated rule in this app. It is enforced by type: MetricTile, IconBubbleTile, PastelFillCard, TrendStatTile and HeroNumeral all take String? and render the dash themselves. A screen cannot pass a zero it does not have, because it has nothing to pass.

2.7The preview and checks harness

Most screens need an account, a store with weeks of rows, a connected strap and a signed-in session before they show anything worth looking at. That made design review and QA slow and made the state on screen unrepeatable. The harness fixes both. LIfeOSApp checks one launch argument in DEBUG: 

// LIfeOS/App/LIfeOSApp.swift
#if DEBUG
if ProcessInfo.processInfo.arguments.contains("--design-preview") {
    HealthActivityDesignPreview()
} else {
    shell
}
#endif

HealthActivityDesignPreview builds an in-memory container, a disposable UserDefaults suite, and an ActivityRecorder that never saves to Health, then switches on --page=. Every page is a real screen fed a fixture; nothing is a mock-up. The fixture uses six real rows lifted from the catalog seed so thumbnails resolve, a WHOOP recovery of 82 and a live reading of 152 bpm, and it labels itself as sample data.

ArgumentRendersModifiers

Two more harnesses sit behind build flags rather than arguments, so they cannot ship even in a debug build by accident: SurfaceDesignPreview (flag SURFACE_DESIGN_PREVIEW) renders the widget gallery, the inbox and the "Widgets & Watch" page and runs SurfaceNativeChecks; LaunchFilmPreview (flag LAUNCH_FILM_PREVIEW) renders the synthetic frames the launch film was cut from.

Native checks

The checks are the answer to "the feature layer has no tests." They are not unit tests: they run inside the app process, against real UserDefaults suites and a real in-memory container, exercising the view models the way the app does. ActivityRecorderChecks starts a session, feeds readings, counts reps, hands off to a watch that never answers, and asserts on each step; SurfaceNativeChecks proves that a notification for one account is rejected once another is signed in and that sign-out empties the widget snapshot. Each prints PASS or FAIL and a title, the QA reports paste the output verbatim, and the rule for a failing check is the same as for a failing test: fix the cause, never the check.

2.9Study notes

Read in this order

  1. LIfeOS/App/LIfeOSApp.swift: forty lines that decide whether a store is open and re-root the tree.
  2. LIfeOS/App/AppShell.swift: onboarding or app, and every URL that arrives.
  3. LIfeOS/App/RootView.swift: read attachAll() and reloadAll() first, then the content switch, then the two shells.
  4. LIfeOS/Features/Today/ViewModel/TodayViewModel.swift: the canonical view model shape.
  5. LIfeOS/Features/Today/Model/TodaySnapshot.swift: what a snapshot is and is not.
  6. LIfeOS/Features/Health/View/HealthActivityDesignPreview.swift: how a screen is rendered without an account.
  7. LIfeOS/Features/Activity/ViewModel/ActivityRecorderChecks.swift: what a native check looks like.

Check yourself

  • Why does a view model take its context through attach rather than init? Because RootView constructs them as @State before the environment context exists, and an empty snapshot is a valid first render.
  • What triggers reloadAll()? ModelContext.didSave, scene activation, and a finished recorder save. Nothing polls.
  • Where is the decision about which sectors map to a tab? LifeSector.ownsTab in the Sectors package; RootView only maps the answer onto its private enum.
  • Why are the quick actions an environment value? Notes and Life own their own navigation stacks, and a toolbar must be attached inside the stack it belongs to.
  • What is the difference between a native check and a unit test? A check runs inside the app process against real defaults and view models; a test runs in the package with no simulator. Both print a verdict; only the check can reach a view model.
  • Which two harnesses are behind build flags rather than launch arguments, and why? The surface gallery and the launch film; a flag cannot be tripped by a stray argument in a debug build.
