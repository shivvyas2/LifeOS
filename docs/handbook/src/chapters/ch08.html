Chapter eight

8Live sessions

Press Begin and a workout is recorded on the phone: a wall-clock timer that survives relaunch, a heart-rate strap over Bluetooth, an effort estimate against today's battery, and one readout struct that every surface renders, from the glass rings on the screen to the lock screen and the Dynamic Island.

8.1Intent

Until 14 September a person starting a workout saw a timer, and if they scanned and tapped for a sensor, a heart rate. They could not see how hard they were working, how much they had left, or whether they should push. Everything needed to answer those questions already reached the app: Whoop recovery and sleep performance sit in DailyMetrics, the profile carries a birth date, the workout builder collects energy, and a strap delivers beats every second. Nothing joined them. This slice is the join.

Working backwards

Tap the plus, choose Run, tap Begin. The screen turns blue. A big rounded clock counts up, and beneath it three glass rings: your heart rate against today's ceiling zone, your estimated effort against today's target band, and your battery, what you have left to spend. The last sensor you used reconnects on its own. Lock the phone and the same numbers sit on the lock screen over the same blue gradient, and in the Dynamic Island as a heart, a number, and the clock. Pause and everything freezes. Finish and the session is saved to Almanac, and to Apple Health if you asked.

Is the effort number Whoop's strain?

No, and the screen always says "estimated" next to it. It is a model on the same 0 to 21 scale, calibrated so a steady hour in zone 3 reads about 12 and a hard ninety minutes about 18. Whoop's real strain for the workout arrives later on its own record through the existing sync, and nothing here overwrites it.

What if I have not entered a birth date?

Then there are no zones, no effort and no battery, and the screen says so with one line: "Add your birth date in Profile for zones, effort and battery." A zone built on an assumed age would be a reading the person never gave, and this app refuses those. Heart rate and calories still show.

Does the timer keep going if the app is killed?

Yes. The timer is wall-clock based and written to a per-account draft at most every ten seconds, so a relaunch restores it exactly. If Health was recording, the recorder asks HealthKit to recover the active session; if it cannot, the timer is kept and the person is told the Health session is gone.

Out of scope here

Apple Watch heart rate and rep counting are Chapter 9. Following a video with the rings over it is Chapter 10. There are no server changes; this chapter is entirely on the device.

Why the maths is in two packages

LiveSessionReadout and PushState live in AppSurfaces, which depends on nothing, so the widget extension can decode them without linking HealthKit or SwiftData. The effort model lives in Integrations, which added AppSurfaces as a dependency. Nothing cycles, and swift test runs the whole model on macOS without a simulator.

8.3Model

The timer

// LifeOSKit/Sources/Integrations/ActivitySessionState.swift
/// Wall-clock based: backgrounding never stops the timer and pauses never count.
public struct ActivitySessionState: Codable, Equatable, Sendable {
    public enum Phase: String, Codable, Sendable { case running, paused, finished }
    public let id: UUID
    public let startedAt: Date
    public let activity: String
    public private(set) var phase: Phase
    public private(set) var accumulated: TimeInterval
    public private(set) var runningSince: Date?
    public private(set) var endedAt: Date?

    public func elapsed(at date: Date = .now) -> TimeInterval {
        accumulated + (runningSince.map { max(0, date.timeIntervalSince($0)) } ?? 0)
    }
    public mutating func pause(at date: Date = .now) {
        guard phase == .running else { return }
        accumulated = elapsed(at: date); runningSince = nil; phase = .paused
    }
}

A pause banks the time so far into accumulated and clears runningSince; a resume starts a new run. There is no tick. Every surface derives the elapsed time from two fields and the clock, which is what lets the lock screen use Text(timerInterval:) and count on its own without an update per second. The id is the Live Activity's key.

Zones, effort, capacity

All of this is value types and pure functions in one file. Nothing touches HealthKit, Bluetooth, SwiftData or the clock; callers pass values in.

// LifeOSKit/Sources/Integrations/LiveEffort.swift
public struct HeartRateZones: Equatable, Sendable {
    public let maxHeartRate: Int
    public init?(birthDate: Date?, on date: Date = .now, calendar: Calendar = .current) {
        guard let birthDate,
              let age = calendar.dateComponents([.year], from: birthDate, to: date).year,
              (10...120).contains(age) else { return nil }
        maxHeartRate = Int((208.0 - 0.7 * Double(age)).rounded())   // Tanaka
    }
    /// 0 below half of maximum, then one zone per ten percent up to 5.
    public func zone(for bpm: Int) -> Int { ... }
}

public struct EffortAccumulator: Equatable, Sendable {
    public static let weights: [Double] = [0, 0.15, 0.28, 0.35, 0.45, 0.63]
    public static let scale = 1500.0
    public static let maxCredit: TimeInterval = 5
    public private(set) var load: Double
    public mutating func add(zone: Int, seconds: TimeInterval) {
        guard seconds > 0, Self.weights.indices.contains(zone) else { return }
        load += Self.weights[zone] * seconds
    }
    public var effort: Double { 21 * (1 - exp(-load / Self.scale)) }
}

Max heart rate is Tanaka's estimate, and the zone bands follow Whoop's (zone 1 starts at 50 percent of max, then 60, 70, 80, 90) so the number on the HUD agrees with the number in the app the person already trusts. Each second in a zone adds that zone's weight to a running load; the load maps through a saturating curve so a very long session approaches 21 without reaching it. The six weights and the 1500 are the values that make three calibration points hold at once, and they are pinned by tests: retuning is a deliberate change with a diff, not a drift.

maxCredit matters more than it looks. A reading credits at most five seconds. A gap in the stream, a strap that dropped for forty seconds, is not effort that was measured, and crediting the whole gap at the zone of the next reading would invent it. 

// LifeOSKit/Sources/Integrations/LiveEffort.swift
public struct EffortCeiling: Codable, Equatable, Sendable {
    public let maxZone: Int
    public let targetEffort: ClosedRange<Double>
    public static let green  = EffortCeiling(maxZone: 5, targetEffort: 14...18)
    public static let yellow = EffortCeiling(maxZone: 4, targetEffort: 10...14)
    public static let red    = EffortCeiling(maxZone: 3, targetEffort: 4...10)
    public static let conservative = yellow
    public static func forCapacity(_ percent: Int) -> EffortCeiling {
        percent >= 67 ? .green : percent >= 34 ? .yellow : .red
    }
}

public struct Capacity: Codable, Equatable, Sendable {
    public enum Source: String, Codable, Sendable { case whoop, health }
    public let percent: Int
    public let source: Source
    public let measuredOn: Date
    public var ceiling: EffortCeiling { .forCapacity(percent) }
}

Capacity is today's battery: what the person has to spend and where the number came from. It is computed once at session start and kept in the draft. CapacityMath.capacity(days:now:) looks at today's row and yesterday's (yesterday stands in while today has not synced; anything older is stale) and resolves in order:

  1. Whoop. Recovery percent present and not calibrating. Blended with sleep performance when present: 0.8 * recovery + 0.2 * sleepPerformance, else plain recovery.
  2. Apple Health. HRV present, with at least three of the previous seven days carrying HRV for a baseline. The ratio to baseline maps piecewise: 0.7 to 1.0 onto 20 to 65 percent, 1.0 to 1.2 onto 65 to 90, clamped. Sleep minutes then adjust by up to plus or minus 10 against a 450-minute reference.
  3. Nothing. Nil. The UI says "Battery unknown" and the recorder uses the yellow ceiling, cautious without claiming a capacity it does not have.

The ceiling follows Whoop's recovery bands. Battery remaining drains as effort approaches the target's top: capacity * (1 - effort / target.upperBound), floored at zero. Zero is a real event, the budget spent, not a missing value. Push state is a four-way word: overLimit when the zone exceeds the ceiling's max zone or effort exceeds the target's top, nearLimit when the zone is at the max or effort is within 1.5 of the top, easy when effort is below the band and the zone is at most 2, onTrack otherwise.

The readout

// LifeOSKit/Sources/AppSurfaces/LiveSessionReadout.swift
public struct LiveSessionReadout: Codable, Hashable, Sendable {
    public var elapsed: TimeInterval
    public var runningSince: Date?
    public var heartRate: Int?
    public var zone: Int?
    public var effort: Double?          // rounded to a tenth before publishing
    public var calories: Int?
    public var distanceMeters: Int?
    public var batteryPercent: Int?
    public var capacitySource: String?  // "whoop" or "health"
    public var ceilingMaxZone: Int?
    public var ceilingTarget: ClosedRange<Double>?
    public var reps: Int?
    public var setIndex: Int?
    public var push: PushState

    /// Anchor for `Text(timerInterval:)`, so the system ticks the timer
    /// without an update per second.
    public var timerAnchor: Date? { runningSince?.addingTimeInterval(-elapsed) }
    public var isPaused: Bool { runningSince == nil }
}

This is the one value every live surface renders. Every reading is optional because a missing sensor is not a zero. WorkoutActivityAttributes.ContentState is a typealias to it, so the widget and the app can never disagree about what a session looks like. LiveSessionReadout+Text is the one place a reading becomes a string, so the HUD, the tiles and the lock screen agree on rounding and on the dash that means no reading.

8.4ViewModel

ActivityRecorder is the largest view model in the app, and it is an NSObject because it is the HKWorkoutSessionDelegate and HKLiveWorkoutBuilderDelegate. It owns the timer, the sensor, the zones, the effort accumulator, the capacity, the draft, the Live Activity controller and the readout. 

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder.swift

Three things about its shape. Its dependencies on the world (the birth date, whether Whoop is connected, whether a watch is nearby, Health authorisation) are closures, so the checks harness can fix them without a profile, a strap or a permission sheet. Its defaults are the UserDefaults.currentAccount suite, so a draft belongs to one account and an account switch clears it. And it has active, flipped off by deactivate(), which every async continuation checks before touching state, so a session that finishes after sign-out writes nothing.

Start

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder.swift
func start(backdatedTo backdatedStart: Date? = nil,
           following video: (id: String, split: String, title: String, channel: String)? = nil) async {
    guard active, !busy, !hasSession else { return }
    busy = true; error = nil; saved = false; healthSaved = false; timer = nil
    zones = HeartRateZones(birthDate: birthDate())
    capacity = loadCapacity()
    effort = EffortAccumulator(); lastReadingAt = nil
    source = .phone
    recordingHealth = saveToHealth
    defer { busy = false }
    if await handOffToWatch() { return }                 // Chapter 9
    sensor.prepareForSession(whoopConnected: whoopConnected())
    do {
        if saveToHealth && source == .phone {
            try await healthStore.requestAuthorization(toShare: Self.workoutTypes, read: Self.workoutTypes)
            guard healthStore.authorizationStatus(for: HKObjectType.workoutType()) == .sharingAuthorized else {
                error = "Allow workout saving in Health, or turn off Save to Apple Health to use the timer."
                return
            }
            let session = try HKWorkoutSession(healthStore: healthStore, configuration: configuration)
            let builder = session.associatedWorkoutBuilder()
            builder.dataSource = HKLiveWorkoutDataSource(healthStore: healthStore, workoutConfiguration: configuration)
            let started = backdatedStart ?? .now
            if timer == nil { timer = ActivitySessionState(activity: selection.rawValue, at: started) }
            session.startActivity(with: started)
            try await builder.beginCollection(at: started)
        } else if timer == nil {
            timer = ActivitySessionState(activity: selection.rawValue, at: backdatedStart ?? .now)
        }
        persist()
    } catch { ... }
}

The clock is read after Health answers, not before. A permission sheet can sit open for a minute, and a timer started before it would count that minute as exercise. Zones and capacity are computed once here; the capacity is nine days of rows read through CapacityInputs, the same helper the workout planner uses, so the battery on the HUD and the battery on the library's Today card are plainly the same number.

A reading arrives

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder.swift
func receiveHeartRate(_ bpm: Int, at date: Date) {
    guard active, isRunning else { return }
    heartRate = Double(bpm); heartRateDate = date
    if let zones {
        effort.add(zone: zones.zone(for: bpm),
                   seconds: EffortAccumulator.credit(previous: lastReadingAt, at: date))
    }
    lastReadingAt = date
    persistReading(at: date)
    guard let builder, healthStore.authorizationStatus(for: .quantityType(forIdentifier: .heartRate)!) == .sharingAuthorized else { return }
    let sample = HKQuantitySample(type: .quantityType(forIdentifier: .heartRate)!,
        quantity: HKQuantity(unit: HKUnit.count().unitDivided(by: .minute()), doubleValue: Double(bpm)), start: date, end: date)
    builder.add([sample]) { _, _ in }
}

Paused readings accrue nothing because the guard on isRunning drops them. The first reading after a resume credits nothing because togglePause cleared lastReadingAt, so the credit function has no previous date and returns zero. Both are pinned by checks. The strap's beats are also written into the Health builder, so a workout saved to Health carries the heart-rate series the strap measured.

Two persist paths

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder.swift
/// State changes: always write the draft and sync.
func persist() {
    refreshReadout()
    writeDraft()
    syncLiveActivity()
}
/// Readings arrive every second: always refresh and sync (the controller
/// throttles the publish), but write the draft at most every ten seconds.
func persistReading(at date: Date) {
    refreshReadout()
    if lastDraftWriteAt.map({ date.timeIntervalSince($0) >= 10 }) ?? true { writeDraft(at: date) }
    syncLiveActivity()
}

refreshReadout() calls LiveReadoutBuilder.readout(...), the pure join of timer, heart rate, zones, effort, capacity, energy, distance, reps and set into one struct. The draft is a Codable private struct with every field optional after the first slice, so a draft written before reps or videos existed still decodes.

Finish and save

finish() marks the timer finished and, for a Health-backed session, calls session.stopActivity and returns; the delegate's .stopped callback is what calls saveFinished(), because collection completes only after HealthKit reaches that state. saveFinished() ends collection, finishes the workout, then writes the local WorkoutRecord with a stable id:

The sensor

LiveHeartRateSensor speaks the Bluetooth SIG heart-rate service (0x180D, measurement 0x2A37). It handles 8-bit and 16-bit frames, treats a no-contact flag as no reading, and rejects values outside 20 to 250. Scans stop after 30 seconds. What the live-session slice added is memory: the last connected peripheral's identifier is written to the per-account defaults under lastHeartRateSensorID on every successful connection and cleared on an explicit disconnect. 

// LIfeOS/Features/Activity/ViewModel/LiveHeartRateSensor.swift
/// Called by the recorder at session start. Reconnects the last sensor,
/// or looks for a lone WHOOP when the account is connected to WHOOP and
/// nothing was ever paired here.
func prepareForSession(whoopConnected: Bool) {
    if rememberedPeripheralID != nil { reconnectIfRemembered() }
    else if whoopConnected { autoPairWhoop() }
}

reconnectIfRemembered uses retrievePeripherals(withIdentifiers:) and connects directly; if nothing connects in 20 seconds it falls back to a scan and connects the discovered peripheral whose identifier matches. autoPairWhoop scans and connects only when WhoopAutoPair.choice(among:) finds exactly one name containing "WHOOP". Several stop the scan with "More than one WHOOP nearby. Choose one under Manage." Nothing auto-pairs a device that is not a WHOOP, because another person's chest strap in a gym is not a reading this person owns.

The rings

SessionRings is a GlassEffectContainer with two shapes. Expanded, a rounded rectangle holding three rings (heart, effort, battery) and, for strength, a rep count, with the rep buttons on a second row inside the same glass. Collapsed, a capsule with the clock, a pulsing heart, the bpm and, for strength, the reps. Tapping the top row toggles between them. It always draws white on glass over a dark wash (.black.opacity(0.30)) so the text reads over a bright frame of video or the pale foot of the gradient alike, and the glass is tinted by the push state. 

// LIfeOS/Features/Activity/View/SessionRings.swift
/// One beat per beat: a scale wave at the live tempo, still when there
/// is no reading to keep time to.
private var pulsingHeart: some View {
    TimelineView(.animation(paused: SessionRingMath.beatPeriod(bpm: readout.heartRate) == nil || readout.isPaused)) { timeline in
        let period = SessionRingMath.beatPeriod(bpm: readout.heartRate) ?? 1
        let phase = timeline.date.timeIntervalSinceReferenceDate.truncatingRemainder(dividingBy: period) / period
        let beat = max(0, sin(phase * .pi * 2))
        Image(systemName: "heart.fill").scaleEffect(1 + 0.35 * beat)
    }
}

The ring fills come from SessionRingMath, pure and tested: the heart ring is the zone over today's ceiling zone, the effort ring is effort over the top of the target band, the battery ring is the percent. A missing reading is an empty ring, never a full one; nothing has been earned yet. The effort ring turns red only past the band, not at its top. The animation timeline is paused when there is no reading or the session is paused, so a still heart costs no frames.

The tiles

Under the hero, glass tiles in an adaptive grid: heart rate with the zone in its label and a freshness rule (a reading older than 15 seconds shows a dash and the sensor's status as its caption); effort with "of 14" as its unit and the battery and its source as caption; reps for strength; calories; distance for walk, run and cycle only. Yoga hides the effort tile: a zone ceiling has no meaning on a mat.

Controls

ActivityControls was extracted from the screen so the video player offers exactly the same buttons in the same order. Two screens that both stop a workout should not disagree about what stopping looks like, and the confirm-discard dialog travels with the button that raises it.

8.6How it works

Step by step: a run with a strap

  1. Begin. start() builds zones from the birth date and capacity from nine days of rows, asks Health, creates the session and builder, starts the timer at the moment Health answered, and persists. sensor.prepareForSession reconnects the remembered strap.
  2. A frame arrives on characteristic 0x2A37. HeartRateMeasurement.beatsPerMinute decodes it; the sensor calls onReading.
  3. receiveHeartRate credits at most five seconds of the reading's zone to the accumulator, records the time, and calls persistReading.
  4. refreshReadout rebuilds the readout: zone from the bpm, effort rounded to a tenth, battery from capacity and effort, push state from zone and effort against the ceiling.
  5. The rings and tiles observe readout and redraw. The draft is written if ten seconds have passed. The Live Activity controller is asked to sync.
  6. LiveActivityThrottle.shouldPublish decides. First state always; a pause, a push-state change or a reps change always; a heart-rate move of 3 bpm or more only if 3 seconds have passed since the last publish; anything else only after a 10-second floor; an identical readout never.
  7. The builder's own statistics callback delivers energy and distance sums, and the watch's heart rate when there is no strap. It updates the same fields and calls persist().
  8. Pause: the timer banks, the Health session pauses, lastReadingAt clears. Readings still arrive and are dropped.
  9. Finish: stop the Health activity, wait for .stopped, end collection, finish the workout, write the record, end the Live Activity, clear the draft, stop the strap.

The Live Activity

Widget extensions cannot render materials, so the lock screen's "glass" tiles are white at 18 percent over a linear gradient from LifeOSTokens.liveGradientTop (the recovery hue) to liveGradientBottom, with a radial white highlight and a half-point white stroke. Row one: the activity icon in a circle, the name, the push headline (or "Paused"), and the timer as Text(timerInterval:). Row two: four tiles, heart with the zone as eyebrow, effort with "EST" and "of 14", calories (or reps and set for strength), and battery with a small ring. A tile with no value shows the dash in the same weight, never a zero.

The Dynamic Island's compact leading is a heart and the bpm tinted by push state; compact trailing is the timer, or reps for strength; minimal is the zone number in a tinted circle. The keyline tint follows push state. Every surface deep-links to SurfaceRoute.activity.url.

8.7Performance and cost

  • No tick. The timer is two fields and the clock. The lock screen counts on its own through Text(timerInterval:); the in-app clock is a one-second TimelineView, which SwiftUI runs only while the view is on screen.
  • Draft writes are rate-limited. A reading a second would be a UserDefaults write a second. persistReading writes at most every ten seconds; state changes (pause, resume, finish) always write.
  • ActivityKit updates are throttled by a pure function. The sensor streams every second; the lock screen does not need to. The 3-second minimum on heart-rate-driven updates and the 10-second floor on everything else keep the activity inside ActivityKit's budget, and the rule is tested rather than tuned by eye. Updates are chained through a Task so they land in order.
  • Effort is O(1) per reading. One multiply-add into a load; the curve is evaluated on read. Nothing keeps a series.
  • Capacity is computed once. Nine rows at session start, then kept in the draft. A restored session does not re-read the store.
  • The pulse is free when still. The heart's TimelineView(.animation) is paused whenever there is no bpm or the session is paused.
  • Scans end. Thirty seconds, then stop, so a sheet left open is not draining the radio. The reconnect fallback times out at twenty.
  • Nothing leaves the device. A workout is a local WorkoutRecord and, optionally, an HKWorkout. The Live Activity uses pushType: nil. There is no server in this chapter.
  • Every continuation checks active. A delegate callback, a recovered session, a finish that lands after sign-out: all guard on it, so a stale session cannot write into the next account's store.
Open on hardware The spec flags one background-execution question: whether iOS 26 keeps the app running during a phone-side HKWorkoutSession or whether workout-processing must join UIBackgroundModes. The plist today carries remote-notification and bluetooth-central. The wall-clock timer means the elapsed time is right either way; what a suspended app would lose is effort accrual for the suspended minutes.

Check yourself

  • Why is the timer started after Health answers rather than before? A permission sheet can sit open for a minute, and a timer started first would count it as exercise.
  • Why does one reading credit at most five seconds? A gap in the stream is not effort that was measured; crediting the gap would invent it.
  • What makes "Repeated save creates one workout" true? The record's external id is derived from the timer's UUID and looked up before insert.
  • Why does the lock screen not need an update every second? It renders Text(timerInterval:) from an anchor date; only readings, not time, need an update, and the throttle spaces those.
  • Why do zones live in Integrations but the readout in AppSurfaces? The widget must decode the readout without linking HealthKit or SwiftData; AppSurfaces depends on nothing.
  • When does the effort ring turn red? Only past the top of the target band, not at it.
