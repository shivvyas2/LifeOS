Chapter twenty-three

23Operations

How to build the app from a clean machine, what has to exist on the server side before it signs anyone in, how a build reaches TestFlight, and how the code is kept honest: 1,298 package tests, 100 Deno tests, 7 catalog tests, a native checks harness, a typography guard and a way of working that survives six sessions editing one checkout.

23.1Setup runbook

1 · Local build

git clone https://github.com/shivvyas2/LifeOS.git
cd LifeOS
cp Config/Secrets.example.xcconfig Config/Secrets.xcconfig
swift test --package-path LifeOSKit      # no simulator needed
open LIfeOS.xcodeproj

The package declares an iOS 26 platform and also builds for macOS purely so that swift test runs from the terminal. The Xcode project holds four targets: LIfeOS (the phone and iPad app, still spelled with the capital I because renaming a target churns the project file for no user-visible gain), AlmanacWatch, AlmanacWatchWidgets and AlmanacWidgets. The display name under the icon is Almanac; the bundle id is com.shivvyas.lifeos; the team is Z42YU5W6WY. The app's folders under LIfeOS/ are picked up automatically, as described in Chapter 2.

A missing Secrets.xcconfig does not fail the buildxcconfig substitution of a missing variable yields an empty string. A clean checkout builds, archives and launches, then shows a sign-in screen that can never sign anyone in. Confirm the file exists and is populated before archiving on any machine that is not the usual one.

supabase functions deploy

Then put the project URL and anon key into Config/Secrets.xcconfig. Thirteen Edge Functions deploy from supabase/functions/: otp-start, otp-check, whoop-callback, whoop-token, fitbit-token, fitbit-sync, plaid-link-token, plaid-exchange, plaid-sync, plaid-disconnect, lifo-agent, lifo-nudge, and the shared modules under _shared/. Two of them declare verify_jwt = false in config.toml: whoop-callback, because a browser following Whoop's 302 carries no Authorization header and cannot be made to, and whoop-token, which validates the bearer itself with resolveUser before touching account data. Stating it in config rather than passing --no-verify-jwt means a deploy from anywhere gets it right.

Two server-side steps cannot live in a migration. The hourly nudge schedule needs the project's own function URL and the service role key, so supabase/functions/lifo-nudge/schedule.sql is run once from the SQL editor after storing both in Vault. And the auth email templates must be pushed, because Supabase's stock templates send a magic link and the app's sign-in is a six-digit code that has to be typable.

4 · The workout catalog

deno run --allow-net --allow-read --allow-write scripts/catalog/verify.ts \
  --out supabase/migrations/<stamp>_workout_videos_seed.sql
supabase db push

Curation is an edit to scripts/catalog/catalog.json plus a verify run. The script checks every id against YouTube's keyless oEmbed endpoint for title, channel and plausible duration, refuses an empty catalog, and writes a seed whose last statement deletes every row not in the verified list, so a seed run is a full sync. The first seed is a migration Supabase has already recorded and will never re-run, which is why later passes write a new timestamped file with --out. The catalog ships at 122 verified videos.

5 · Device

HealthKit background delivery, the Whoop and Fitbit OAuth round trips, the Plaid universal link, a real HKWorkoutSession, the watch hand-off and push delivery cannot be verified in the simulator. All need a physical device with a signing team, and the watch checks need a paired watch. The list of what is still pending on hardware is in Appendix A.

23.2Secrets

There is no runtime .env on iOS. The app is a signed bundle; anything shipped inside it is extractable. The governing rule is therefore: what must never leak lives server-side.

TierLocationContentsIn git?
1 · Build configConfig/Secrets.xcconfigSupabase URL and anon key, Whoop client id and redirect, Plaid redirect, Fitbit client id and redirect, ElevenLabs keyGitignored. Template committed as Secrets.example.xcconfig
2 · RuntimeKeychain, per account slotSupabase session (access and refresh token), Whoop tokensNever
2b · RuntimeUserDefaults, per account suitePlaid sync cursors, connection state, tour and migration markers, the APNs tokenNever; dies with the app container on purpose
3 · ServerEdge Function environmentSUPABASE_SERVICE_ROLE_KEY, OPENAI_API_KEY, WHOOP_CLIENT_SECRET, FITBIT_CLIENT_SECRET, PLAID_SECRET, Twilio credentials, OTP_PEPPER, APNS_KEYNever. Never on the device either
3b · DatabaseTables with no client policiesplaid_items.access_token, fitbit_connections tokens, whoop_connections tokens, lifo_usage, otp_eventsReadable only by the service role from inside a function

Nothing in tier 1 is truly secret except the ElevenLabs key. The anon key is designed to ship in clients and is safe precisely because RLS gates every row; the OAuth client ids are public by design. The xcconfig has one trap: // starts a comment, so every URL in it breaks the scheme separator with $() or the value truncates to lifeos:.

service_role is the one that mattersIt bypasses RLS entirely. It belongs only in an Edge Function environment and in Vault for the cron schedule: never in an xcconfig, never in the app target, never in git. Every other secret in this system is recoverable by rotation; this one grants total read and write access to everything, including three tables of plaintext bank and wearable credentials that are an accepted single-user trade and must be encrypted before a second person's data lands in them.

23.3Shipping to TestFlight

Everything the repo can settle is settled: display name, bundle id, team, iOS 26 floor, export compliance declared exempt. The parts that need an Apple ID are in docs/handbook/testflight-release.md; the two that bite are here.

Bump the build number first, and commit it. App Store Connect rejects a (version, build) pair it has already seen, and it rejects it after the upload finishes. CURRENT_PROJECT_VERSION is 17 today, in both Debug and Release; raise it for every upload, even a re-upload, and a rejected upload still burns the number. Through build 15 the number in git never moved off 1 because each archive was made from an uncommitted edit, so nothing in the repository could answer what was uploaded last. Committing it is what made the guess go away.

Then: destination Any iOS Device, Product → Archive, Distribute App → TestFlight, accept automatic signing (the Apple Distribution identity, not the Apple Development one a local archive uses). Internal testers get the build with no review. Two warnings are not failures: the missing dSYM for LinkKit.framework is Plaid shipping no debug symbols in any slice, and must not be silenced by stripping the app's own symbols; and the first Live Activity request on a fresh install raises the system's own consent alert.

The app icon is rendered from docs/brand/lifeos-icon.svg with headless Chrome at 1024 pixels. The original artwork clipped to a squircle and left the corners transparent; iOS applies its own mask and rejects an icon with an alpha channel at validation, so the shipping SVG lets the gradient run to the edges. Check hasAlpha reads no with sips before committing.

23.4Testing strategy

Logic that can be tested without a simulator lives in the package and is developed test-first. Feature view models are exercised through the native checks harness against the real store, because the Xcode project still has no test target. SwiftUI view bodies are verified by design-preview captures and a build, because asserting on view structure is ceremony that breaks on every layout change without catching real defects.

The one test that matters mostFor every screen, an empty store must produce a snapshot whose readings are all nil. It is a four-line test per feature and it is the regression guard against the single worst bug this app can have: a confident zero where there is no data.

Two habits keep the suite useful. Assertions are written so they cannot pass for the wrong reason: the Plaid cursor tests were rewritten so the "cursor did not move" assertion fails on an empty store, and the money tests dropped a stale comment that described a case they did not cover. And when a check fails during a slice, the rule is fix the cause, never the check: the strength-session check that regressed "Repeated save creates one workout" was fixed by deleting the row it left in the shared context, not by relaxing the assertion.

23.5The design preview and native checks harness

Since 14 September 2026 the app has a DEBUG-only launch argument, --design-preview, that mounts a fixture instead of the signed-in shell. It exists because the recorder, the sensors and the Live Activity cannot be reached by swift test, and because every design QA capture needs the same screen in the same state on every run, with no account loaded.

ArgumentEffect
--page=galleryThe default: a gallery of surfaces
--page=activityBegin Activity over HealthActivityFixture, a fixed WHOOP recovery of 82 percent and a live reading of 152 bpm
--page=player --video=<id>The video player on one catalog id, used for the embed spot-check
--page=checksRuns ActivityRecorderChecks and prints one PASS or FAIL line per check to the console
--page=inbox, --page=settingsThe notification inbox and the settings screen
--live, --strength, --dark, --live-activity, --hud-collapsed, --hud-expandedDrive the in-session fixture: a running session, a strength activity with reps, dark mode, a real Live Activity request, the rings folded to a bar

The checks are the recorder's test suite. Each is a named closure that builds a recorder over an in-memory store with injected answers for Health authorization, the watch bridge and the age, drives it, and asserts. They cover the paths a unit test cannot: a timer starting without Health access, paused readings accruing nothing, a draft restoring after relaunch, a second account being unable to see the first's draft, a watch that never answers, a packet with an unknown version. The rule that applies to them is the same as for tests: fix the cause, never the check.

23.6Driving the simulator from the terminal

idb is not installed and simctl cannot tap, so UI automation goes through clicks at absolute screen coordinates with cliclick, and only while the Simulator is frontmost. The recipe that works, run before every click:

osascript -e 'tell application "System Events" to set frontmost of process "Simulator" to true'
sleep 1
cliclick -w 150 c:X,Y

Coordinates come from the Simulator's own geometry: the device screen is drawn into the first AXGroup of the window, so read its position and size through System Events and scale a pixel measured on the full-resolution screenshot (1206 by 2622 for an iPhone 17) into it. Re-read the group after every boot or window move, because the origin changes. Screenshot after every tap rather than firing three and checking at the end, since a tap during a transition is swallowed. The simulator keychain survives simctl uninstall, so a reinstall skips onboarding; xcrun simctl keychain <sim> reset clears it while the device is booted. Never tap within a hundred pixels of a Plaid entry point without a screenshot confirming what is under the point: on 1 September 2026 a mapped tap landed seventy pixels high, opened Plaid Link and sent a real login code. Build destinations must be iOS 26 runtimes; check xcodebuild -showdestinations, not simctl list devices.

23.7Working in parallel

Five or six sessions routinely run against the one checkout at /Users/shivvyas/LIfeOS, switching branches and pushing under each other, so HEAD in the shared checkout can move mid-task. The conventions that make this survivable:

  • Never commit to main. A branch per logical change: feat/, fix/, docs/, chore/. Branches are reviewed and merged by hand; unrelated changes mixed into one commit or dumped on main make that impossible.
  • Conventional commits. type(scope): imperative summary with a short body explaining what and why, matching the history. No em dashes anywhere in a message, and no attribution trailers.
  • A private worktree for any multi-commit task. git worktree add .claude/worktrees/<name>, then copy the untracked Config/Secrets.xcconfig in, because the app will not sign in without it. Never under a temporary directory that a tool may clear mid-task. Re-read origin/main immediately before every push.
  • Each slice leaves a paper trail. A spec under docs/superpowers/specs/, a plan under docs/superpowers/plans/, and a QA report under docs/design/<slice>/report.md with the captures beside it. The report records every deviation from the plan and every check still pending on hardware.

23.8Guards that run without a test

scripts/check-typography.sh greps the app and package sources for any font declared outside LifeOSType: a literal point size, a UIKit systemFont(ofSize:), a rounded or serif design, or one of Apple's semantic text styles. The app once carried 376 hand-written font calls across 28 sizes because nothing stopped a screen inventing its own. Adding a step is a deliberate edit to Typography.swift, not something that happens by accident on a Tuesday. It exits non-zero on any hit.

The schema test in 21.13 is the other guard worth knowing by name. When you add a field to an existing model, add its name to the list there; the test reads the schema itself rather than the source, so it catches a default removed by a refactor as well as one never written.

23.9Study notes

Read in this order

  1. Config/Secrets.example.xcconfig, every key annotated with where its real secret lives.
  2. supabase/config.toml, the auth and function blocks.
  3. docs/handbook/testflight-release.md.
  4. LIfeOS/App/LIfeOSApp.swift and App/Surfaces/SurfaceDesignPreview.swift, for how --design-preview takes over the scene.
  5. LIfeOS/Features/Activity/ViewModel/ActivityRecorderChecks.swift.
  6. scripts/check-typography.sh and scripts/catalog/verify.ts.
  7. LifeOSKit/Package.swift, for the eight targets and their dependency edges.

Check yourself

  • Why does a clean checkout build without secrets? xcconfig substitution of a missing variable is an empty string, not an error.
  • Why does whoop-callback skip JWT verification? A browser following Whoop's redirect carries no bearer; the function holds no secret and only redirects into an app that checks PKCE and state itself.
  • What must happen before every TestFlight upload? Raise CURRENT_PROJECT_VERSION in both configurations and commit it.
  • Where do the recorder's tests run? On a simulator, through --design-preview --page=checks, because they need HealthKit, Bluetooth and ActivityKit.
  • Why a worktree under .claude/worktrees and not a temporary directory? A temporary directory can be cleared mid-task; the worktrees directory persists and is where every other session puts its own.
