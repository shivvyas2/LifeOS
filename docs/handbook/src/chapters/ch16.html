Chapter sixteen

16Social

Find people, keep the ones you found, message them, and compare a day's effort in a private group. Built on the Supabase project the app already has, with row level security doing every bit of the guarding and no chat service in between.

Revision D described a personal app with no accounts. Since then Almanac gained sign-in, and with it the first feature that is about someone other than the person holding the phone. The design constraint was cost: the app ships free, so a friends list, a mailbox and a leaderboard had to fit on Postgres rows behind PostgREST, with nothing per user to pay for. They do. This chapter describes the three tables that arrived on 27 August 2026, the shared-figures table that followed, and the groups and daily health comparisons that landed on 14 September.

16.1Intent

Working backwards

From your profile, tap Together. Search a name, send a request, and once it is accepted you can message that person, see the three figures they chose to share, and invite them into a group. A group is a private chat with an optional leaderboard that ranks Effort, Recharge and Rest for today or yesterday, on the app's own 0 to 100 scale, with the device each score came from printed beside it. Health scores are shared per group, off by default, and stop the moment you say so.

Why is authorisation in the database and not in the app?

Because the client can only filter for display, never for privacy. Every table carries a policy written against auth.uid(), and every write that has to be atomic goes through a security definer function that takes the caller's identity from the token, never from an argument. A leaked or mistaken query returns nothing it should not, and the Swift side is free to be a thin request shaper.

Why no chat SDK?

A message is a row. SocialAPI is PostgREST over URLSession, the same idiom SupabaseAuth and SupabaseREST established, and the whole social layer adds no dependency. Polling replaces realtime: five seconds while a chat is open, eight in a group, and nothing at all otherwise.

Are the leaderboard numbers WHOOP's or Apple's?

No, and the screen says so. Effort, Recharge and Rest are app-defined comparisons computed on the device from DailyMetrics, each against the person's own goal or their own 28-day baseline. Only the derived score, its source and its day leave the phone. Raw heart rate variability, resting heart rate and sleep minutes never reach the leaderboard endpoint.

What does a friend request let someone see?

A display name and whatever profile fields the person filled in. Nothing else until it is accepted. Pending is not enough to read shared figures: asking to be someone's friend must not be a way to read their numbers while they decide, or the request itself becomes the attack.

What Social does not do: read receipts, edits, deletes or push for messages. The messages table carries no read state, so the inbox never claims a message is unread; it only says whether the last word was theirs. A message is a fact once sent.

16.3Model

Every type the screens render is a Codable value decoded straight from PostgREST. There is no SwiftData model in this feature: nothing social is cached on the device, and a screen that loses the network shows what it last fetched plus one quiet sentence. 

// LifeOSKit/Sources/Integrations/SocialAPI.swift
public struct SocialProfile: Codable, Sendable, Equatable, Identifiable {
    public let userID: UUID
    public let displayName: String
    public let firstName: String?      // every field past the name is optional:
    public let country: String?        // a question someone may decline to answer
    public let birthDate: Date?
    public let heightCM: Double?
    public let avatarPath: String?     // the object's path inside the avatars bucket
}

public enum FriendshipStatus: String, Codable, Sendable { case pending, accepted }

public struct Friendship: Codable, Sendable, Equatable, Identifiable {
    public let id: Int
    public let requester: UUID
    public let addressee: UUID
    public let status: FriendshipStatus
}

public struct SocialMessage: Codable, Sendable, Equatable, Identifiable {
    public let id: Int                 // negative while provisional, see ChatViewModel
    public let sender: UUID
    public let recipient: UUID
    public let body: String
    public let createdAt: Date
}

A friendship is one row whoever asked first, pending until the addressee accepts. The unique constraint is on the ordered pair, and the API guards the reverse direction before inserting. A profile that pads itself with placeholders for the fields somebody skipped looks broken rather than private, which is why the optionals stay optional all the way to the screen.

The decoder is the one piece of the model worth a paragraph. PostgREST emits timestamps with fractional seconds, which the default date strategy does not parse, and a bare date column such as birth_date arrives with no clock at all, which neither ISO 8601 formatter accepts. Before the third branch was added, a profile carrying a birthday failed to decode entirely, taking the person's name down with it. SocialAPI.decoder tries fractional, then plain, then the day format, and is internal rather than private so a test can exercise each branch.

    public let id: Int
    public let groupID: UUID
    public let sender: UUID
    public let body: String

    public let createdAt: Date

public struct LeaderboardEntry: Codable, Sendable, Equatable, Identifiable {
    public let userID: UUID
    public let displayName: String
    public let avatarPath: String?

groups(token:) asks for social_groups with the caller's own group_members row embedded and filtered, so one request returns the groups and, for each, whether this person is a member or merely invited. sharesWellness is optional because the column arrived in a second migration and an older row shape must still decode.

Shared figures and wellness days

// LifeOSKit/Sources/Integrations/SharedStatsClient.swift
public struct SharedStats: Codable, Sendable, Equatable, Identifiable {
    public let userID: UUID
    public let shares: Bool          // the owner's standing answer
    public let streak: Int?          // nil is "not sent", not zero
    public let daysTracked: Int?
    public let workouts: Int?
    public var hasFigures: Bool { shares && (streak != nil || daysTracked != nil || workouts != nil) }
}

shares is separate from the figures because they say different things. A person who turned sharing on this morning and has not opened the app since is sharing, with nothing to show, which is not the same as having declined. The profile screen draws the panel only when hasFigures is true: a row of dashes is not a fact.

SocialWellnessDay is one day's three scores with a source per score and an observedAt. Its shape is enforced twice, once in Swift and once by the table's check constraints: a score and its source are both null or both present, and every score is between 0 and 100.

16.4ViewModel

Five plain @Observable classes, none with retry logic of its own. Each reads the session from the keychain on every call rather than capturing the token once, because AppShell refreshes the session hourly and on foregrounding, and a screen left open across that refresh would otherwise strand itself on a rotated token with endless 401s. Identity does not rotate, so myUserID is the one thing still safe to capture.

A newer search never loses to a slower older one

Search re-runs on every keystroke, so an older request can still be waiting on the network when a newer one is issued. Without tracking which query is in flight, a slow response for "al" could land after the fast response for "alex" and silently replace the right results with the wrong ones. 

// LIfeOS/Features/Social/ViewModel/FriendsViewModel.swift
private var searchTask: Task<Void, Never>?
private var searchGeneration = 0

func search() {
    searchTask?.cancel()
    searchGeneration += 1
    let generation = searchGeneration
    // ... guards that name why nothing would happen: no config, signed out, no id yet
    let issuedQuery = query
    searching = true
    searchResults = []
    searchTask = Task {
        defer { if generation == searchGeneration { searching = false } }
        do {
            try await Task.sleep(for: .milliseconds(250))
            let results = try await api.search(trimmed, accessToken: accessToken)
            guard !Task.isCancelled, issuedQuery == self.query else { return }
            searchResults = results.filter { $0.userID != myUserID }
        } catch {
            guard !Task.isCancelled, issuedQuery == self.query else { return }
            errorMessage = Self.reason("Search failed", error)
        }
    }
}

Three guards together: the previous task is cancelled, a 250 millisecond sleep debounces the keystrokes, and the response is applied only if the query it was issued for is still the query on screen. The generation counter is what lets the defer clear the spinner for the latest search alone. The signed-in person is filtered out of results, because finding yourself in your own friends search is noise.

The three early guards each set a sentence instead of returning silently, because saying nothing is what "it just spins" looks like from the outside. reason(_:_:) carries the server's own message through: an expired token, a missing grant and a dropped connection all arrive as "it did not work" otherwise, and PostgREST always says which.

A send can never lose its row

// LIfeOS/Features/Social/ViewModel/ChatViewModel.swift
private(set) var messages: [SocialMessage] = []   // refresh() only ever assigns this
private(set) var pending: [SocialMessage] = []    // provisional rows, kept apart
private var nextProvisionalID = -1                // server ids are always positive

func send() async {
    guard !sending else { return }
    let text = draft.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !text.isEmpty, text.unicodeScalars.count <= 2000, let api, let accessToken, let myUserID else { return }

    let provisionalID = nextProvisionalID
    nextProvisionalID -= 1
    pending.append(SocialMessage(id: provisionalID, sender: myUserID, recipient: friend.userID,
                                 body: text, createdAt: .now))
    sending = true
    do {
        try await api.send(text, to: friend.userID, accessToken: accessToken)
        pending.removeAll { $0.id == provisionalID }
        if draft.trimmingCharacters(in: .whitespacesAndNewlines) == text { draft = "" }
        await refresh()
    } catch {
        pending.removeAll { $0.id == provisionalID }
        errorMessage = "Message wasn’t confirmed. Your draft is still here; check the conversation before trying again."
    }
    sending = false
}

The optimistic row goes into pending, not messages, so a poll landing mid-send can never wholesale-replace it. The screen renders messages + pending. A failed post removes the row it added rather than leaving a message on screen that never sent, and keeps the draft. Reentry is guarded so a fast double-tap before the disabled state applies cannot post twice. The draft is cleared only if it still equals what was sent, so a sentence typed during the round trip is not thrown away.

Group chat goes one step further. GroupViewModel.send generates a clientID per attempt and reuses it on retry; the server's send_group_message inserts with on conflict (sender, client_id) do nothing and returns the existing id, so a retry after a timeout that actually landed cannot post a duplicate. A failed send is held in failedSend with a Retry button, the composer is disabled until it is resolved, and a later refresh that finds the client id in the timeline clears it.

The rest

  • InboxViewModel loads three things, not one per friend: the friendships, the profiles behind them, and the whole mailbox in one 200-row request. The grouping into one thread per counterpart is InboxDigest.threads, in the package, because it is the only real logic the inbox has and it should be testable without a network. The badge counts requests only: a conversation is not a task.
  • GroupsViewModel loads the groups, then publishes the day's wellness scores if any group has sharing on, then reads and, if sharing is on, pushes the three profile figures. A refresh is skipped while a change is busy, and its results are dropped if the signed-in user changed while it was in flight.
  • GroupViewModel refreshes under a generation counter too, and checks the roster before anything else: if the caller is no longer an accepted member, it sets accessLost, clears the messages and board, and the screen says so instead of rendering a stale chat. Messages merge by id rather than replace, so a page loaded through older() survives a poll. The leaderboard has its own generation so a metric or day switch cannot be overwritten by the previous request landing late.

16.5View

Social is reached from the profile, not from a tab. ProfileOverview offers a Together shortcut, and ProfileScreen pushes SocialHubScreen for it. This is a place you go, not a home you live in, and the bar is the scarcest surface in the app.

Together

SocialHubScreen is an UnderlinePicker with three sections. People embeds FriendsScreen. Groups lists invitations first, each as a panel with Decline and Join, then the joined groups as an adaptive grid of coloured cards. Rankings is the same grid with a trophy and "View leaderboard", and opening a group from it lands on the leaderboard section instead of the chat. The toolbar carries the inbox tray and a Create button; CreateGroupScreen takes a name up to 60 characters, a description up to 240, and invitees chosen from the friends list, capped at 49 so the group never exceeds 50. It generates its group id up front, which is what makes a retried create idempotent on the server.

People

FriendsScreen is one list with three shapes. A search field that, once typed in, replaces the screen's own sections with results. Otherwise requests above friends, in that order, because a decision waiting on you outranks a list you already know. A search result's trailing control is always exactly one of Add, Requested or Friends, never a fourth "request me back" state; accepting still happens from the requests section, which already owns that decision. Tapping a friend opens UserProfileScreen, which shows the photo, the relationship's actions (message and remove, accept and decline, cancel a sent request, or add), and the shared figures panel when there are figures to draw.

Conversations

FriendChatScreen and the group chat share SocialMessageBubble and SocialComposer. Mine is ink on the right with a small bottom-trailing radius; theirs is paper on the left. Day separators appear where the calendar day changes. The composer shows a counter past 1800 characters and disables send past 2000, the same limit the table's check constraint enforces. followLatest is read from scroll geometry: the list follows a new message only if the reader was already within 140 points of the bottom or the message is their own, so someone reading history is not yanked down by a reply. Polling runs in a .task(id: scenePhase) loop and stops the moment the scene leaves the active phase.

The chat's first version on 27 August rode a night aurora. The 14 September restyle replaced that with SocialCanvas, the cream gradient every social screen now shares, with a dark counterpart, so a conversation and the friends list read as one place.

The leaderboard

SocialLeaderboard keeps the server's ranks intact, ties included. A podium of three is drawn only when it would not arbitrarily feature some people from a tie that crosses the podium boundary, and the winner's avatar is larger only when all three ranks are distinct. Accessibility sizes skip the podium for a single readable list. Each row prints the score, the source device and how long ago it synced, and the footer says the one thing a reader needs: equal scores share a rank; compare the same day; devices and goals differ. A DisclosureGroup explains the selected metric's formula in plain words, and a date picker allows today or yesterday and nothing else, matching the server's window.

Style

SocialTheme is four pastels (coral, mint, lilac, yellow) chosen by a stable hash of a uuid, so a person or a group is the same colour on every screen and every launch. SocialAvatar shows the profile photo when there is one and initials on that pastel when there is not. InitialBubble in the inbox hashes the name by hand for the same reason: String.hashValue is randomised per launch, and a friend who changed colour every time the app opened would be a small, constant lie.

16.6How it works

Friendship, end to end

  1. On appear, FriendsViewModel upserts the caller's own profiles row from the local profile name. This is what makes the person findable; a failure here is the difference between having friends and not, and it used to be discarded. It is now a publishWarning that outlives a successful list fetch.
  2. Search is an ilike filter on display_name, limited to 20, with %, * and backslash escaped first so a search for a literal "50%" does not match everything.
  3. Add fetches the caller's own friendships and, if the pair is already linked in either direction, returns without inserting. Idempotent, not an error: asking someone who already asked you is not a mistake worth surfacing. The button flips to Requested before the round trip so it does not flicker.
  4. Accept sends a PATCH carrying exactly one column, status. The database grants update on friendships to that column alone, and Postgres enforces column grants before policies even run, so the same statement that accepts a request can never smuggle in a new requester or a new timestamp.
  5. Remove is a DELETE scoped by id, the same call for declining a pending request and ending an accepted friendship, since either way the row stops existing.
  6. Sending a message requires the sender column in the body, and RLS insists it equal auth.uid(). The only place that identity exists on the device is the access token's sub claim, so SocialAPI.subject(ofAccessToken:) reads it without verifying the signature. Verification is the server's job; this only reads a claim already trusted to authenticate every other call.

Groups, end to end

Reads are plain PostgREST selects gated by is_group_member, a security definer helper that exists to avoid recursive membership policies and that takes the caller only from auth.uid(). Every write is an RPC, because each has an invariant a bare insert cannot hold: create_social_group checks every invitee is an accepted friend and rolls the whole thing back if one is not; invite_group_member locks the group row before counting to 50; leave_social_group hands ownership to the longest-standing member or deletes the group when the owner was the last one; send_group_message locks the group so a concurrent removal cannot race a send in. The anon role is revoked from all of them, and truncate, which bypasses row level security, is revoked from everyone.

Wellness scores, end to end

RootView.socialActivity assembles a SocialActivitySnapshot from the local store: the streak, a count of tracked days, a count of workouts, and the last 30 days of DailyMetrics run through SocialWellness.scores against the person's exercise and sleep goals. The scoring rules are strict on purpose.

  • Effort is exercise minutes over the goal, capped at 100. Apple Health uses exercise time, WHOOP tracked workout time, Fitbit fairly plus very active minutes. A duplicate reading is never summed across providers; MetricArbiter already chose one source per metric and the score uses that one.
  • Rest is sleep minutes over the goal, capped at 100. Extra sleep earns no extra points.
  • Recharge is 50 + 100 × (0.6 × (HRV ÷ usual HRV − 1) + 0.4 × (1 − RHR ÷ usual RHR)), clamped to 0 to 100, where "usual" is the median of at least seven distinct earlier days within 28, all from the same provider, never including today. A WHOOP reading still calibrating, a non-finite number, an HRV outside 0 to 500 or a resting rate outside 20 to 150 yields nil, not zero. Fifty means near your own baseline, and the screen says this is an estimate, not a recovery percentage.
  • Only today and yesterday are published. The server refuses a day outside current_date − 2 to current_date + 1, an observation more than five minutes in the future or four days in the past, and an older observation can never overwrite a fresher row.
  • The day key is a Gregorian local date even when the device uses another calendar, so two people in different locales rank on the same day.

Publishing happens from RootView after provider state changes, from the hub on refresh, and when sharing is switched on, and only if some group has shares_wellness set. The server-side ranking function joins members with sharing on to their daily row and rank()s by the chosen metric, so ties share a position and a null score is simply absent from the list rather than ranked last.

16.7Performance and cost

  • Three requests to build the inbox, not one per friend. Friendships, profiles by an in.() list, and the whole mailbox in one 200-row request ordered newest first. The limit is on messages, not conversations, so a very busy thread can crowd a quiet one off the end. That is the right failure: what falls off is what was least recent.
  • Polling is bounded to an open screen. Five seconds in a direct chat, eight in a group, both inside .task(id: scenePhase) so backgrounding ends the loop. No screen polls while not on screen, and nothing polls the friends list at all.
  • Search is debounced and cancelled. 250 milliseconds, one in-flight request, late responses dropped. A person typing a six-letter name costs at most one or two round trips rather than six.
  • Optimistic writes, no waiting. Add flips to Requested and a message appears in pending before the round trip; both are reverted on failure rather than left lying.
  • Group messages page by id. Fifty newest on open, id.lt for older, merged into the existing dictionary so a poll cannot discard a loaded page.
  • Avatars are downloaded per row with a token and cached only by the task. SocialAvatar keys its .task on avatarPath, so a list that re-renders does not refetch faces unless the path changed.
  • Nothing raw leaves the phone. The leaderboard endpoint receives three integers, three source names, a day and a timestamp. HRV, heart rate and sleep minutes stay in DailyMetrics. The profile figures are three counts. There is no AI in this feature and no token budget to protect.
  • Cost is Postgres rows and PostgREST calls. No realtime channel, no storage beyond the avatars bucket Chapter 17 owns, no third-party chat. The gin index on display_name, the two friendships indexes, the (least, greatest, created_at) conversation index and the (group_id, id desc) timeline index are the whole query plan.

Tests

Sixty Swift tests in five suites, all pure: request builders are static and free of self, so a test asserts on the URLRequest a call would produce without a network or a stub URLProtocol.

  • SocialAPITests (22): every decode branch including the bare birthday, wildcard escaping, the accept sending only status, the friendship request being a no-op in both directions, the sender derived from the token's subject, and a refusal carrying the server's reason.
  • GroupAPITests (9): groups scoped to the caller, no request without a valid session, message pages read newest first and shown chronologically, retry preserving the idempotency key, the wellness upload carrying day and source and no raw signals, and a membership denial arriving as an error rather than an empty success.
  • SharedStatsClientTests (8): sharing off nulls the figures rather than omitting them, an empty id list never leaves the device, the two hasFigures cases.
  • SocialWellnessTests (15): missing and recorded zero remain different, goal progress capped, manual and unattributed data excluded, the baseline cannot mix providers or use today, duplicate days cannot complete calibration, non-finite signals yield no score, the Gregorian day key in other calendar locales, naps cannot replace the main night.
  • InboxDigestTests (6): one row per person carrying their newest message, the newest conversation leads, a message from someone with no profile is dropped.

The database has its own suite: 43 pgTAP assertions for groups and chat and 23 for the wellness leaderboard, each file inserting disposable identities inside a transaction that is rolled back, switching to the authenticated role and setting the JWT claim by hand. They pin the things Swift cannot: that creation is idempotent, that a blank name is a constraint error, that an invalid invitee rejects creation atomically, that authenticated cannot truncate, that nonmembers and invitees cannot read rankings, and that a stale device write does not overwrite a fresher row. The wellness suite ran with the CLI's pgTAP runner unavailable, through the management API instead; the validation notes record that live two-account verification and three-provider accounts were not exercised.

16.9Study notes

Read in this order

  1. supabase/migrations/20260827130000_friends_and_messages.sql: three tables and seven policies. Everything in Swift is shaped by these.
  2. LifeOSKit/Sources/Integrations/SocialAPI.swift: the request builders, the decoder, and subject(ofAccessToken:).
  3. LIfeOS/Features/Social/ViewModel/FriendsViewModel.swift: the search generation counter and the three named guards.
  4. LIfeOS/Features/Social/ViewModel/ChatViewModel.swift: pending kept apart from messages.
  5. supabase/migrations/20260914090000_social_groups.sql: why every write is an RPC, and the row locks inside them.
  6. LifeOSKit/Sources/Integrations/SocialWellness.swift: the three formulas and every reason a score is nil.
  7. supabase/migrations/20260829120000_shared_stats.sql: why the figures are a separate table from profiles.
  8. LIfeOS/Features/Social/View/SocialLeaderboard.swift: the podium rule for ties.

Check yourself

  • Why are the shared figures not columns on profiles? The select policy on profiles is using (true) for every signed-in user, because search needs it, and row level security is row level. A column there would be world-readable. A table of its own gets a policy that can name friendship.
  • How does a slow search response lose to a faster newer one? The task is cancelled, and the response is applied only if the query it was issued for still equals the query on screen. A generation counter clears the spinner for the latest search alone.
  • Why can a poll never erase a message being sent? Provisional rows live in pending; refresh() only ever assigns messages; the screen renders the sum.
  • Why does accept send only one column? The database grants update on friendships to status alone. Any other key fails the whole request before RLS runs.
  • Where does the sender id in a message come from? The access token's sub claim, read without verification, because the server already verified it when it issued the token and verifies it again on the request.
  • What makes a group retry safe? A client-generated clientID reused on retry, and a unique (sender, client_id) on the server with on conflict do nothing returning the existing id.
