Chapter thirteen

13The Life board and the nine sectors

Nine sectors of a life, scored once a month by a rule that shows its evidence and a person who has the last word. The same arithmetic that closes a month also projects the month still being lived, so the board can say where a sector will land and which lever moves it most.

13.1Intent

Shiv had been scoring himself by hand every month across nine sectors: Family, Romance, Soul, Friends, Growth, Money, Mission, Body, Mind. The practice worked. What it lacked was evidence and memory: a feeling recorded on a page, nothing underneath it, and no way to see a year at a glance. The app already held much of the evidence and had no concept of a sector at all. The Life tab is that concept.

Five decisions settled the shape, and the reasoning is what a future reader needs.

  • The app proposes, the user decides. Every month a rule proposes a score per sector with the rows behind it; the person confirms or overrides, and the person's number is what gets stored. Full automation was rejected because Romance and Soul have no honest data source, and one invented number costs trust in all nine.
  • Monthly close, as a ritual. Scores change once a month. Between closes the board holds steady, and Today remains the daily surface. A continuously drifting score duplicates Today's job and invites gaming the number.
  • Rules score, the model explains. A deterministic rule computes the number; the on-device model turns the evidence rows into one sentence. A model-judged score could differ on two runs with no way to see why, and a score you cannot explain is a score you stop trusting.
  • The close-time check-in fills the cold start. A sector with no tracked data asks two or three short questions during the close. The answers become its evidence, stored and comparable next month, so every sector is scorable in month one.
  • No overall life score. An average of nine sectors sits near the middle forever and moves by fractions, which reads as nothing happening in a month where one sector collapsed and another soared. The header carries the two facts that prompt action instead: the lowest sector and the biggest mover.

Two later projects extended the spine. The sector screens project gave every sector the same history screen and amended the original "board as hub" decision: Body, Money and Mission now open a history like the other six, with an extra row through to their full tab. The dry run project added the in-flight mode, where a sector shows a range it can still close in rather than a number, and a ranking of what still moves it.

13.3Model

The nine sectors

// LifeOSKit/Sources/Persistence/LifeSector.swift
public enum LifeSector: String, Codable, Sendable, CaseIterable {
    case family, romance, soul, friends, growth, money, mission, body, mind

    /// Reading order on the board. Kept separate from `allCases` so that

Raw values are written to the store, so a case may be added but never renamed: a rename orphans every score already recorded against it. The same append-only rule applies to check-in question ids.

A scored month

// LifeOSKit/Sources/Persistence/SectorScore.swift
@Model
public final class SectorScore {
    public var sectorRaw: String
    public private(set) var month: Date       // always the first day of the month
    public var proposedScore: Int?            // what the rule said, nil with no evidence
    public var userScore: Int?                // what the person said, nil until decided
    public var closedAt: Date?
    public var evidenceData: Data?            // the rows, frozen at close time
    ...
    public var isScored: Bool { userScore != nil }
}

proposedScore and userScore are both kept, permanently. The distance between what the rule computed and what the person felt is the most interesting number in the system, and averaging them would erase it. The evidence is archived rather than recomputed: change a goal in March and February's reasoning must still read the way it did in February. Every row is keyed by Date.startOfMonth, so closing August on 3 September files the score under 1 August.

The one scoring rule

// LifeOSKit/Sources/Persistence/Evidence.swift
public struct EvidenceRow: Codable, Sendable, Equatable {
    public let label: String
    public let value: String          // already formatted, rendered verbatim
    public let normalised: Double     // clamped into 0...1 on the way in
    public let weight: Double         // never negative; zero means shown, not counted
}

public struct Evidence: Codable, Sendable, Equatable {
    public let rows: [EvidenceRow]

    public var proposedValue: Double? {
        guard !rows.isEmpty else { return nil }
        let totalWeight = rows.reduce(0) { $0 + $1.weight }
        guard totalWeight > 0 else { return nil }
        let weighted = rows.reduce(0) { $0 + $1.normalised * $1.weight }
        return (weighted / totalWeight) * 10
    }

    public var proposedScore: Int? { proposedValue.map { Int($0.rounded()) } }
}

Identical for all nine sectors: each row normalises to 0...1, rows are weighted, the weighted mean scales to 0...10 and rounds. One arithmetic path means one thing to test and one thing to explain. A sector with no evidence proposes nothing, not zero: zero out of ten for Romance in month one is both wrong and demoralising. Weights live in code, not in settings, because user-editable weights turn every score into a dial to twist until the number is agreeable. A zero-weight row is how a scorer shows a figure (earned, spent, unclaimed) without letting it argue.

Every scorer is built from values already fetched, never from a store, which is why evidence() neither throws nor awaits and why every scoring test runs without a container. Two details recur. Days with no data are excluded rather than scored as misses, so a charging night does not argue against the person. And "blocked" plan work returns nil from progressFraction rather than zero: waiting on someone else is not a failure of the person being scored.

Money's rule changed when budgets arrived. With buckets, adherence takes the top weight and the saving rate steps down, because a budget is a plan the person set and beating it measures what they decided mattered, where a saving rate measures what happened to be left over. Without buckets the evidence is exactly what it was before budgets existed, which withNoBucketsTheEvidenceIsUnchangedFromToday pins.

Each option carries its own place on the shared scale. A question with no options is free text: recorded as context, shown on the close, never scored. An answer that matches no option is stale data from a question that has since changed, and it is dropped rather than guessed at.

13.4ViewModel

The board

LifeBoardViewModel.load() builds nine Cards in board order, each with a six-month history for the sparkline. In closed mode a card carries last month's userScore; in flight it carries a SectorBand instead. The header is BoardSummary (lowest and biggest mover, comparing the last two closed months) or, in flight, the days left and the mean share of the month that is decided. The close banner is decided by CloseSchedule. 

// LifeOSKit/Sources/Sectors/CloseSchedule.swift
let oldestGap = scoredCounts
    .filter { month, scored in

    .keys

The oldest month with a gap inside a twelve-month look-back is offered first, so a gap two months back surfaces before a more recent one and is never buried. The fallback to the previous month exists to break a deadlock in the naive version: a query over SectorScore rows only sees months that already have a row, rows are created only by record(), and record() runs only during a close. On a fresh install there are no rows, so the query returns nothing, no banner shows, and no close can ever start.

The close

MonthlyCloseViewModel drives one pass. advance() asks CloseProgress for the first sector in board order that is neither committed in the store nor skipped this session, loads that sector's stored answers, loads the month's inputs once through MonthInputsLoader, and recomputes. recompute() is the single call into the factory, and it runs on every answer, including one keystroke at a time into a free-text field. 

// LIfeOS/Features/Life/ViewModel/MonthlyCloseViewModel.swift
func recompute() {
    guard let sector else { return }
    evidence = SectorEvidenceFactory.evidence(
        for: sector, inputs: monthInputs, answers: answers, calendar: calendar
    )
    proposed = evidence.proposedScore
    chosenScore = ChosenScore.seeded(
        current: chosenScore, hasChosen: hasChosenScore,
        proposed: proposed, previousUserScore: previousUserScore
    )

    let isEmptyNow = evidence.isEmpty
    if NoteRequest.shouldRequest(wasEmpty: evidenceWasEmpty, isEmptyNow: isEmptyNow) {
        scheduleNoteRequest(for: sector)
    }
    evidenceWasEmpty = isEmptyNow
}

Three pure policies sit behind that method, each a few lines and each tested.

  • ChosenScore.seeded. Before the person touches the stepper, the number shown tracks the proposal, falling back to last month's score, then to 5. The moment they touch it, their pick is authoritative and no later recompute may replace it, however small the change that triggered the recompute.
  • AnswerPersistence.isImmediate. A choice button is one discrete event and saves at once. Free text is a stream of keystrokes, and every context.save() makes RootView reload nine view models, so text is debounced 600 milliseconds and flushed synchronously before Skip or Next clears the answers.
  • NoteRequest. The sentence is requested only on the transition from no evidence to some, after a 400 millisecond debounce, and applied only if the sector on screen is still the one it was asked about. Asking on appearance would ask about nothing for a check-in sector, and a request in flight when the close advances must not write its sentence over the next sector's.

commit() records the proposal and its evidence, then commits the chosen score. SectorStore.record returns an existing decided row untouched and SectorStore.commit refuses to overwrite a decided score, so the store does not depend on the view model getting the "never re-offer a committed sector" rule right. skip() moves on without writing anything; a skipped sector stays genuinely unscored and is offered again next time, because a score nobody looked at is noise in the history.

In flight

InFlightSectorViewModel.load() reads the current month's inputs and answers, builds the SectorBand and the Leverage ranking, and notes whether the ceiling came from GoalTargets.default so the screen can say whose numbers they are. Answers given here are written against the current month through the same saveAnswer upsert the close uses, so an answer given on the 12th is visible, scored, and revisable at close with no new model.

13.5View

The deck

SectorStack lays the nine cards out at their full height (190 points) and pulls each one up over the one before it, so all that shows is a 78-point band carrying the sector and its score. Tapping a card lifts it clear of the deck: its z-index jumps, the cards below slide down by the open height less the peek, and the space that appears carries the trend line, a six-month RoundedBarChart, and an Open button. Only one card is ever open, because a deck with several cards open is a list with gaps in it. An open card is sized to what it has to show: 320 points with a chart, 226 without, so a sector with one month does not spend space on a void.

Nothing renders below the band while a card is closed. A covered card has only the peek of room and anything taller gets sliced by the card in front; the trend line used to show as a clipped strip of letter-tops under every title. VoiceOver reads every card whole, because the visual truncation must never truncate what is spoken.

Nine cards that physically overlap need nine distinct colours, and the app's shared ModuleHue has six. SectorPalette.tone is therefore a second, feature-local palette: one muted earth family in light and dark, with a single shared cardInk chosen so it clears contrast on all nine. The six-case hue mapping still exists for the close and the detail screen, which use shared components that take a ModuleHue.

The banner

CloseBanner is deliberately not AlertBanner. That component is red on pink with an ECG glyph and it is the app's anomaly surface: it means something is wrong with your body. An unclosed month is a piece of admin, and borrowing the alarm styling for it spends the alarm. The banner is a dashed outline, collapsed by default, because the deck is the reason anyone opens this screen.

The close screen

One sector per screen, titled "4 of 9". Questions first where the sector has them, then a PastelFillCard with the proposal (its own dash when there is no evidence: not scored badly, not scored at all), the evidence rows label left and value right, the model's sentence if one arrived, "Last month you said 7", and a HeroNumeral with a 0...10 stepper. Skip and Next in the toolbar. The sheet owns its view model, and the board reloads on dismissal rather than on completion, because scoring three sectors and swiping the sheet away used to leave the deck showing dashes for scores that were already saved.

The history screen

Four bands, each omitted rather than rendered empty: the trend as bars from the window minimum (a score is a rating, not a count building from nought, so a flat year of 4s and a flat year of 9s must not both draw as full bars), the reasoning frozen at the latest close, every question's answers laid across the last six months with a dash for a month not answered, and the free-text notes newest first. Observations sit above them when there are any. Body, Money and Mission get one extra row, "Open Body", and LifeSector.ownsTab is the one place that decides which three.

The in-flight screen

The range at display size, the days left, then "What moves it most" as a ranked list of levers with their worth in points, the check-in questions for a sector that has them, and the floor and ceiling evidence under "If nothing changes" and "If you finish at your targets". Money with no buckets says so in a line instead of inventing a ceiling. A ceiling built from default targets is disclosed in one line and points at Health.

13.6How it works

Loading a month

MonthInputsLoader.load is the only place store reads happen for scoring. It builds a MonthWindow (the exact instants a month spans, with a half-open [start, end) for filtering and an inclusive lastDay for the stores whose to: bound is by day), reads metrics, goals, transactions, buckets, plan entries, project pages and journal dates, filters the undated stores by updatedAt or createdAt, and assembles one MonthInputs. It moved out of the close view model when the in-flight board needed the same thing for the current month, and the move fixed a bug the in-flight case exposed: PlanStore.recentTicks reads a day with no tick as a miss, so running the window to the end of a month still being lived scored every day still to come as a habit already broken. Habits are now judged only across the days already lived.

Notes changed what the loader reads without changing what old months mean. Journalling and goals moved to note pages, so NoteEvidence bridges them in, and the legacy plan entries are still read and summed alongside, because a month already closed must keep scoring the way it did.

Projecting the rest of it

// LifeOSKit/Sources/Sectors/ProjectedInputs.swift
public static func coasting(
    _ inputs: MonthInputs, progress: MonthProgress, calendar: Calendar = .current
) -> MonthInputs {
    guard progress.remainingDays > 0, progress.elapsedDays > 0 else { return inputs }
    let remaining = Double(progress.remainingDays)
    let elapsed = Double(progress.elapsedDays)
    var projected = inputs

    if let average = averageReading(inputs.readings) {
        projected.readings += Array(repeating: average, count: progress.remainingDays)
    }
    let earned = inputs.amounts.filter { $0 > 0 }.reduce(0, +)
    let spent = -inputs.amounts.filter { $0 < 0 }.reduce(0, +)
    if earned > 0 { projected.amounts.append(earned / elapsed * remaining) }
    if spent > 0 { projected.amounts.append(-(spent / elapsed * remaining)) }
    projected.budget = inputs.budget.map { scaled($0, by: (elapsed + remaining) / elapsed) }
    ...
    return projected
}

Coast means continuing at the current pace, not stopping. This is the subtle one. For Body the two are nearly the same, since BodyScorer counts only days with data. For Money they are opposites: spending nothing for the rest of the month is the best case, so an empty tail would put the floor above the ceiling and invert the card. One definition serves every sector, and it is the one that reads correctly for spend.

Perfect fills the remaining days at the person's own targets. Not a theoretical maximum, which produces ceilings nobody reaches, and not a personal best, which is undefined in month one. A ceiling built from GoalTargets is reachable by definition, and it makes setting a target consequential for the first time. Only a tracked metric is raised, and always with max against the running average: a person already averaging 20,000 steps against an 8,000 target must not be "perfected" down to 8,000. Perfecting spend spends up to each bucket's remaining allowance and no further, and cannot repair a bucket already blown. Income is not a lever and keeps coasting. Goal statuses are never touched, because a ceiling must never assume a goal closes.

One lever perfected is built on the coast and then overwrites only the dimension named, so a lever's delta is never contaminated by a second lever quietly improving beside it. Leverage.ranked runs the factory once per tracked lever, subtracts the coasting value, clamps at zero (perfecting a lever cannot make a month worse, and a negative row would read as advice to stop), and sorts. A sector scored only from answers has no levers.

The band

// LifeOSKit/Sources/Sectors/SectorBand.swift
public var decided: Double? {
    guard let floor, let ceiling else { return nil }
    return min(max(1 - Double(ceiling - floor) / 10, 0), 1)
}

Decided is literally the share of the score that can no longer move. The board header shows the mean across only the sectors that have a band, not all nine, because a sector nobody has evidence for has not been judged settled or unsettled; folding it in would let silence read as certainty. Money with no buckets has no ceiling: nothing in the data says what a good remaining spend would be, zero is a fantasy and any other figure is invented, so the card shows a floor and points at bucket setup. A ceiling below its floor is always a projection bug, never a fact, and is clamped up.

History and observations

SectorDetailViewModel fetches twelve months of scores and their answers, maps them to plain records, and makes one pure call: SectorHistory.build. Only decided months appear. Question tracks follow the order the questions are asked in and align by index to the months, so a missing answer leaves a gap rather than shifting later answers left. Free text becomes a note, not a track.

Observations are two deterministic rules, both needing three calendar-adjacent months so a single unusual month never fires one: the same answer three months running, and the person scoring below the proposal three months running. The second is the signal the spine kept proposedScore and userScore in separate columns to preserve: the rule is measuring something the person does not feel. "Consecutive" is checked on the calendar, not on array position, because a partial close can leave a sector unscored in the middle month and three entries spread across a longer stretch are not three months running. No model is called from this screen at all, which also keeps it free and instant.

The sentence

SectorNoteTask is an on-device CoachTask with no remote name. Its prompt is only the rows the rule used, so the sentence cannot cite a figure that played no part in the number, and it deliberately never carries last month's score, because the instructions forbid mentioning a score and feeding the model a number on the same scale works against that. The close runs it through the ordinary CoachRouter so availability caching and refusal handling behave as they do everywhere else; an unavailable model leaves the close fully usable with rows and no sentence.

13.7Performance and cost

  • Inputs loaded once per sector, not per keystroke. The close rebuilds MonthInputs in advance(); recompute() only re-runs the factory against values already in memory. Scoring is a handful of reductions over small arrays and runs on every keystroke without cost.
  • Free text debounced, choices immediate. One context.save() per pause rather than per character, because every save reloads nine view models. The pending value is flushed synchronously on Skip, Next and screen dismissal so no keystrokes are lost.
  • One model call per sector, at most. The sentence is requested on the transition into having evidence, debounced 400 milliseconds, on device, and discarded if the sector has moved on. Nothing about a sector leaves the phone.
  • No model on the board or the history. Observations are rules. The board is nine store reads and a summary.
  • In-flight is eight factory runs per sector at most. Two for the band and one per tracked lever (up to four for Body and Growth, one elsewhere). It is recomputed when the board mode switches and when a screen loads, not continuously.
  • The archive is a JSON blob per row. Evidence is encoded once at close and decoded on read; nothing is recomputed against changed goals, and the history screen renders the stored strings verbatim.
  • Everything is local. Sector scores, answers and evidence are SwiftData rows in the account's own store. There is no sync for them and no server table. Cost is zero.

Tests

13.9Study notes

Read in this order

  1. LifeOSKit/Sources/Persistence/Evidence.swift, the one rule.
  2. LifeOSKit/Sources/Sectors/BodyScorer.swift, then MoneyScorer.swift, to see two scorers shape rows.
  3. LifeOSKit/Sources/Sectors/SectorEvidenceFactory.swift, the routing and the merges.
  4. LifeOSKit/Sources/Sectors/MonthInputsLoader.swift, where the stores are read.
  5. LIfeOS/Features/Life/ViewModel/MonthlyCloseViewModel.swift, the close pass and its three policies.
  6. LifeOSKit/Sources/Sectors/ProjectedInputs.swift, coasting and perfect.
  7. LifeOSKit/Sources/Sectors/SectorBand.swift and Leverage.swift.
  8. LIfeOS/Features/Life/View/SectorStack.swift, the deck.

Check yourself

  • Why does a sector with no evidence propose nil rather than zero? It has not been judged badly; it has not been judged. Zero for Romance in month one is wrong and demoralising.
  • Why are proposedScore and userScore both stored? The gap between them is the signal; the standing-gap observation is the first place it is read.
  • Why is the evidence archived rather than recomputed? A goal changed in March must not rewrite what February's reasoning said.
  • What does coasting mean, and why not an empty tail? The rest of the month looks like the part already lived; an empty tail would put Money's floor above its ceiling.
  • Why does the in-flight board never compute a score of its own? The moment a projection scores by another path, the band and the close can disagree, and a band that contradicts the close is worse than none.
  • Why does CloseSchedule fall back to the previous month? Rows exist only after a close, so a query over rows can never start the first close.
