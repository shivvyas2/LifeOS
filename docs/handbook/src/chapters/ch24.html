Chapter twenty-four

24Cost and the allowance

Almanac ships free, so every user costs money and none of them pay it. That single fact caps the architecture. This chapter says where the money goes, which lines are metered by a constraint in the database rather than by good intentions, and what the app costs to run today.

24.1The ceiling

Total running cost must stay under roughly two dollars per user per calendar month, covering cloud inference, speech, bank data, the database, and notifications. There is no revenue per user, so this comes out of pocket and unit economics decide what can be built. The number was fixed on 25 August 2026 and nothing since has moved it.

The requirement is that spending cannot exceed the allowance, not that it usually does not. Those are different engineering problems, and only the first survives concurrency and a looping client. So the lines that scale with use (cloud tokens) are capped in Postgres, the lines that scale with connections (Plaid) are bounded by a count the person controls, and the lines that scale with nothing (Supabase, APNs, Vercel, YouTube) are on free tiers whose limits are named below.

The allowance is internal Users are never shown a balance, a meter, a percentage, or a dollar figure. It exists to bound what the app costs to run, not to be a feature. The only moment it becomes visible is when it runs out, and then it is one sentence: exhausted comes back as a 429 from lifo-agent, and Chapter 14 shows how the coach screen turns that into words.

24.3The token ledger

The cloud tier is metered by one table and one function. lifo_usage holds one row per user, per day, per kind; lifo_debit adds to it in a single statement. Both live in supabase/migrations/20260827090000_lifo_usage.sql, with the kind column added by 20260830090000_proactive_nudges.sql when the nudge got its own allowance. 

-- supabase/migrations/20260830090000_proactive_nudges.sql
alter table public.lifo_usage
  add column kind text not null default 'chat';
alter table public.lifo_usage drop constraint lifo_usage_pkey;
alter table public.lifo_usage add primary key (user_id, day, kind);

create function public.lifo_debit(p_user uuid, p_tokens bigint, p_kind text default 'chat')
returns bigint language sql security definer set search_path = public as $$
  insert into lifo_usage (user_id, day, kind, tokens)
  values (p_user, current_date, p_kind, p_tokens)
  on conflict (user_id, day, kind)
  do update set tokens = lifo_usage.tokens + excluded.tokens
  returning tokens;
$$;

revoke execute on function public.lifo_debit from public, anon, authenticated;
grant execute on function public.lifo_debit(uuid, bigint, text) to service_role;

Three things in that SQL carry the cost model. The upsert-and-add is one statement, so two concurrent turns cannot both read the same balance and each write their own. The table has RLS enabled with zero policies, so no client can read or forge its own usage; the service role inside an Edge Function is the only writer and reader. And the function's execute grant is revoked from every client role, so even a definer function cannot be called from the app.

The caps themselves are constants in the function, not in the schema, so changing one is a deploy rather than a migration: 

// supabase/functions/_shared/lifo.ts
export const DAILY_TOKEN_CAP = 150_000;
/// The nudge's own daily allowance, separate from DAILY_TOKEN_CAP.
export const NUDGE_TOKEN_CAP = 4_000;

export const MAX_CHAT_MESSAGES = 64;
export const MAX_CHAT_TOOLS = 16;
export const MAX_CONTEXT_LENGTH = 32_000;

The door in lifo-agent/index.ts reads the day's chat row before calling the provider and refuses with exhausted at or above the cap. After the reply it debits whatever the provider reported in usage.total_tokens, on every path: a normal answer, a refusal, a tool call, and a streamed turn, where the debit runs in the stream's flush because usage only arrives with the last chunk. The debit is deliberately non-fatal: a failed write to the ledger costs a log line, never the person's answer.

This is a cap, not a reservation Revision D described a proxy that reserved the worst-case cost before calling and settled afterwards under a check constraint. That is not what shipped. What shipped reads the balance, calls, then adds what was billed. A turn that starts at 149,999 tokens will complete and push the row past the cap; the next turn is refused. The overshoot is bounded by one turn, and one turn is bounded by MAX_CONTEXT_LENGTH plus the model's own output limit, which is why the three bounds above matter as much as the cap. The reservation design is worth revisiting before a second person's turns and nudges share the same provider key.

What a turn costs in tokens

Prices are not in the repository, on purpose: the model name is a string in _shared/lifo.ts and the key is in the function environment, so a price change is never a code change. The arithmetic that is in the code is the shape of a turn.

TurnInput, roughlyOutput, roughlyWhere the number comes from
Coach chat, one questionSCOPE plus up to 32,000 characters of context plus the thread; about 8,000 to 10,000 tokens at the capA few hundred tokens; verbosity: "low" and reasoning_effort: "low"MAX_CONTEXT_LENGTH, TUNING
Daily brief, answer, sector noteThe task prompt plus the digest render; smaller than chat because there is no threadOne paragraph or one sentence, schema-constrainedTASKS table
Morning nudgeAbout 300 tokensAbout 60 tokensComment in _shared/nudge.ts

At 150,000 chat tokens a day the cap allows something like fifteen to twenty full-context turns, or far more short ones, per person per day. At the list price OpenAI published for gpt-5-mini when this was written (a quarter of a dollar per million input tokens and two dollars per million output, a figure to re-check rather than trust), a person who hit the cap every single day of a month would cost about a dollar and a quarter in input and well under a dollar in output. Nobody hits the cap every day. The nudge, at 4,000 tokens a day, cannot reach a cent a month. The ceiling holds with room in it, and the cap is what makes that a statement about the worst day rather than the average one.

Why low reasoning effort Medium effort is most of the wait and most of the output tokens. The thinking already happened on the device when MetricsDigest and ContextBundle were built: the model is handed sums, averages and deltas, not a year of rows to reason over. A question over a week of a person's own numbers is not a reasoning problem. If the provider ever rejects the tuning parameters, the door retries once without them, so a rejected parameter costs a slower answer, never no answer.

24.4The lines that are not metered

Speech

ElevenLabs is the one paid service the app calls directly, and the one line the ledger does not see. Speech to text runs on scribe_v2 per recorded question; text to speech runs on eleven_flash_v2_5 and is billed per character. Three things bound it. Spoken replies are off until a person turns them on (AssistantVoice.enabledKey defaults to nothing). The text sent to be spoken is cleaned of markdown and cut at ElevenLabsVoiceClient.maxCharacters, 1,200 characters, on a sentence boundary, which is about ninety seconds of speech. And every spoken reply is also a chat turn, so it already sits under the token cap.

The key ships in the bundle ELEVENLABS_API_KEY is read from Config/Secrets.xcconfig into Config/App-Info.plist as ElevenLabsAPIKey, and AppConfig.elevenLabsAPIKey hands it to both clients. A signed bundle is extractable, so a stranger with the .ipa has the key, and there is no per-user cap on it because there is no server between the app and ElevenLabs. Today the only kill switch is rotating the key in the ElevenLabs dashboard and shipping a build. Moving speech behind an Edge Function with its own kind in lifo_usage is item 2 of the privacy plan in Appendix A, and it is a cost item as much as a privacy one.

Plaid

Plaid bills per connected Item per month, and the app can never call Plaid except through the four Edge Functions in Chapter 20. Two rules keep the count honest. plaid-exchange removes the Item at Plaid if inserting its row fails, so nothing bills for a bank the app cannot find again. And plaid-disconnect removes the Item at Plaid before deleting the row, so a disconnected bank stops billing the month it is disconnected. The environment is set by PLAID_ENV, which defaults to sandbox; sandbox Items are free, which is how the whole bank path was built and tested before a real institution was touched. The price per Item is Plaid's and is not in the repository.

Supabase

Everything server-side runs on one Supabase project on the free tier. The rows it holds per user are small: a profile, a few hundred note pages at most, friendships, messages, shared stats, and one token row per connected provider. Health rows, transactions and sector scores never reach it. The lines that would push a project off the free tier, in the order they would go, are Edge Function invocations (every coach turn, every sync, every OTP), then storage bytes (avatars are pinned to one JPEG per user at 512 points, so this is bounded by user count), then database size (notes are the only unbounded table, and ink drawings above 1.5 MB stay on the device). At a personal scale none of these is close.

Sign-in

Email codes go through Resend's SMTP, configured in config.toml with a sixty second max_frequency, and are free at this volume. SMS is the expensive channel and is treated that way: phone sign-in is offered only for US and India numbers, the otp-start guard refuses a resend inside 45 seconds and rate-limits by pumping prefix, and the committed configuration short-circuits every test number before Twilio is called. The Twilio price per verification is Twilio's and is not in the repository.

Free by construction

APNs costs nothing and the nudge sends at most once per user per local day, claimed by the primary key on nudge_log before the model is asked. The universal-link site is two static files on Vercel's hobby tier. YouTube embeds are free and keyless; the catalog is a read-only table of 122 verified ids seeded by a script that checks each one against the oEmbed endpoint, which is also keyless. Apple's Foundation Models cost nothing per call, which is what makes the on-device tier a real fallback rather than a cheaper cloud.

24.5Why the ceiling holds

The obvious approach does not work: 

read spend  ->  if under cap  ->  call  ->  add cost

Two concurrent requests both read a balance under the cap and both proceed. The app's answer is not to pretend this cannot happen but to make the damage one turn wide and every turn small.

PropertyHow
The add is atomiclifo_debit is one insert ... on conflict do update; two debits never lose each other
The overshoot is boundedOne turn at most past the cap, and a turn is bounded by 64 messages, 16 tools and 32,000 context characters before the model is called
Every path is meteredRefusals, tool calls and streamed turns all debit; an unmetered path would be a free one, and a looping client would find it
Budgets do not bleedChat and nudge are separate kinds with separate caps; a heavy evening of questions cannot cost the next morning's nudge
The client cannot read or write the ledgerRLS with no policies, execute revoked from every client role
The prompt cannot be widened from the clientSCOPE is prepended on the server and a thread carrying its own system message is refused
A missing key fails closedNo OPENAI_API_KEY means the nudge sends its fallback sentence and the coach falls back to the device; nothing is attempted at a guessed cost

The nudge adds one more guard the chat does not need: the rule decides whether to send and the model only phrases. Letting a model decide would bill every user every night and calibrate toward yes. Rules are free and instant, and the fallback sentence in _shared/nudge.ts is what gets delivered when the model is down or the 4,000-token allowance is spent, so an outage costs nothing and still says something.

24.6What it costs today

Measured usage does not exist yet: the app has one real user and a few TestFlight testers, and the ledger is the only meter. What can be said honestly is the shape.

The sensitive input is not the per-token price, which the ledger bounds, but the two lines the ledger does not see: how many people turn voice on, and how many banks each connects. The first is fixed by moving speech server-side under its own kind. The second is a product decision, and the honest reading of the ceiling is that a person with three banks and voice on is over it, and a person with one bank and voice off is nowhere near it.

Why not the cheapest model Providers list models an order of magnitude cheaper than gpt-5-mini. They are not better than Apple's on-device model at the questions this app gets, so escalating to one means paying for a worse answer than the free tier already produced. The selection rule is not cheapest available but cheapest model meaningfully more capable than the device, and the cap is what makes that affordable. Changing the model is an edit to one string in _shared/lifo.ts and a function deploy, not an App Store release.

24.7Study notes

Read in this order

  1. supabase/migrations/20260827090000_lifo_usage.sql: the ledger and why it has no policies.
  2. supabase/migrations/20260830090000_proactive_nudges.sql: the kind column and the rewritten debit.
  3. supabase/functions/_shared/lifo.ts: the caps, the bounds, the task table, the tuning and its retry.
  4. supabase/functions/lifo-agent/index.ts: the balance read, the call, the debit on every path.
  5. supabase/functions/lifo-nudge/index.ts and _shared/nudge.ts: rules decide, the model phrases, the fallback sentence.
  6. LIfeOS/Features/Coach/Model/ElevenLabsVoiceClient.swift: the character cap and the cleaning before send.
  7. supabase/functions/plaid-exchange/index.ts and plaid-disconnect/index.ts: the two rules that keep the Item count honest.

Why are the caps constants in the function rather than a check constraint in the schema?

Changing a cap is then a deploy, not a migration, and the ledger stays a plain count that any future cap can read.

What stops a client from asking for the same answer in a loop for free?

Every path debits, including refusals and streamed turns, and the ledger is unreadable and unwritable from the client.

By how much can a person exceed the daily chat cap?

By one turn, because the check happens before the call and the debit after; the turn itself is bounded by the three request limits.

Which paid line is not metered at all today, and what bounds it?

ElevenLabs speech; voice off by default, a 1,200-character cut, and the fact that every spoken reply is also a capped chat turn.

Why does the nudge have its own kind and cap?

So a heavy chat evening cannot spend the next morning's nudge, and so the nudge, at 4,000 tokens, can never cost more than a fraction of a cent.
