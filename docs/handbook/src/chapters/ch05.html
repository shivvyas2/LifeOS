Chapter five

5Onboarding

Five pages of pitch with a cat that waves, then an identity, a six-digit code, a name, and the connections. Signup is mandatory and it is the only way in: a store belongs to an account, so there is nowhere for a signed-out person's data to live.

5.1Intent

Working backwards

Almanac opens on a lit 3D cat and five pages that say what the app is, one domain per page in the order the tabs appear. Signing in takes an email address or a phone number and a code, a first and last name, and then offers WHOOP, Fitbit, a bank through Plaid and Apple Health. Every connection is skippable. Nothing on the way in asks for a password. A returning user is sent straight into the app once the code is accepted; a new one gets one welcome screen and then Today.

Why is there an account at all?

Because the data outlives the phone, and because the app now supports several people on one device. The account is what lets Supabase hold notes, a profile and provider links, what Row Level Security keys every row to, and what names the SwiftData file this person's data lives in (Chapter 4). Without it a lost device is a lost year, and a second person signing in would inherit the first person's everything.

Why no password?

A password is a credential to lose, store and reset. A one-time code delivered to a channel the user already controls proves the same thing with no secret at rest and no reset flow to build.

Email or phone?

Email first. It is free through Resend to 3,000 a month, needs no A2P registration, and carries none of the SMS failure modes. An SMS costs about five cents and can fail four different ways. Phone is offered as the alternative, to the US and India only, and the app asks Supabase which channels are actually enabled before it renders the choice.

Why can every connection be skipped?

A screen that blocks on a WHOOP login is a screen people abandon. Everything Almanac shows degrades to a blank rather than a wrong number, so an unconnected app is honest, not broken. Every connection is offered again in Settings.

Flow anatomy

  • IntroScreen: five pages over one persistent SceneKit scene, with a "Skip" and a sign-in door for a returning user.
  • IdentityScreen: email and phone tabs, a dial-code picker, one field, one complaint at a time.
  • CodeScreen: six boxes, verification fired on the sixth digit, a shake on a wrong code.
  • ProfileStepScreen: photo, first and last name, birthday, height, gender, country. Only the name is required.
  • ConnectionsScreen: WHOOP, Fitbit, bank accounts, Apple Health, each with its live state.
  • FirstRunTour: one welcome screen after the account exists, shown once per account, however the person arrived.

5.3Model

// LIfeOS/Features/Onboarding/Model/OnboardingModels.swift
enum OnboardingStep: Equatable {
    case intro
    case identity            // phone or email
    case code                // OTP (phone or email)
    case profile             // name, country
    case connections         // Whoop and Health, all optional
    case signedIn            // returning user; nothing left to ask
}

enum AuthMode: Equatable {
    case signUp
    case signIn
}

OnboardingStep is a single value because the alternative, a pile of booleans, can represent states that do not exist. A user cannot be on the code screen and the profile screen at once, and the type should say so. AuthMode is the door the user came through, and it changes copy and nothing else. With OTP there is no password, so sign-in and signup are the same three steps; picking the wrong door is harmless by design, because the branch after verify is what actually routes. 

// LIfeOS/Features/Onboarding/Model/OnboardingModels.swift
struct SignupDraft: Equatable {
    var channel: SupabaseAuthChannel = .email
    var phone = ""
    var dialCode = "+1"
    var email = ""
    var code = ""
    var firstName = ""
    var lastName = ""
    var country = Locale.current.region?.identifier ?? "US"

    var photo: Data?          // already downsized
    var birthDate: Date?
    var heightCM: Double?     // always centimetres, whatever the field shows
    var gender: Gender = .unspecified

    var e164: String { dialCode + phone.filter(\.isNumber) }

    var canSendCode: Bool {
        channel == .phone
            ? PhoneOTP.isAcceptable(e164)
            : email.contains("@") && email.contains(".")
    }
    var canVerify: Bool { code.filter(\.isNumber).count >= 6 }
    var canFinishProfile: Bool {
        !firstName.trimmingCharacters(in: .whitespaces).isEmpty
            && !lastName.trimmingCharacters(in: .whitespaces).isEmpty
    }
}

The draft holds what the user typed, before any of it is trusted. The three can… properties are the only validation in the feature, and they live on the model rather than in a view so a disabled button and a rejected submit can never disagree. Three details are worth noticing:

  • The photo is Data, not UIImage. That keeps the draft a value type that can be compared for equality, and it means the bytes are already the downsized JPEG that will be uploaded, so no view holds a multi-megabyte camera-roll original.
  • Height is always centimetres internally. The imperial fields on the profile step are bindings that translate for display. Storing the number in whichever unit the user happened to be typing is how a height ends up silently wrong after a locale change.
  • Only the name is required. Everything else on the profile step sharpens what the app can say, and none of it is worth blocking someone at the door for.

Gender is deliberately not a biological-sex field wearing a friendlier label. It is how someone wants to be addressed, "Prefer not to say" is the default and a real answer, and stored returns nil for it so nothing is written to the server. If health baselines ever need sex, that is a different question with different answers, and HealthConnectionViewModel already reads it from Health's own characteristic rather than from here (17.4).

DialCountries.all is built from Locale.Region.isoRegions crossed with a hand-typed table of known dial codes, so the list is complete and localised while a region with no known code is dropped rather than guessed at. Offering the wrong prefix sends an SMS into the void, and the user has no way to tell that is what happened. otpRegions is ["US", "IN"]: the country picker on the identity screen is filtered to those two, and the view model resets a draft whose locale is elsewhere to the US.

5.4ViewModel

// LIfeOS/Features/Onboarding/ViewModel/OnboardingViewModel.swift

    private(set) var mode: AuthMode = .signUp

    private(set) var errorMessage: String?
    private(set) var phoneSendFailed = false

    private(set) var isSignedIn: Bool
    private(set) var session: AuthSession?

    private var store: any AuthSessionStoring
    private var auth: SupabaseAuth?
    private var restoreTask: Task<Bool, Never>?

    func loadChannels() async
    func restoreSession() async -> Bool
    func sendCode() async
    func verifyCode() async
    func saveProfile() async
    func signOut()
}

The rules that live here, and nowhere else:

  • Channel availability is asked, not assumed. loadChannels() reads auth/v1/settings. Email stays the default when it is configured and the draft quietly falls back to phone when it is not; phoneUnavailableNote explains a missing SMS provider rather than leaving a dead tab on screen.
  • Email sends a six-digit code, not a magic link. Including {{ .Token }} in the project's email template is what makes GoTrue send a code, and verifyCode() posts it to auth/v1/verify exactly as phone does, with no per-channel branch.
  • The account, not the door, decides what comes next. After verify the step is session.hasProfile ? .signedIn : .profile. A "Sign in" tap with no account still creates one; a "Get started" tap on an existing account skips the profile step it already has answers for.
  • Verify also records the account. The same call adds the session to AccountStore, clears the pre-accounts keychain slot, and re-points the view model's own store at the per-account slot. From here on every network client in the app reads this account's token (Chapter 4).
  • A failed profile write does not strand the user. The account already exists by then, so saveProfile() records the error and advances to .connections anyway. Blocking the last step of signup on a metadata write would trade a cosmetic failure for an unusable app.
  • The photo goes to storage before the row. saveProfile() uploads the avatar first and only then saves the profiles row, so the row never points at an object that does not exist. A failed upload costs the picture and not the profile; it is a try?.
  • Names still go to user_metadata as well. The profile row is the source of truth for display, but hasProfile is derived from user_metadata.first_name when a session is refreshed, and that is what decides whether a returning user is sent through signup again. Both writes are needed.
  • Resend is rate-limited in the UI. A sixty-second countdown starts on every send. Sixty, not forty-five: phone's Edge Function cooldown is 45 seconds, but email posts straight to GoTrue, whose auth.email.max_frequency is 60. The countdown has to clear the stricter of the two or "Resend code" invites a 429.
  • isSignedIn is stored, not computed. A computed store.load() != nil is invisible to @Observable, which once left the shell showing the app after a sign-out until something else happened to redraw it.
  • Restoring is one call, and it is shared. restoreSession() holds the in-flight Task so a launch, a foreground and the keep-alive loop arriving together await one refresh. Supabase rotates the refresh token on use, so the second of a concurrent pair would present a token the first had just retired and be refused.
// LIfeOS/Features/Onboarding/ViewModel/OnboardingViewModel.swift
func verifyCode() async {
    guard let auth, draft.canVerify else { return }
    isBusy = true
    errorMessage = nil
    defer { isBusy = false }

    do {
        let session = try await auth.verify(
            code: draft.code.filter(\.isNumber),
            destination: draft.destination,
            channel: draft.channel
        )
        try AccountStore().add(Account(userID: session.userID,
            label: session.email ?? session.phone ?? "Account"), session: session)
        AccountStore().clearLegacySession()
        store = KeychainAuthSessionStore(account: session.userID)
        self.session = session
        isSignedIn = true
        step = session.hasProfile ? .signedIn : .profile
    } catch let error as AuthError {
        errorMessage = error.readable
    } catch {
        errorMessage = "That code didn't work"
    }
}

The initialiser has one more rule worth knowing. It reads the keychain synchronously and, if a session is there, decides the opening step at once: .connections if the per-account defaults say the person got that far and quit, otherwise .signedIn or .profile by hasProfile. That is what lets a relaunch land on the app without flashing the intro for a frame.

hasProfile defaults to false on decode, by hand A session already in the keychain from before this field existed has no hasProfile key. A synthesised Decodable would throw on it and sign every existing user out on the upgrade, so AuthSession writes its own initialiser and defaults the missing key to false. That default is safe only because the flag is read once, immediately after verify(); a restored session never consults it again.

5.5View

The intro and the cat

IntroScreen renders IntroPage.all in a TabView pager under a hero that stays put while the pages slide. The pages are data rather than five hand-written views for the same reason as before: a loop cannot let page three fall out of step with page one. At accessibility text sizes the pager is replaced with a single continuous reading surface, so a nested horizontal pager does not fight vertical accessibility scrolling. The copy height is measured with onGeometryChange and the largest page wins, so the hero does not jump between pages of different length.

The hero is OnboardingCat, a UIViewRepresentable over an SCNView. It is a real lit character rather than an image sequence: an orthographic camera, an ambient light and one omni key light, a physically based coat material, and a body built from about thirty scaled spheres plus two extruded ear shapes and two extruded arcs for the smile. The horizontal ink lines that make it read as the app's dotted illustration style come from a surface shader modifier: 

// LIfeOS/Features/Onboarding/View/OnboardingCat.swift
coat.shaderModifiers = [.surface: """
    #pragma body
    float row = _surface.position.y * 16.0;
    float edge = abs(fract(row) - 0.5);
    float aa = max(fwidth(row), 0.025);
    float ink = 1.0 - smoothstep(0.14 - aa, 0.14 + aa, edge);
    _surface.diffuse.rgb *= mix(1.0, 0.035, ink);
    """]

Rows are computed from view-space y, so they stay horizontal as the cat turns, and fwidth softens each edge at the rendered resolution so the lines do not shimmer. Motion is a handful of SCNActions: a breathing rise, a head tilt, a tail curl, an eye blink on a 4.6 second keyframe loop, and a wave that plays on page change and on tap. All of it is cheap by construction: the view is capped at 30 frames per second, the scene is paused whenever the screen is not active or Reduce Motion is on, and dismantleUIView drops the scene entirely. With Reduce Motion the cat still turns to face each page, it just snaps instead of animating.

The signup scaffold

struct SignupScaffold<Content: View, Action: View>: View {

Every signup step is the same shape: a back control, the wordmark, a progress rule, a title, a subtitle, one field group, and one primary action pinned to the bottom in a safeAreaInset. SignupScaffold owns that shape so the three screens differ only in their content, which is what keeps them from drifting apart visually as they are edited. Sign-in mode hides the progress rule and counts two steps rather than three; a returning user has no profile step to count.

The code screen does the work instead of asking for it

This is the screen people fail on, so it is built to remove the ways of failing. The single tracked text field is gone; CodeField from DesignSystem draws six boxes and calls back the moment the sixth digit lands, so verification fires without a tap. Autofill can land a whole code with no keystroke, so a Verify button is kept for that user. A wrong code bumps a counter, and the counter drives both a spring shake and an error haptic: 

// LIfeOS/Features/Onboarding/View/SignupScreens.swift
@State private var wrongAttempts = 0
...
CodeField(text: $model.draft.code, count: 6) { verify() }
    .shake(wrongAttempts)
    .animation(.spring(response: 0.28, dampingFraction: 0.4), value: wrongAttempts)
...
.onChange(of: model.errorMessage) { _, new in
    guard new?.isEmpty == false else { return }
    wrongAttempts += 1
}
.sensoryFeedback(.error, trigger: wrongAttempts)

A counter rather than a Bool, because two bad codes in a row must shake twice, and a Bool that is already true animates nothing.

One complaint at a time

The identity screen can have three things to say at once: a validation error, a configuration problem, and a note that SMS is off. Stacked, they read as a broken app. InlineStatus.resolve picks the single most actionable one, with precedence error, then configuration, then warning, and treats whitespace as absence so an empty string never paints a red gap. The "Use email instead" escape is kept below the status rather than folded into it: it is an action the user can take, not another thing going wrong.

The profile step

A PhotosPicker circle at the top, two name fields, then four labelled rows that read as a set: birthday, height, gender, country. The birthday picker opens on a plausible adult date thirty years back rather than today, so the wheel is not three decades of scrolling. Height shows feet and inches where the locale is imperial and centimetres elsewhere, through bindings that only translate; the stored truth is centimetres. The picked photo is downsized before it is kept, because a camera-roll original is several megabytes and this is displayed at 96 points (17.6 for the maths).

Connections, and the flow

ConnectionsScreen is the only onboarding screen that reads live state. It takes the four shared connection view models that AppShell owns, so a connection made here is already made when Settings opens later. Each row shows the provider's own statusDetail, a spinner while it connects or syncs, a "Connected" label once it has, and a disabled button with "Available when this service is enabled" when the build lacks the provider's configuration. The Apple Health row calls health.connect(), which is the permission prompt and the first sync in one; the same view model serves Today's empty-state button and the Connections page in Settings. 

// LIfeOS/Features/Onboarding/View/ConnectionsScreen.swift
struct OnboardingFlow: View {
    @Bindable var model: OnboardingViewModel
    ...
    var body: some View {
        Group {
            switch model.step {
            case .intro:       IntroScreen(onStart: { model.beginSignup() },
                                           onSignIn: { model.beginSignIn() })
            case .identity:    IdentityScreen(model: model)
            case .code:        CodeScreen(model: model)
            case .profile:     ProfileStepScreen(model: model)
            case .connections: ConnectionsScreen(model: model, whoop: whoop, fitbit: fitbit,
                                                 health: health, plaid: plaid, onFinish: onFinish)
            case .signedIn:    ProgressView().controlSize(.large)
            }
        }
        .animation(.easeInOut(duration: 0.28), value: model.step)
        .onChange(of: model.step) { _, step in
            if step == .signedIn { onFinish() }
        }
    }
}

onFinish is called from onChange rather than from the .signedIn view body, because a body can run more than once for a single state and onFinish flips persisted app state.

The welcome

FirstRunTour replaced a six-page second carousel with one scrollable screen: the cat, "Welcome home.", three rows pointing at Today, connections and the coach, and an "Open my day" button. It is presented by AppShell as an overlay rather than a fullScreenCover, because iOS can restore a previously presented cover at launch and two covers contending for one window silently drops one. Its flag, hasSeenFirstRunTour, is stored in the per-account defaults and is separate from hasFinishedOnboarding, so it fires exactly once per account however the person arrived: signup, sign-in, or skip. A 400 millisecond delay and a cancellation check keep a stale tour from presenting over a shell that is already going away.

5.6How it works

Step by step, for a new user on a fresh install:

  1. LIfeOSApp finds no account, so AccountSession.container is nil and AppShell is mounted with hasStore: false. It renders OnboardingFlow.
  2. The identity screen's .task asks auth/v1/settings which channels exist and logs, rather than shows, a missing anon key.
  3. "Send code" posts to auth/v1/otp for email or to the otp-start Edge Function for phone (Chapter 20). The step becomes .code and the sixty-second countdown starts.
  4. The sixth digit fires verifyCode(). On success the session goes into the per-account keychain slot, the account into the roster, and the step branches on hasProfile.
  5. The profile step uploads the avatar, saves the profiles row, mirrors it into the per-account local caches, writes the names into user_metadata, and records "onboarding.step" = "connections" so a quit here resumes here.
  6. Connections are offered. "Continue to LifeOS" calls onFinish.
  7. AppShell.onFinish hands the account and session to AccountSession.signIn, which opens this account's store, clears the resume marker, and animates hasFinishedOnboarding to true. The whole scene re-roots on the new account id and RootView mounts for the first time.
  8. Four hundred milliseconds later the tour fades in, once.

For a returning user the shell's launch task calls restoreSession(). If the refresh succeeds, a store is open and the step is .signedIn, it sets hasFinishedOnboarding and pulls the profile from the server with ProfileSync.pull(), because the profile belongs to the account and not to the phone that typed it. A refused refresh is the only thing that sends someone back to signup.

5.7Performance and cost

  • No store, no tab hierarchy. Onboarding never touches SwiftData. The tabs, their view models and their first fetches are constructed only after an account has a store, which is also what prevents the uncatchable Core Data exception a fetch against an empty schema would raise (Chapter 4).
  • The keychain is read synchronously at init. isSignedIn and the opening step are decided before the first render, so a relaunch that restores a session never paints the intro carousel for a frame.
  • The cat costs what a 30 fps SceneKit view costs, and only while it is on screen. It pauses when the scene phase is not active, when Reduce Motion is on, and when the view disappears. Geometry is thirty low-segment spheres; the ink lines are a few shader instructions rather than a texture.
  • One refresh, however many callers. The shared restoreTask is the difference between one token rotation and a refused second one.
  • Email is the free channel. The default channel costs nothing per send; phone is rate-limited on both sides and restricted to two regions so SMS pumping has nowhere to aim (PhoneOTP.pumpingPrefix exists for the server's benefit).
  • Avatars are 512 points, scale 1, JPEG 0.8. A profile photo is a few tens of kilobytes by the time it is held in the draft, uploaded, and cached.
  • The profile pull is two small requests. One row, and a bucket listing scoped to the account's own folder; the picture itself is only downloaded when the listing's timestamp differs from the recorded one (17.6).
  • Nothing about the intro leaves the device. The first network request is the settings probe, made when the identity screen appears, not at launch.

Tests

  • SessionRefreshTests (twelve tests) drives every branch of the refresher against a stub URLProtocol: an expired session is refreshed and saved, a rejected refresh token signs out, being offline, an outage and a 429 all keep the stored session, and a logout during a refresh cannot resurrect it.
  • AuthSessionProfileTests pins the hasProfile rules: a verified user with a first name has one, a whitespace-only name does not, a stored session without the key still decodes, and a refresh does not forget it.
  • AuthErrorMappingTests maps every Edge Function failure kind, plus the generic 502 fallback on both channels, to a specific readable sentence.
  • PhoneOTPTests: Indian mobiles accepted, Indian landline lengths rejected, US and the local test number accepted, other countries and short values rejected.
  • SignInChromeTests: InlineStatus precedence and blank handling; the code field fills from the left, ignores non-digits, and drops overflow.
  • AccountStoreTests (seventeen tests) covers the roster: a second account does not evict the first, signing out clears the legacy slot too, removing an account leaves its store on disk, a mismatched identity cannot open another account's store.
  • SessionKeepAliveTests: the wake is late enough to act on, an already expired session still waits the floor, a clock jump cannot produce a spin.

The signup screens themselves have no automated test; they are exercised by hand against the project's test-number map, where +1 123-456-7890 with code 123123 returns a real session and never reaches Twilio. Email has no equivalent bypass and depends on the Resend SMTP block being pushed to the hosted project.

The guest bypass is gone Earlier editions described a "Skip for now" guest mode. It no longer exists. A store belongs to an account, notes sync to one, and connections are held per account, so there is nowhere for a signed-out person's data to live that would not become somebody else's the moment they signed in. The intro's "Skip" only skips the pitch; it lands on the identity screen.

5.9Study notes

Read in this order

  1. Features/Onboarding/Model/OnboardingModels.swift: the step enum and the draft are the whole contract.
  2. Features/Onboarding/ViewModel/OnboardingViewModel.swift: read init, verifyCode, saveProfile, restoreSession in that order.
  3. App/AppShell.swift: the gate on line 57 and the three .task blocks.
  4. LifeOSKit/Sources/Integrations/SupabaseAuth.swift: AuthSession and its hand-written decoder.
  5. Features/Onboarding/View/SignupScreens.swift: CodeScreen first, then the profile step's height bindings.
  6. LifeOSKit/Sources/DesignSystem/SignInChrome.swift: InlineStatus.resolve and CodeField.
  7. Features/Onboarding/Model/ProfilePhotoStore.swift: ProfileSync.pull and the stamp.
  8. Features/Onboarding/View/OnboardingCat.swift: the shader and the idle actions.

Check yourself

  • Why does tapping "Sign in" with no account still create one? Because OTP has no password; the only thing that distinguishes a new user is hasProfile, read after verify, and the mode only changes copy.
  • Why is the resend countdown 60 seconds and not 45? Phone's Edge Function cooldown is 45s, but email goes straight to GoTrue whose max_frequency is 60s; the client has to clear the stricter one.
  • What would break if AuthSession used a synthesised decoder? Every session stored before hasProfile existed would fail to decode and sign its user out on upgrade.
  • Why is the tour an overlay and not a fullScreenCover? iOS can restore a cover at launch, and two covers contending for one window silently drops one.
  • Why does the profile step upload the photo before saving the row? So the row can never point at an object that does not exist; a failed upload loses the picture, not the profile.
  • Why does the identity screen probe auth/v1/settings rather than assuming both channels? A phone tab whose SMS provider is off is a button that silently fails; asking first turns that into a warning with a working alternative.
