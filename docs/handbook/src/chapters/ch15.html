Chapter fifteen

15The calendar assistant

The assistant is LIFO's sibling with hands. It reads your calendar through six tools, creates events, and asks before it changes or deletes one. The gate that asks is a property of the code, not a request in the prompt, and the reply is drawn as a day you can move around in rather than described in a sentence.

15.1Intent

Ask "what's on tomorrow?" and the answer needs no tool call: today and tomorrow are inlined in the prompt. Ask "find me an hour on Thursday" and the model calls find_free_time against the local event cache. Say "move the dentist to four" and it calls get_events to learn the id, then update_event, which does not run until a card on screen shows the event as it is now, what it would become, and whether a location is being dropped, and you tap Confirm. Every reply carries an agenda card: a week strip with a dot on the days the reply touched, and the whole of the selected day's agenda underneath, read live from the store rather than from the model's prose.

The assistant is separate from the coach on purpose. The coach's context is metrics and it has no tools; the assistant's context is the calendar and it has six. Neither task sees the other's data. They share the engines, the router, the invoker, the confirmation gate and the chat store, which is why the assistant honours the same tier preference the coach does and drifts nowhere on its own.

The weaker privacy guarantee, stated Every other cloud workload sends derived numbers. On a cloud turn the assistant sends event titles, times and locations, which are content and cannot be aggregated without destroying their use. The control is the tier preference in Settings: "On device" means nothing you ask ever leaves the phone, for the assistant as for the coach. The design spec also asked for a one-time disclosure before first use; that copy does not exist in the app today and is an open item.

15.3Model

What a tool may touch

// LifeOSKit/Sources/Assistant/CalendarAccess.swift
@MainActor
public protocol CalendarReading: Sendable {
    func events(from: Date, to: Date) throws -> [CalendarEventSnapshot]
    func snapshot(id: UUID) throws -> CalendarEventSnapshot?
    func freeSlots(from: Date, to: Date, durationMinutes: Int) throws -> [DateInterval]
}
extension CalendarStore: CalendarReading {}

public protocol CalendarWriting: Sendable {
    func create(_ draft: CalendarEventDraft) async throws
    func update(id: UUID, with draft: CalendarEventDraft) async throws
    func delete(id: UUID) async throws
}

Reads come from the cache and writes go through CalendarSync, which the app declares conformant in one line at the top of the view model. That is the whole reason a write made by asking lands in the same place as a write made by tapping: the sync routes the draft to the source that owns the event, then re-syncs so the cache reflects what the provider actually stored, since providers normalise all-day handling and time zones and trusting the local draft would drift.

Each argument set is a @Generable struct with @Guide descriptions, so the same declaration yields a schema for Apple's session and, through ToolSchema, an OpenAI function declaration with additionalProperties: false. Dates are ISO-8601 on the way in and rendered as EEE MMM d HH:mm in the user's zone on the way out. A garbled date throws a ToolDateError whose description tells the model the format to use, and the invoker turns that into a result string the model can recover from rather than a crash. 

// LifeOSKit/Sources/Assistant/CalendarTools.swift
func eventLine(_ event: CalendarEventSnapshot, timeZone: TimeZone = .current) -> String {
    let start = ToolDates.render(event.startDate, timeZone: timeZone)
    let end = ToolDates.render(event.endDate, timeZone: timeZone)
    let span = event.isAllDay ? "all day" : "\(start) to \(end)"
    return "\(event.id.uuidString) | \(span) | \(event.title)"
}

Every tool result and the inlined context render an event with its id first, and the instructions say never to invent one. The model can therefore only reference ids it has actually seen, and an update or delete with an unknown id returns "No event with that id" rather than touching the wrong row. Creates are not gated, per the design decision; a created event is announced and appears on the card, where it can be edited or deleted by hand.

What a turn touched

Tools hand the model text, because that is what a model consumes. The same events arrive in CalendarEventCollector as values, because that is what a card needs. The alternative was parsing the reply back into events, which means trusting a model to restate a date correctly in order to draw it correctly, and a card that disagrees with the sentence above it is worse than no card. The collector is an actor, deduplicates by id (a turn asking about today and then this week surfaces the same lunch twice) and returns chronologically whatever order the tools ran in.

A reply persists the touched event ids on ChatMessage.eventIDsData as JSON, optional so an existing store migrates without a plan. Ids rather than events, because an event can be moved or deleted after the sentence about it was written, and a card showing what was true last Tuesday is worse than no card. They are re-resolved against the store whenever the conversation is reopened, and one that has since been deleted simply stops appearing.

15.4ViewModel

AssistantViewModel takes its ModelContext in init, unlike every other view model in the app, because it builds a ChatStore, a CalendarStore, an EventKitSource and a CalendarSync from it. That is why RootView creates it once inside attachAll() rather than at property declaration. Its state is the messages, the pending writes, the events per reply, whether it is thinking, whether the calendar is authorized, and the draft. 

// LIfeOS/Features/Assistant/ViewModel/AssistantViewModel.swift
func send() async {
    let text = draft.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !text.isEmpty, !isThinking else { return }
    draft = ""
    isThinking = true
    defer { isThinking = false; pending = [] }

    try? chat.append(conversationID: conversationID, role: .user, text: text)
    reloadMessages()

    let broker = ConfirmationBroker { [weak self] write in
        Task { @MainActor in self?.pending.append(write) }
    }
    self.broker = broker
    let collector = CalendarEventCollector()
    let tools: [any CoachTool] = isAuthorized
        ? CalendarAssistant.tools(reading: store, writing: sync, collector: collector)
        : []
    ...
    let reply = try await AssistantTurn.run(
        instructions: ChatInstructions(
            CalendarAssistant.instructions(authorized: isAuthorized) + "\n\n" + calendarContext()
        ),
        thread: thread, tools: tools, broker: broker, remote: remote
    )
    let events = await collector.collected()
    try? chat.append(conversationID: conversationID, role: .assistant,
                     text: reply.text, toolSummaries: reply.toolSummaries,
                     eventIDs: events.map(\.id))
}

Three things are per turn: the broker, the collector, and (inside AssistantTurn) the invoker. The broker is rebuilt so a card from an old turn cannot resolve a new one; the collector so the cards under a reply are the events that reply was about rather than everything the conversation has ever looked at; the invoker so the six-call cap and the activity chips are turn state. With no authorized calendar the tool list is empty and the instructions say so, so the model explains what to connect rather than calling something that would fail.

The instructions are one string for both tiers, unlike the coach's two, because nothing in them is device-only and the current date and time zone the context prefix carries are exactly what the cloud has no other way to know; without them an update gets built against no notion of today. The conversation id lives in the account's own defaults suite under its own key, distinct from the coach's, because the two screens write into one store and "whichever conversation was written to last" is no longer necessarily this screen's own.

confirm(_:) and cancel(_:) remove the card from pending immediately and then resolve the broker. The broker prunes its own copy on resolve; without the first line the view's copy lingered with live-looking buttons until the whole turn finished. events(on:) reads one day straight from the store on every call rather than caching, because a person moving across the strip is asking about seven different days in a few seconds, a one-day fetch is a single indexed range query, and the alternative is a cache invalidated by every write the assistant makes. save(_:editing:) and delete(id:) from the card's own sheet go through the same CalendarSync the tools write through.

15.5View

AssistantSheet is presented from the quick actions bar on every tab through the calendar.badge.clock action (not a bare calendar glyph, because the month button in Today's top bar is already that). It is a NavigationStack with a Schedule link to MonthScreen on the left and Done on the right. If Apple Intelligence is unavailable on the device the whole sheet is one sentence saying so. Otherwise it is the conversation, a reconnect row when the calendar is not authorized but history exists (the empty state carries the connect button, and a conversation with history hides that state, so someone who revoked access later still needs a way back in), and the composer.

The conversation is a LazyVStack of user bubbles, assistant replies, then the pending confirmation cards, then a "Thinking" row while a turn is in flight and no card is up. The list scrolls to the newest message or the newest card as either count changes. An assistant reply is an InsightCallout of the text, an AssistantAgendaCard when the reply touched events or is the latest reply (a reply about the schedule that draws no schedule is the text-only answer this screen was changed to stop producing; older replies keep a card only if they touched events, so scrolling back through twenty turns is not twenty week strips), and a row of activity chips ("Checked your calendar", "Created an event") from the invoker's summaries.

A confirmation card lists the preview lines the tool produced and two buttons. For an update the lines are the event now, what it becomes, and, when the arguments carry no location and the event has one, "Removes the location", because the update is a full replacement and the card must surface what a glance would miss. For a delete it is the one line of the event being deleted.

AssistantAgendaCard opens on the day the reply was about, not today: a question about next Tuesday that answers itself with this morning is not an answer. The header is the weekday large with an accent dot, filled on today and hollow otherwise, and the date stacked small on the right. The strip is the seven days of that week; days the reply touched carry a three-point dot that is always laid out and only coloured when set, because hiding it would shift every other column as the selection moved. The rows are the selected day's whole agenda, all-day events first, each a day-part glyph, a title and a time with a dotted rule between, past events at 42 percent opacity so the day is still the day but what is left of it is what you are being asked about. A plus under the list creates on the day being looked at. Taps go out through onTapEvent and onAddEvent to the same EventSheet Today uses; the card owns no store and no calendar, so it previews like any other view.

15.6How it works

The gate is structural

// LifeOSKit/Sources/Insights/ToolGate.swift
public actor ConfirmationBroker {
    func decision(for write: PendingWrite) async -> Bool {
        pending.append(write)
        onPending(write)
        return await withCheckedContinuation { continuation in
            continuations[write.id] = continuation
        }
    }
    public func confirm(_ id: UUID) { resolve(id, allowed: true) }
    public func cancel(_ id: UUID)  { resolve(id, allowed: false) }
}

ToolInvoker.invoke checks requiresConfirmation and, for a gated tool, awaits broker.decision(for:) before tool.call. The continuation suspends the tool's execution path until the UI resolves it; there is no other way a gated call proceeds. That is what makes the gate a property of the code rather than a request in the prompt, and it is the substantive improvement over the app this was ported from, which asked the model in the system prompt to confirm first and therefore depended on the model choosing to. A cancelled write returns "User declined this change" as the tool result so the model can acknowledge it. The invoker records didExecuteGatedWrite the moment the gate opens, and AssistantTurn reads it to refuse a device retry after a cloud failure, so a confirmed create can never happen twice.

The loop

On the cloud path RemoteChatEngine sends the thread, the six function declarations and the context, and loops on tool-call replies as described in 14.6. The context is repeated on every round because a stateless server has no memory of the last one. On the device path OnDeviceChatEngine binds each tool through SessionTool and Apple's session drives the calls itself; the invoker is the same object in both cases, so the cap, the gate and the error shaping are identical whichever model is answering. The seventh call in a turn is refused with a message telling the model to say the request could not be completed.

The context prefix

// LifeOSKit/Sources/Assistant/AssistantContext.swift
return """
Current time: \(formatter.string(from: now)) (\(label))
\(todayLines)
\(tomorrowLines)
"""

Today and tomorrow are inlined so "what's on today?" needs no tool call: the cheapest possible path and the most reliable one on a small model. The time zone label is printed as the caller reached for it (Foundation relabels UTC as GMT, and the test pins that it comes back as UTC). Relative dates are resolved against the stated current time, times are stated in the user's zone, replies are a sentence or two, and the model is told to ask before assuming a duration.

Free time

CalendarStore.freeSlots filters all-day events out of the busy set, because "Anniversary" is context, not a meeting, and treating it as busy would zero out the whole day. The pure core merges overlapping busy intervals, subtracts them from the window, and drops gaps shorter than the requested duration; it is nonisolated static so six tests exercise it without a container.

The spec's floor was superseded The design spec floored the assistant on the device and escalated through the router's table, and costed it at a rounding error on that basis. Since the conversational core landed, the assistant runs through AssistantTurn.run exactly like the coach: cloud first under Automatic, device under On device, no fallback under Cloud. The on-device path is the fallback, not the floor.

15.7Performance and cost

  • Two days inline. The most common question costs zero tool rounds.
  • Everything reads the cache. No tool touches EventKit; reads are indexed range queries on CalendarEvent, and writes go through the provider once and re-sync a 30-day-back, 90-day-forward window.
  • One fetch for all cards. resolveEventCards gathers every id across the conversation into one events(withIDs:) query and a dictionary lookup, rather than one round trip per reply.
  • Bounded rounds. Six tool calls per turn, seven rounds at most, and the thread is capped at twenty messages by ChatStore.recent. The server independently bounds the request at 64 messages, 16 tools and 32,000 characters of context, so the endpoint cannot be used as a general proxy on the project's key.
  • Not streamed, on purpose. A tool call arrives in a stream as fragments of a JSON argument string spread across chunks; the server grants a stream only to a turn with no tools, and the assistant is not the screen someone watches word by word.
  • Per-turn objects, no caches. The broker, collector and invoker are cheap value-sized actors made per turn; events(on:) is a fresh one-day query per strip tap. Nothing has to be invalidated.
  • Cost. Per the spec's model, a cloud turn is roughly 1,000 tokens of tool declarations, 600 of instructions and inlined events, and up to 2,000 of history per round, with about 300 out. On the mini model that is well under a cent per turn and shares the coach's 150,000-token daily cap rather than needing one of its own.

15.9Study notes

Read in this order

  1. Assistant/CalendarAccess.swift, the two protocols, then the one-line conformance at the top of AssistantViewModel.swift.
  2. Assistant/CalendarTools.swift, top to bottom, watching where eventLine is used.
  3. Insights/ToolGate.swift and ToolInvoker.swift, to see how a continuation becomes a gate.
  4. Assistant/AssistantContext.swift, for the instructions and the prefix.
  5. Features/Assistant/ViewModel/AssistantViewModel.swift, following send and then resolveEventCards.
  6. Features/Assistant/View/AssistantAgendaCard.swift, then the sheet.
  7. Persistence/CalendarStore.swift, the free-slot core.

Check yourself

  • Why can the model not route around the confirmation? The gated call is suspended on a continuation inside the invoker; nothing the model emits resumes it.
  • Why store event ids on the reply rather than the events? Events change; ids re-resolve to the current truth and a deleted one vanishes.
  • Why do writes go through CalendarSync and not the store? So the provider is the source of truth and the cache reflects what it actually stored.
  • Why is the loop on the device when the model is in the cloud? Every tool reads local state; a server-driven loop would have to call back into the phone.
  • Why are today and tomorrow inlined? The most common question then needs no tool call, which is both the cheapest and the most reliable path.
  • Why does an all-day event not block free time? It is context, not a meeting; treating it as busy would zero out the day.
