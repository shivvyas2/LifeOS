Chapter four

4The app shell, accounts and sign-in

Before any tab exists, three objects decide whose data is open, whether a session still signs them in, and which shell to draw around the screens. This chapter follows a launch from @main to the first rendered tab, then the sign-in that gets a new person there, then what keeps them signed in and how several people share one phone.

4.1Intent

Signing in is required and it is the only entry point. That was already true in the first edition and the reason has only strengthened: a store belongs to an account, notes sync to one, and every connection is held per account. There is nowhere for a signed-out person's data to live that would not become somebody else's the moment they signed in. What is new is that the shell must handle more than one account on a device, must keep a session alive for someone who never closes the app, and must survive an upgrade from the single-store world without looking like it deleted a year of notes.

Working backwards

Almanac opens on the intro the first time and on Today every time after. Signing in takes an email or a phone number and a six-digit code, then a name. A returning person types the code and lands straight in the app. Two people can sign in on one phone and switch between them without either seeing the other's notes, journal or health.

Why no password?

A password is a credential to lose, store and reset. A one-time code delivered to a channel the person already controls proves the same thing with no secret at rest and no reset flow to build.

Email or phone?

Email is the default. It is free through Resend to 3,000 a month, needs no A2P registration, and carries none of the SMS failure modes. Phone goes through Twilio Verify behind an Edge Function, and when a text cannot be delivered the app offers email rather than retrying.

How does the app know I am returning?

The account tells it, not the door you came through. After the code is accepted, AuthSession.hasProfile says whether a name was ever saved; with OTP there is no other difference between signing up and signing in.

What happens if I stay in the app for two hours?

An access token lives an hour. A loop keyed on the sign-in state sleeps until 45 seconds before expiry and renews. Before that loop existed, every authenticated call after the first hour failed with a JWT expired error and nothing was watching the clock.

4.3Launch: from @main to the first tab

LIfeOSApp holds one piece of state, an AccountSession, and switches on whether it has a container: 

// LIfeOS/App/LIfeOSApp.swift
@ViewBuilder private var shell: some View {
    if let container = session.container {
        AppShell(onSignedIn: { session.signIn($0, session: $1) },
                 onSignedOut: { session.signOut() },
                 hasStore: true, accountID: session.scope?.id)
            .modelContainer(container)
            // Re-rooted per account, so no screen carries the previous
            // account's view models or scroll position into the next one.
            .id(session.scope?.id ?? "none")
            .environment(\.accountSession, session)
            .task(id: session.scope?.id) { purgeSeededHistoryOnce() }
    } else {
        // Nobody signed in. The onboarding flow needs no store.
        AppShell(onSignedIn: ..., onSignedOut: ..., hasStore: false, accountID: nil)
    }
}

AccountSession.init does three things before the first frame. It adopts a pre-accounts session if the roster is empty and the legacy keychain slot holds one, moving the old default.store into the new account's directory in the same breath. It removes a current account whose keychain session does not match its id, so a stale pointer can never open somebody else's store. Then it adopts the current scope, which opens the container and hands the owner id to PushService and SurfaceCoordinator. A container that cannot open is not something the person can fix, and carrying on with the previous account's container would show them somebody else's data, so the safe failure is nothing open.

AppShell is the second lock. A session alone is not enough to build the tab hierarchy: every screen below RootView reads through a ModelContext, and mounting it in a scene with no container gets as far as the first fetch before CoreData throws an NSException for an entity it cannot find, which is not catchable from Swift and takes the whole process. So the gate is three-way: 

// LIfeOS/App/AppShell.swift
if onboarding.isSignedIn && hasFinishedOnboarding && hasStore {
    RootView(whoop: whoop, fitbit: fitbit, plaid: plaid, health: health, onSignOut: { ... })
} else {
    OnboardingFlow(model: onboarding, ...)
}

hasFinishedOnboarding is an @AppStorage in the account's own defaults suite. Its job is narrower than its name: isSignedIn resolves synchronously from a keychain read, so on a relaunch that restores a session the flag is already true on the first render, instead of flashing the intro carousel for a frame before the launch task settles. The first-run tour is keyed on its own flag so it fires exactly once per account however the person arrived, and it is an overlay rather than a fullScreenCover because iOS can restore a previously presented cover at launch and two covers contending for one window silently drops one.

4.4Signing in: a code, then a name

OnboardingStep is a single enum rather than a pile of booleans, so an impossible combination cannot be represented: intro, identity, code, profile, connections, signedIn. AuthMode is which door the person came through, and it changes copy and nothing else.

SupabaseAuth is the whole auth client: no SDK, because the three calls needed here are small and a dependency would pull in far more surface than that. The anon key is sent as the API key on every call; it is public by design and Row Level Security is what protects rows. Phone is always offered because SMS goes through the otp-start Edge Function and Twilio Verify, not GoTrue's own provider; email availability still comes from auth/v1/settings, and the identity screen waits for that answer rather than offering a channel that cannot deliver. 

// LifeOSKit/Sources/Integrations/SupabaseAuth.swift
public func sendCode(to destination: String, channel: Channel) async throws {
    if channel == .phone {
        _ = try await postFunction("otp-start", body: ["phone": destination])
        return
    }
    _ = try await post("otp", body: ["email": destination, "create_user": true])
}

public func verify(code: String, destination: String, channel: Channel) async throws -> AuthSession {
    if channel == .phone {
        let data = try await postFunction("otp-check", body: ["phone": destination, "code": code])
        return try decode(data)
    }
    let data = try await post("verify", body: ["token": code, "type": "email", "email": destination])
    return try decode(data)
}

Before a phone number reaches the server, PhoneOTP.isAcceptable refuses what will never be sent to: only Indian mobiles (+91 then ten digits starting 6 to 9) and NANP numbers (+1 then ten digits) are accepted, and pumpingPrefix produces the country-plus-early-digits key the server uses to catch SMS pumping against a neighbouring range. The Edge Function enforces the same rules; this copy exists so the form can refuse without a round trip.

AuthError.fromHTTP maps every failure the classifier knows about onto a sentence a person can act on, and the Twilio cases are the interesting ones. A trial-account failure (21608) blames the account, not the number, because the number is not the problem. An opted-out number (21610) is given the remedy: text START. An unregistered campaign (30034) and a carrier block (60410) are named rather than lumped into a generic failure. And an empty-bodied 502 with no message stays channel-neutral, because email is now the default and the copy must not assume SMS. AuthErrorMappingTests has one test per case, each named for the sentence it guards.

The code screen

This is the screen people fail on, so it does the work instead of asking for it. Six boxes rather than one tracked field. Verification fires the moment the sixth digit lands. A wrong code shakes and buzzes through .sensoryFeedback(.error, trigger:) rather than quietly turning a line red, and the trigger is a counter rather than a Bool because two bad codes in a row must play twice. The Verify button stays even though the sixth digit auto-verifies, because autofill can land a full code without a keystroke and a screen with no button leaves that person nothing to press.

The resend countdown is 60 seconds, not 45: the phone Edge Function's cooldown in otp_guard.ts is 45 seconds, but email posts straight to GoTrue, governed by auth.email.max_frequency, which is 60. The countdown has to clear the stricter of the two or "Resend code" invites a 429.

4.5The returning-user door

With OTP there is no password, so signing in and signing up are the same three steps. The intro offers two doors, "Let's get started" on the last page and "Already have an account? Sign in" beneath it, and picking the wrong one is harmless by design: the branch after verify is what routes. 

// LIfeOS/Features/Onboarding/ViewModel/OnboardingViewModel.swift
let session = try await auth.verify(code: draft.code.filter(\.isNumber),
                                    destination: draft.destination, channel: draft.channel)
try AccountStore().add(Account(userID: session.userID,
                               label: session.email ?? session.phone ?? "Account"), session: session)
AccountStore().clearLegacySession()
store = KeychainAuthSessionStore(account: session.userID)
self.session = session
isSignedIn = true
// The only thing that separates a returning user from a new one, and it is
// known only now. The door they came through does not decide this; the account does.
step = session.hasProfile ? .signedIn : .profile

hasProfile is derived from user_metadata.first_name in the verify response. That is why saveProfile still writes the name to user metadata even though the profile row now lives in the profiles table: the flag that decides whether a returning person is sent through signup again is read from the session, not from a table the session has not loaded yet. AuthSession decodes the flag by hand with a default of false, because sessions already in the keychain have no such key and a synthesised decoder would throw on them and sign every existing person out on upgrade.

The profile step saves in a deliberate order: the picture goes to storage before the row, so the row is never saved pointing at an object that does not exist; a failed upload costs the picture and not the profile. A failed profile write does not strand the person at the last step either: the account exists either way, so the error is shown and the step advances to connections. onboarding.step is written to the account's defaults at that point so a relaunch mid-signup resumes at connections rather than at the profile.

4.6Keeping a session alive

Two pure pieces decide, and one loop acts. SessionRefresher.restore() is asked on launch and on every return to the foreground. Its governing rule is that signing someone out is destructive and cannot be undone without a fresh code, so it happens only when the server has definitively refused the credential: 

// LifeOSKit/Sources/Integrations/SessionRefresh.swift
public func restore() async -> Outcome {
    guard let stored = store.load() else { return .signedOut }
    guard stored.isExpired() else { return .active(stored) }
    guard let refreshToken = stored.refreshToken, !refreshToken.isEmpty else {
        store.clear(); return .rejected
    }
    do {
        let refreshed = try await auth.refresh(refreshToken: refreshToken)
        guard !Task.isCancelled,
              store.load()?.refreshToken == stored.refreshToken,
              store.load()?.userID == stored.userID else { return .signedOut }
        guard refreshed.userID.isEmpty || refreshed.userID == stored.userID else {
            store.clear(); return .rejected
        }
        let session = refreshed.carryingForward(stored)
        try? store.save(session)
        return .active(session)
    } catch let error as AuthError where Self.isRefusal(error) {   // 400, 401, 403, 422
        guard store.load()?.accessToken == stored.accessToken else { return .signedOut }
        store.clear(); return .rejected
    } catch {
        return .active(stored)   // offline, outage, rate limit: keep it and try later
    }
}

Every guard in that function is a bug that happened. Re-reading the store after the network call and comparing the refresh token is what stops a logout during a refresh from resurrecting the session. Comparing the user id is what stops a refresh from replacing the account's identity. carryingForward exists because a refresh response is allowed to be sparse and must not erase what is already known. And the authURL helper exists because appendingPathComponent percent-encoded the ? in token?grant_type=refresh_token, GoTrue answered 404, and for a while no stored session could ever be renewed: an hour after signing in every authenticated call began failing, and signing in always looked fine. AuthRefreshURLTests pins the query staying a query.

OnboardingViewModel.restoreSession coalesces concurrent callers onto one task, because Supabase rotates the refresh token on use and two concurrent refreshes would have the second present a token the first just retired, signing the person out for doing nothing but foregrounding the app during launch.

SessionKeepAlive covers the case neither event reaches: someone who keeps the app open past the hour. It is two numbers and a function, pure so the schedule can be tested without waiting an hour for it: 

// LifeOSKit/Sources/Integrations/SessionKeepAlive.swift
public static let margin: TimeInterval = 45   // inside isExpired's own minute of slack
public static let floor: TimeInterval = 5     // never a spin against the auth endpoint

public static func delay(untilExpiry expiresAt: Date, now: Date = .now) -> TimeInterval {
    max(expiresAt.timeIntervalSince(now) - margin, floor)
}

AppShell runs the loop in a .task(id: onboarding.isSignedIn), so it starts the moment somebody signs in and stops the moment they sign out rather than waking on a timer behind the signup screen. The margin is deliberately inside isExpired's sixty seconds of slack: waking earlier finds a session the refresher considers healthy, does nothing, and spends the wake for nothing. The floor is what stops a session that arrives already expired, or a clock that jumps backwards, from turning the loop into a spin.

4.7Several accounts on one device

Section 1.7 explained why isolation is a file per account. This section is the bookkeeping that makes switching safe. AccountStore keeps two things: a roster in defaults, because a list of who has used this phone is not a secret and enumerating accounts must not need a keychain read each, and a keychain item per user id, because a refresh token is a credential in its own right. 

// LifeOSKit/Sources/Integrations/AccountStore.swift
public var currentScope: UserScope? {
    // Nil rather than "the first account we can find": a current id naming an
    // account that has been signed out must never silently open somebody else's store.
    guard let id = defaults.string(forKey: Self.currentKey),
          accounts.contains(where: { $0.userID == id }) else { return nil }
    return UserScope(id: id)
}

public func add(_ account: Account, session: AuthSession) throws {
    guard !account.userID.isEmpty, account.userID == session.userID else {
        throw AccountStoreError.identityMismatch
    }
    try keychain(for: account.userID).save(session)
    ...
}

@discardableResult
public func setCurrent(_ userID: String) -> Bool {
    // Refuses an account with no stored session rather than switching to one that cannot sync.
    guard accounts.contains(where: { $0.userID == userID }),
          keychain(for: userID).load()?.userID == userID else { return false }
    defaults.set(userID, forKey: Self.currentKey)
    return true
}

KeychainAuthSessionStore() with no arguments defaults to whichever account is current, read straight from defaults rather than through AccountStore because the store is main-actor bound and this type is used from wherever a network call happens to be made. This matters more than it looks: every network client in the app builds one of these to get a token, and before accounts there was one slot, so after a switch they would all have carried on presenting the previous account's token and reading the previous account's rows.

The legacy slot deserves its own sentence because it is what made logging out impossible for a build. It has no user id, so it is not "one account's" session and the per-account clear never reached it; it survived every sign out and the next launch adopted it and signed the person back in, into a scene with no store open, and the first note fetch threw. A credential that can restore an account is that account's session whatever slot it sits in.

AccountDeviceAccess is the last piece: device permissions are app-wide in iOS, so Calendar access granted while one account was open must also be granted by the next one. allowsCalendar requires both the system authorisation and the account's own flag.

4.8The app delegate and push registration

PushDelegate is the whole reason the app has a delegate: the device token arrives through didRegisterForRemoteNotificationsWithDeviceToken and nowhere else, the orientation query arrives through supportedInterfaceOrientationsFor, and the watch mirroring handler must be installed at launch. PushService is one object rather than two because registration and the inbox share the state that matters: the token, which arrives long after the sign-in that asked for it and is needed again at sign out to delete the row.

  • Authorisation is never requested at launch. A permission prompt on first run, before the app has shown anyone anything worth being interrupted about, is the fastest way to a permanent no. It is asked from the notification inbox, the first time that screen is opened.
  • The registration is keyed to the active account and re-pushed on every foreground, because the row carries the timezone the send hour is read in; somebody who has flown somewhere would otherwise keep being nudged at eight in the morning where they used to live.
  • Deregistration happens before the session goes, with the token captured by value, because deleting the row needs the access token of the account whose row it is. Left behind, that row would push one person's sleep onto a phone now showing somebody else's name.
  • A nudge that arrives while the app is open is still shown. The point of the channel is that LIFO speaks first; suppressing it because someone happens to be looking at the app would drop the message entirely. A tap puts the nudge in the inbox and RootView opens the coach on it, seeding the sentence but not the numbers, which are worked out now against the store as it stands.

4.9Two shells, one set of screens

RootView reads the platform's size class once and draws one of two shells. A compact width gets the pill bar floating over the content along the bottom, and it stays put when the keyboard opens, letting the keyboard cover it: without .ignoresSafeArea(.keyboard) the whole stack is lifted and the bar rides up to sit on top of the note being written, in the strip someone is actually looking at.

A regular width gets the same bar stood on end as a left rail, as an overlay so a screen's canvas runs the full width underneath it. Overlays claim no layout room, which is why railInset exists for the screens to apply themselves. The rail withdraws while the pane is being worked with and comes back when that stops: 

// LIfeOS/App/RootView.swift
content
    // Scrolling or dragging anywhere in the pane counts as working with the
    // content. Simultaneous, not exclusive: it observes the touch rather than
    // claiming it, so scroll views, text selection and Pencil strokes all still see it.
    .simultaneousGesture(
        DragGesture(minimumDistance: 12)
            .onChanged { _ in withdrawRail() }
            .onEnded { _ in scheduleRailReturn() }   // 1400 ms later
    )
    .overlay(alignment: .leading) {
        PillNavBar(selection: $tab, items: navItems, axis: .vertical)
            .opacity(isRailVisible ? 1 : 0)
            .offset(x: isRailVisible ? 0 : -(metrics.gutter + 76))   // parked off the edge
            .allowsHitTesting(isRailVisible)
    }
    .overlay(alignment: .leading) {
        if !isRailVisible {
            Color.clear.frame(width: 28).contentShape(.rect)
                .onTapGesture { showRail() }   // a way back without scrolling something first
        }
    }

The keyboard is the other way of working with the pane, and the one where the rail is most in the way: on a landscape iPad the keyboard takes half the height and the note being written is what is left. So keyboardWillShow withdraws the rail and keyboardWillHide brings it back, and a tab change brings it back too, because a tab change is navigation, not content work. The 1400 millisecond return delay is what stops it flickering between the flicks of a fast scroll. Compact width never hides the bar: along the bottom it overlaps nothing that is being read.

Orientation

The iPhone target allows landscape in its build settings so that a workout video can be watched sideways, but almost nothing else in the app is laid out for it. OrientationLock therefore defaults to portrait on a phone and every orientation on an iPad, and the one screen that wants more asks for it while it is on screen and hands it back when it leaves. release() also requests a geometry update back to portrait, because a phone still held sideways would otherwise stay in a landscape the next screen cannot draw.

4.11Study notes

Read in this order

  1. LIfeOS/App/LIfeOSApp.swift: the two-way switch on a container.
  2. LIfeOS/App/AccountSession.swift: init, then adopt(_:), then signOut().
  3. LifeOSKit/Sources/Integrations/AccountStore.swift: the roster and the keychain per account.
  4. LIfeOS/App/AppShell.swift: the three-way gate, the keep-alive loop, and handle(_ url:).
  5. LifeOSKit/Sources/Integrations/SessionRefresh.swift: read every guard as a bug report.
  6. LifeOSKit/Sources/Integrations/SupabaseAuth.swift: the three calls and AuthError.fromHTTP.
  7. LIfeOS/Features/Onboarding/ViewModel/OnboardingViewModel.swift: verifyCode and saveProfile.
  8. LIfeOS/App/RootView.swift, the wideShell and the rail functions.

Check yourself

  • Why are there two locks before RootView mounts? A session without a store reaches the first fetch and CoreData throws an exception Swift cannot catch; a store without a session is somebody's data with nobody signed in.
  • Which HTTP statuses sign a person out, and why only those? 400, 401, 403 and 422: the server refused the credential itself. 429 and 5xx are failures to answer, and a transport error is not an answer at all.
  • Why is the keep-alive margin 45 seconds rather than 90? isExpired has 60 seconds of slack; waking before that finds a healthy session and does nothing.
  • Why does KeychainAuthSessionStore() read the current account id from defaults directly? It is built from wherever a network call is made; going through the main-actor AccountStore would not be possible there, and defaulting to the current account is what stops every client presenting the old token after a switch.
  • What decides whether a person sees the profile step? AuthSession.hasProfile, derived from user metadata in the verify response. The door they tapped decides only copy.
  • Why is the resend countdown 60 seconds when the phone cooldown is 45? Email is governed by GoTrue's 60-second frequency; the countdown must clear the stricter of the two.
