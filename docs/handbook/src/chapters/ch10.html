Chapter ten

10The workout library

A curated table of 122 verified YouTube workouts, a pure planner that turns preferences, today's battery and the week's splits into one session, a library that filters the catalog to it and says every time it had to widen, and a player that puts the glass rings over the video wherever the person drags them.

10.1Intent

Almanac could show what the body did and how recovered it was, but never suggested a session and had no way to follow one. The request was plain: pull up workouts from YouTube matching what the person wants to do (strength, then push, pull, legs, arms, chest), coordinated with how much they can push today, with the live HUD on the video. Three constraints shaped everything that follows.

  • The app ships free. No runtime AI calls, no per-user YouTube API quota. The catalog is a table the service role writes; the app reads it with the person's own token and caches it.
  • YouTube's terms. Videos play in YouTube's own player and nothing may obscure its controls or branding. The rings default to the top leading corner, the region farthest from the control bar, and a drop onto that bar is moved off it.
  • A video the catalog cannot verify never ships. Every id is checked against YouTube's keyless oEmbed endpoint at seed time, and the seed migration is generated, never hand-edited.

Working backwards

Open Health, Fitness, "Plan today's workout". The Today card already knows: "Pull day. You did push on Saturday, so today is pull. Battery 83% · up to zone 5. 30 min." Below it a rail of chips (Saved, then the splits with Pull already lit, then three lengths, then the equipment you said you own) and a list of videos with real thumbnails, the channel, the minutes, three intensity dots and the split. Search by title, channel or muscle. Tap the heart to keep one; hold a row to schedule it for a day, and a "Tue 15" chip appears on it. Tap a row and the video opens in YouTube's player; tap Start and the rings float over the picture. Drag them wherever you like, tap the corner button or turn the phone for full screen, and the same video keeps playing.

Why not let the AI plan the workout?

Cost and honesty. A pure function from four inputs is free, deterministic, and every rule in it is a test. The reason it gives ("You did push on Saturday, so today is pull.") is the rule itself, in words.

What happens offline?

The cache is the source the screen renders; the network only ever adds to it. A refresh that fails leaves the last catalog on screen and says "Showing the last catalog we downloaded." An empty cache with no network says "The library needs a connection the first time." and never a fake list. Thumbnails come from YouTube's image host and fall back to a deliberate tile.

Why does the Saved list ignore today's plan?

A heart is a decision the person already made. Intersecting saves with the plan hid a push video saved today from tomorrow's pull-day Saved list, while its heart was still filled in the full list. The Saved chip is a different list, not a narrower one: the saved rows, newest mark first, narrowed only by the search.

Enums are text, as the notes table does, so a new split lands as data. The revoke all is not decoration: Supabase grants all on a new public table to anon and authenticated by default, so without it the sentence "signed-in users get read-only access" would be untrue at the grant layer. It also takes away TRUNCATE, which bypasses row-level security. The final review added it, matching the social groups table.

The seed today holds 122 rows: 22 cardio, 16 upper, 16 mobility, 15 legs, 8 each of push, pull and full, 7 lower, 5 core, 5 arms, 4 each of chest, back and shoulders. Seventy-five come from FitnessBlender, thirteen each from Sydney Cummings and Heather Robertson, five from Caroline Girvan, and the rest from a handful of others. Intensity skews moderate: 71 at 2, 40 at 1, 11 at 3. Thumbnails are not stored; the app derives https://i.ytimg.com/vi/<id>/hqdefault.jpg.

The cache

// LifeOSKit/Sources/Persistence/CatalogVideo.swift
/// A cached catalog row. The server is the source of truth; a refresh
/// replaces the set, so a video pulled from the catalog disappears here.
@Model
public final class CatalogVideo {
    #Unique<CatalogVideo>([\.youtubeID])
    public var youtubeID: String
    public var title: String
    public var channel: String
    public var durationS: Int
    public var goal: [String]
    public var split: String
    public var muscles: [String]
    public var equipment: [String]
    public var intensity: Int
    public var verifiedAt: Date
    public var cachedAt: Date
    public var durationMinutes: Int { Int((Double(durationS) / 60).rounded()) }
}

CatalogStore.upsert updates matches, inserts new rows and deletes absent ones, so the cache mirrors the server after every successful refresh. It builds its lookup with uniquingKeysWith rather than uniqueKeysWithValues: the primary key makes a duplicate id impossible from the real table, and a trap on a malformed response is a crash where keeping the last row is not.

BookmarkStore.toggleSaved and schedule delete the row when it ends up neither saved nor scheduled, so the table never accumulates empty marks. Both read the row's fields before a possible delete, because a deleted model is not a thing to ask questions of. schedule normalises to startOfDay with the caller's calendar so a picker's time of day never decides which day a workout lands on.

The planner

// LifeOSKit/Sources/Sectors/WorkoutPlanner.swift
public static func plan(goal: String?, sessionMinutes: Int?, batteryPercent: Int?,
                        recentSplits: [(date: Date, split: String)], now: Date,
                        calendar: Calendar = .current) -> TrainingPlan {
    let minutes = sessionMinutes ?? 30
    let recent = recentSplits.filter { $0.date >= weekAgo && $0.date <= now }.sorted { $0.date > $1.date }
    let cap: Int = { switch batteryPercent {
        case .some(let b) where b >= 67: return 3
        case .some(let b) where b >= 34: return 2
        case .some: return 1
        case .none: return 2 } }()

    if (batteryPercent ?? 100) <= 33 || (batteryPercent == nil && hardYesterday) {
        return TrainingPlan(split: "mobility", minutes: minutes, maxIntensity: 1,
                            reason: "Recovery is low today, so this is a mobility day.")
    }
    switch goal {
    case "mobility": ...
    case "endurance": return TrainingPlan(split: "cardio", ..., reason: "Endurance today, paced by your battery.")
    case "strength", "hypertrophy":
        if let last = recent.first(where: { rotation.contains($0.split) }) {
            let next = rotation[(rotation.firstIndex(of: last.split)! + 1) % rotation.count]
            return TrainingPlan(split: next, ..., reason: "You did \(last.split) on \(weekday), so today is \(next).")
        }
        return TrainingPlan(split: "push", ..., reason: "First session this week: push.")
    default:
        return TrainingPlan(split: "full", ..., reason: "Set a goal for a plan built around you.")
    }
}

Four rules in order: a red or unknown-after-a-hard-day battery forces mobility at intensity 1; a mobility or endurance goal picks its own split, capped by battery; strength and hypertrophy rotate push, pull, legs off the most recent of those three within seven days; no goal means full body. The weekday in the reason is looked up on an en_US_POSIX copy of the calendar, because some process environments resolve the locale to abbreviated names and the reason string should be deterministic. The battery cap on intensity is the same band table as the effort ceiling in Chapter 8, so "up to zone 4" on the Today card and the yellow ring on the HUD are the same fact.

The filter

// LifeOSKit/Sources/Sectors/WorkoutLibraryFilter.swift
public static func apply(videos: [LibraryVideo], plan: TrainingPlan, goal: String?, split: String?,
                         band: DurationBand?, equipment: Set<String>, query: String = "") -> (rows: [LibraryVideo], note: String?) {
    let chosenSplit = split ?? plan.split
    // The intensity cap and the equipment the person owns are never
    // widened away: a battery ceiling and a kit list are facts, not
    // preferences to relax when the list comes back short.
    let base = videos.filter { video in
        video.intensity <= plan.maxIntensity
            && (equipment.isEmpty || !Set(video.equipment).isDisjoint(with: equipment))
            && (normalizedQuery.isEmpty || matches(video, query: normalizedQuery))
    }
    var note: String?
    var result = base.filter { $0.split == chosenSplit && inBand($0) }
    if result.isEmpty {
        result = base.filter { $0.split == chosenSplit }
        if !result.isEmpty { note = "Widened to any length." }
    }
    // Only when the split is the plan's own. A chip the person tapped is
    // an instruction, and answering it with another split while the chip
    // still reads selected would be the screen contradicting itself.
    if result.isEmpty, split == nil {
        result = base.filter { video in goal.map { video.goal.contains($0) } ?? true }
        if !result.isEmpty { note = "Widened to any split for your goal." }
    }
    let rows = result.sorted { closeness to plan.minutes, then title }
    return (rows, note)
}

The plan first: its split, its intensity cap, its length give or take fifteen minutes. An empty result widens one step at a time and says which step it took, so a short list is never a mystery. Three things never widen: the intensity cap, the equipment, and the search query. The rows are ordered by closeness to the requested length, then title, so a 30-minute plan lists the 28-minute video before the 45.

The view model

// LIfeOS/Features/Workouts/ViewModel/WorkoutLibraryViewModel.swift
func load() {
    guard let context else { return }
    let store = MetricsStore(context: context, calendar: calendar)
    let today = now()
    goals = try? store.goals()
    videos = (try? CatalogStore.all(context: context)) ?? []
    loadBookmarks()
    capacity = CapacityInputs.todayCapacity(store: store, now: today, calendar: calendar)

    let weekAgo = calendar.date(byAdding: .day, value: -7, to: today) ?? today
    let recent: [(date: Date, split: String)] = ((try? store.workouts(from: weekAgo, to: today)) ?? [])
        .compactMap { record in record.split.map { (date: record.start, split: $0) } }

    plan = WorkoutPlanner.plan(goal: goals?.trainingGoal, sessionMinutes: goals?.sessionMinutes,
                               batteryPercent: capacity?.percent, recentSplits: recent,
                               now: today, calendar: calendar)
    applyFilters()
}

Everything the screen needs is read in one pass: preferences, the cache, today's battery, and the week of splits the rotation turns on. The clock and the calendar are injected so tests can fix a day. Every filter property (splitFilter, durationBand, equipmentFilter, query, savedOnly) re-runs applyFilters() on set, which maps the cached models into LibraryVideo values, calls the pure filter, and maps the chosen ids back. 

// LIfeOS/Features/Workouts/ViewModel/WorkoutLibraryViewModel.swift
func refreshIfDue(force: Bool = false) async {
    guard let context, !isRefreshing else { return }
    let newest = videos.map(\.cachedAt).max()
    let due = force || newest.map { now().timeIntervalSince($0) > Self.refreshInterval } ?? true
    guard due else { return }
    guard let baseURL = AppConfig.supabaseURL, let anonKey = AppConfig.supabaseAnonKey else { noteOffline(); return }
    guard let token = sessions.load()?.accessToken else { noteSignedOut(); return }
    isRefreshing = true
    defer { isRefreshing = false }
    do {
        let rows = try await WorkoutCatalogClient(baseURL: baseURL, anonKey: anonKey).videos(accessToken: token)
        guard CatalogRefresh.shouldReplace(cacheCount: videos.count, incoming: rows.count) else {
            refreshNotice = "The catalog came back empty. Showing the last one we downloaded."
            applyFilters()
            return
        }
        try CatalogStore.upsert(rows, context: context, now: now())
        refreshNotice = nil
        load()
    } catch {
        noteOffline()
    }
}

The refresh runs when the newest cached row is more than a day old, or on pull to refresh. A signed-out person is told to sign in rather than to find signal, because the catalog is read with their own token. And a 200 with no rows is refused by CatalogRefresh.shouldReplace: an unseeded table, a policy that stopped matching, or a range quirk all look like an empty array at the client, and replacing a full cache with that would leave a person who had the whole library a second ago with nothing.

Bookmarks are refetched after every change rather than mutated in place, because toggleSaved and schedule can delete a row, and a deleted model left in the dictionary would be read by the next row that asks. pruneStaleSchedules runs on every load and clears any day that has passed, keeping the save, so a row never carries a stale chip and the schedule sheet never opens on a day its own picker will not accept.

10.5View

The library

WorkoutLibraryScreen is pushed on whichever stack the person is already on (the Fitness segment's training card, or Begin Activity's "Follow a video"), so the way back is the way they came. It sits on a GradientCanvas in the activity hue with the Today card, a status line when the list is non-empty, the chip rail, then the rows or an empty state. The search field is in the navigation bar drawer, always visible, covering no row. The preferences sheet is raised once, decided in attach rather than in every load, because deciding it in load put the sheet back up the moment a Health sync ran.

Rows are cards in a LazyVStack, so scheduling is a context menu rather than a swipe: only a List row can be swiped. The heart is a sibling of the opening button, never inside it, because SwiftUI gives a button nested in a button no defined semantics and saving a video would also open it. The channel and the minutes are two Texts, not one: a long channel name used to push the minutes off the end of the line, and the minutes are the number a person scans for. The channel truncates; the minutes never do. A scheduled row shows its day chip in place of the equipment chips, because four chips beside a thumbnail truncate to "T…" and "Dum…".

VideoWorkoutScreen holds one YouTubePlayerHost in its state and shows the same web view in three layouts. // LIfeOS/Features/Workouts/Model/VideoWorkoutLayout.swift
static let embedOrigin = "https://www.youtube-nocookie.com"
static let idPattern = /^[A-Za-z0-9_-]{11}$/

static func embedURL(youtubeID: String) -> URL? {
    guard youtubeID.wholeMatch(of: idPattern) != nil else { return nil }
    // `fs=0` removes YouTube's own full screen button. That button hands
    // the video to a system layer above the whole app, where no HUD can
    // be drawn; the screen offers its own full screen instead.
    return URL(string: "https://www.youtube-nocookie.com/embed/\(youtubeID)"
        + "?origin=\(embedOrigin)&enablejsapi=1&playsinline=1&rel=0&modestbranding=1&fs=0")
}

The id pattern is checked before anything is interpolated into a URL or the wrapper page, and a row that fails shows "This video will not play here." There is no JavaScript bridge: the person taps YouTube's play button, the one gesture the embed needs, and the recorder times the session rather than trying to follow the video's clock.

The draggable HUD

// LifeOSKit/Sources/AppSurfaces/HUDPlacement.swift
/// (0, 0) is the top leading corner inside the inset; (1, 1) the bottom
/// trailing one.
public struct Anchor: Equatable, Sendable {
    public var x: Double
    public var y: Double
    public static let topLeading = Anchor(x: 0, y: 0)
    public var stored: String { "\(x),\(y)" }
}

/// Where a dropped HUD settles: inside the container, and off the strip
/// it is not allowed to cover, on whichever side of it is nearer and fits.
public static func settle(origin: CGPoint, hud: CGSize, container: CGSize, inset: CGFloat,
                          avoiding strip: CGRect?) -> CGPoint

A position is kept as an anchor, a fraction of the free travel in each axis, rather than a point. The same anchor puts the rings in the same relative place over a small player in portrait, a letterboxed one in full screen and the whole screen in landscape, and it stays meaningful when the HUD collapses to the bar. DraggableHUD stores one anchor per placement ("compact", "fullscreen", "landscape") in AppStorage. The rings follow the finger freely while dragging; the settle rule is applied once, on release, so it reads as a snap rather than a wall. The strip it avoids is the bottom 56 points of the player, where YouTube draws its control bar and logo. Four accessibility actions move it to each corner. It renders at zero opacity until measured, because a HUD drawn at the inset for one frame and then jumping to its saved spot reads as a glitch on every appearance.

Orientation

// LIfeOS/App/OrientationLock.swift
@MainActor
enum OrientationLock {
    static let standard: UIInterfaceOrientationMask =
        UIDevice.current.userInterfaceIdiom == .pad ? .all : .portrait
    private(set) static var mask = standard

    static func allow(_ allowed: UIInterfaceOrientationMask) { ... }

    /// Back to the default, and back upright: a phone still held sideways
    /// would otherwise stay in a landscape the next screen cannot draw.
    static func release() {
        allow(standard)
        guard standard == .portrait else { return }
        for scene in UIApplication.shared.connectedScenes.compactMap({ $0 as? UIWindowScene }) {
            scene.requestGeometryUpdate(.iOS(interfaceOrientations: .portrait))
        }
    }
}

The iPhone target now lists landscape in its build settings so the player can turn, but almost nothing else in the app is laid out for it. So the app delegate answers every orientation query from OrientationLock.mask, which defaults to portrait on a phone; the player screen asks for .allButUpsideDown in onAppear and hands it back in onDisappear, forcing the scene upright so the next screen is not asked to draw a landscape it has no layout for. iPad keeps every orientation, as it always has.

10.6How it works

Step by step: from curation to a saved session

  1. A human edits scripts/catalog/catalog.json. verify.ts parses it (ids match the eleven-character pattern, goals and splits and equipment are from the fixed vocabularies, intensity is 1 to 3, no duplicate ids), then calls YouTube's oEmbed endpoint for every id and fails the run if any returns an error, a title that does not start with the row's title, a channel that differs beyond case and spacing, or a duration more than 10 percent off a length stated in the title.
  2. It writes the seed: one upsert per row and one trailing delete ... where youtube_id not in (...) naming every verified id, so a seed run is a full sync and a row dropped from the JSON leaves the server on the next push. An empty catalog is refused before a single network call, because the trailing delete would make it a migration that wipes the table. After the first push the file name is frozen, so later passes use --out to write a new timestamped migration.
  3. The library opens. attach loads the cache, the preferences, today's capacity and the week's splits, plans, filters, and raises the preferences sheet once if no goal is set. .task calls refreshIfDue().
  4. If the newest cached row is older than a day, one PostgREST select runs with the person's token. Rows replace the cache unless the answer is empty and the cache is not.
  5. Tapping a row pushes VideoWorkoutScreen. The web view loads a wrapper page, based at the privacy-enhanced host, containing an iframe of the embed URL.
  6. Start maps the split to an activity (cardio to .other, mobility to .yoga, everything else to .strength) and calls recorder.start(following:) with the video's id, split, title and channel. The video belongs to this start: a start that bails leaves nothing behind for the next freeform walk.
  7. The rings appear over the player through DraggableHUD. The session runs exactly as in Chapters 8 and 9.
  8. Finish writes the record with videoID, split and sets. The Fitness segment's row shows the split chip; tomorrow's planner reads it for the rotation.
The embed that would not play On the first spot-check zero of six seed videos rendered; every one gave YouTube's "Error 152" card. Loading the embed URL straight into the web view gave the harder error 153; wrapping it in an iframe on a page of our own moved every id to 152; the fix was matching the query's origin parameter to the page's own baseURL and pointing both at youtube-nocookie.com. Six of six then rendered. The report records the elimination.

10.7Performance and cost

  • Zero per-user API cost. The catalog is one table read with the anon key and the person's JWT. No YouTube Data API, no quota, no key. Thumbnails are static images from YouTube's CDN.
  • One fetch a day. refreshInterval is 86,400 seconds; a refresh is otherwise only on pull. The library works entirely from the cache after the first download.
  • Curation is free at runtime. Verification runs on a laptop before a migration; the app never verifies anything.
  • The planner and filter are pure and cheap. One pass over at most 122 rows per filter change, with the cached models mapped to value types once per pass. No index is needed at this size.
  • One web view. The player host lives in the screen's state, so rotation and full screen never reload the video or lose the person's place.
  • Bookmarks are one dictionary. A row asks a dictionary, not the store; the dictionary is rebuilt after a write, when the store is the truth.
  • Capacity is shared, not recomputed differently. CapacityInputs.todayCapacity serves the recorder and the planner, so the battery is read once the same way.
  • The HUD's settle is pure. Corner cases (a HUD wider than its player, a drop onto the control strip) are tests rather than thumbs on a device.
  • What leaves the device. One authenticated read of the catalog; image requests to i.ytimg.com; the embed to youtube-nocookie.com, the privacy-enhanced host. Bookmarks, schedules and preferences never leave.

Check yourself

  • Why does the seed end with a delete? So a seed run is a full sync; a row removed from the JSON leaves the server on the next push instead of living forever.
  • Why is an empty 200 not believed? An unseeded table or a policy that stopped matching looks the same as an empty catalog, and replacing a full cache with it strands the person.
  • Which three filters are never widened, and why? Intensity cap, equipment, search: a battery ceiling and a kit list are facts, and a query is what the person is typing.
  • Why is the web view held in the screen's state? Each layout branch would otherwise get a fresh view identity and restart the video on every rotation.
  • Why is the HUD position an anchor and not a point? A fraction of free travel survives a size change: the small player, full screen, landscape, and the collapse to a bar.
