Chapter nineteen

19Integrations

Eleven external systems feed or serve the app, and one had to be cut. Each is confined to the Integrations target or a single feature file, so no screen knows a vendor exists: a ViewModel sees rows in DailyMetrics and a connection state, nothing more.

Revision D described four integrations. Since then Apple Health went from nine types to forty seven, Fitbit arrived as a second strap, Plaid brought bank sync, EventKit brought the calendar, the coach gained a cloud tier and a voice, YouTube embeds carry the workout library, and APNs delivers the morning nudge. Two straps writing the same row also forced a real merge rule, the arbiter, which sits in the middle of this chapter because every health source now goes through it. The chapter takes each system in turn: what it provides, how it authenticates, the client code, the wire format, how its readings reach the spine, how it fails, and which tests pin it.

19.1Apple HealthKit

The primary source, and since 27 August the widest. Revision D read nine types with anchored queries. The reader now covers forty seven metrics, and the design decision that made that possible without forty seven schema changes is worth understanding first.

The vocabulary lives outside HealthKit

HealthMetric is a plain Swift enum in Integrations with no HealthKit import. It carries the vocabulary (a title, a unit label, a decimal count, a display group) and the merge rules (which metrics a strap outranks the phone on, which a person can type). The translation to HKQuantityTypeIdentifier lives in one static function on HealthKitReader, behind #if canImport(HealthKit), which is what keeps the package building for macOS and swift test running from the terminal. 

// LifeOSKit/Sources/Integrations/HealthMetric.swift
public enum HealthMetric: String, CaseIterable, Sendable, Identifiable {
    // Movement
    case steps, activeEnergyKcal, restingEnergyKcal, exerciseMinutes,
         standMinutes, distanceKm, flightsClimbed, activeZoneMinutes
    // Heart and fitness
    case restingHR, walkingHR, hrvMs, vo2Max, cardioRecoveryBpm, readinessScore
    // ... body, sleep, vitals, intake, mind, gait, cycle

    /// Measured by a strap worn on the body, so a wearable outranks the phone.
    public var claimedByWearable: Bool { ... }
    /// A person can type this into the app, so a background sync must not
    /// replace what they entered on purpose.
    public var acceptsManualEntry: Bool {
        switch self {
        case .weightKg, .waterML: true
        default: false
        }
    }
    public var healthIsAuthoritative: Bool {
        !claimedByWearable && !acceptsManualEntry
    }
}

Adding a metric is four lines in this enum plus one mapping line in the reader. Nothing else changes, because of how the row stores it. DailyMetrics keeps its ten original named columns (steps, sleep, weight and so on) because the sector scorers, the charts and the Whoop merge read them by name. Everything else lands in extrasData, a JSON dictionary keyed by HealthMetric.rawValue. A missing key means no reading; nothing writes a zero to stand in for one. A parallel sourcesData bag records who wrote each value, which is what the arbiter reads back.

Reading a day

Revision D used anchored queries and persisted anchors. That is gone. The reader now asks for one day at a time with HKStatisticsQuery, summing counts and averaging measurements, because a day is the unit the spine stores and a statistics query de-duplicates across sources for free. Summing raw samples yourself double-counts steps on a day you carried a phone and a watch. 

// LifeOSKit/Sources/Integrations/HealthKitReader.swift
/// Counts accumulate across the day; measurements are averaged over it.
/// Summing a heart rate would produce a number in the thousands.
static func option(for metric: HealthMetric) -> HKStatisticsOptions {
    switch metric {
    case .steps, .activeEnergyKcal, .restingEnergyKcal, .exerciseMinutes,
         .standMinutes, .distanceKm, .flightsClimbed, .waterML,
         .dietaryEnergyKcal, .proteinG, .carbsG, .fatG, .caffeineMg,
         .daylightMinutes:
        .cumulativeSum
    default:
        .discreteAverage
    }
}

/// What to multiply HealthKit's number by to get the unit the app stores.
static func scale(for metric: HealthMetric) -> Double {
    unit(for: metric) == .percent() ? 100 : 1
}

The scale function exists because of a real bug. HKUnit.percent() yields 0.98 for a 98 percent blood oxygen reading, and the app stores percentages as percentages everywhere else, Whoop included. A Health-sourced SpO2 landed two orders of magnitude below a Whoop one and rendered as "1.0". It went unnoticed because Whoop owns that field and Health only fills its gaps.

Sleep is a category, not a quantity, so it is summed by hand from HKCategoryValueSleepAnalysis samples. One query answers six metrics: total asleep, deep, REM, core, awake and in-bed. .inBed is deliberately not counted as sleep, because it is time on a mattress and would inflate the night by however long its owner reads before turning the light off. Mindful minutes sum a category's durations; menstrual flow takes the day's latest ordinal sample, because a value entered later is a correction.

A metric that errors is dropped rather than failing the day. One unreadable type must not cost the user the other forty six.

Which days to re-read

HealthSyncWindow is a pure function from "when did we last sync" to "which days to read", oldest first. It always includes today, because a step count climbs until midnight. It includes the day of the last sync as well as the days since, because a night's sleep is recorded against the morning it ends and the day already covered can still gain a value. A first sync backfills thirty days, the month the dot grid shows. A stamp from the future means a clock change, not a sync that has not happened, and yields just today.

Live changes and the foreground rule

changes(for:) returns an AsyncStream fed by one HKObserverQuery per type. An observer rather than a timer: a step count changes dozens of times an hour and not at all overnight, so any interval short enough to look live is mostly wasted queries. The stream buffers one event (bufferingNewest(1)) because a batch of samples landing together is one reason to re-read the day, not thirty. Every observer handler calls its completion even on the error path, because HealthKit retries a query whose handler never completed, and a silent leak of those is how an app ends up with a hundred live observers.

Background delivery is deliberately off enableBackgroundDelivery needs an entitlement and wakes the app to write rows nobody is looking at. The launch and foreground syncs already cover the time the app was away, and the observer covers the time it is open. Revision D listed background delivery as a freshness mechanism; the code that shipped chose not to.

Authorisation and the cycle gate

The authorisation trap from Revision D still holds: HealthKit never says whether read access was granted, only whether it was asked, so branching on status is always a bug and an empty result is indistinguishable from a refusal. The settings row therefore links out to Health rather than claiming a state.

What is new is a second prompt. The first request asks for HealthMetric.universal, everything that applies to everyone, plus the biological sex characteristic. Cycle metrics (basalBodyTemperatureCelsius, menstrualFlowLevel) are requested in a separate requestCycleAuthorisation() and only when cycle tracking is on. Not because they are more private than a heart rate, but because a permission sheet that asks every person for menstrual data tells most of them the app has misread who they are. healthSuggestsCycleTracking() reads Health's own sex field to pick the default, and it is a default only: the setting is offered either way. The display side of the gate is HealthDaySummary.groups(for:includingCycle:), which withholds cycle rows even for a day that was read while the switch was on.

Two write purpose strings ship. The main app's declares that it saves activities the user chooses to record; the watch's declares that it saves workouts recorded on the wrist. Revision D's "read-only in V1" is no longer true: the live session recorder in Chapter 8 writes workouts, and App Store validation demanded the string.

Applying a day

HealthApply.write is the one place the HealthMetric vocabulary meets DailyMetrics columns. It is separated from the reader so the mapping can be tested against a real in-memory store without a device: MetricArbiter can be perfectly correct and still be wired into the wrong column, and only this layer catches that. Every write goes through MetricsStore.upsert, a merge rather than a replace, so the columns Health has nothing to say about are left exactly as Whoop or the user left them.

HealthApplyTests (nine tests) pins that Health fills an empty day across every column, that Whoop values survive a Health sync, that a later sync corrects a step count, that an empty Health day changes nothing, that counts are stored as integers, and that every write records its provenance. 19.2Whoop

Still the only source of Recovery percentage, Strain and Whoop's sleep scoring, and still the integration with the most code: eleven files in Integrations and one archive model in Persistence. Everything from Revision D holds, so this section states the design briefly and spends its words on what changed: server-held connections, a wider digest, the arbiter, and the two URL schemes.

The five collections, defined once

WhoopCollection pairs each endpoint path with its OAuth scope, and WhoopOAuth.defaultScopes is derived from it plus offline. This exists because path and scope once drifted: two endpoints were added to the client while the authorize request still asked for three scopes, Whoop 401'd a token it had just issued, and the sync read that as a dead credential and deleted it. Colocating them makes a fetchable-but-unauthorised collection unrepresentable, and everyCollectionsScopeIsRequestedAtAuthorization pins it.

CollectionPathScopeFeeds
Recoveryrecoveryread:recoveryRecovery %, HRV, resting HR, SpO2, skin temp, calibrating flag
Sleepactivity/sleepread:sleepAsleep minutes, stages, performance, efficiency, consistency, need and debt components
Cyclecycleread:cyclesDay strain, calories, average and max HR
Workoutactivity/workoutread:workoutWorkoutRecord rows with six zone durations, exercise minutes

OAuth: PKCE on the phone, the secret on the server

Whoop registers apps as confidential clients, so the token exchange runs in the whoop-token Edge Function. The app builds the authorize URL with an S256 challenge over a random 32-byte verifier, hands the returned code and verifier to the function, and the function performs the exchange with WHOOP_CLIENT_SECRET. PKCE is kept even though the exchange is server-side because it binds the code to this app instance.

The redirect is two hops. Whoop requires an https redirect URI, so it points at whoop-callback, which 302s to a custom scheme. Sign-in opens in real Safari via UIApplication.open because Whoop's login sits behind a Cloudflare challenge that never clears inside ASWebAuthenticationSession. The pending verifier and state are persisted to the Keychain as a list capped at five and fresh for fifteen minutes, because Safari backgrounds the app and iOS may kill it before the callback returns, and because tapping Connect twice creates two valid in-flight authorisations.

Two URL schemes, and which one the bridge sends The app claims both almanac and lifeos. The bridge sends lifeos://whoop-callback because that is the scheme every build already installed knows, including ones that predate the rename. Pointing it at almanac stranded anyone who had not updated: Safari was handed a scheme no installed app claimed and refused it as an invalid address. The comment in whoop-callback/index.ts records the plan to move to almanac once no old build is in use, and why lifeos is the weaker claim: a device that had the app before its bundle identifier changed carries the old install as a separate app that also claims it.

The connection now lives on the server too

Migration 20260913090000_whoop_account_connections.sql added a whoop_connections table, and whoop-token now stores every issued pair there under the caller's user id. The phone still keeps its own copy in the Keychain, scoped to the signed-in account, but three things changed:

  • Restore. A fresh install, or a second device, calls WhoopTokenExchange.restore() ({"action": "restore"}). If the server has a live pair it returns it; a 404 means this account never linked Whoop. WhoopConnectionViewModel.syncIfStale tries this once per process before deciding the strap is disconnected.
  • Refresh under a lock. Whoop rotates the refresh token on every use, so two devices refreshing at once would invalidate each other. The function claims the row through claim_whoop_refresh, a 30-second lock, and a second caller gets refresh_busy (503) rather than a dead credential. The update is conditioned on the lock still being held, so a late refresh cannot resurrect a removed or reconnected row.
  • Disconnect is a DELETE. The row goes, then the Keychain is cleared.

The function short-circuits when the stored access token has more than sixty seconds left, returning it without touching Whoop, so a restore or a refresh check costs one database read.

Token lifecycle on the device

WhoopTokens.isExpired treats a token as expired sixty seconds early, and WhoopSync.sync refreshes proactively before fetching rather than reacting to a 401 mid-sync. Only a refused refresh clears the credential. A 401 from a collection endpoint throws accessDenied and keeps the tokens: it usually means the grant predates a scope the app now needs, and the fix is reconnect, which the message says in those words. aCollectionRejectionKeepsTheConnection and aRejectedRefreshDoesClearTheConnection pin the two branches.

Wire format

Whoop's timestamps carry fractional seconds, which Foundation's stock ISO 8601 strategy rejects, so WhoopClient.decoder tries fractional first then plain. Pages take start, end and limit=25 (Whoop's maximum) and follow next_token up to a cap of 20 pages, logging when the cap truncates. Records with a score_state other than SCORED are archived but not derived.

The DTO to sample mapping lives exactly once, as a computed sample property on each DTO, because the live sync and rederive() once drifted apart. Three widenings landed on 26 August and all three are in that one mapping: 

// LifeOSKit/Sources/Integrations/WhoopClient.swift
// An empty object (every member nil) means Whoop reported no zone
// data at all, not that every zone measured zero: `nil` here, not
// `[0, 0, 0, 0, 0, 0]`, which would claim a reading that was never taken.
zoneMinutes: score?.zone_durations.flatMap { z -> [Int]? in
    let raw = [z.zone_zero_milli, z.zone_one_milli, z.zone_two_milli,
               z.zone_three_milli, z.zone_four_milli, z.zone_five_milli]
    guard raw.contains(where: { $0 != nil }) else { return nil }
    return raw.map { WhoopSleepMath.minutes(fromMilliseconds: $0) ?? 0 }
}
  • Zone durations. Six int64 milliseconds per workout, stored as six columns on WorkoutRecord. They feed the live effort model in Chapter 8 and the coach's digest. An empty object decodes to nil, not six zeros; anEmptyZoneDurationsObjectDecodesToNil pins it.
  • Sleep need components. Baseline, need from debt, need from strain and need from a recent nap, the last one negative by definition and preserved with its sign.
  • The calibrating flag. user_calibrating lands on DailyMetrics.whoopRecoveryIsCalibrating, optional so an existing store migrates. A recovery produced during calibration is not a score that supports a comparison, and presenting it unqualified is the same class of error as a false zero.

Archive first, derive second

WhoopSync.sync() fetches all five collections for a rolling fourteen days, splits every page into one payload per record with WhoopRawSplit (recovery is keyed by its cycle_id because it carries no id of its own), stores them in WhoopRawRecord under (kind, externalID) in one batched save, and only then derives. There is no cursor: idempotency comes from upserts, so re-syncing is always safe. WhoopDerivation.rederive() rebuilds every derived row from the archive with no network call. The body measurement carries no date, so its archive row uses receivedAt and a stable external id of self.

Derivation attributes sleep to the morning it ends, excludes naps from the day roll-up while still storing them as SleepRecords, converts kilojoules to kilocalories with the exact divisor 4.184, and never lets a nil field overwrite a stored value. What changed is that the columns other sources also write (resting HR, HRV, SpO2, respiratory rate, sleep minutes, exercise minutes, weight) now go through the arbiter instead of being assigned directly. The Whoop-only columns (recovery, strain, sleep performance) are still written directly, and whoopOnlyColumnsAreWrittenDirectly pins that distinction.

Sync triggers

Revision D had three manual triggers. There is now an automatic one: syncIfStale() runs on launch and on every return to the foreground, gated by SyncStalenessPolicy (19.14). It is silent by design because the screens already show correct, if stale, local data; only a dead credential surfaces. The nightly server-side job and the webhook receiver remain unbuilt.

Auto-pairing the strap's broadcast

A Whoop 4.0 can broadcast heart rate over Bluetooth. WhoopAutoPair.choice(among:) decides whether to connect without asking: only a device whose name contains "whoop", and only when there is exactly one. Another person's strap in a gym is not a reading this person owns. The live sensor that consumes it is in Chapter 8.

Tests

WhoopTests (29), WhoopWireFormatTests (28, on payloads captured from a live v2 response, so a decode failure means the API moved), WhoopPaginationTests (16), WhoopTokenTests, WhoopArbitrationTests (5) and WhoopArchiveTests in PersistenceTests. Workout is the one collection with no captured fixture; its tests use a hand-built payload.

19.3Fitbit

The second wearable, added 27 August. It reads nine range collections through an Edge Function and merges by rank. The interesting part is what it deliberately does not do: the phone never holds a Fitbit token.

Why the tokens stay on the server

Fitbit rotates its refresh token on every use and the old one stops working. Two devices sharing one credential would sign each other out on every sync. So exactly one writer may hold it, and that writer is a row in fitbit_connections. FitbitAuthStoring has no token methods at all; it holds only the pending PKCE attempts, in the Keychain, scoped to the signed-in account so a second account cannot complete the first one's authorisation. 

// LifeOSKit/Sources/Integrations/FitbitAuthStore.swift
/// Deliberately has no token methods.
///
/// This is the whole difference from `WhoopTokenStoring`, and it is not an
/// oversight: Fitbit rotates its refresh token on every use, so exactly one
/// writer may hold it, and that writer is a row in the database.
public protocol FitbitAuthStoring: Sendable {
    func pendingAuths() -> [FitbitPendingAuth]
    func savePending(_ pending: FitbitPendingAuth) throws
    func clearPending()
}

OAuth

Fitbit permits a custom scheme for a native app, so the redirect is lifeos://fitbit-callback with no bridge function. FitbitOAuth.session builds the authorize URL with PKCE and sends the ten scopes as one space-separated parameter. Repeating the parameter makes Fitbit issue a narrower grant without saying so, and the first sign of it is a 403 much later. The scope list is pinned on both sides: FitbitOAuth.defaultScopes in Swift and FITBIT_SCOPES in _shared/fitbit.ts, each with its own test, and the Deno one checks that no scope the app does not read is requested (no location, no social, no ECG).

fitbit-token exchanges the code with FITBIT_CLIENT_SECRET, upserts the pair on user_id, and returns only {connected, fitbit_user_id, scopes}. No token in the response is the whole point.

The sync and its lease

FitbitSync.sync(days:token:) posts {days} to fitbit-sync with the Supabase access token. The function reads the connection through read_fitbit_connection (a security-definer RPC, because the table has RLS enabled and zero policies), refreshes if the access token is within sixty seconds of expiry, and pulls the nine collections sequentially.

Refresh runs under a lease. claim_fitbit_refresh sets refresh_lease_until thirty seconds ahead only if no lease is live, and returns the row; a second sync on another device gets nothing back and the function answers retry: true, which the app reads as "come back shortly" rather than a fault. aRefreshLockDoesNotBecomeAnEmptySuccessfulSync pins that an empty retry response throws retryLater instead of reporting zero days written. 

// supabase/functions/fitbit-sync/index.ts
/// Stop while there is still headroom rather than at zero. A sync that spends
/// the user's last request leaves nothing for the retry, and Fitbit's quota
/// resets only at the top of the hour.
const QUOTA_FLOOR = 10;

// Sequential, not Promise.all: the quota headroom arrives in each response,
// and it can only stop the loop if the loop is still running.
for (const collection of COLLECTIONS) {
  if (stoppedForQuota) { failures[collection.key] = "rate_limited"; continue; }
  ...
  const remaining = quotaRemaining(response.headers);
  if (remaining !== null && remaining <= QUOTA_FLOOR) stoppedForQuota = true;

Fitbit allows 150 requests an hour. Range collections cost one request for up to 30, 100 or 365 days depending on the endpoint, which is why per-date collections (the daily activity summary, nutrition) are absent: they cost a request per day. Each collection's cap is declared in both FitbitCollection.maximumRangeDays and the function's COLLECTIONS table, and exceeding it is a 400 that names nothing useful.

Wire format and derivation

FitbitWireFormat.swift declares every numeric field optional. Fitbit omits what a device did not record, and a non-optional field turns one missing number into a whole failed range. SpO2 arrives as a bare array rather than an envelope. Resting heart rate is under a key called activities-heart. Skin temperature is a nightly variation from baseline, not an absolute, and is stored as wristTemperatureCelsius without pretending to be a body temperature. VO2 max is a string that may be a range like "40-44"; the derivation takes the midpoint.

FitbitDerivation is split in two: days(from:) is pure and turns payloads into [FitbitDay], and derive writes them through the arbiter with .fitbit as the source. Dates are parsed with a POSIX locale in the user's own time zone, because an ISO parser treats yyyy-MM-dd as UTC midnight and shifts every night by a day for anyone west of Greenwich. Fitbit's "light" sleep is filed as Apple's "core", the same stage under two vendors' names, so the sleep panel's total adds up.

The sync archives the raw response before deriving, under kinds prefixed fitbit-, using WhoopArchive because that type is already a generic raw-record store and only its name is Whoop-specific. The order of the error checks after the write is deliberate: a declined scope must not discard the six collections that arrived intact, so partial(failed:) is thrown after the days are written.

19.4The arbiter: who wins a column

Revision D's rule was "Whoop writes its columns, HealthKit fills the gaps", implemented as a boolean called fillGapsOnly. That worked with exactly two writers. A second strap broke it: fillGapsOnly could not tell a Whoop value from a typed one, and the question "should Fitbit replace this HRV" has a different answer depending on whether Whoop, the phone or the person wrote it. So provenance is now recorded per metric per day, and the merge is a rank. 

// LifeOSKit/Sources/Integrations/MetricSource.swift
public enum MetricSource: String, Sendable, CaseIterable, Equatable {
    case manual, whoop, fitbit, appleHealth
}

public struct SourceRanking: Sendable, Equatable {
    public let primaryWearable: MetricSource   // .whoop unless the user chose Fitbit

    /// 4 typed, 3 the authority, 2 a secondary reading, 1 a fallback, 0 unknown.
    public func rank(_ source: MetricSource?, for metric: HealthMetric) -> Int {
        guard let source else { return 0 }
        switch source {
        case .manual:
            return 4
        case .appleHealth:
            return metric.healthIsAuthoritative ? 3 : 1
        case .whoop, .fitbit:
            guard metric.claimedByWearable else { return 2 }
            return source == primaryWearable ? 3 : 2
        }
    }
}

The resolve function is eight lines and pure. A missing incoming reading never changes anything (a source having no reading is not evidence of zero). An empty column takes whatever arrives. Otherwise the incoming source must rank greater than or equal to the holder: equal rank means the same source syncing again, which must be allowed to correct itself, and that is what lets an afternoon Health sync raise the morning's step count.

The one subtle case is a value written before provenance existed. MetricSource.legacy(for:) reads an unattributed value as rank 0 for almost every metric, so the first sync after upgrade re-attributes it. Weight and water are the exception: an unattributed typed metric is read as .manual, because treating it as unknown would let the next Health sync silently replace a figure the person typed. That is the one path that destroys data a person entered by hand, and anUnattributedTypedValueIsTreatedAsTyped exists to keep it closed.

Why the vocabulary and the rule live apart from the sources MetricArbiter, MetricSource and HealthMetric import nothing from HealthKit, Whoop or SwiftData. Every branch is exercised in MetricArbiterTests without a device, a prompt, a network or a store. Each sync (HealthApply, WhoopDerivation.merged, FitbitDerivation.merged) is a loop around this one call, and WhoopArbitrationTests and HealthApplyTests then check the wiring into real columns.

19.5Plaid

Bank accounts and transactions, through four Edge Functions and a device-side cursor. Chapter 11 owns the feature; this section is the integration contract.

  • Secret on the server. Every Plaid endpoint requires client_id and secret on the request, so the device never calls Plaid. PlaidClient calls plaid-link-token, plaid-exchange, plaid-sync and plaid-disconnect, all resolving the user from the bearer token.
  • Access tokens never reach the phone. plaid_items holds them behind RLS with no policies, and plaid-exchange returns only item_id and the institution name.
  • The cursor lives on the device. PlaidItemStore keeps a /transactions/sync cursor per item, serialised with an NSLock, and only advances it after the rows are stored. The function pulls at most three pages per call and returns has_more, so a years-long initial pull is several calls.
  • OAuth banks. Institutions like Chase hand the browser to the bank, and the bank redirects to https://almanac.shivvyas.com/plaid-oauth, a universal link that iOS routes back into the app. Chapter 20 covers the two-file site behind it.
  • Failure kinds. classifyPlaidFailure maps to three kinds: item_login_required (reconnect banner, not a spinner), rate_limited (retry later), upstream_failure (opaque, because Plaid's error bodies echo request parameters). Balance failures travel separately from transaction failures because /transactions/sync serves cached data and succeeds with an expired login, while /accounts/balance/get is the call that actually throws it.

19.6EventKit and the calendar

The calendar is read and written through a protocol so that a second provider (Google, planned) slots in without the cache or the assistant changing. Chapter 6 covers the screens and Chapter 15 the tools; this section covers the source. 

// LifeOSKit/Sources/Integrations/CalendarSource.swift
public protocol CalendarSource: Sendable {
    var source: CalendarEventSource { get }
    var isAuthorized: Bool { get async }
    func requestAccess() async throws -> Bool
    func events(from: Date, to: Date) async throws -> [CalendarEventSnapshot]
    func create(_ draft: CalendarEventDraft) async throws -> CalendarEventSnapshot
    func update(sourceID: String, with draft: CalendarEventDraft) async throws -> CalendarEventSnapshot
    func delete(sourceID: String) async throws
}

EventKitSource is an actor because EKEventStore is not Sendable. Three details matter:

  • Permission is per account, not per phone. iOS grants calendar access to the app. AccountDeviceAccess.allowsCalendar requires both the system grant and a flag in the account's own defaults suite, so a second person signing in does not inherit the first person's calendar. The source also captures the account id at construction and refuses to answer if the current account has changed since.
  • Recurring occurrences get a qualified id. Every occurrence of a series shares one eventIdentifier, so the natural key is qualified with the occurrence start (id#timestamp). A qualified id never resolves through event(withIdentifier:), which makes a write against an occurrence fail with unknownEvent instead of silently editing the wrong one; the tool layer refuses recurring writes with a real explanation before that can happen.
  • The prompt is never at launch. requestAccess() is called from the agenda card's empty state, when the person has just asked for the thing that needs it.

CalendarSync pulls every authorised source over a window of 30 days back and 90 forward, merges with CalendarMerge (EventKit wins a collision on lowercased title plus start date, which is what stops every event appearing twice when a Google account is also added under iOS Settings), and hands the result to CalendarStore.apply. A source that throws is skipped: partial data beats an empty screen, and sync is ambient, never a user-visible request. Writes route to the source that owns the event and then re-sync, so the cache reflects what the provider actually stored rather than the local draft.

CalendarSyncTests, CalendarMergeTests and EventKitSourceIDTests cover the merge, the prune-only-what-you-fetched rule and the occurrence key.

Both channels are six-digit codes. The email template puts {{ .Token }} on the page instead of the stock magic link, which cannot be typed into an app. Phone goes through Twilio Verify rather than GoTrue's own SMS provider because the function can classify Twilio's failure codes into sentences a person can act on, and rate-limit by phone, prefix and IP (Chapter 20).

AuthError.fromHTTP is the one place server codes become copy. A {"error": "sms_opted_out"} body becomes "That number opted out of our texts. Text START to our number to opt back in". A bare 502 with no message is channel-neutral, because email is now the default and the old copy assumed SMS. AuthErrorMappingTests pins every mapping.

The refresh URL bug

// LifeOSKit/Sources/Integrations/SupabaseAuth.swift
/// Deliberately not `appendingPathComponent` on the whole path.  That
/// treats what it is given as a single component and percent-encodes the
/// `?` into `%3F`, which sent the one call that carries a query to
/// POST /auth/v1/token%3Fgrant_type=refresh_token.  GoTrue answers 404 to
/// that, so a stored session could never be renewed.
private func authURL(_ path: String) throws -> URL {
    let parts = path.split(separator: "?", maxSplits: 1, omittingEmptySubsequences: false)
    var components = URLComponents(
        url: baseURL.appendingPathComponent("auth/v1/\(parts[0])"),
        resolvingAgainstBaseURL: false
    )
    if parts.count > 1 { components?.query = String(parts[1]) }
    guard let url = components?.url else { throw AuthError.transport }
    return url
}

This is worth reading because of how it presented: sign-in always worked, and an hour later every authenticated call began failing 401. AuthRefreshURLTests now pins the query string.

Session lifecycle: three pieces

  • SessionRefresher.restore() runs on launch and on every foreground. It returns signedOut, active or rejected, and only a definitive refusal (400, 401, 403, 422) clears the store. Offline, a 5xx and a 429 keep the session. A refreshed session carries forward the user id, phone, email and refresh token from the one it replaces, because refresh responses may be sparse. Two guards protect against races: a sign-out during the refresh cannot be resurrected (the store's refresh token is compared before saving), and a refresh cannot change the account's identity.
  • SessionKeepAlive answers the case the refresher cannot: a person who keeps the app open for over an hour. It schedules a renewal 45 seconds before expiry, inside isExpired's own minute of slack so the wake finds a session the refresher will actually renew, with a five-second floor so a clock that jumps backwards cannot become a spin against the auth endpoint.
  • AccountStore holds the roster of accounts that have signed in on this device (ids and labels in defaults) and one Keychain session per user id. Signing in as a second person no longer overwrites the first. currentScope returns nil rather than the first account it can find, so a current id naming a signed-out account never opens somebody else's store. The pre-accounts session slot is adopted once and cleared on sign out, because a credential that can restore an account is that account's session whatever slot it sits in. Chapter 4 covers what the shell does with this.

KeychainAuthSessionStore() defaults its account to whichever id is current. This matters more than it looks: every network client in the app builds one to get a token, and before accounts there was one slot, so after a switch they would all have kept presenting the previous person's token.

REST

SupabaseREST.upsert sends Prefer: resolution=merge-duplicates so a push that lost its response and retried does not create a second copy of every row. fetch(table:since:) orders by updated_at ascending and uses gte on the cursor, inclusive, because a row written in the same millisecond as the previous page's last row must not be skipped; re-reading one row is free, missing one is silent data loss. Both take and return bytes rather than dictionaries because a [String: Any] is not Sendable and the call crosses an isolation boundary. delete is deliberately narrow (one column, one value): the one thing the app deletes over REST is its own push registration.

SessionRefreshTests (twelve, serialised, over a stub URLProtocol), SessionKeepAliveTests, AccountStoreTests (seventeen) and AuthSessionProfileTests pin the above.

19.8Apple Foundation Models

The on-device tier. Revision D's correction still stands: on iOS 26 there is no public LanguageModel protocol, so the app keeps two thin protocols of its own, Engine for one-shot tasks and ChatEngine for conversations, and the remote engines conform to the same ones. When iOS 27 ships Apple's seam, the remote engines conform to it and the protocols are deleted without a caller changing. 

// LifeOSKit/Sources/Insights/ModelAvailability.swift
public enum ModelAvailability: Sendable, Equatable {
    case available
    case unavailablePermanently
    case unavailableForNow

    public static func from(_ availability: SystemLanguageModel.Availability) -> ModelAvailability {
        switch availability {
        case .available: return .available
        case .unavailable(let reason):
            switch reason {
            case .deviceNotEligible: return .unavailablePermanently
            case .appleIntelligenceNotEnabled, .modelNotReady: return .unavailableForNow
            @unknown default: return .unavailableForNow
            }
        }
    }
}

Apple's availability is collapsed to the one distinction the router acts on: can this answer still change. Hardware eligibility never changes while the process is alive, so it is the only answer the router may remember. Everything else is re-read every time, and an unknown reason is assumed transient because re-checking costs a property read while wrongly caching "never" would disable the free tier for the life of the process.

OnDeviceEngine creates a LanguageModelSession per call. LanguageModelSession is a non-Sendable final class and Engine is Sendable, and a one-shot task has no conversation to remember. OnDeviceChatEngine also creates a session per turn, because the conversation's memory lives in the thread the app renders, not in the session; it flattens the thread into one prompt, binds each CoachTool as a SessionTool, and streams snapshots through onPartial, cleaning markdown on the way past so the screen never shows a raw asterisk for a second. Chapter 14 covers the router that chooses between this and the cloud.

The floor is iOS 26 because FoundationModels does not exist before it. There is no older-OS cohort that always escalates; unavailability is only the runtime reasons above.

19.9ElevenLabs: hearing and speaking

LIFO's voice loop uses ElevenLabs twice, both from the app target with the key from Secrets.xcconfig under ELEVENLABS_API_KEY. This is the one vendor called from the device with a real key. The key is passed into each call, never stored on a type, and never logged. It is a personal key for a single-user build; the cost chapter (Chapter 24) records what it spends.

  • Scribe (speech to text). ElevenLabsSpeechClient.transcribe posts a WAV clip as multipart form data to v1/speech-to-text with model_id: scribe_v2. A clip under 1,024 bytes is rejected before upload as too short to hear.
  • Text to speech. ElevenLabsVoiceClient.speech(for:voice:apiKey:) posts to v1/text-to-speech/{voiceID} with eleven_flash_v2_5, the low-latency model, because a coach that speaks three seconds after the text has been read is repeating, not answering. Speech is billed per character, so the text is capped at 1,200 characters (roughly ninety seconds) and truncated on a sentence boundary, because a voice stopping mid-number sounds like a fault.
  • Three voices. AssistantVoice names Rachel, Adam and Sarah by ElevenLabs' public stock voice ids, which are stable across accounts and need no provisioning. Three, deliberately: a list of dozens is a settings screen nobody finishes. Spoken replies are off until asked for, because a coach that starts talking in a room the phone knows nothing about is a worse default than silence.

VoicePlayer holds the AVAudioPlayer because it stops the moment it is deallocated, sets the session to .playback with .spokenAudio and .duckOthers, meters the level at 30 Hz for the orb in Chapter 14, and hands the session back with notifyOthersOnDeactivation so a podcast returns to full volume. A delayed completion from an old player is checked by identity so it cannot stop a newer reply.

19.10Apple Speech and the microphone

SpeechListener in Features/Coach/Model is the microphone. One tap opens it and no second tap is needed: it watches the level, decides when the sentence is over, and transcribes what it recorded. It is nonisolated because the AVAudioEngine tap runs on the I/O thread, and every AVAudioSession activation runs on a private serial queue because setActive on the main thread can stall the UI.

The layering is: ElevenLabs Scribe is primary, Apple Speech is the backup when there is no key, the upload fails, or the clip is too short. But Apple's recogniser runs alongside Scribe even when Scribe will do the final transcript, for one reason: Scribe transcribes a clip that is only uploaded once the turn is over, so it cannot put a word on screen while someone is still talking. Apple's partials do exactly that and nothing else.

The decision "is the sentence over" lives in Insights as SpeechEndpointer, a pure state machine fed one RMS reading per audio buffer. Its clock is the audio itself, buffer frames over the sample rate, rather than the wall clock: a thread busy elsewhere would otherwise put time into a silence the speaker never left. SpeechCapturePlan decides, from whether a Scribe key exists and whether Apple's recogniser is authorised and available, whether the app can listen at all. Both are tested in SpeechEndpointerTests and SpeechCapturePlanTests against a made-up room. onEndOfSpeech fires the moment the endpointer decides, before any transcript exists, because the second or two spent uploading otherwise looks like the mic ignoring you.

19.11YouTube embeds

The workout library (Chapter 10) plays curated YouTube videos. Two pieces touch the vendor.

WorkoutCatalogClient is a read-only PostgREST call against workout_videos, ordered by updated_at, with the user's bearer token. The table grants select to authenticated users and nothing else. The catalog itself is generated by scripts/catalog/verify.ts from catalog.json, which checks each id against YouTube's oEmbed endpoint before it is allowed into the seed migration.

YouTubePlayerView wraps a WKWebView owned by the screen, not the view, so rotating the phone or entering full screen does not give SwiftUI a new view identity and restart the video. There is no JavaScript bridge: the person taps YouTube's own play button and the recorder times the session. The load itself had to be learned by elimination: 

// LIfeOS/Features/Workouts/View/YouTubePlayerView.swift
// Loading the embed URL straight into the web view answers with
// "Video player configuration error, Error 153": the embed needs a
// page with an origin to sit in. So the iframe is wrapped in a
// page of our own, based at the host the embed's `origin` names,
// which is what youtube-ios-player-helper does too.

The QA report records the numbers: zero of six seed videos rendered on the first pass (error 152), and six of six after the page's baseURL was matched to the embed's origin parameter and both were pointed at youtube-nocookie.com. A video whose owner has barred embedding shows YouTube's own "Watch on YouTube" card, which no delegate can see without the bridge this slice leaves out; the "Open in YouTube" link under the player is the way out.

19.12APNs and the morning nudge

The proactive half of LIFO sends one notification at eight in the morning local time, when a rule finds something worth saying. The integration has a device half and a server half.

Device. PushService asks once for notification permission and registers with APNs. PushTokenClient.register upserts {token, user_id, platform, timezone} into device_tokens, where the token is the primary key. That key is a correctness requirement: several accounts can share one device, and a token left registered under the account that signed out would push one person's sleep data onto a phone showing somebody else's name. Registering under a second account replaces the row in one upsert, and sign-out deletes it. The time zone rides along because the send hour is local, and a row with no usable zone never sends.

NudgePayload(userInfo:) reads the tapped notification. It carries the sentence, the trigger name and the day, and deliberately not the numbers: a phone that has been off for days would otherwise open on figures two days stale, so the tap-through re-evaluates locally.

Server. _shared/apns.ts signs one ES256 provider token from the .p8 in the function environment and reuses it for fifty minutes, because Apple throttles senders that mint a token per push. Every send carries apns-collapse-id: lifo-nudge so a phone that has been off for three days gets today's nudge and not three, and apns-expiration twelve hours out so a morning observation does not arrive after midnight. A 410, or a 400 with BadDeviceToken (the one that actually appears after a reinstall), deletes the row so the job does not push at a dead token forever. The reason is logged; the token never is, because a device token in a log line is a way to push at somebody from outside the function. The triggers, cooldown and cron are in Chapter 20.

19.13Screen Time: still cut

Unchanged from Revision D and recorded so it is not re-attempted. Apple's DeviceActivity API lets a report extension render usage figures and lets nothing read them: not the host app, not SwiftData, not the coach. Since the product thesis is the join across domains, a signal that provably cannot enter the join has no home here. The MacBook has no API at any privilege level.

19.14What the integrations share

The staleness rule

// LifeOSKit/Sources/Integrations/SyncStalenessPolicy.swift
public static func shouldSync(lastSync: Date?, now: Date = .now,
                              calendar: Calendar = .current,
                              staleAfter: TimeInterval = 3_600) -> Bool {
    guard let lastSync else { return true }
    guard lastSync <= now else { return true }          // clock moved backwards
    if lastSync < calendar.startOfDay(for: now) { return true }
    return now.timeIntervalSince(lastSync) > staleAfter
}

Two clocks, not one. Staleness handles the common case: data older than an hour is worth refreshing on foreground. The day boundary handles the one that matters most: the first open of the morning must pull the night's sleep, and a sync from 23:50 is only minutes old while still knowing nothing about the night. Whoop, Fitbit and Health all consult it, which is why the three connection cards refresh themselves at the same moments.

Per-account credentials

Every Keychain store (KeychainAuthSessionStore, KeychainWhoopTokenStore, KeychainFitbitAuthStore) defaults its account attribute to the id under accounts.current. Every per-account preference (sync cursors, "seen the tour", calendar consent) lives in UserDefaults.currentAccount, a suite named for the account. Device preferences (appearance, the assistant's voice, which engine answers) stay in standard on purpose: they belong to the phone, not to whoever is signed in.

The secret rule

Whoop, Fitbit, Plaid, Twilio and OpenAI each require a secret, and each has an Edge Function that holds it. The device holds public identifiers (client ids, the anon key), one personal ElevenLabs key, and its own tokens. 23.2 tabulates the tiers.

Read in this order

Check yourself

  • Why does a Fitbit HRV reading not overwrite a Whoop one, while a Health step count does overwrite yesterday's Health step count? HRV is claimedByWearable, so the secondary strap ranks 2 against the primary's 3. Steps are healthIsAuthoritative, so Health ranks 3 against its own 3, and equal rank is allowed to correct itself.
  • What would happen if you deleted MetricSource.legacy(for:)? An unattributed typed weight would rank 0 and the next Health sync would replace it. That is the one path that destroys hand-entered data.
  • Why does Whoop keep a token in the Keychain but Fitbit does not? Fitbit's refresh token is single use and rotates, so only one writer may hold it; the server row is that writer. Whoop's is held both places, with a server-side lock around refresh.
  • Which HTTP statuses sign a user out, and why not 429? 400, 401, 403 and 422 are the server refusing the credential. 429 and 5xx are temporary by definition, and opening the app on a plane must not log you out.
  • Why is HealthKit's percent scaled by 100 and what bug did it fix? HKUnit.percent() yields a 0 to 1 fraction; the app stores percentages as percentages, and Health SpO2 was rendering as 1.0.
  • Why does the Whoop bridge send lifeos:// and not almanac://? Every installed build knows lifeos; pointing at almanac stranded builds that predate the rename.
