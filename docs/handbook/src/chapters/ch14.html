Chapter fourteen

14LIFO, the coach

LIFO is the one screen in Almanac that talks back. It reads a fortnight of your own numbers, your month's money and your nine sector scores, answers in cards rather than paragraphs, can listen and speak, remembers the conversation it is in, and, once a day at most, speaks first. This chapter is how all of that is built, where the words go, and what it costs.

14.1Intent

Working backwards

Ask LIFO how you slept this week and it answers with a table of your actual nights, on the cloud when the cloud can answer and on the phone when it cannot. Say it out loud and it stops listening when you stop talking, reads one warm sentence back while the cards are still arriving, and never reads a table aloud. Ask a follow-up and it knows what it said. Some mornings it sends a line first: three short nights against your own baseline, a streak that today would break, a strong week worth naming. Tap it and the conversation opens on that sentence.

Which model answers?

The cloud first, the device second. The cloud tier is OpenAI's gpt-5-mini behind the lifo-agent Edge Function; the device tier is Apple's Foundation Models. It used to be the other way round on the grounds that the free engine should be tried first, and the result was a worse common answer with the better one appearing only when the weaker model failed outright. Quality picks the tier; a metered daily cap on the server is what keeps that affordable.

What leaves the phone?

On a cloud turn, one rendered text block: a fortnight of derived daily numbers, the month's money summary with up to thirty recent transactions, the sector scores, and the last twenty turns of the conversation. Never the raw Whoop series (HRV, SpO2, skin temperature, respiratory rate), which exist only in the on-device render. Every answer carries a disclosure you can open that shows the verbatim text that was sent and which tier answered.

How does it avoid inventing numbers?

Two ways. The prompt is the data: the model is told to cite only figures that appear in the text it was given, and the render omits a missing field rather than writing zero. The reply is then parsed by CoachResponse into paragraphs, tables and lists, and a table cell displays exactly the string the answer supplied; nothing is recalculated on the way to the screen.

Why cards instead of a paragraph?

A paragraph about six metrics is six numbers hidden in prose. The coach is instructed with a small presentation grammar (a marker string, then rules: short paragraph for a simple question, a two-column table for metrics, up to three bullets for actions, at most three sections) and the screen renders those shapes natively. A short answer stays short; nothing is forced into a dashboard.

What the coach deliberately does not do: it has no tools. The calendar assistant in Chapter 15 carries six and runs a tool loop; LIFO carries none, which is exactly what lets its whole reply be streamed. It does not diagnose, it does not pick investments, and it declines requests that are not about coaching this person over their own data, because the guardrail that says so lives on the server where a client cannot strip it.

Why the brain lives in the package and the mouth in the feature

Everything that decides is in Insights: which tier, what the model may see, when a sentence ends, how a reply splits between voice and screen. Everything that touches hardware is in Features/Coach: the microphone, the audio session, SceneKit, the network calls to ElevenLabs. The line is drawn so that every decision is a value type with a test, and the feature folder is left holding only the parts that need a device to run.

14.3Model

A task names a floor, not a model

// LifeOSKit/Sources/Insights/CoachTask.swift
public enum Tier: Sendable, Equatable {
    case onDevice
    case cloud(Role)
    public enum Role: String, Sendable, Codable { case reasoning, vision }
}

public protocol CoachTask: Sendable {
    associatedtype Output: Generable & Decodable
    associatedtype Context: Sendable
    var floor: Tier { get }
    var remoteName: String? { get }
    var instructions: String { get }
    func prompt(_ context: Context, for audience: MetricsDigest.Audience) -> String
}

Three things in this declaration carry most of the design. Output is both Generable and Decodable, so one struct yields a schema for Apple's model and decodes the JSON that comes back from the cloud; that constraint is what lets RemoteEngine.run stay generic. remoteName is the server-side name of the task, or nil for one that never leaves the phone: the model behind a name lives in the Edge Function, so changing which model answers is a deploy, not an App Store release. And prompt takes an audience, which is the whole privacy mechanism in one parameter: a remote engine can only ever ask for the .offDevice render.

Three tasks exist. AnswerTask is named answer on the server and takes a ContextBundle. BriefTask and SectorNoteTask are on-device only; the sector note is what the monthly close in Chapter 13 asks for, and the brief has a cache but no screen yet.

A chat turn is a thread, not a prompt

// LifeOSKit/Sources/Insights/Chat/ChatEngine.swift
public struct ChatTurnMessage: Sendable, Equatable {
    public enum Role: String, Sendable { case user, assistant }
    public let role: Role
    public let text: String
}

public struct ChatInstructions: Sendable, Equatable {
    public let onDevice: String   // may name data that must not leave the phone
    public let cloud: String      // this one travels
}

public protocol ChatEngine: Sendable {
    func reply(
        to thread: [ChatTurnMessage],
        instructions: String,
        tools: [any CoachTool],
        invoker: ToolInvoker,
        onPartial: @escaping @Sendable (String) -> Void
    ) async throws -> AssistantTurn.Reply
}

ChatInstructions is two strings rather than one because the tiers are not owed the same render. A single string would have to choose, and whichever it chose would be wrong on the other tier. onPartial is handed the answer so far, cumulative, not the piece that just arrived. Foundation Models yields snapshots and the cloud yields deltas, and a screen that assigns the whole text it is given cannot lose a fragment the way one that appends can.

What the screen holds

// LIfeOS/Features/Coach/ViewModel/CoachViewModel.swift
struct LifoTurn: Identifiable, Equatable {
    let id: UUID
    let question: String      // empty when LIFO spoke first
    let answer: String
    let sent: SentContext?    // nil for a seeded opening line
}

struct SentContext: Equatable {
    let text: String          // the verbatim render, not a description of it
    let tier: AssistantTurn.Tier
    var headline: String {
        let place = tier == .cloud ? "the cloud" : "this device"
        let facts = text.split(separator: "\n")
            .filter { !$0.trimmingCharacters(in: .whitespaces).isEmpty }.count
        return "\(facts) lines of your data, answered on \(place)"
    }
}

SentContext.text is the thing itself. A summary of what was sent is a second thing that can be wrong; the verbatim string cannot. The headline counts lines rather than characters because the render is one fact per line and "1,847 characters" is a number nobody has a feel for.

The conversation on disk

ChatMessage is a SwiftData model with a conversation id, a role stored as a raw string (so the enum can gain cases without a migration), the text, tool summaries, and an optional JSON blob of calendar event ids. ChatStore.recent(conversationID:limit:) returns the last twenty messages oldest first, which is the order both a transcript and a prompt want. The store is local only; chat history never leaves the device. The coach and the calendar assistant write into the same store under different conversation ids, each kept in the account's own UserDefaults suite so two people sharing a phone cannot resume into each other's transcript.

CoachViewModel is @MainActor @Observable and owns one session. Its state is a phase (idle, listening, thinking, answered), the live transcript while listening, the answer as it streams, a status line, a history of turns, and the question in flight.

pendingQuestion exists because a turn used to be appended to history only once there was an answer to append it with, which meant the one moment you most want to see what you said, while it is being thought about, was the one moment nothing showed it. It is pinned before any store read in send, so whatever the rest of the method does or fails to do, the question is on screen from the moment it was asked.

The send method does the following, in order: stops any speech in or out, pins the question, mints a new turnID, decides once whether the answer will be held for the voice, builds the context bundle from the last fourteen days of MetricsStore rows plus whatever bundleExtras returns, appends the question to ChatStore, reads the thread back, renders one instruction string per audience, and hands everything to AssistantTurn.run. The bundleExtras closure is set by RootView and pulls the money snapshot and the sector cards out of the view models that own them, so the coach never holds screens it does not render.

Every failure is mapped to a sentence the screen can act on. A refusal shows the model's own words. A spent budget says "That is today's thinking budget used up. It resets tomorrow." An on-device context overflow says the question covered too much at once, not that the network is down. A missing session says to sign in again, which used to read as a connectivity problem and sent people to check their wifi. Anything else is logged with the real error and, depending on whether a session exists, either asks for a retry or offers the Apple Intelligence setting through needsAppleIntelligence. On every failure the half-streamed answer is cleared: a fragment under a failure line reads as LIFO contradicting itself.

A router that is built and not used CoachViewModel still constructs a CoachRouter with a RemoteEngine, but send routes through AssistantTurn.run and never calls it. The router is the one-shot path and its live caller today is the monthly close's sector note. The unused property is a leftover from before the conversational core landed, and it is safe to delete.

14.5View

LifoCoachScreen is one view with two presentations, chosen by CoachScreenStyle: .text, a cobalt gradient fading into ink with a composer along the bottom, and .voice, a sage gradient fading into forest black with the orb in the middle and a microphone button below. Switching never recreates the model, so an answer already being generated survives the switch. The screen forces the dark scheme and caps its content at 800 points wide, which is how it reads on an iPad without becoming a wall of text.

The text screen shows an opening when the transcript is empty (a two-line headline, three suggestion cards for sleep, spending and today's focus) and the transcript otherwise. Each turn is a white bubble for the question, right-aligned and black on white because your own words are the brightest thing on the screen, then a CoachResponseView card, then a closed DisclosureGroup labelled with the sent headline and a cloud or iPhone glyph. The turn in flight draws from pendingQuestion with a "Thinking" row until the first chunk lands, and then the answer as it is written, with no cursor and no per-character animation because the text arrives fast enough that animating it would slow it down.

CoachResponseView parses the reply and renders each block: a paragraph as text with inline markdown attributes, a two-column table of up to six rows as a grid of metric cells (one column at accessibility type sizes), a wider table as a horizontally scrolling Grid with alternating row tints, a list as numbered action rows with dividers. Each block fades and lifts in a beat after the one above, with state on the block so a block already on screen is never re-animated when the text under it streams on.

The voice screen shows CoachVoiceOrb, a SceneKit sphere with a physically based emerald shell, a geometry shader that swells the surface with layered sine currents, a surface shader that paints jade bands and a faint shimmer, and an additive halo plane behind it. A CADisplayLink at 30 to 60 frames per second feeds the shader a phase and an energy uniform; energy comes from AudioEnvelope, which smooths the microphone or playback level with a fast attack and a slow release so the sphere breathes rather than twitches. Drag tilts it, tap gives it an impulse, Reduce Motion freezes it, Reduce Transparency hides the halo, and leaving the screen invalidates the display link. Under the orb sit the live transcript while listening, the pending question and streaming answer, or the latest turn with its disclosure.

14.6How a turn is answered

The router

AssistantTurn.run restates CoachRouter's rules for the chat path. With no remote engine configured, the device answers. Otherwise the tier preference is read now, not captured, because the switch in Settings can be flipped while the screen is open. onDevice means the device and nothing else. cloud means the cloud with no fallback, because someone who chose the stronger model wants to be told when it did not answer rather than quietly handed a weaker one. automatic tries the cloud and falls back to the device on any error except a refusal. 

// LifeOSKit/Sources/Insights/AssistantTurn.swift
} catch RemoteEngineError.refused(let reason) {
    throw RemoteEngineError.refused(reason)       // never re-asked of a second model
} catch {
    guard await invoker.didExecuteGatedWrite == false else { throw error }
    guard availability() == .available else { throw error }
    let retry = ToolInvoker(tools: tools, broker: broker)
    onPartial("")                                  // clear the cloud's half sentence
    return try await device.reply(
        to: thread, instructions: instructions.onDevice,
        tools: tools, invoker: retry, onPartial: onPartial
    )
}

Two guards matter. A refusal is never retried on the other tier, because a second model is not a second opinion on a refusal, it is a way around one. And a turn in which the user already confirmed a gated write is never retried, because the write has already happened and a fresh invoker would let a second model ask for the same create, raise a second card, and get a second yes from someone with no way to see that the first landed. That guard is set the moment the gate opens, not after the call returns, since a write that threw may still have reached the calendar.

The cloud engine

RemoteChatEngine.reply has two paths. With no tools, which is the coach's case, it sends one request with stream: true and reads the server's event stream line by line through ChatWire.payload(inLine:) and ChatWire.streamEvent(payload:). The text is accumulated in the engine, cleaned, and handed to onPartial whole on every frame. A refusal or a spent budget arrives as an ordinary JSON body with a status, never inside the stream, so the failure is read the same way as on the unstreamed path. A stream that carried no text at all throws unavailable rather than returning an empty bubble.

With tools, which is the calendar assistant's case, it runs the loop: send the thread and the function declarations, and if the reply is tool calls, run each one on the device through the shared ToolInvoker, append an assistant message carrying the calls and a tool message per result, and send again. The loop runs at most ToolInvoker.invocationLimit + 1 rounds, seven, bounded by the invoker's own cap rather than a second number of the engine's invention. A call whose arguments will not parse is still answered, with a message telling the model to explain rather than retry, because a provider left waiting on a result simply asks again and spends the remaining rounds on it. 

// LifeOSKit/Sources/Insights/Chat/ChatWire.swift
public static func request(baseURL: URL, anonKey: String, accessToken: String,
                           messages: [Message], tools: [any CoachTool],
                           context: String = "", stream: Bool = false) throws -> URLRequest {
    var request = URLRequest(url: baseURL.appendingPathComponent("functions/v1/lifo-agent"))
    request.httpMethod = "POST"
    request.setValue(anonKey, forHTTPHeaderField: "apikey")
    request.setValue("Bearer \(accessToken)", forHTTPHeaderField: "Authorization")
    var body: [String: Any] = [
        "task": "chat",
        "messages": messages.map(\.payload),
        "tools": try tools.map { try ToolSchema.function(for: $0) },
    ]
    if !context.isEmpty { body["context"] = context }
    if stream { body["stream"] = true }
    request.httpBody = try JSONSerialization.data(withJSONObject: body)
    return request
}

The user's data travels in a context field of its own, never as a system message the client wrote. The server wraps it in a system message of its own placed behind SCOPE. A client-authored system message would land after the guardrail, providers weight the later one heavily, and that is a way around the guardrail rather than a way to carry data; the server refuses any message whose role is not user, assistant or tool.

The device engine

OnDeviceChatEngine creates a LanguageModelSession per turn, binds any tools through SessionTool, flattens the thread into one prompt with User: and Assistant: lines, and streams the response. Foundation Models yields snapshots of the whole answer so far, which is exactly the shape onPartial is defined in, so there is nothing to accumulate. The style appended is ResponseStyle.conversation unless the instructions carry the structured coach marker, in which case CoachPresentation.instruction is used instead, so the device writes cards too.

The server's side of the contract

lifo-agent is the door. It rejects anything but POST, resolves the caller from the bearer token through resolveUser (the anon key admits the app to the project; the token says which user is asking and is what gets billed), validates the body with parseRequest, reads today's lifo_usage row for the chat kind and returns 429 exhausted at 150,000 tokens, builds the OpenAI body, calls the provider once with reasoning_effort and verbosity set to low and once more without them if the provider returns 400, and either relays the stream or parses the reply. It debits what the provider billed on every path, success, refusal and parse failure alike, through the atomic lifo_debit function, because a refusal still consumed real tokens and leaving those unmetered would let a user burn unlimited budget by asking off-topic questions in a loop. The bundle in the request is used for one completion and discarded; log lines carry ids, task names, token counts and latency, never content. Chapter 20 covers the function internals; what matters here is the shape the device relies on. 

// supabase/functions/_shared/lifo.ts
const SCOPE = `You are LIFO, a personal life coach inside the LifeOS app.
You coach one person using only their own data, which arrives in the prompt:

SCOPE is first in every system prompt and always. The conversational style behind it is a verbatim copy of ResponseStyle.conversation, and both a Swift test and a Deno test pin the same prohibitions and permissions, because the copy had already drifted once at birth: it dropped the quotation-mark rule and the "if you can answer without asking, answer" clause, and the cloud model was allowed two habits the device model was not. Two prompts that are meant to agree and are written twice do not stay agreeing unless something checks.

14.7Speech in, speech out

Closing the mic when the sentence ends

SpeechEndpointer is the whole of the "stop when I stop talking" rule, as a value type with no audio types in it. The listener feeds it one RMS reading per buffer, timed by audio frames over the sample rate rather than the wall clock, so a busy thread cannot put time into a silence the speaker never left. A single fixed level cannot work: what means speech in a bedroom means silence in a café. So the room measures itself. The first 0.4 seconds learn the noise floor from the quietest frame; after that the floor learns only from non-voice frames, drops the moment the room does and climbs slowly, and is clamped to 0.004 to 0.12 so a calibration that lands on speech cannot put the bar above every later voice. 

// LifeOSKit/Sources/Insights/SpeechEndpointer.swift
public var openThreshold: Double { max(noiseFloor * 3 + 0.020, 0.055) }
public var continueThreshold: Double { max(noiseFloor * 2 + 0.012, 0.035) }

guard elapsed - lastVoiceAt > tuning.trailingSilence else { return .keepListening }
guard spokenFor >= tuning.minSpeech else {
    hasHeardSpeech = false; speechStartedAt = 0; lastVoiceAt = 0   // a blip, not a sentence
    return .keepListening
}
decided = true
return .finished

Two thresholds, because a frame has to be clearly louder than the room to begin a sentence but only a little louder to continue one; that is what keeps the soft tail of a word from reading as the end of a thought. The tuning is named rather than left as numbers in a callback: 1.5 seconds of trailing silence ends the turn, voice under 0.35 seconds is a cough, seven seconds of nothing closes the mic, and sixty seconds is the backstop for a room so loud every frame reads as voice. A verdict is latched once so buffers still in flight cannot finish the same turn twice.

Two transcribers, one sentence

ElevenLabs Scribe transcribes a clip uploaded once the turn is over, which is accurate but cannot show a word while someone is still speaking. Apple's recognizer reports partial results as they are heard. SpeechCapturePlan decides the split: with a Scribe key Apple runs in the liveTextOnly role, pinned to on-device recognition where the hardware allows so the clip does not go to a second vendor merely to draw the words, and its final result is dropped so the two transcripts cannot race. Without a key Apple is the transcriber and is never pinned, since that transcript is the sentence and accuracy outranks the preference. A recognizer failure ends the turn only when Apple owned the sentence; on the Scribe path it has cost the words under the waveform and nothing else.

SpeechListener is deliberately not on the main actor: the audio engine's tap runs on the I/O thread, and every AVAudioSession activation runs on a private serial queue because setActive on the main thread stalls the UI. The clip is always written to a temporary WAV, on both paths, so a second pass over the file is possible when the live partials came back empty. When the endpointer says the sentence is over, onEndOfSpeech fires before any transcript exists, and the screen switches to "Hearing that back" at that moment rather than claiming to listen through the whole upload. Level callbacks are throttled to one every 80 milliseconds.

Say one line first

When the reply will be spoken, the model is asked for one extra line, prefixed SAY:, before the written answer: one or two warm sentences, at most one figure, no markdown, not a reading of the details. SpokenReply parses this from partial text as well as whole text, because a stream spends most of its life half arrived, and reports isSpokenLinePending while the text so far could still turn out to begin with the prefix. 

// LifeOSKit/Sources/Insights/SpokenReply.swift
public static let prefix = "SAY:"
public let spoken: String?          // nil until the line is complete, nil when there is none
public let shown: String            // empty while the spoken line is still arriving
public let isSpokenLinePending: Bool

The view model holds the cards while the voice fetches. received(_:) parses each chunk, keeps latestShown, and the first time a spoken line is complete calls speak, which fetches audio from ElevenLabsVoiceClient using the eleven_flash_v2_5 model for latency and plays it through VoicePlayer. Whatever happens to the audio, a failure, a cancellation, or a voice switched off between asking and answering, reveal runs on the way out, because silence is acceptable and a blank screen is not. A two-second timeout reveals regardless, so a slow synthesis is a reason to hear first, not a reason to see nothing. The turnID keeps a late exit from an old reply from revealing a new one early, and spokeThisTurn keeps a line from being read once per chunk. The spoken line is for the voice only: it is not rendered, not kept in history, and not written to the store the next prompt is built from. If the model was asked for a line and did not write one, the first plain paragraph of the answer is read instead, never a table.

Speech is billed per character, so ElevenLabsVoiceClient caps the text at 1,200 characters, cut on a sentence boundary because a voice stopping in the middle of a number sounds like a fault rather than a limit. VoicePlayer holds its AVAudioPlayer because one that is deallocated stops playing, sets the session to spoken audio that ducks other apps, meters the level every 33 milliseconds for the orb, and hands the session back on stop so a podcast returns to full volume. Voice is off by default, since a coach that starts talking in a room the phone knows nothing about is a worse default than silence, and the three voices (Rachel, Adam, Sarah) are ElevenLabs stock voices with stable public ids, offered only once speech is on.

14.8LIFO speaks first

Every sentence LIFO produced before September was a reply. The proactive half is a scheduled job that reads rows the server already has, decides by rule whether there is anything worth saying, phrases it with one small model call, and sends it through APNs. The design decision that shapes everything is rules decide, the model writes. Letting a model read a nightly digest and decide for itself was rejected on two grounds: it bills for every user every night whether or not anything happened, and models calibrate "is this worth interrupting someone" poorly, usually toward yes.

The four triggers

_shared/nudge.ts holds four pure functions from rows to an optional fired result, each carrying a name, the numbers that made it fire, and a deterministic fallback sentence that is sent when the model is unreachable so an outage never swallows an observation.

  • short_sleep: three nights each more than an hour under the person's own median over the previous four weeks, requiring at least fourteen baseline nights. Not a fixed seven hours: a fixed number tells a habitual six-hour sleeper they are failing every day.
  • steps_collapsing: the last three days average under 60 percent of the trailing fortnight, with a baseline of at least 2,000 steps so someone who does not carry their phone is not nudged about steps.
  • streak_at_risk: a workout streak of three or more days counted back from yesterday, since at eight in the morning nobody has trained yet.
  • strong_week: a week averaging 25 percent above the previous three, or a personal best in the last three days against at least 21 days of history.

The positive is evaluated first. A genuinely strong week is rare, the negatives are still true tomorrow, and a channel that only ever carries bad news gets switched off, after which none of the rest matters. A missing day is dropped, never treated as zero, so a phone that has not synced does not fire a sleep nudge.

Volume and delivery

The job runs hourly because the send hour, eight in the morning, is local, and each run picks up whichever users' device_tokens row carries a timezone that has just reached it. A row whose timezone the runtime does not recognise never sends, on the rule that a nudge at the wrong hour is worse than no nudge. Nothing sends outside seven to nine local whatever the send hour is set to. One push per user per day is enforced by the primary key on nudge_log (user_id, day): the job inserts before it phrases, and a second overlapping run conflicts on 23505 and stops. The same trigger cannot fire again for seven days. The job makes one query per table for the whole batch rather than three per user, then loops sequentially because the expensive step is a model call per firing user and a burst of parallel APNs connections is how a sender gets throttled. A dead token (APNs says unregistered) is deleted so the job does not push at it forever.

On the phone, PushDelegate is the only reason the app has a UIKit delegate at all, because the device token arrives through didRegisterForRemoteNotificationsWithDeviceToken and nowhere else. PushService keys the registration to the active account, upserts the token and current timezone on every foreground (which is what keeps the hour right for someone who has flown somewhere), and deletes the row on sign out before the session is thrown away. The table makes the token its own primary key, so registering under a second account replaces the first account's row in one upsert and the wrong-account push is unrepresentable rather than merely unlikely. Authorization is asked for from the notification inbox, never at launch, because a permission prompt before the app has shown anything worth being interrupted about is the fastest route to a permanent no.

A tapped notification lands in the inbox and sets PushService.pending; RootView opens the coach on it through coach.seed(_:). The sentence is written to ChatStore as an assistant turn as well as appended to the transcript, because the store is what send renders into the thread, and a nudge that skipped it would be on screen and invisible to the model answering the reply. The payload carries the sentence, the trigger name and the day, deliberately not the figures: a phone that has been off for days would otherwise open on numbers two days stale, so whatever the conversation goes on to say is worked out against the store as it stands now. A seeded turn has an empty question and draws no bubble, since an empty bubble reads as a message you sent and deleted.

What is still not built Device-side triggers (a sector ceiling slipping out of reach, a spend spike), the sector_snapshots upload and the open-commitment rows from the proactive spec are slice 3 and have no code. The server path is complete to the APNs request; the QA report notes that no real push had been delivered when it was written, and that the APNs key, the App ID capability and the schedule.sql cron job are one-time setup steps rather than code. Until APNS_KEY is set the function returns apns_not_configured and sends nothing, on purpose.

14.9The privacy boundary

MetricsDigest is the only thing an engine is ever given about health. DailyMetrics is a SwiftData class, not Sendable, full of per-source detail; the digest is a value type of derived numbers. Because Engine.run takes a digest, the compiler rather than a reviewer stops a raw row reaching a model. The render then differs by audience: 

// LifeOSKit/Sources/Insights/Context/MetricsDigest.swift
if audience == .onDevice {
    if let v = day.hrvMs { parts.append("hrv \(number(v))ms\(delta(v, averages.hrvMs))") }
    if let v = day.spo2Pct { parts.append("spo2 \(number(v))%") }
    if let v = day.skinTempCelsius { parts.append("skin \(number(v))C") }
    if let v = day.respiratoryRate { parts.append("resp \(number(v))") }
}

HRV, SpO2, skin temperature and respiratory rate are the raw Whoop physiology, and they appear only in the on-device render. Everything else in a day block (recovery, sleep and its stages, debt, strain, resting heart rate, steps, exercise, workouts with their high-zone minutes) is a derived daily figure and travels. A calibrating recovery is marked rather than dropped. A delta against the fortnight baseline appears only where a baseline exists, so a comparison is never implied that was not made.

ContextBundle adds the month's money and the sector scores. On device it renders the digest plus one sector line, because the local window is small and a transaction list would push the health data out of it. Off device it renders everything under one 8,000 character budget: the user, sector and money-summary lines are built first and never trimmed, the digest takes what is left and drops whole days oldest first to fit, and the recent transactions get only what remains, which is why they are the first thing to disappear under a tight budget.

14.10Performance and cost

  • The daily cap is enforced where it can be. 150,000 tokens per user per day for chat, 4,000 for nudges, read before the call and debited after it through lifo_debit, an upsert-and-add in one SQL statement so two concurrent turns cannot both read the same balance and each write their own. The two kinds are separate rows so a heavy chat evening cannot eat the next morning's nudge. When the cap is hit the router falls back to the device rather than to a bill or an error.
  • Low reasoning effort. The chat body asks for reasoning_effort: low and verbosity: low. The default is medium and medium is most of the wait; a coaching question over a fortnight of numbers is not a reasoning problem, the thinking already happened on the device when the digest was built. Low also spends fewer tokens, the same lever as the cap pulled from the other end.
  • Streaming, with usage. The wait for a first word is the whole of how fast this feels, and it used to be the wait for the last one. The server re-emits the provider's stream in its own {"delta"} shape so the device never learns a provider's chunk format, asks for stream_options.include_usage so a streamed turn is still metered, and debits in flush, which a client that walks away still reaches.
  • Character budgets on the prompt. The digest fits 6,000 characters on device and the whole bundle 8,000 off device, pinned by tests, dropping whole days oldest first so a day that renders at all renders completely and the newest day, the one a question is about, is always present.
  • Missing fields cost nothing. A blank field is omitted rather than written as nil; the same information for zero tokens.
  • One request per turn for the coach. No tools means no rounds. The calendar assistant's loop is bounded at seven rounds and the invoker refuses the seventh call.
  • Speech is capped and cleaned. 1,200 characters at most, with markdown stripped first, because paying a per-character meter to narrate asterisks is paying twice for a formatting bug. The reply is only asked for a spoken line when the voice screen is up and speech is on, so a typed question costs no extra tokens for a voice nobody will hear.
  • The orb is cheap. One sphere with 96 segments, built once; the motion is a GPU shader driven by two uniforms, with no per-frame mesh allocation, and the display link stops when the screen leaves or Reduce Motion is on.
  • Brief cache. BriefCache is an actor with an in-flight map so two callers arriving for the same day generate once, and only a real answer is kept, since caching a refusal would strand the user without a brief until midnight. It is ready for the day the brief gets a screen.
  • The nudge job batches. One query per table across every user due this hour, a 94-day lookback stated in one constant so a new trigger cannot silently be starved of rows, and roughly 300 tokens in and 60 out per fired user.

The agent spec's cost check assumed twenty questions a day at about 3,000 tokens in and 500 out on the mini model, one brief a day, and speech on half the replies, and landed around $0.60 for mini traffic, $0.40 for escalations and $0.50 for Flash speech per user per month, inside the ceiling in Chapter 24 with the ledger capping the tail. Those are modelled, not measured.

14.12Study notes

Read in this order

  1. Insights/CoachTask.swift, for the floor, the audience and the three tasks.
  2. Insights/Context/MetricsDigest.swift, then ContextBundle.swift, to see exactly what a model is shown and how the budget trims it.
  3. Insights/AssistantTurn.swift, the chat router, with CoachRouter.swift beside it for the one-shot rules it restates.
  4. Insights/Chat/RemoteChatEngine.swift and ChatWire.swift, the stream reader and the tool loop.
  5. supabase/functions/_shared/lifo.ts and lifo-agent/index.ts, the other end of the wire.
  6. Features/Coach/ViewModel/CoachViewModel.swift, following send from top to bottom, then received, speak and reveal.
  7. Insights/SpeechEndpointer.swift with its test file open next to it.
  8. supabase/functions/_shared/nudge.ts, then lifo-nudge/index.ts.

Check yourself

  • Why does the cloud go first when the device is free? Quality picks the tier; the device answered worse on the questions this app gets, and the daily cap makes the cloud affordable.
  • Why is a refusal never retried on the other tier? A second model is not a second opinion on a refusal; it is a way around one.
  • What stops a raw Whoop row reaching OpenAI? The type system: Engine.run takes a MetricsDigest, and the remote engine can only request the .offDevice render, which omits the four physiology fields.
  • Why is onPartial cumulative? Because both tiers can honestly produce it and a screen that assigns cannot lose a fragment the way one that appends can.
  • Why does the context travel in its own field and not as a system message? So the server can place it behind SCOPE; a client system message would land after the guardrail and outweigh it.
  • Why two thresholds in the endpointer? Beginning a sentence must clear the room clearly; continuing one need only stay a little above it, so the soft tail of a word is not the end of a thought.
  • Why does the nudge job insert into nudge_log before it phrases? The primary key on (user_id, day) is the one-per-day rule, and inserting first makes two overlapping cron runs safe without any locking logic.
  • What is the one place a vendor key still ships in the app? ElevenLabs, until lifo-speak exists.
