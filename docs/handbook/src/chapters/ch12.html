Chapter twelve

12Notes and the plan

A block editor over a PARA library, synced to Supabase, with a derived index underneath that turns a pile of pages into something you can ask questions of. Habits are the one thing from the old Plan tab that did not become a page, and this chapter explains why.

Revision D described a Plan tab with four lists behind a segmented pill. That tab is gone. Goals, content items, loose notes and journal entries all became pages on 26 August 2026, migrated once and never rewritten, and the tab slot they occupied now belongs to Notes. What survived is the one plan kind that is not a document: a habit, which is a daily tick with a streak behind it. 12.9 covers what is left of the plan; everything before it is the notes tab as it is on disk today.

12.1Intent

Working backwards

Notes is a library with four shelves and a page you can write on. Every page is a list of blocks: paragraphs, headings, to-dos, quotes, code, a sketch you draw in line with the text. Type a slash to change what a line is, type two brackets to link to another page, and the page you linked to lists you at the bottom. Pick up a Pencil and it writes, draws or annotates depending on where it is. Everything saves on the device first and reaches the server afterwards.

Why PARA rather than folders you name yourself?

Because PARA sorts by actionability, not by subject. A note about running belongs under a marathon project while the race is ahead and under the area that outlives it once the race is run. Encoding that as the top of the hierarchy is the method's whole point, so NoteBucket is an enum with four cases rather than four folders a person could rename into meaninglessness. The app calls the third shelf Research, because PARA's own word, Resources, is vaguer than what the shelf holds.

Why blocks instead of one text field with formatting?

A block editor's trick is that the document is a list of small typed pieces rather than one string with ranges hung off it. Splitting, merging, reordering and turning a paragraph into a to-do become list operations, and none of them can corrupt the others. The operations themselves are pure functions in NoteBlockEditor, tested against literal arrays rather than a screen.

If blocks are JSON inside the page, how does the app find every open to-do?

It does not search the JSON. On every save, NoteIndexer mirrors the page's to-do blocks and wiki links into two derived SwiftData models, NoteTask and NoteLink. They are never pushed to the server, and every row can be rebuilt from the documents, so the worst an indexer bug can do is show a stale list. The repair is one function.

Does a note leave the device?

Only when someone is signed in, and only after the write has landed locally. NoteSync pushes dirty rows to two Postgres tables guarded by row level security, then pulls what other devices wrote. Sync can fail without anyone noticing and without losing an edit: push runs before pull, the newer updatedAt wins, and a row is marked synced only after the server confirms it.

What Notes deliberately does not do, yet: collections that cut across the shelves, goals as their own model, a mindmap of the link graph, voice capture, a share extension. Those are phases three to six of the notes redesign spec and none of them has code. Phase one, the index layer, shipped. Phase two, the phone's Inbox stream and its pinned composer, was built on 28 August and then set aside in the 13 September restyle: the store still knows what an Inbox is and the screen still compiles, but nothing routes to it. 12.5 says exactly what the phone shows instead.

12.3Model

The page

A page is a NoteDocument. Every field carries a default, because SwiftData adds a property to an existing store without a migration plan only when it can fill it in, and this model has grown four times since it was created. 

// LifeOSKit/Sources/Persistence/NoteDocument.swift
@Model
public final class NoteDocument {
    public var id: UUID = UUID()
    public var title: String = ""
    public var icon: String = ""
    public var kindRaw: String = NoteKind.note.rawValue     // note | journal | task
    public var bucketRaw: String = NoteBucket.projects.rawValue
    public var accentRaw: String = NoteAccent.sage.rawValue
    public var folderID: UUID?                              // nil: loose on the shelf
    public var blocksData: Data = Data()                    // the blocks, JSON encoded
    public var drawingData: Data?                           // a PKDrawing, when inked
    public var entryDate: Date?                             // the day a journal entry is about
    public var dueDate: Date?
    public var statusRaw: String = PlanStatus.todo.rawValue
    public var isFavorite: Bool = false
    public var openedAt: Date?                              // drives Recent; written on open
    public var archivedAt: Date?                            // Archive is this flag, not a bucket
    public var filedAt: Date?                               // nil means still in the Inbox
    public var syncedAt: Date?
    public var deletedAt: Date?                             // a tombstone, reaped after push
    public var originPlanEntryID: UUID?                     // the plan row this came from
}

Four of those fields carry the whole design, and each earns a sentence.

  • blocksData is JSON, not a relationship. Blocks are only ever read and written as a document, no query asks for one block, and a relationship would buy one migration hazard per block field in exchange for nothing. When the JSON cannot be decoded the getter hands back a blank page rather than throwing: the bytes stay on disk untouched until someone saves over them, and the person at least has somewhere to type.
  • archivedAt is a flag, not a fifth shelf. An archived page keeps the bucket it was filed on, so restoring it needs no decision.
  • filedAt is the whole Inbox concept. A bucket cannot answer "has anyone decided where this goes", because every page has a bucket from the moment it is created. The stamp is written by filing and never by editing, so a page you keep writing in stays unfiled until you choose a home for it.
  • syncedAt and deletedAt are the sync contract. updatedAt > syncedAt is the entire dirty test. A delete writes a tombstone the server can pull as a fact, rather than an absence it cannot observe.

Three enums sit behind the raw strings. NoteKind decides how a page is listed, not how it is edited: a note, a journal entry titled by its day, or a task page that exists to hold to-dos. NoteBucket is the four shelves. PlanStatus is reused from the old plan rather than declared again, which is what lets the monthly close in Chapter 13 read goal progress off notes without learning a second vocabulary. Raw strings with typed accessors, for the reason Revision D gave: a new case is a code change, not a migration, and an unrecognised value reads as the default instead of failing the fetch.

A NoteFolder is the same shape with fewer fields: a name, an emoji or an accent dot, a shelf, an optional parentID, and the same syncedAt and deletedAt pair. Folders nest arbitrarily in the model and one level in practice.

The block

// LifeOSKit/Sources/Persistence/NoteBlock.swift
public struct NoteBlock: Codable, Sendable, Identifiable, Equatable {
    public var id: UUID
    public var kind: NoteBlockKind      // paragraph, three headings, three lists, quote,
                                        // callout, code, divider, sketch
    public var text: String
    public var isChecked: Bool          // kept on every block so a tick survives a transform
    public var indent: Int              // 0 through 4, purely visual
    public var drawing: Data?           // sketch blocks only
    public var sketchHeight: Double?    // dragged height, so ink crops the same on every device
    public var dueDate: Date?           // to-do blocks only; authored, so it lives here
    public var goalID: UUID?            // to-do blocks only; authored, for the same reason
}

Two details matter. Indent is a number on a flat array, not a tree: a nested list item is still a sibling, which is what keeps every editing operation a list operation. And dueDate and goalID live on the authored block rather than on the derived NoteTask row, because the row is rebuilt on every save and would lose them.

NoteBlockParser owns the Notion-style typed prefixes. candidates is every prefix sorted longest first, and that order is the whole correctness argument: - [ ] starts with - , so checking kinds in declaration order would turn every to-do typed by hand into a bullet reading "[ ] whatever". --- and the code fence are whole-line markers rather than prefixes, so a line reading "--- and then some" stays a paragraph. The same type renders blocks as Markdown for the share sheet and for the coach's context window, and parses Markdown back into blocks for paste and for the plan migration. Round-tripping is not a goal; a sketch becomes _[sketch]_ on the way out, because saying a drawing was here beats dropping it silently.

NoteLinkScanner finds [[wiki links]]. Case is preserved in what was typed and folded at lookup, so [[Marathon]] and [[marathon]] reach the same page without rewriting either.

The derived rows

// LifeOSKit/Sources/Persistence/NoteIndex.swift
@Model
public final class NoteTask {
    public var id: UUID = UUID()          // the block's own id: stable across reindexes
    public var documentID: UUID = UUID()  // scoped by page, so a pasted block cannot collide
    public var text: String = ""
    public var isChecked: Bool = false
    public var indent: Int = 0
    public var dueDate: Date?
    public var goalID: UUID?
    public var sortOrder: Int = 0         // position in its page
    public var documentUpdatedAt: Date = Date.distantPast   // copied down, so a cross-page
}                                                           // list can order pages

@Model
public final class NoteLink {
    public var sourceID: UUID = UUID()
    public var targetTitleFolded: String = ""   // lowercased: one edge per title
    public var targetID: UUID?                  // nil: the page does not exist yet
}

Two rules make these safe. They are never pushed, so two devices cannot disagree about them. And every row is reconstructible from the documents, so any inconsistency is repaired by NoteIndexer.rebuildAll. A NoteTask keeps the block's own id so the row is stable across reindexes rather than churning a new identity on every keystroke; it is scoped by documentID because a block copied and pasted into a second page keeps its id.

A resolved edge can dangle NoteLink.targetID being non-nil is not proof the page is still there. reindex only rewrites the edges out of the document being saved, so renaming or deleting a page leaves every edge that pointed at it holding an id that now names something else or nothing at all. The next launch's rebuildAll repairs them. Until then a consumer must treat the lookup as a miss it can survive, not as a page it is owed. This is written on the model so it is not rediscovered as a mystery bug.

What views see

Views never hold a NoteDocument. NoteCardSnapshot is a page flattened for display: title, icon, excerpt, accent, folder name, task progress, whether it has ink, how many links it carries. NoteFolderSnapshot is a folder row with its children already attached and a count that rolls up through them. NotesSnapshot is everything the sidebar needs in one read. NoteBacklink is a page that links here, with the line the link appears on, so the backlinks pane shows context rather than a bare list of titles.

12.4ViewModel

Three view models, one per concern, and the store does the deciding for all of them. NotesStore lives in the package because the app target has no test target, so any rule worth pinning (what "All" includes, when a page is filed, what order a shelf sorts in) is put where swift test can reach it.

The library

// LIfeOS/Features/Notes/ViewModel/NotesViewModel.swift
@Observable @MainActor
final class NotesViewModel {
    private(set) var snapshot: NotesSnapshot = .empty
    private(set) var cards: [NoteCardSnapshot] = []
    private(set) var isSearching = false

    var selection: NoteSelection = .recent { didSet { if selection != oldValue { load() } } }
    var filter: NoteShelfFilter = .all   { didSet { if filter != oldValue { load() } } }
    var sort: NoteSort = .recentlyEdited { didSet { if sort != oldValue { load() } } }
    var query: String = ""               { didSet { if query != oldValue { load() } } }

    func attach(_ context: ModelContext, sync: NoteSyncing? = nil)
    func load()
    func createNote(kind: NoteKind = .note, title: String = "") -> UUID?
    func openTodaysJournal() -> UUID?
    func createFolder(named:in:icon:)  func renameFolder(_:to:)  func deleteFolder(_:)
    func toggleFavorite(_:)  func toggleArchive(_:)  func delete(_:)  func move(_:to:folderID:)
}

NoteSelection is one enum rather than a pair of optionals, because "a folder is selected" and "a shelf is selected" are mutually exclusive and two nullable properties make a fourth, meaningless state representable. load() reads the snapshot once, then either a search or the cards for the selection. Every mutating method funnels through mutate(id:), which fetches the live object, applies the change through the store, reloads, and fires a sync. Nothing in the UI waits on the server; the write has already landed locally by the time requestSync() runs, and a failure there only means the next pass carries the row.

NoteSyncing is a one-method protocol the view model asks for, so a preview and a design capture can hand it nothing. The real NoteSync conforms in one line at the top of RootView, which is the only place that knows both types.

The page

NoteEditorViewModel holds the blocks in memory and writes them back on a delay. Saving on every keystroke would mean a SwiftData write and a didSave notification per character, and every screen in the app reloads on that notification. 

// LIfeOS/Features/Notes/ViewModel/NoteEditorViewModel.swift
private func scheduleSave() {
    guard !isLoading else { return }
    saveMessage = "Saving…"
    saveTask?.cancel()
    saveTask = Task { [weak self] in
        try? await Task.sleep(for: .milliseconds(600))
        guard !Task.isCancelled else { return }
        self?.saveNow()
    }
}

/// Called on the way out, so a page closed inside the debounce window still lands.
func flush() {
    saveTask?.cancel()
    saveTask = nil
    saveNow()
}

Ticking a checkbox is the exception: it is a decision, not a keystroke, and toggleCheck saves at once so it survives the app being closed a second later. The screen calls flush() on disappear and whenever the scene leaves the active phase.

The keystroke rules are not here. splitBlock, backspaceAtStart, indent, transform and completeLink each call the matching pure function on NoteBlockEditor, apply the returned blocks, move the caret to the returned focus, and schedule a save. The view model also tracks the two queries the accessory bar renders: slashQuery, the text after a leading slash, and linkQuery, the partial title inside an unclosed [[. linkSuggestions filters a title index the model refreshes after every save, and resolveLink creates the page when nothing carries that title, the way Obsidian does.

setDrawing compares bytes before writing, because PencilKit reports a change on every stroke and on every tool switch, and rewriting identical bytes would mark the page dirty for a sync that carries nothing new.

The Inbox

NoteInboxViewModel is 78 lines: a chip, a draft, a sticky to-do toggle, and a capture() that hands the draft to NotesStore.capture, clears it on success and leaves it alone on failure so a thought is never silently dropped. It is thin by the same rule as LifeBoardViewModel: what a chip means lives in the store. It compiles, its store methods are tested, and no screen constructs it today.

12.5View

Two shells over one library

NotesHubScreen reads layout.isRegular from the environment and builds one of two arrangements. Both drive the same NotesViewModel and the same NoteShelfScreen; only the chrome around the shelf differs.

The phone is a NavigationStack with the shelf at its root. The leading toolbar button presents the library as a full-height sheet titled "Your library", and choosing anything in it sets the selection, clears the path and closes the sheet in one binding, so the rail and the sheet cannot drift apart about what a tap does. A page is pushed onto the path. Two small pieces of state, pendingNewFolder and pendingRename, exist because a sheet cannot present a second sheet: the library records what was asked for, dismisses, and the hub presents the folder sheet in onDismiss.

The iPad is an HStack of up to three columns: the rail, the shelf, and the open page. Whether the third column exists is measured, not derived from the size class. 

// LIfeOS/Features/Notes/View/NotesHubScreen.swift
private static let libraryWidth: CGFloat = 268
private static let minShelfWidth: CGFloat = 340
private static let minPageWidth: CGFloat = 520   // below this the page stops being somewhere you would write

private var isThreeColumn: Bool {
    guard layout.isRegular else { return false }
    let spokenFor = layout.railInset + (isLibraryVisible ? Self.libraryWidth : 0)
    return paneWidth - spokenFor >= Self.minShelfWidth + Self.minPageWidth
}

A single overall threshold was wrong: at 1024 points a pane read as wide enough, but the library and the tab rail take 380 of that before the shelf and the page have divided anything, leaving a 310-point column to write in. Subtracting what is already spoken for is what lets collapsing the library buy a third column on a screen that could not otherwise hold one. Rotating an iPad or resizing a Stage Manager window flips isThreeColumn, and the open page moves between the detail column and the navigation path with it, or it would vanish. Exactly one of openPage and a .page route on the path is ever non-empty, which is what stops them disagreeing.

The detail column rebuilds its editor per page with .id(openPage), so the editor never shows the previous page's blocks for a frame while the new ones load. NoteEditorHost exists because @State cannot be initialised from a navigation destination's argument; it creates the editor view model in a .task keyed on the document id and keeps it alive while the page is on screen.

The rail and the library

The iPad rail, NotesSidebar, is text rows on the canvas rather than a List, which brings its own background, separators and insets, all of which would have to be undone. Recent and Favourites lead, Habits pushes its own screen, then the four shelves, each expanded on first launch because four collapsed rows tell a new user nothing about what PARA is. Every shelf and folder row is a drop destination for NoteDragPayload; a drop on a shelf files the page loose on it, and a drop on Archive archives rather than refiles, because Archive is a state, not a place. The drop highlight is a different colour from the selection highlight: "this is where it will land" and "this is what you are looking at" are different statements.

The phone library, NotesLibraryList, is the same inputs and callbacks in the app's own card vocabulary: Recent, Favourites and Habits as a row of tiles, then each shelf as one soft card with its folders under a hairline and a quiet row to add one. The whole list sits inside one GlassEffectContainer, so neighbouring glass tiles merge and separate as they move rather than each rendering its own lens. Colour is Apple's: system grays for every icon square and fill, and the accent orange for exactly one thing, whatever is selected.

The shelf

NoteShelfScreen is a header, a search field, a count, a kind filter (shown only when a shelf or folder is selected, since Recent and Favourites already cut across kinds), a sort menu with the four orders NoteSort allows, and a LazyVStack of NoteCard. Each card carries its move targets as a menu as well as being draggable, because drag and drop is a pointer gesture and the same move has to exist for a finger.

The page

NoteEditorScreen caps its measure at 760 points even on an iPad, because prose at 1000 points across is unreadable and this is the one screen in the app that is genuinely prose. Above 1040 points of editor width, and only when there are backlinks to show, the backlinks list moves out from under the text into a 280-point inspector column beside it.

The body is a ZStack: a column of NoteBlockRow underneath, and an InkCanvasView sized to the measured height of that column on top. A canvas sized to the screen instead would clip strokes the moment the page scrolled. Under the last block sits 160 points of clear, tappable space that focuses the last block, because without it the bottom half of a short page is dead.

Each block row draws its gutter mark in SwiftUI and its text in UIKit. Putting the bullet inside the text view as a literal character was the alternative, and it makes the bullet deletable, which means a list item can silently stop being one. BlockTextView wraps a UITextView for three things SwiftUI's text field cannot do here: intercept Return so it splits the block instead of inserting a newline, intercept Backspace at offset zero so it merges with the block above, and paint [[links]] as the person types. Apple Pencil Scribble arrives free with UITextView, which is the fourth. Every font comes from LifeOSType.UIKitScale, so a heading in a note is the same size as the same heading anywhere else in the app.

NoteAccessoryBar is one strip above the keyboard with three states that take turns: a slash menu while slashQuery is set, a link picker while linkQuery is set, otherwise a formatting bar with indent, ink and dismiss. Three floating panels competing for the same corner of a phone screen was the alternative. Escape backs out one layer at a time: the block menu, then the link picker, then the keyboard. Closing the page on the first press would lose someone mid-sentence.

The Pencil rule

There are two kinds of drawing on a page and they are deliberately different. SketchBlockView is a block in the flow: it pushes the text below it down and moves with the paragraph it belongs to, which is what a diagram between two paragraphs wants. It is Pencil-only by default on iPad so a finger still scrolls past it, and finger-drawable by default on a phone. InkCanvasView floats over the whole page for annotation.

The ink layer used to claim every Pencil touch, on the theory that picking up the Pencil should mean drawing. The cost was hidden and larger than the benefit: a layer that swallowed the touch first meant Scribble could never fire anywhere, and sketch blocks were unreachable for the same reason. So the rule is stated by where the Pencil is, not by what it is. Over a text block it writes. Over a sketch block it draws in that block. With ink mode on, it annotates the page, and a double-tap or squeeze of the Pencil turns ink mode on without a trip to the toolbar.

NoteToolPicker is one PKToolPicker shared by the ink layer and every sketch block. Two of them fight: whichever became visible last wins, and the loser leaves a stale observer behind that keeps receiving tool changes for a canvas nobody is drawing in. It also tracks which canvases already observe, because PencilKit keeps duplicate observers rather than ignoring them and a view that updates twenty times would otherwise register twenty.

The hardware keyboard

NotesCommands is a CommandMenu installed in the scene, so its shortcuts work wherever focus is and appear in the overlay an iPad shows when Command is held. It reads a NotesCommandTarget from focusedSceneValue: a struct of closures, one per action, because opening a page means pushing on a phone and filling the detail column on an iPad and the scene must not have to know which. closePage is optional and nil when nothing is open, which is what greys out Command-W rather than letting it fire into an empty column. Command-Option-0 is Recent and Command-Option-1 to 4 are the shelves, matching how editors number their tabs.

12.6How it works

Step by step, from a keystroke

  1. The UITextView reports text, or a Return, or a Backspace at offset zero. NoteBlockRow forwards it as a closure call.
  2. The editor view model applies the matching NoteBlockEditor function to its block array, moves the caret, and schedules a save 600 milliseconds out. A second keystroke inside that window cancels the first task.
  3. saveNow() fetches the live document and calls NotesStore.update, which returns early if the blocks are equal and otherwise assigns them and calls touch.
  4. touch stamps updatedAt, calls NoteIndexer.reindex, and saves once. Every document mutation in the store funnels through this one function, which is why the index is rewritten here and nowhere else.
  5. reindex fetches and deletes the page's existing rows, inserts one NoteTask per to-do block, and, only if the page carries any links, builds the folded title index and inserts one NoteLink per link.
  6. The view model refreshes its backlinks and title index, updates the "Saved on this device" label, and asks NoteSync to run.

The indexer's two deletes

reindex and rebuildAll delete rows differently, on purpose, and the code says not to "fix" either to match the other. 

// LifeOSKit/Sources/Persistence/NoteIndexer.swift
// Inside reindex: fetch and delete each, NOT `context.delete(model:where:)`.
// The batch form runs against the persistent store and cannot see rows
// inserted earlier in this same unsaved transaction, so a second reindex
// would duplicate rows instead of replacing them.
let existing = try context.fetch(
    FetchDescriptor<NoteTask>(predicate: #Predicate { $0.documentID == documentID })
)
for row in existing { context.delete(row) }

// Inside rebuildAll: the batch form is correct HERE. This deletes everything
// before anything is inserted, and the rows it clears are already saved.
try context.delete(model: NoteTask.self)
try context.delete(model: NoteLink.self)

rebuildAll also starts from empty rather than reindexing page by page, because a per-document pass never visits a page that is no longer there, and so could never clear the rows a deleted page left behind.

Filing

Where a page lands, and when it counts as filed, is decided in the store and pinned by tests.

  • createDocument stamps filedAt only when a folder was given. Choosing a folder is choosing a home. A page created loose on a shelf is not filed, because the shelf was the default, not a decision.
  • capture writes one block into Areas with no title and no filedAt. The title is left empty on purpose: displayTitle already falls back to the first textual block, so storing the sentence twice would show it twice on the card.
  • move stamps filedAt if it is nil. Editing never does.
  • Deleting a folder empties it onto its parent rather than taking the pages with it. Losing a folder is an organising decision; losing what was in it is a different decision that must never be made by implication. Those pages change outside touch, so the store reindexes them by hand in the same loop.

Sync

NoteSync coalesces overlapping calls into one in-flight task, reads the access token fresh from the keychain on every pass rather than capturing it (the app shell refreshes the session hourly, so a captured token would be stale within the hour), and returns quietly for a guest. Then:

  1. Push folders first. A page whose folder has never been pushed would arrive pointing at a row the server does not have, and a pull on another device would file it at the root until the folder caught up.
  2. Push documents in batches of 25. A page carrying ink is large, and a person offline for a week can have many. One oversized body is a 413 that fails every page in it, including the small ones. Each batch is marked synced as soon as the server confirms it, and the mark does not touch updatedAt, so an edit made mid-flight stays dirty.
  3. Pull rows newer than the cursor, rewound one second so a row written in the same instant as the cursor is not stranded on the far side of it. For each row: a local copy newer than the server's wins and stays dirty; a tombstone deletes the local row after clearing its index; an update reindexes; an insert stamps filedAt from createdAt, because a page from another device was filed on the device that made it and is not new capture here. Ink that was too large to push comes back null, and null means "not carried", not "erased", so the local drawing is kept.
  4. Advance the cursor to the newest updatedAt seen, in the per-account defaults suite rather than the shared one, so two people on one device cannot read each other's position.

The one trigger in the app today is a write: every mutating path in the two view models ends in requestSync(). There is no launch or foreground pull, so on a second device the first pull happens as the tail of the first push.

The one-time migrations

RootView.attachAll runs three idempotent steps on every launch. PlanNoteMigration.seedIfEmpty creates one Journal folder, and only when the tree is completely empty, because pre-filling shelves with folders nobody asked for is how a fresh install feels like someone else's mess. PlanNoteMigration.run turns goals, content, notes and journal entries into pages (12.9). NoteIndexMigration.run stamps every page that predates the Inbox as filed, then rebuilds the index. That stamp is keyed by a marker in the per-account defaults, and the marker is spent only when there was history to interpret: on a fresh install the first launch runs before the first pull, and consuming the one-shot on an empty store would leave every page that arrives afterwards stranded in the Inbox.

12.7Performance and cost

  • One write per pause, not per character. The 600 millisecond debounce in the editor is the single most consequential number in this chapter: without it every keystroke would fire a SwiftData save and a didSave notification that reloads every view model in the app.
  • The title index is built once per rebuild, not once per page. Letting each reindex build its own made rebuildAll quadratic in the size of the library: one fetch of every document per document, decoding the blocks of each untitled page every time, on the main actor before the UI was live. rebuildAll now builds the index once and passes it down.
  • A page with no links never fetches the library. reindex scans for links first and returns before building a title index when there are none, which is most pages. Otherwise the editor would pay a fetch of every document on every debounced keystroke.
  • Delete and reinsert beats a diff. A page holds tens of blocks, the rewrite is cheap, and a diff would need its own correctness argument for every field.
  • The sidebar is one read. NotesStore.snapshot walks the folders and documents once to build the tree, the per-shelf counts, the recent list and the favourites. Four separate reads would each walk the same rows.
  • Search has no index and does not need one. It is a substring match over titles and block text, case and diacritic insensitive, capped at 40 results. That is fine until a person has thousands of notes, and the derived rows are where an index would go when it is needed.
  • Ink stays on the device past 1.5 megabytes. A dense PencilKit page is a few hundred kilobytes, a pathological one is megabytes, and base64 adds a third. One runaway page must not stall every other page's sync behind it, so NoteDocumentRow leaves oversized ink out of the payload and the page syncs its text.
  • Opening a page does not dirty it. markOpened advances openedAt without touching updatedAt, so reading on one device cannot fabricate an edit that wins a sync conflict against a real one on another.
  • Blocks travel as real JSON. The blocks column is jsonb, so a malformed document is refused by Postgres at write time rather than surfacing on another device later, and a future server-side reader can query into it.
  • Cost is zero beyond Postgres rows. No AI, no third-party service, no per-user fee. Two tables, five indexes, one policy each, all scoped to auth.uid(). user_id defaults to auth.uid() on the server and the client never sends it, so ownership is decided from the token rather than asserted by the device.

12.9The plan that remains

PlanEntry still exists with all five kinds, and PlanScreen still renders four sections. Only one of them is reachable. The notes tab's library offers a Habits row that pushes PlanScreen with section: .constant(.habits) and showsSections: false, and the add sheet in RootView sets plan.section = .habits before it opens. Goals, notes and content are pages now.

Why habits stayed behind

A habit is a daily tick with a streak behind it. Today toggles those ticks live from its own screen, and turning a habit into a document would either break Today or leave two rows claiming to be the same habit. So HabitTick stays a flat table keyed by entryID and day, PlanStore.tickedHabitIDs(on:) answers a whole day in one fetch for Today, and the streak rule from Revision D is unchanged: 

// LifeOSKit/Sources/Persistence/PlanStore.swift
public func streak(for entry: PlanEntry, endingOn end: Date = .now) throws -> Int {
    let ticks = try recentTicks(for: entry, days: 365, endingOn: end)
    var count = 0
    for (index, done) in ticks.reversed().enumerated() {
        if done { count += 1 }
        else if index == 0 { continue }   // today still open
        else { break }
    }
    return count
}

Walk backwards from today, counting until a gap. An unticked today is skipped rather than treated as a break, because the day is not over; yesterday unticked still ends the streak.

How the rest moved

PlanNoteMigration.run is idempotent through originPlanEntryID on each page rather than through a flag in UserDefaults, because a flag says "this device has migrated", which is the wrong question once a second device syncs the same pages down. PARA's own rule decides where each kind lands:

Folders are made only when there is something to put in them, and the original plan rows are left in place. They are what the months already closed were scored against, and rewriting history to match a new filing system is the kind of thing an app should never do behind someone's back. NoteEvidence is the bridge the monthly close uses: journal dates come off journal pages by entryDate, and a project page's status is what its to-do blocks say when it has any, because ticking the last box is a clearer statement that a thing is done than remembering to flip a menu afterwards.

Check yourself

  • Why are blocks JSON inside the page rather than SwiftData rows? Blocks are only ever read and written as a document; a relationship would add a migration hazard per field for no query that needs it. The derived rows exist for the one query that does.
  • What single field is the Inbox? filedAt. Nil means nobody has chosen where the page belongs. Filing stamps it; editing never does.
  • Why does reindex fetch-and-delete while rebuildAll uses the batch delete? The batch form cannot see rows inserted earlier in the same unsaved transaction, so inside reindex it would duplicate rows. rebuildAll clears already-saved rows before inserting anything, so the batch form is correct there.
  • What made a rebuild quadratic, and what fixed it? Each page's reindex built its own title index by fetching every document. rebuildAll now builds it once and passes it down; a single save still builds it on demand, and only when the page has links.
  • Why push folders before documents, and why batches of 25? A page arriving before its folder would be filed at the root on another device until the folder caught up. One oversized body is a 413 that fails every page in it, including the small ones.
  • Why did habits not become pages? Today ticks them live from HabitTick; a document version would either break Today or duplicate the habit.
