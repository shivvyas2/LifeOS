Chapter twenty-one

21Data reference

Every type a screen reads through, as it exists in LifeOSKit/Sources/Persistence today: twenty SwiftData models, the value types beside them, and the stores that are the only way anything writes. The package depends on nothing, builds for macOS, and is where the app's most important rule lives.

21.1Four rules every model obeys

The models below look different but they were written to the same four rules. Learn the rules and most of the reference reads itself.

  1. Every metric is optional. A missing value and a zero must never be the same thing. Zero steps means you did not move; nil steps means the watch was on the charger. In a health app a false zero is worse than a blank, because it is a wrong number presented with confidence. The optional travels unchanged from the column through the snapshot to the tile, which renders the dash itself.
  2. A field added to an existing model is optional or defaulted. SwiftData will not migrate a store in place when a mandatory attribute has no default, and it does not fail loudly: the container never opens, the shell has no account to show, and the app sits on its spinner. Section 21.13 tells the story of the day this happened.
  3. Enums are stored as raw strings with typed accessors. kindRaw, statusRaw, bucketRaw, sectorRaw. A new case is a code change rather than a migration, and an unknown value read back from an older store falls to a sensible default instead of failing the row.
  4. Views never hold a @Model. Every store hands out a detached value type: PlanItemSnapshot, CalendarEventSnapshot, NoteCardSnapshot, ChatMessageSnapshot. A managed object handed to a card is a live handle on the database and a reason every view needs a container to preview. The snapshot costs one map per fetch and buys back both testability and the compile-time guarantee that nothing above the store mutates rows.
Why raw JSON bags appear so oftenFive models keep an array or dictionary as encoded Data rather than as a relationship: DailyMetrics.extrasData, WorkoutRecord.setsData, NoteDocument.blocksData, ChatMessage.eventIDsData and SectorScore.evidenceData. The reasoning is the same each time: the value is only ever read and written as a whole, no query asks for one element of it, and a relationship would cost one migration hazard per field in exchange for nothing. Where a query is needed, the JSON is mirrored out into derived rows instead, which is exactly what NoteTask and NoteLink are.

21.2DailyMetrics

One row per calendar day, the join key for the entire application. #Unique([\.date]) makes a second row for the same day impossible, and date is always Calendar.startOfDay, never a timestamp.

Two design points deserve a closer look. The first is why the named columns stopped growing. Height and max heart rate are absent on purpose because they are constants, and a column restating the same value on every row is noise. Everything else Apple Health can supply lands in the extras bag, added by one enum case and one mapping, because most people have no data for most of it and a schema change per metric for fields nothing queries is the wrong trade.

// LifeOSKit/Sources/Persistence/DailyMetrics.swift
public func setExtra(_ key: String, _ value: Double?) {
    var bag = extras
    if let value { bag[key] = value } else { bag.removeValue(forKey: key) }
    extras = bag
}

Writing nil removes the key rather than storing a zero. The bag keeps the distinction the whole model is built on: a key that is missing means no reading, and nothing ever writes a zero to stand in for one. The getter returns an empty dictionary rather than throwing when the bytes cannot be read, because a day whose extras are unreadable still has its named columns, and losing the screen over the tail would be the worse failure.

The second is provenance. sourcesData is a parallel bag rather than a field folded into extras, because that bag is numbers and a source is a name. It stores a raw string rather than a typed MetricSource because Persistence sits below Integrations and must not import it; the vocabulary lives up there. A store written before provenance existed reads back no attribution, which MetricArbiter treats as rank zero for everything except the two typed metrics, weight and water, where an unattributed value is read as typed so that the next Health sync cannot silently replace a figure a person entered by hand.

UserGoals is a singleton by convention: exactly one row, created with defaults on first access by MetricsStore.goals().

The last three were added on 14 September 2026 for the workout library, and the middle one is the field that briefly shipped without a default. The row converts to GoalTargets, a plain Sendable struct, before it reaches any scorer or view model.

Evaluation

// LifeOSKit/Sources/Persistence/GoalEvaluation.swift
public func evaluate(_ reading: DayReading, against targets: GoalTargets) -> DayStatus {
    guard reading.hasAnyData else { return .noData }
    var met = 0
    if let steps = reading.steps, steps >= targets.steps { met += 1 }
    if let sleep = reading.sleepMinutes, sleep >= targets.sleepMinutes { met += 1 }
    if let exercise = reading.exerciseMinutes, exercise >= targets.exerciseMinutes { met += 1 }
    if let water = reading.waterML, water >= targets.waterML { met += 1 }
    return met >= targets.requiredCount ? .onTarget : .missed
}

A day with no metrics at all is .noData, excluded from judgement, because leaving the watch on the charger is not a failure. A day with some data is judged on what it has, so an unlogged metric cannot launder a bad day into a blank one. Exactly meeting a goal counts, since the comparison is greater-or-equal. currentStreak expects statuses most-recent-first, treats .noData as transparent, counts .onTarget, and stops at the first .missed.

Anomalies

AnomalyEvaluation flags one vital sitting outside its own recent range. The baseline needs at least seven actual readings (minimumBaselineDays) or there is no verdict, which is the app-wide rule that absence of data is never a judgement. Thresholds are relative for metrics that scale with the person (heart rate) and absolute for metrics with a physiological unit (a degree of skin temperature means the same at any baseline). The wording rule for anything rendered from an AnomalyFinding is descriptive, never diagnostic: "well above your baseline" is a fact, "see a doctor" is a claim the data cannot support.

21.4Source records and the raw archive

WorkoutRecord and SleepRecord hold data that is genuinely not daily. They roll up into DailyMetrics, which is derived state and always safe to recompute from them.

ModelKeyFields worth knowing

SleepRecordexternalIDstart, end, attributedDate (the morning you woke), performance, consistency and efficiency percentages, light, REM, SWS, awake and no-data minutes, cycle count, respiratory rate, sleep need, debt, need from strain, need from nap (negative or zero), disturbance count, isNap: Bool?

Three small decisions on WorkoutRecord show the rules at work. Six zone columns rather than one array, because SwiftData stores scalars cleanly and an array attribute would be a migration this does not need. percentRecorded kept, because a workout at 40 percent recorded is not a workout with a low strain, and collapsing the two would be the false zero the app refuses. setsData as JSON with empty sets stored as nil, so an existing store migrates without a plan and a session with no sets is not a session with an empty list.

WhoopArchive is the reader and writer of the raw archive. It upserts on (kind, externalID) because a re-sync returns records already seen, and it has a batched store(_:) that saves once per page, because a save per record turns a fourteen-day sync into hundreds of disk transactions on the main actor. FitbitSync reuses the same archive under fitbit- kinds, since it was already a generic raw-record store and only its name is Whoop-specific. The archive is why a derivation bug six months out is fixable without asking a rate-limited API for the data again.

21.5Money

Four models and three value types. The one sentence to remember is written into the type: positive is money in, negative is money out. Plaid is the opposite, its amount is positive for outflows, and the ingestion layer negates on the way in. A silent sign flip turns income into expenses and every rollup lies, which is why the convention is a doc comment on the class rather than a note in a spec.

ModelFieldsInvariant
MoneyEntryid, externalID (Plaid transaction_id), sourceRaw, date, amount, currencyCode, merchant, category, categoryCode, merchantID, logoURL, accountID, accountName, pending, timestampsdate is start of day; externalID is the upsert key; categoryCode keys arithmetic and category is display text only
MoneyAccountexternalID, name, type, subtype, mask, availableBalance, creditLimit, currentBalance, currencyCodecredit and loan types contribute -abs(balance) to net worth; creditLimit is never defaulted to zero because utilisation against zero computes to 100 percent and means nothing
SpendBucketname, monthlyLimit, claimedRaw, sortOrderlimit is positive; a claim key is held by at most one bucket, enforced on write

The spending predicate is one property so that the category list always sums to the figure above it:

// LifeOSKit/Sources/Persistence/MoneyEntry.swift
public var isSpending: Bool {
    amount < 0 && !pending && !MoneyCategoryRule.isTransferLike(categoryCode)
}

MoneyCategoryRule.isTransferLike keeps transfers between your own accounts and credit card payments out of both income and expenses: they appear as a real debit and a real credit, so counting them leaves net correct while overstating both sides, and the savings rate is computed from those two. It matches the underscore-delimited prefix (TRANSFER_IN_, TRANSFER_OUT_) rather than a bare prefix, because without the underscore a code that merely starts with the same letters would be excluded as if it were a transfer.

MoneySummary.savingsRate is nil when income is zero. Undefined is not zero, and this is the sharpest case of the app's central rule. MoneyParts splits an amount for display and rounds to the cent before splitting, because splitting a Double first lets a fraction of .995 round up to 100 cents and render as $19.100. It lives in the kit, where it is tested, rather than in a view where it is eyeballed. MoneyEntry.claimKey is categoryCode ?? category: Plaid's raw detailed code when there is one, else a manual entry's free-form category.

21.6Plan entries and habit ticks

PlanEntry is one model carrying five kinds: goal, habit, note, content and journal. A block renderer can lay out any entry without knowing which feature produced it, and a new kind is an enum case rather than a table. PlanStatus is todo, inProgress, done, blocked or scheduled, and both enums are stored raw so an unknown value reads as .note and .todo.

HabitTick is one completion of a habit on one day, separate from the entry because a habit's history is a set of days rather than a field, and because it lets the existing dot grid render a habit exactly like the Today grid. PlanItemSnapshot is the detached form, with fraction derived from progressValue and progressTarget and clamped to 0...1.

The plan tab's goals and journal entries were migrated onto note pages on 27 and 28 August 2026. PlanNoteMigration runs once, idempotent through NoteDocument.originPlanEntryID rather than a flag, so a second device does not produce a second copy of everything the first one migrated. The rows it deliberately leaves behind still score months that were already closed, which is why NoteEvidence returns both.

21.7Calendar events and chat messages

CalendarEvent is a cache of provider events, never the source of truth for them. The natural key is (source, sourceID), and sourceID is EventKit's identifier qualified with the occurrence start for recurring rows, because EventKit reuses one identifier across a series. CalendarEventSnapshot is the value form, and being Sendable is the point: a tool result crosses into an engine, and a @Model cannot make that trip. CalendarEventDraft is what a caller supplies to create or edit, with no id and no source, because routing decides those. CalendarDayIndex.group indexes overlapping events onto every visible day with an exclusive end date.

ChatMessage persists a conversation locally only. It carries toolSummaries, rendered as activity chips, and eventIDsData, the ids of the events a reply was about. Ids rather than the events, on purpose: an event can be moved or deleted after the sentence about it was written, and a card showing what was true last Tuesday is worse than no card. They are re-resolved against the calendar when the conversation reopens through CalendarStore.events(withIDs:), so a deleted event simply stops appearing. ChatStore.append takes an at date for tests, because appends in a tight loop share a wall-clock timestamp and the recency ordering must not be flaky over ties.

21.8Notes

Notes are the largest model family and the only one synced to Supabase. Four persisted models, two derived, and a set of value types.

Two fields on NoteDocument carry whole features. The Inbox is filedAt and nothing else: every page has a bucket from the moment it is created, so a bucket cannot answer "has anyone decided where this goes", and the stamp is written by filing, never by editing, so a page you keep writing in stays in the Inbox until you decide otherwise. The Archive shelf is archivedAt, a flag rather than a bucket, so a restored page returns to the shelf it came from instead of needing to be refiled. Every field carries a default because this model will keep growing and rule two applies.

NoteBlock is a value type with a kind (paragraph, three headings, bulleted, numbered, todo, quote, callout, code, divider, sketch), text, isChecked, indent 0 through 4, optional drawing and sketchHeight for sketch blocks, and optional dueDate and goalID for to-dos. The whole array is stored as JSON. A block editor's trick is that the document is a list of small typed pieces rather than one string with formatting hung off ranges, so splitting, merging and turning a paragraph into a to-do all become list operations, and none of them can corrupt the others. Nesting is purely visual: a nested item is still a sibling in the array.

NoteBlockParser.shortcut resolves Notion-style typed prefixes, and the order of its candidates is the whole correctness argument: - [ ] starts with - , so checking kinds in declaration order would turn every to-do typed by hand into a bullet reading [ ] whatever. Longest match first is the only rule that cannot be broken by adding a kind later. NoteLinkScanner finds [[targets]], preserving case in the text and folding it at lookup. NoteBucket is the four PARA shelves as an enum rather than four folders a person could rename into meaninglessness, with research standing in for PARA's vaguer "resources". NoteAccent is eight named pastels, colour living in the design system so that Persistence never imports SwiftUI and swift test keeps running on macOS.

The value types: NoteCardSnapshot (a page flattened for a card, with doneCount, taskCount, hasInk, linkCount), NoteFolderSnapshot (a sidebar row with its children already attached, built once in the store rather than by the view walking a flat list on every render), NotesSnapshot (everything the sidebar needs in one read), NoteBacklink, NoteStreamChip and NoteStream (a chip resolves to either cards or tasks, because flattening to-dos into cards would lose which page each came from). NoteEvidence is the bridge the monthly close reads: journal dates for the journalling streak, and project statuses where a page with to-do blocks reports what those blocks say rather than its own menu property.

21.9Sectors

LifeSector names the nine sectors: family, romance, soul, friends, growth, money, mission, body, mind. Raw values are written to the store, so a case may be added but never renamed, since a rename orphans every score recorded against it. boardOrder is kept separate from allCases so adding a sector cannot silently reshuffle the grid.

// LifeOSKit/Sources/Persistence/SectorScore.swift
@Model
public final class SectorScore {
    public var sectorRaw: String
    /// Always the first day of the month being scored.
    public private(set) var month: Date
    /// What the rule said, or nil when there was no evidence at all.
    public var proposedScore: Int?
    /// What the person said. Nil until they pass through this sector.
    public var userScore: Int?
    public var closedAt: Date?
    /// The rows behind the proposal, frozen at close time.
    public var evidenceData: Data?
}

Both scores are kept permanently, because the distance between what the rule computed and what the person felt is the most interesting number here, and averaging them would erase it. The evidence is archived rather than recomputed: change a goal in March and February's reasoning must still read the way it did in February. month is private(set) and normalised through Date.startOfMonth on the way in, so closing August on 3 September files the score under 1 August.

CheckInAnswer stores one answer to one question for one sector-month, as text whatever the question's shape, because its value is comparison against last month rather than arithmetic. Evidence is the one shared scoring rule: a weighted mean of EvidenceRows on a 0...10 scale, clamped on the way in rather than trusted, with proposedValue nil when there is nothing to go on. Deliberately not zero: a sector with no evidence has not been judged badly, it has not been judged. proposedScore is expressed in terms of proposedValue so a projection sorting on the unrounded value can never rank against a different number than the one shown.

21.10The workout catalog and bookmarks

CatalogVideoRow is the wire row, snake_case on the server and decoded by the client; CatalogVideo is the cached copy with #Unique([\.youtubeID]), the same ten fields plus cachedAt, a computed thumbnailURL on i.ytimg.com and durationMinutes. The server is the source of truth: CatalogStore.upsert replaces the whole set, updating matches, inserting new rows and deleting absent ones, so a video pulled from the catalog disappears here. It builds its lookup with uniquingKeysWith rather than uniqueKeysWithValues, because a trap on a malformed response is a crash where keeping the last row is not.

WorkoutBookmark is a person's mark on a video: saved, scheduledFor (a calendar day, never a timestamp), or both. One row per video and absent means neither, so BookmarkStore.toggleSaved and schedule both delete a row that ends up neither saved nor scheduled. The store reads row.saved into a local before the delete, because a deleted model is not a thing to ask questions of, even one it answered correctly a line earlier. Bookmarks are local only.

21.11Accounts, scopes and the container

Until 27 August 2026 the app had one store file, no owning column on any model, and one keychain slot. A second person signing in on the same device inherited the first person's notes, journal, chat, money and health data. The server was never the problem, since Row Level Security scopes every row to auth.uid(); the device was.

UserScope is the answer: a struct holding the Supabase user id, with storeURL(base:) under Application Support in a directory named for the account, and defaultsSuiteName for a UserDefaults suite of the account's own. Isolation is by file rather than by an owner column on forty models, because a column means a predicate on every read, and a predicate forgotten once is a leak that looks like working software. A separate file cannot leak: the rows are not there to be read. The defaults suite matters as much as the store: sync cursors, connection tokens and "have they seen the tour" were all in the shared suite, and a second account would have resumed a notes pull from the first account's cursor and silently missed every row written in between. Device preferences (appearance, the assistant's voice, which engine answers) stay in standard on purpose, because they belong to the phone rather than to whoever is signed in on it.

// LifeOSKit/Sources/Persistence/LifeOSContainer.swift
public static let schema = Schema([
    DailyMetrics.self, UserGoals.self, WorkoutRecord.self, SleepRecord.self,
    WhoopRawRecord.self, PlanEntry.self, HabitTick.self,
    MoneyEntry.self, MoneyAccount.self, SpendBucket.self,
    SectorScore.self, CheckInAnswer.self, CalendarEvent.self, ChatMessage.self,
    NoteDocument.self, NoteFolder.self, NoteTask.self, NoteLink.self,
    CatalogVideo.self, WorkoutBookmark.self,
])

Twenty models. LifeOSContainer.make(for:) opens one account's store; make(inMemory:) serves tests and previews. Two adoption paths move a store rather than copy it, which is atomic and costs the same for one note or a thousand: adoptLegacyStore(into:) moves SwiftData's default.store into the first account that signs in after the upgrade, so scoping the store never looks like the app deleting a year of notes, and adopt(_:into:) hands one scope's store to another. Both refuse when the destination already has a store, because choosing which of two rows wins for every model in the schema has no obviously right answer, and both move the -wal and -shm files alongside the database, since moving the database alone leaves the most recent writes behind in a log the new file cannot find.

AccountDeviceAccess records that device permissions are app-wide in iOS but permission to import that device's calendar into an account must also be granted by that account. SampleMetricsPurge deletes every DailyMetrics row once, removing the sixty days of invented history a fresh install used to seed. The seeded values did more than look wrong: most Health fields were fill-gaps-only, so every seeded day refused the real reading for as long as it existed. Only the derived table is removed; workouts, sleep and Whoop records are left and a resync rebuilds the days.

21.12The stores

Every store is a @MainActor value type over a ModelContext, with the calendar injected so tests are not at the mercy of the machine's locale. The pattern is MetricsStore's, and every later store copied it.

MoneyIngesting is the write side of MoneyStore as a protocol, so PlaidSync can be tested against a store that fails on demand. Failure is the interesting case: the cursor must not move when the ingest did not happen. CalendarStore.freeSlots has a nonisolated static pure core that merges busy intervals, subtracts them from the window and drops gaps shorter than the requested duration; all-day events do not block time, because "Anniversary" is context, not a meeting.

Three one-time migrations sit beside the stores. PlanNoteMigration is described above. NoteIndexMigration stamps every page that predates the Inbox as filed, then builds the index, idempotent through a marker in the account's own defaults suite; the marker is only spent when there was history to interpret, because on a fresh install the first launch runs before the first pull and consuming the one-shot then would strand every page that arrives afterwards in the Inbox. NoteIndexer is the only writer of NoteTask and NoteLink. It deletes and reinserts rather than diffing, never saves on its own because it runs inside the transaction already changing the document, and fetches rows to delete rather than using the batch delete(model:where:), because the batch form runs against the persistent store and cannot see rows inserted earlier in the same unsaved transaction. rebuildAll is the opposite: the batch form is correct there because everything is cleared before anything is inserted. It builds the folded title index once for the whole pass, since building it per document made a rebuild quadratic in the size of the library.

21.13Adding a field without breaking installed stores

On 15 September 2026 the goals row gained equipmentRaw: [String], mandatory and with no default. SwiftData refused to migrate any store written before it. The container never opened, the shell had no account to show, and the app sat on the signed-in spinner. The error, when it surfaces at all, reads "Validation error missing attribute values on mandatory destination attribute". The fix was one character group, = [], and a test that holds the added columns to the rule:

// LifeOSKit/Tests/PersistenceTests/SchemaMigrationTests.swift
@Test func fieldsAddedToTheGoalsRowHaveDefaults() throws {
    let goals = try #require(LifeOSContainer.schema.entities.first { $0.name == "UserGoals" })
    let added = ["trainingGoal", "equipmentRaw", "sessionMinutes"]
    for name in added {
        let attribute = try #require(goals.attributesByName[name], "missing \(name)")
        #expect(attribute.isOptional || attribute.defaultValue != nil,
                "\(name) has no default and is not optional")
    }
}

The rule, and how the models already follow it: whoopRecoveryIsCalibrating: Bool? and SleepRecord.isNap: Bool? are optional rather than defaulted Bools; ChatMessage.eventIDsData: Data? and WorkoutRecord.setsData: Data? are optional JSON; every field on NoteDocument and NoteFolder carries an initial value. When you add a field to a model that has rows on somebody's phone, make it optional or give it a default, and add its name to the list in that test.

Why the app hangs instead of crashingAccountSession opens the container for the current account after the session is restored. A container that throws leaves the session without a store, and the shell renders its waiting state until one arrives. Nothing is wrong with the shell; the failure is a step earlier, which is why the symptom looks like a network problem and is not.

21.14Study notes

Read in this order

  1. LifeOSKit/Sources/Persistence/DailyMetrics.swift, for the rule and the two bags.
  2. MetricsStore.swift, for the upsert-as-merge pattern every store copies.
  3. GoalEvaluation.swift and Streak.swift, the shortest pure logic in the app.
  4. MoneyEntry.swift, for a type that carries its own sign convention.
  5. NoteDocument.swift then NoteBlock.swift, for JSON-in-a-column and the parser order argument.
  6. NoteIndexer.swift, for the fetch-versus-batch-delete distinction.
  7. UserScope.swift and LifeOSContainer.swift, for per-account stores and the two adoption moves.
  8. Tests/PersistenceTests/SchemaMigrationTests.swift, then add a field to a model in a scratch branch and watch it fail.

Check yourself

  • Why is savingsRate nil rather than zero when there is no income? Because undefined is not zero; rendering 0 percent would be a confident wrong number.
  • What breaks if NoteIndexer.reindex used context.delete(model:where:)? A second reindex in the same unsaved transaction would duplicate rows, because the batch delete cannot see rows inserted earlier in that transaction.
  • Why is LifeSector a case you may add but never rename? Raw values are stored; a rename orphans every score already recorded against it.
  • Why does the store move -wal and -shm with the database? SQLite keeps the most recent writes in the write-ahead log; moving the database alone leaves them in a file the new location cannot find.
  • How does the Inbox know a page is unfiled? filedAt is nil. Buckets cannot answer, because every page has one from creation.
  • Why does MoneyStore.ingest fetch all ids up front? externalID is unindexed and this runs on the main actor; one scan per page instead of one per row.
