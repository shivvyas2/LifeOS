Chapter nine

9The Watch companion

When an Apple Watch is paired, the watch owns the workout and the phone shows it. Heart rate, energy, reps and sets cross the mirrored HealthKit session once a second; pause, resume, end and the rep buttons cross back. A pure rep counter on wrist acceleration fills the slot the HUD reserved, labelled "auto" because its accuracy on real movement is still unmeasured.

9.1Intent

Before this slice the watch app was a read-only dashboard: steps, sleep and movement mirrored from the phone, with no way to start, see or end a workout. A person wearing a watch and no strap saw a timer on the phone and no beats, because the phone only ever received heart rate from a Bluetooth strap. And strength sessions showed a "reps" slot that never filled.

Working backwards

Tap Begin on the phone with a watch on your wrist and the phone says "Asking your Apple Watch…". Within a few seconds Almanac opens on the watch with the workout running, and the phone's rings show the watch's heart rate. Or start from the watch: choose Strength, and the phone's lock screen shows the session before you have touched the phone. Curl, and the rep count on your wrist climbs on its own; tap +1 if it missed one, tap −1 if it counted an extra. Pause on either device and both pause. End on either and exactly one workout lands in Health, saved by the watch.

Who owns the session?

Whichever device created the HKWorkoutSession. When a watch is paired, installed and Health saving is on, the watch does, and it alone writes the workout to Health. The phone never creates a session of its own for a watch-owned workout, so nothing is saved twice. When no watch answers within ten seconds, the phone path from Chapter 8 runs unchanged.

Why is the rep count labelled "auto" on the watch and not on the phone?

Only a watch session counts reps by itself. On a phone-only strength session every rep is a tap, and calling that "auto" would invert the honesty label.

What has actually been verified on a real watch?

Nothing yet. The rep counter is pinned by tests on synthetic signals, the wire format and the recorder's watch path are pinned by tests and simulator checks, and both targets build. The watch simulator cannot run a real workout session, so the watch screen is verified by compilation only. Five hardware checks and two recovery-behaviour checks are recorded as pending in the QA report, to be run by the author on his own phone and watch.

Why Motion is its own package target

The watch target links two package products, AppSurfaces and Motion, and neither depends on anything. CoreMotion stays in the watch target: the controller feeds CMDeviceMotion.userAcceleration samples at 50 Hz into the pure counter. That is what lets the algorithm be tuned against synthetic signals on macOS, and later against a recording from hardware, without a watch in the loop.

9.3Model

The wire format

// LifeOSKit/Sources/AppSurfaces/WatchWire.swift
/// What the watch sends the phone over the mirrored session's data channel.
/// Every reading is optional: a packet without heart rate says "no reading",
/// never zero. `completedSets` holds reps per finished set, oldest first.
public struct WatchPacket: Codable, Equatable, Sendable {
    public var kind: String = WatchWire.packetKind
    public var v: Int = WatchWire.version
    public var sentAt: Date
    public var heartRate: Int?
    public var heartRateAt: Date?
    public var energyKcal: Double?
    public var reps: Int?
    public var setIndex: Int?
    public var completedSets: [Int]?
}

public enum PhoneCommand: String, Codable, Sendable {
    case configure, pause, resume, end, nextSet, addRep, removeRep, discard
}

public struct PhoneCommandEnvelope: Codable, Equatable, Sendable {
    public var kind: String = WatchWire.commandKind
    public var v: Int = WatchWire.version
    public var command: PhoneCommand
    public var sentAt: Date
    public var maxHeartRate: Int?      // sent once with .configure
}

Both shapes carry a version, currently 2, and a kind. The version gate is strict: a packet with an unknown v is ignored, never guessed at. The kind field exists because the two shapes otherwise share every required key (v and sentAt), and a command would decode as an empty packet. A test pins that a command is never read as a packet. 

// LifeOSKit/Sources/AppSurfaces/WatchWire.swift
public static func packet(from data: Data) -> WatchPacket? {
    guard let packet = try? decoder.decode(WatchPacket.self, from: data),
          packet.kind == packetKind, packet.v == version else { return nil }
    return packet
}

Dates are encoded as seconds since 1970. heartRateAt is when the reading was measured, not when the packet was sent, so effort accrual on the phone credits the right seconds.

The two commands that end a session

end finishes the workout and saves it to Health on the wrist. discard throws it away. The distinction is the fix for a critical finding in the final review: the phone originally sent end when it refused a mirrored session or the person discarded, which would have written a stub workout into Health for a session the person had thrown away.

The rep counter

// LifeOSKit/Sources/Motion/RepCounter.swift
public struct RepCounter: Sendable {
    public struct Sample: Sendable { public var t: TimeInterval; public var x, y, z: Double }
    public let settleSeconds: Double      // 1.0
    public let minPeriod: Double          // 0.6
    public let maxPeriod: Double          // 4.0
    public let threshold: Double          // 0.15
    public private(set) var reps: Int = 0
    private let fastTau = 0.15
    private let slowTau = 2.0
    private var axis: Vec?
    private var riseT: TimeInterval?
    private var refractoryUntil: TimeInterval = -.infinity

    /// Feed one sample; returns true when this sample completed a rep.
    public mutating func add(_ sample: Sample) -> Bool
    public mutating func reset()
}

The algorithm, as it stands after two corrections during implementation:

  1. Each axis is smoothed twice with exponential moving averages: a fast one (0.15 s) follows the movement, a slow one (2 s) follows posture and gravity drift. Their difference is a vector d.
  2. The first lift whose magnitude passes the threshold, and is still growing, fixes the axis for the set. The rising condition is the second fix: settling can end mid-fall, and locking the axis onto a fading swing spent the first cycle on a half swing and undercounted by exactly one in two of six tests.
  3. The signal s is d projected onto that axis. It is signed: a rep is a swing, not a rectified bump. The first version rectified the signal with sqrt(x²+y²+z²), and a fall crossing could then structurally never follow a rise.
  4. A rep is a rise of s above +threshold followed by a fall below −threshold, with the half cycle between them lasting between 0.3 and 2.0 seconds.
  5. Nothing counts during the first second after reset(), the person picking up the weight, and each counted rep starts a 0.3-second refractory window.
Calibration is synthetic Every constant is pinned by tests on 50 Hz sine waves with white noise. Ten cycles at 1 Hz and 0.4 g count ten; 0.08 g counts nothing; 3 Hz jitter counts nothing; one ten-second push counts nothing; nine cycles whose first second is swallowed by settling count eight. Real-world accuracy is unknown until hardware. The "auto" label and the +1 and −1 buttons are the honesty.

9.4ViewModel

On the wrist

// AlmanacWatch/WatchWorkoutController.swift
@MainActor @Observable
final class WatchWorkoutController: NSObject, HKWorkoutSessionDelegate, HKLiveWorkoutBuilderDelegate {

    /// adds to them instead of overwriting them.

start(_:) flips state to .starting synchronously before its first await, so a second Start tap during the authorisation prompt cannot open a second session. It requests Health sharing for workouts, heart rate and energy, creates the session and builder, begins collection, then calls startMirroringToCompanionDevice(). A mirroring failure is recorded, not fatal: the watch still records and saves; the phone simply does not see it. For strength it starts device motion at 50 Hz. 

// AlmanacWatch/WatchWorkoutController.swift
motion.startDeviceMotionUpdates(to: .main) { [weak self] data, _ in
    guard let self, let data else { return }
    MainActor.assumeIsolated {
        guard self.state == .running else { return }
        let acceleration = data.userAcceleration
        if self.counter.add(RepCounter.Sample(t: data.timestamp, x: acceleration.x, y: acceleration.y, z: acceleration.z)) {
            self.reps = self.counter.reps + self.manualReps
            self.sendPacket(force: true)
        }
    }
}

.main is the main-thread queue, so the handler is already on the main actor; assumeIsolated keeps every sample in order rather than scattering fifty hops a second through Task. The manual tally is separate from the counter's so that an automatic rep adds to the taps instead of overwriting them, which was the critical bug the review found. removeRep() spends the manual tally first and then offsets the automatic one, never below zero, and does nothing while the count is unknown, because a dash must not become a zero.

The clock is kept the way ActivitySessionState keeps it on the phone: a pause banks accumulated, a resume starts runningSince. The screen's timer is anchored at runningSince - accumulated, so it reads the workout's elapsed time rather than the time since this run began.

Ending has two paths, and they must never be confused. end() stops the activity; the .stopped delegate callback then ends collection, calls finishWorkout(), and the .ended callback resets. discard() detaches the delegates first, so no late .ended re-enters the teardown, then discards the builder and ends the session without finishing it. recover(), wired from handleActiveWorkoutRecovery(), adopts a session still active in HealthKit after watchOS relaunched the app; a session already stopped is settled at once, and a recovered strength session restarts motion with an unknown rep count rather than a zero.

On the phone: the bridge

// LIfeOS/App/Surfaces/WatchSessionBridge.swift
/// Owns the workout session mirrored from the watch. One per app: HealthKit
/// hands the session to whichever handler is installed at launch, so the
/// bridge is installed by the app delegate and the recorder subscribes.
@MainActor
final class WatchSessionBridge: NSObject, HKWorkoutSessionDelegate {
    static let shared = WatchSessionBridge()
    private(set) var session: HKWorkoutSession?
    private(set) var placeholderSessionID: UUID?
    private var dropping = false
    var onSession: ((HKWorkoutSession) -> Void)?
    var onPacket: ((Data) -> Void)?
    var onStateChange: ((HKWorkoutSessionState, Date) -> Void)?
    var hasSession: Bool { session != nil && !dropping }

    static func installMirroringHandler() {
        healthStore.workoutSessionMirroringStartHandler = { session in
            Task { @MainActor in
                let bridge = WatchSessionBridge.shared
                let unattended = bridge.onSession == nil
                bridge.adopt(session)
                if unattended { bridge.requestPlaceholderActivity(for: session) }
            }
        }
    }

The handler is installed from PushService's app delegate at launch, before any session can arrive. The placeholder matters for a workout started on the wrist: HealthKit launches the phone app in the background with no scene and so no recorder. The Live Activity has to be requested inside that launch, so the bridge asks for it itself, keeps the id, and the recorder's timer adopts that id when a screen finally attaches, so the card already on screen is updated rather than duplicated. 

// LIfeOS/App/Surfaces/WatchSessionBridge.swift
/// Whether a watch could take the session right now.
static var watchAvailable: Bool {
    guard WCSession.isSupported() else { return false }
    let wc = WCSession.default
    // Not `isReachable`: on iOS that is true only while the watch app is
    // already in the foreground, which is never the case for a person
    // tapping Begin on the phone.
    return wc.activationState == .activated && wc.isPaired && wc.isWatchAppInstalled
}

/// Sends a last command and drops the session only once it has left, in
/// the send's completion handler: releasing the session in the same
/// run-loop turn can cancel the send before the watch ever hears it.
func end(after command: PhoneCommand) {
    guard let session, let data = try? WatchWire.encode(PhoneCommandEnvelope(command: command, sentAt: .now)) else {
        end(); return
    }
    dropping = true
    session.sendToRemoteWorkoutSession(data: data) { _, _ in
        Task { @MainActor in self.end() }
    }
}

dropping exists because hasSession stays true through that window, and without it the next Start would refuse the hand-off against a session already on its way out.

On the phone: the recorder's watch half

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder+Watch.swift
func handOffToWatch() async -> Bool {
    guard saveToHealth, watchAvailable(), let watch, !watch.hasSession else { return false }
    // Ask on the phone first. Authorization is shared with the paired
    // watch, so without this the first prompt a person ever sees is on the
    // wrist, while the phone is already counting down its ten seconds.
    guard await healthAuthorizationForHandoff() else { return false }
    let configuration = HKWorkoutConfiguration()
    configuration.activityType = selection.healthType
    source = .watch
    notice = Self.waitingForWatch
    try? await WatchSessionBridge.startWatchApp(configuration)
    let deadline = Date.now.addingTimeInterval(watchHandoffTimeout)
    while Date.now < deadline, watch.session == nil, active {
        try? await Task.sleep(for: .milliseconds(100))
    }
    guard active else { return true }
    if let mirrored = watch.session {
        if timer == nil { adoptMirroredSession(mirrored) }
        if notice == Self.waitingForWatch { notice = nil }
        return true
    }
    source = .phone
    notice = "Apple Watch did not answer. Recording on iPhone."
    return false
}

The hand-off is offered only when the workout is meant for Health, since the watch writes it there; a person who turned Health saving off keeps the phone. No timer starts until the watch answers, so nothing counts a session the watch may never take, and busy keeps the button reading "Starting…".

adoptMirroredSession handles both arrivals: the answer to a hand-off, and a session the person started on the wrist. If the phone is already recording its own session it refuses with a notice and sends discard. Otherwise it builds a fresh timer starting where the watch started, adopting the bridge's placeholder id if there is one, ends any stray Live Activity, stops the strap (the watch streams its own heart rate; two feeds would double every reading into the effort accrual), sets recordingHealth false so the draft never claims a Health session of the phone's own, and sends configure with the person's max heart rate so the watch can show a zone chip. 

// LIfeOS/Features/Activity/ViewModel/ActivityRecorder+Watch.swift
func receiveWatchPacket(_ data: Data) {
    guard active, hasSession, source == .watch, let packet = WatchWire.packet(from: data) else { return }
    // The counts are applied before that reading, so the one refresh carries
    // this packet's reps rather than the previous packet's.
    let refreshes = packet.heartRate != nil && packet.heartRateAt != nil && isRunning
    if let energy = packet.energyKcal { self.energy = energy }
    if selection == .strength {
        if let value = packet.reps { reps = value }
        if let value = packet.setIndex { setIndex = value }
        if let value = packet.completedSets { completedSets = value }
    }
    if let bpm = packet.heartRate, let at = packet.heartRateAt { receiveHeartRate(bpm, at: at) }
    if !refreshes { persistReading(at: packet.sentAt) }
}

Heart rate goes through the same receiveHeartRate as a strap reading, so effort accrual, throttling and the Live Activity stay one path. The ordering comment records a bug the checks found: a packet carrying both a heart rate and a rep change once published the previous rep count, because the single readout refresh ran inside receiveHeartRate before the counts were applied.

addRep, removeRep and nextSet each have two paths: on a watch session they send the command and wait for the echo packet; on a phone session they count locally. Pause, resume and finish likewise send commands for .watch and let the mirrored session's state change drive the timer, exactly as the phone's own session delegate does.

On the phone, the surfaces from Chapter 8 grew a rep slot: the rings show the count and "auto" or "reps"; the tiles gain a Reps tile captioned "Counted from your wrist · auto" or "Tap +1 for each rep" and, after a set, "Earlier sets: 2 reps"; the Dynamic Island's compact trailing shows reps instead of the timer for strength; the lock screen's third tile shows the set and reps instead of calories. The connections panel says "Apple Watch is recording this session", "Apple Watch ready", or "Apple Watch not nearby".

9.6How it works

Step by step: started on the phone

  1. Begin, with Health saving on and a paired watch. The phone asks for its own Health authorisation first, because authorisation is shared with the paired watch and the first prompt should be on the phone.
  2. HKHealthStore.startWatchApp(toHandle:) launches Almanac on the watch with the configuration. The phone says "Asking your Apple Watch…" and polls the bridge every 100 ms for up to ten seconds.
  3. The watch delegate's handle(_:) passes the configuration to the controller (or parks it in pendingConfiguration if the scene's task has not run yet). The controller starts the session and begins mirroring.
  4. HealthKit calls the phone's workoutSessionMirroringStartHandler. The bridge adopts the session and calls onSession; the recorder's adoptMirroredSession builds the timer from the watch's start date and sends configure.
  5. Packets arrive once a second and on every rep. Heart rate accrues effort; reps and sets update the readout; the rings, tiles and Live Activity refresh through the Chapter 8 paths.
  6. Pause on the phone sends pause; the watch pauses its session; the mirrored state change comes back through the bridge and pauses the phone's timer. Pause on the watch takes the same last two steps.
  7. Finish on the phone sends end through end(after:) and calls saveFinished(), which writes the local record with the sets and never touches a builder. The watch ends collection, finishes the workout into Health, and resets.

Started on the wrist

Steps 4 to 7 are the same. The difference is step 3: there is no phone scene yet. HealthKit launches the phone app in the background, the bridge adopts the session unattended and requests the placeholder Live Activity, and when the person opens the phone the recorder attaches, finds watch.session already held, adopts it, and takes over the card by its id.

Ownership rules, stated once

  • The watch is offered the session only when saveToHealth is on.
  • The phone never creates a Health session for a .watch workout, and never writes an HKWorkout for one.
  • If the phone is already recording when a mirrored session arrives, it keeps its own and discards the mirrored one. It never merges, and it never ends it, since ending means saving.
  • A finished, saved timer is the resting Done screen; a workout started on the wrist then is a new one, not a continuation.
  • A .watch draft restores with Health saving on, asks recoverActiveWorkoutSession, hands anything returned to the bridge, and otherwise keeps the timer and waits for the next packet.

9.7Performance and cost

  • Packets are rate-limited on the watch. sendPacket(force: false) sends at most once a second from the builder's statistics callback; a rep forces one immediately because a rep is what the person is watching.
  • No strap and watch at once. Adopting a mirrored session stops the Bluetooth stream, so two feeds cannot double the effort accrual, and the radio is not held open for nothing.
  • Motion samples never leave the main actor. assumeIsolated on the .main queue keeps 50 samples a second in order without 50 task hops.
  • The counter is O(1) per sample. Two EMAs, one projection, a few comparisons. It keeps no history.
  • Motion stops on every end. end, discard, a failed start and the delegate's failure path all call stopMotion(), so the accelerometer is not left running after a session.
  • One placeholder at a time. A second session arriving before the recorder adopts the first cannot leave two cards on screen.
  • The hand-off costs nothing when there is no watch. watchAvailable is three synchronous reads of WCSession; a person with no watch never waits.
  • Nothing leaves either device. The mirrored session's data channel is HealthKit's own, device to device. No server, no push.

Check yourself

  • Why does watchAvailable not read isReachable? On iOS it is true only while the watch app is in the foreground, which is never so when the person taps Begin on the phone; startWatchApp exists to launch it.
  • Why is the session dropped inside the send's completion handler? Releasing it in the same run-loop turn can cancel the send before the watch hears it.
  • Why does the phone ask for Health authorisation before offering the watch? Authorisation is shared; without it the first prompt lands on the wrist while the phone is counting down.
  • What does kind prevent? A command decoding as an empty packet, since the two shapes share every required key.
  • Why are manual and automatic reps tracked separately? So an automatic rep adds to the taps instead of overwriting them.
  • Why is discard a separate command from end? On the wrist end means finish and save; sending it for a refused session would write a stub into Health.
