Chapter three

3Design system

Sixteen feature folders have to read as one app. That happens because they share a small set of primitives and differ by exactly one variable, the module hue, rather than because each screen was designed carefully on its own. This chapter is the inventory of those primitives and the three scales they are built on: colour, type and space.

Everything here lives in LifeOSKit/Sources/DesignSystem, a target with no dependencies that also builds for macOS. That second fact shapes more of the code than it looks: it is why colours are explicit light and dark pairs rather than UIKit dynamic colours, why the width class is the package's own enum rather than UserInterfaceSizeClass, and why the six-box code field keeps its keyboard configuration behind an #if os(iOS). The price is a few lines per component; the return is swift test running from a terminal in seconds with no simulator.

3.1Principle

The hub is neutral; the domains are tinted. Today is a warm off-white canvas. Every domain screen is the same canvas with a whisper of its hue washed in across the top 260 points. This is a change from the first edition, where domain screens were saturated-at-top gradients: the restyle kept the hue as a tint rather than a paint job, so cards became solid white with one soft shadow instead of frosted glass fighting a gradient. The two visual languages resolved into one hierarchy, and adding a module is still a token, not a design exercise.

Three rules hold the whole thing together. The accent never varies by module and has exactly two meanings: today, and act. Numerals are the rounded face and words never are. And a missing value is a dash, drawn by the component, never by the screen.

Colours are AdaptiveColor pairs, resolved explicitly by the consuming view with token.resolve(scheme). It is one more line per use than a dynamic colour, and it is the line that makes TokensTests possible: alertColorsDifferByScheme and fabFillAndGlyphStayOppositeInBothSchemes read both halves of a pair and compare them, which a UIKit dynamic colour would not let a terminal test do.

3.3One type scale

Before Typography.swift existed there were 376 hand-written .system(size:weight:) calls across 28 distinct sizes between 9 and 104, and three of those sizes accounted for 178 of them. Nobody chose that; it is what happens when every screen picks its own number, and the drift is invisible until two screens sit side by side. The scale has nine text steps and three numeral steps, fewer than the app had, on purpose: a scale only does its job if the steps are far enough apart that picking the wrong one is obvious. 

// LifeOSKit/Sources/DesignSystem/Typography.swift
public enum LifeOSType {
    public static let eyebrow      = Font.system(size: 11, weight: .semibold)   // tracked uppercase markers
    public static let caption      = Font.system(size: 12, weight: .regular)
    public static let label        = Font.system(size: 13, weight: .medium)     // dense rows, chips
    public static let secondary    = Font.system(size: 15, weight: .regular)
    public static let rowTitle     = Font.system(size: 15, weight: .semibold)
    public static let body         = Font.system(size: 17, weight: .regular)    // reading text
    public static let sectionTitle = Font.system(size: 20, weight: .semibold)
    public static let screenTitle  = Font.system(size: 24, weight: .bold)
    public static let display      = Font.system(size: 34, weight: .bold)       // one per screen at most

    /// The date on the hub, and nothing else. Its tracking travels with it.
    public static let masthead = Font.system(size: 104, weight: .bold)
    public static let mastheadTracking: CGFloat = -5

    public static let numeral      = Font.system(size: 28, weight: .bold, design: .rounded)
    public static let numeralLarge = Font.system(size: 44, weight: .bold, design: .rounded)
    /// The only place a size may be passed in. Hero numerals size to their space.
    public static func numeral(_ size: CGFloat, weight: Font.Weight = .bold) -> Font
}

Two families, each with exactly one job. Text is the system sans, always. Numerals are rounded, and only numerals. Rounded digits are easier to read at a glance, which is why the money screen reached for the face in the first place, and a rounded label next to a sans label is the drift the scale exists to stop. A serif was briefly the notes tab's title face and is deliberately gone: it looked right on that one screen and wrong beside every other.

The masthead is the one step outside the pattern and the reason it exists is instructive. The hub's date was flattened into display to fit the scale, which took it from 104 to 34 points and turned the masthead the whole screen is built around into an ordinary heading. A scale that cannot express the biggest thing in the app is missing a step rather than being violated by one, so the step was added, with its negative tracking attached, because a caller who took the font without the tracking would get a subtly wrong masthead.

Two companions keep the scale from being bypassed. LifeOSType.UIKitScale restates the same sizes as UIFont for the note editor's text view, so changing a step changes both. LifeOSTextRole and the .lifeOSText(_:) modifier give the same steps Dynamic Type behaviour through @ScaledMetric, so screens can adopt accessibility sizes one at a time without touching the masthead or the numerals.

3.4Space, radius and the glass panel

// LifeOSKit/Sources/DesignSystem/Space.swift
public enum Space {
    public static let half: CGFloat = 4     // the only sub-grid value, for optical nudges inside a control
    public static let x1: CGFloat = 8
    public static let x2: CGFloat = 16
    public static let x3: CGFloat = 24
    public static let x4: CGFloat = 32
    public static let x5: CGFloat = 40
    public static let x6: CGFloat = 48
    public static let x8: CGFloat = 64
    public static let x10: CGFloat = 80
}

public enum Radius {
    public static let small: CGFloat = 12
    public static let medium: CGFloat = 20
    public static let large: CGFloat = 28
    public static let pill: CGFloat = 999
}

Named by multiples rather than by role, because roles drift (someone always needs a "medium-large") while multiples cannot. Radii sit on the same grid so cards nest without optical drift. The same file holds GlassPanel, PrimaryButton and SecondaryButton. GlassPanel is where the app takes Liquid Glass from the system rather than imitating it with a material: one .glassEffect(.regular, in:), so every frosted panel in the app gets real refraction and highlights from one place, and the notes drawer, the profile's frosted panel over the photo and the coach's canvas all read as the same surface.

3.5Layout metrics: phone and iPad

Every number that varies with width lives in LayoutMetrics, for the same reason Space exists. The app distinguishes exactly two widths and maps the platform's size class onto them once, in RootView, so the package never imports UIKit's enum. 

// LifeOSKit/Sources/DesignSystem/LayoutMetrics.swift
public static func metrics(for width: LayoutWidth) -> LayoutMetrics {
    switch width {
    case .compact:
        LayoutMetrics(gutter: 20, sectionSpacing: 22,
                      maxContentWidth: .infinity, heroScale: 1.0,
                      fabBottomInset: 72, contentBottomInset: 130,
                      railInset: 0,
                      statColumns: 2, tileColumns: 3, isRegular: false)
    case .regular:
        LayoutMetrics(gutter: 32, sectionSpacing: 30,
                      maxContentWidth: 1060, heroScale: 1.3,
                      fabBottomInset: 28, contentBottomInset: 32,
                      railInset: 112,
                      statColumns: 4, tileColumns: 6, isRegular: true)
    }
}

contentBottomInset13032Compact clears the floating pill bar, which overlaps the scroll view. Regular has a side rail instead, and the old inset left a band of dead space.

3.7Motion pieces

Four components animate, and each earns it by being made of the app's own vocabulary rather than decoration dropped on top.

  • DotBloom is the onboarding animation: a month of dots filling in one by one with a spring per column. The first thing a new person sees is the grid they will read every morning, so the animation teaches the interface instead of entertaining. It respects reduce motion.
  • ScanlineCat is the intro's greeting, a cat drawn as horizontal scanlines or as dots on the grid's own pitch. All geometry is in ScanlineCatSilhouette (three primitives: ellipse, rect, triangle, in a unit box) and ScanlineSlicer (which cuts shapes into merged x-spans at a given y, in closed form, so slicing costs no rasterisation). Both are pure and tested; ScanlineSlicerTests is the largest suite in DesignSystemTests at 443 lines. The view only decides colour, timing and how the cat assembles on appear: rows drift in from the side they are nearest, the face goes on last and solid because a striped eye cannot read as an eye.
  • GlassGlobe is the coach's orb: a Siri-like glass slime, clear and silver, morphing on a TimelineView at 30 frames per second. Audio intensity makes it breathe. Hue is kept out of it; the colour is the light on glass.
  • SlateAurora is the coach's backdrop, a three-by-three MeshGradient from onyx through blue slate to an alabaster bloom. Fixed rather than scheme-resolved, because the coach is an immersive dark surface in both appearances.

The live gradient and push-state tints

A running session paints the recovery blue from the top to near white at the bottom, on the in-session hero, the lock screen Live Activity and the Dynamic Island alike, so the numbers read as the same data wherever they appear. On that gradient the three push colours say how hard the session is pushing against the day's capacity: green is easy going, amber is near the ceiling, red is over it. They are the same in both schemes because the gradient is. Chapter 8 has the maths that picks one.

3.8Dark mode

Every hue has a dark variant, deep top and near-black bottom, and every surface token has both halves. These were defined before any screen existed, because retrofitting a gradient system to dark mode later is significantly harder than doing it once at the start, and the restyle to a light canvas proved the point: the dark tokens changed values but no screen had to learn that dark mode exists.

No colour is defined only inside a scheme branch Every token has a light value and a dark value, always both. A colour that exists only in the dark branch renders as whatever the parent inherited in light mode, usually black on black, and usually discovered by a user rather than a preview. The two exceptions are deliberate and named: SlateAurora and the live gradient are the same in both schemes because the surfaces they paint are immersive.

3.9The typography check

The scale is only the scale if nothing else declares a font. scripts/check-typography.sh is what keeps it that way: it greps every Swift file under LIfeOS and LifeOSKit/Sources, excluding Typography.swift itself, and fails on four patterns. 

# scripts/check-typography.sh
check "Literal font sizes outside the scale (use a LifeOSType step):" \
  '\.system(size: [0-9]'

check "UIKit fonts outside the scale (use LifeOSType.UIKitScale):" \
  '\(systemFont\|monospacedSystemFont\)(ofSize:'

check "Rounded or serif faces declared outside the scale:" \
  'design: \.\(rounded\|serif\)'

check "Apple semantic text styles (use a LifeOSType step):" \
  '\.font(\.\(largeTitle\|title[0-9]*\|headline\|subheadline\|body\|callout\|footnote\|caption[0-9]*\))'

The first pattern matches a literal point size and not a computed one, because an icon drawn at a fraction of its container is not type and has no step to pick. The fourth is the subtle one: Apple's semantic styles are a second scale nobody chose, and they do not line up with ours. The script exits non-zero on any hit, so it belongs in the same pre-push habit as swift test. It is also honest about the present: the intro and signup screens still carry three .subheadline and .body calls that predate the scale, and running the script today lists exactly those three. That list is the work remaining, not a reason to loosen the check.

3.10Study notes

Read in this order

  1. Tokens.swift: the hues, the accent, the surfaces, and the comment on every one.
  2. Typography.swift: the scale and the story of the 376 calls it replaced.
  3. Space.swift: the grid, the radii, and GlassPanel.
  4. LayoutMetrics.swift: read the doc comment on railInset; it is a complete bug post-mortem.
  5. PillNavBar.swift and ActionFan.swift: one component, two orientations, and why.
  6. SignInChrome.swift: CodeField over a hidden text field, and InlineStatus.resolve.
  7. ScanlineSlicer.swift then ScanlineCatSilhouette.swift: geometry a test can assert on.
  8. scripts/check-typography.sh: run it, and read what it finds.

Check yourself

  • Why are colours AdaptiveColor pairs rather than UIKit dynamic colours? The package builds for macOS so tests run from a terminal, and a test can read both halves of a pair.
  • Which face may a word never be set in? Rounded. It is for numerals only, and a rounded label beside a sans label is the drift the scale exists to stop.
  • Why does masthead exist as its own step? Flattening the hub's date into display took it from 104 to 34 points; a scale that cannot express the biggest thing in the app is missing a step.
  • Why is railInset 112 and not 96? The rail's footprint is 32 gutter plus 64 width; the rest is breathing room for its shadow. At 80 every screen's leading edge was under the rail.
  • Why is the code field one hidden text field rather than six? So the system keyboard, .oneTimeCode autofill and paste keep working; the boxes are a rendering of that field and hold no state.
  • Which two surfaces are the same colour in both schemes, and why is that allowed? The coach's aurora and the live session gradient; both are immersive surfaces whose tokens resolve as dark by design.
