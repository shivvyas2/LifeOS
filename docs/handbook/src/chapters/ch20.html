Chapter twenty

20The backend

One Supabase project: seventeen migrations, thirteen Edge Functions, two email templates, a cron job, and a two-file static site. Everything in this chapter exists for one of three reasons: a secret that cannot ship in an .ipa, data that must cross between people, or work that a sleeping phone cannot do.

Revision D described a schema of five tables and two deployed functions. The backend has grown since, but its rules have not: every table has Row Level Security enabled without exception, every policy scopes to auth.uid(), every metric column is nullable, and the service-role key exists only in function environments. This chapter walks the configuration, the migrations in order, the functions one by one, the tests, and the operational shape the cron job forces. Every RLS claim below is quoted from the SQL on disk.

20.2The migrations, in order

Migrations are the schema's history. Reading them in order is reading the product's history. Each entry below names what the migration creates and quotes the RLS shape it leaves behind.

20260811 · initial_schema

Five tables mirroring the SwiftData models: daily_metrics (unique on (user_id, date), date typed as date not timestamptz so a device in another zone cannot write to the adjacent day), workout_records, sleep_records (with a check that ended_at > started_at), whoop_raw and sync_state. A touch_updated_at() trigger sets updated_at = now() on every update so a client can never advance it past the server's clock and win a conflict it should have lost. Every table gets four policies of the same shape: 

-- supabase/migrations/20260811164841_initial_schema.sql
create policy "own rows readable" on public.daily_metrics
  for select to authenticated using ((select auth.uid()) = user_id);
create policy "own rows insertable" on public.daily_metrics
  for insert to authenticated with check ((select auth.uid()) = user_id);
create policy "own rows updatable" on public.daily_metrics
  for update to authenticated using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
create policy "own rows deletable" on public.daily_metrics
  for delete to authenticated using ((select auth.uid()) = user_id);

(select auth.uid()) rather than bare auth.uid() is a Postgres planner idiom: the subselect is evaluated once per statement instead of once per row.

20260825 · otp_abuse_guard

otp_events records every SMS start, failed check, successful check and block, keyed by a peppered SHA-256 of the phone, a "pumping prefix" (country code plus the first digits), and a hash of the IP. RLS is enabled with no policies, so no client can read or write it; only the service role reaches it. otp_user_id_for_phone(p_phone) is a security definer function that looks a phone up in auth.users, with execute revoked from anon and authenticated and granted to service_role only.

20260826 · plaid_items

(user_id, item_id) primary key, the Plaid access_token in plaintext, and a unique constraint on (user_id, institution_id) so the same bank cannot be connected twice. alter table public.plaid_items enable row level security; with no policies: the credential is readable only by the service role.

20260827 · lifo_usage

The token ledger: (user_id, day) with a tokens bigint. RLS on, no policies. lifo_debit(p_user, p_tokens) is an atomic upsert-and-add returning the new total, granted to service_role only. This is the database constraint behind the cost ceiling in Chapter 24.

20260827 · friends_and_messages

Three tables. profiles is the one table any signed-in user may read (for select to authenticated using (true)) because people search for each other by name; inserts and updates are own-row only. friendships encodes the state machine in policy: 

-- supabase/migrations/20260827130000_friends_and_messages.sql
create policy "ask for a friendship"
  on public.friendships for insert to authenticated
  with check (requester = auth.uid() and status = 'pending');
create policy "addressee answers"
  on public.friendships for update to authenticated
  using (addressee = auth.uid())
  with check (addressee = auth.uid() and status = 'accepted');
create policy "either side may end it"
  on public.friendships for delete to authenticated
  using (auth.uid() in (requester, addressee));

A request can only be created pending, only the addressee can accept, and only accepted is a valid update target. messages lets participants read their conversation and lets a sender insert only when an accepted friendship exists in either direction.

20260827 · friendship_column_grants

Two lines: revoke update on friendships from authenticated, then grant update (status). The update policy already constrains rows; this constrains columns, so the addressee cannot rewrite who the requester was.

20260828 · notes

note_folders and note_documents, with client-generated UUID primary keys (the device creates pages offline), a blocks jsonb column, a deleted_at tombstone so deletions sync, and partial indexes for archived pages and journal entries. One policy each, for all using (auth.uid() = user_id) with check (auth.uid() = user_id). The sync that drives this is in Chapter 12.

20260828 · profiles_and_avatars, then avatars_signed_in_only

The first adds the onboarding fields to profiles and creates a public avatars bucket. The second, the same day, reverses the public part: the bucket becomes private, accepts only image/jpeg, and reads require a signed-in user. The write policies pin the object name to exactly {uid}/avatar.jpg: 

-- supabase/migrations/20260828150000_avatars_signed_in_only.sql
create policy "own avatar insert"
  on storage.objects for insert to authenticated
  with check (
    bucket_id = 'avatars'
    and (storage.foldername(name))[1] = (select auth.uid())::text
    and name = (select auth.uid())::text || '/avatar.jpg'
  );

One file per person, in their own folder, no other name possible. The app reads avatars with a signed URL and its own token (Chapter 17).

20260829 · fitbit_connections, then fitbit_lock

A user-keyed row holding both Fitbit tokens, the expiry, the granted scopes and a needs_reauth flag. RLS enabled, deliberately no policies, so the row's own owner cannot read it from a client. The second migration adds refresh_lease_until and two security definer RPCs: claim_fitbit_refresh, which sets a lease only if none is live and returns the row, and read_fitbit_connection. Both have execute revoked from public, anon and authenticated. The migration comment explains why: Fitbit's refresh token is single use, so two devices sharing it would sign each other out, and a single server row with a lock is the only arrangement where exactly one writer rotates it.

20260829 · shared_stats

profile_stats holds three figures a person may choose to share (streak, days tracked, workouts) behind a shares flag. The select policy is the first one that crosses users: 

-- supabase/migrations/20260829120000_shared_stats.sql
create policy "own stats and accepted friends' stats"
  on public.profile_stats for select to authenticated
  using (
    user_id = auth.uid()
    or exists (
      select 1 from public.friendships f
      where f.status = 'accepted'
        and ((f.requester = auth.uid() and f.addressee = profile_stats.user_id)
          or (f.addressee = auth.uid() and f.requester = profile_stats.user_id))
    )
  );

Every statement is drop policy if exists then create, which is what made the migration re-runnable after it first failed halfway.

20260830 · proactive_nudges

device_tokens with the APNs token as primary key and the user's time zone, four own-row policies. nudge_log keyed (user_id, day) with the trigger name and never the sentence, RLS on and no policies. And a change to the ledger: lifo_usage gains a kind column, its primary key becomes (user_id, day, kind), and lifo_debit is dropped and recreated with a third parameter. Chat and nudges do not share a budget, because a heavy chat evening must not eat the next morning's nudge.

The deploy order this migration forces The old lifo_debit(uuid, bigint) is dropped. A deployed lifo-agent that still calls it with two arguments fails every debit after the migration runs, and a new lifo-agent that calls it with three fails before. So the order is: push the migration, then deploy lifo-agent and lifo-nudge together, in that window. The plan file for slice 2 records that the migration was applied on 29 August and the functions deployed after it.

20260913 · whoop_account_connections

whoop_connections, user-keyed, holding the pair and a refresh_lock uuid with refresh_locked_until. RLS on, then revoke all ... from anon, authenticated and grant all ... to service_role. claim_whoop_refresh(p_user_id, p_lock) takes a thirty-second lock the same way Fitbit's does, keyed by a caller-supplied UUID so the release can be conditioned on still holding it.

20260914 · social_groups

The largest migration. Four tables (social_groups, group_members with an invited | accepted status and a shares_activity flag, group_messages with a (sender, client_id) unique key for idempotent sends, group_activity) and nine security definer functions. The shape is different from the friends tables: clients get select only, and every write goes through a function that enforces the rule in code. 

-- supabase/migrations/20260914090000_social_groups.sql
revoke all on public.social_groups, public.group_members, public.group_messages,
  public.group_activity from anon, authenticated;
grant select on public.social_groups, public.group_members, public.group_messages,
  public.group_activity to authenticated;

create policy "members and invitees see group" on public.social_groups for select to authenticated
 using (exists(select 1 from public.group_members m where m.group_id=id and m.user_id=auth.uid()));
create policy "accepted members read chat" on public.group_messages for select to authenticated
 using(public.is_group_member(group_id));

is_group_member is itself a definer function so a policy on group_members can consult group_members without recursion. The functions carry the product rules: only accepted friends can be invited, a group holds at most 50 people, an owner who leaves hands the group to the earliest-joined member or deletes it when alone, and send_group_message returns the existing id when a retried client_id matches the same body and raises when it matches different text. group_leaderboard accepts exactly three metric names and raises on anything else.

20260914 · group_wellness_leaderboards

A second, separate consent. shares_wellness on group_members, and group_wellness_daily holding three 0 to 100 scores per day, each paired with its source and checked so a score cannot exist without one: check ((effort is null) = (effort_source is null)). Own-row select only; publish_group_wellness accepts at most two days (today and yesterday), rejects a day outside a narrow range, rejects an observed_at more than five minutes in the future or four days in the past, and only overwrites a row with a newer observation. Health scores are never readable as rows by anyone but their owner; other members see only the ranked result of group_wellness_leaderboard.

20260915 · workout_videos and its seed

workout_videos keyed by youtube_id with a split, arrays for goal, muscles and equipment, an intensity from 1 to 3 and a verified_at. Grants are revoked from both roles and select is granted back to authenticated with a policy of using (true): a catalog, readable by anyone signed in, writable by nobody but the migration. The seed is generated by scripts/catalog/verify.ts, carries 122 insert ... on conflict do update rows, and ends with a delete where youtube_id not in (...) so the seed is a full sync rather than an append.

20.3The shared door

_shared/supabase.ts is forty lines and the most important file in the folder. Every function that touches a user's row calls resolveUser(req) first: 

// supabase/functions/_shared/supabase.ts
/// Resolves the caller from their own token.
///
/// This is a security boundary, not a formality. Every one of these functions
/// reads a bank credential keyed by user, so a service-role client that
/// trusted a user_id from the request body would let any signed-in user pull
/// anyone else's transactions.
export async function resolveUser(req: Request): Promise<string | null> {
  const authorization = req.headers.get("Authorization");
  if (!authorization) return null;
  const client = createClient(SUPABASE_URL, SUPABASE_ANON_KEY,
    { global: { headers: { Authorization: authorization } } });
  const { data, error } = await client.auth.getUser();
  if (error || !data.user) return null;
  return data.user.id;
}

The user id comes from GoTrue validating the bearer token, never from the body. Only after that does serviceClient() build the privileged client, and every query it runs is filtered by that id. _shared/plaid.ts re-exports these so the Plaid functions have one import, and its comment states the rule for the folder: a module named for one integration must not be the front door for another.

OTP: the abuse guard

SMS costs money per message and "SMS pumping" is a known fraud where a bot requests thousands of codes to premium-rate ranges. allowStart in otp_guard.ts counts otp_events rows through PostgREST with Prefer: count=exact and Range: 0-0 (so no row bodies are transferred) across six windows:

KeyWindowLimitError
phone45 seconds0 prior startsrate_phone
phone1 hour5rate_phone
phone24 hours10rate_phone
IP1 hour10rate_ip
IP24 hours25rate_ip
prefix1 hour15rate_prefix

allowCheck blocks after five failed checks in fifteen minutes. Phones are accepted only in two ranges (+1 with ten digits, +91 with ten digits starting 6 to 9), and PhoneOTP in Swift mirrors the rule so the form refuses a number the server would never send to, without a round trip. The identities are stored hashed with a pepper (OTP_PEPPER, falling back to the service key), so the events table holds no phone numbers.

otp-check then does something GoTrue has no built-in for: it mints a session for a phone-verified user. mintSession finds or creates the user with a synthetic email (p{digits}@phone.lifeos.internal), generates a magic link through the admin API, and immediately verifies its hashed_token to obtain a session, which is returned verbatim. The lookup uses otp_user_id_for_phone with the digits only, because GoTrue strips the leading + before storing auth.users.phone, and the one Deno test in otp_session_test.ts pins exactly that.

classifyTwilioFailure maps Twilio's numeric codes to nine kinds, and SEND_FAILURE_STATUS maps every kind to an HTTP status; a test checks that no kind can be added to one without the other. The distinction the code comments insist on: 21608 (trial account, unverified number) cannot happen on a paid account and is the operator's problem, while 21610 (opted out) is per number and only the user can undo it. Each gets copy that sends the reader to the right fix.

Whoop and Fitbit tokens

Both are described in Chapter 19. The pattern to notice here is shared: read the row, short-circuit if the access token is still good, claim a lock or lease before refreshing, condition the write on still holding it, and release in finally. Neither function ever logs a provider's error body on the token path, because OAuth errors can echo credentials.

Plaid: the exchange that must not strand an Item

// supabase/functions/plaid-exchange/index.ts
// Past this point the Item exists at Plaid and bills monthly. Any failure
// below must not strand it: without a row, plaid-disconnect has nothing to
// look up and the device never learns the item_id, so the Plaid dashboard
// becomes the only remedy. Best-effort remove it before returning.
try {
  const { error } = await db.from("plaid_items").insert({ ... });
  if (error) {
    await removeExchangedItem(exchanged.access_token);
    if (error.code === "23505") {
      return json({ error: "institution_already_connected" }, 409);
    }
    return json({ error: "storage_failed" }, 500);
  }
} catch (storageError) {
  await removeExchangedItem(exchanged.access_token);
  throw storageError;
}

Plaid bills per live Item. The function checks for a duplicate institution before spending the exchange, treats a failed lookup as a refusal rather than as "no duplicate", and if the insert fails after the exchange it removes the Item at Plaid before answering. The unique constraint is the last line of defence against the check-then-insert race, and a 23505 from it is reported the same way as the guard. plaid-disconnect is the mirror: it removes the Item at Plaid first and deletes the row only when Plaid confirms it is gone or says ITEM_NOT_FOUND.

lifo-agent: the coach's cloud tier

The most consequential function. Its request path is worth a diagram because every step is a guard, and the guards are the cost ceiling.

The guardrail lives on the server. SCOPE in lifo.ts tells the model it is LIFO, coaching one person over their own data, declining essays and world knowledge, never diagnosing, never recommending securities, and citing only numbers it was given. It is the first system message on every request, and the client cannot strip what it never carries. A client that sends a message with role: "system" is refused outright by parseRequest, because a later system message displaces an earlier one in most providers' weighting. The context (the device's rendered digest, or the calendar assistant's rules) arrives in its own field and is placed as a second system message behind SCOPE.

Two tasks with schemas, one without. answer and nudge ask for strict JSON against a named schema, and parseOutput validates the reply against that task's own schema rather than a literal field name, throwing loudly on a property type it does not know how to check so a future schema cannot silently skip validation. chat declares no schema, because a completion may come back as prose or as tool calls and there is no single shape to check.

The style prompt is copied, and pinned twice. CONVERSATION is a verbatim copy of ResponseStyle.conversation in Swift: no markdown, no dashes, no quotation marks for emphasis, figures with units, one question at most. The two tiers are meant to write identically, and the copy had drifted at birth, so a Deno test and a Swift test each pin the same prohibitions.

Bounds, not tuning knobs. MAX_CHAT_MESSAGES = 64, MAX_CHAT_TOOLS = 16, MAX_CONTEXT_LENGTH = 32000. Without them the endpoint is a general OpenAI proxy on the project's key for any authenticated user. The device sends at most a 20-turn window, six calendar tools, and a context budgeted at 8,000 characters.

Streaming. A chat turn with no tools may ask for a stream, and the coach does, because the wait for the first word is the whole of how fast it feels. The function re-emits the provider's SSE as its own {"delta": "..."} frames closed by [DONE], so the client never learns OpenAI's chunk format and swapping providers is not an app release. stream_options.include_usage is set because usage arrives only in a final chunk, and without it a streamed turn would be free against the cap. A tool-bearing turn is never streamed: a tool call arrives as fragments of a JSON argument string across chunks, and reassembling those on the server would put half the device's round loop up here.

Low reasoning effort. The body sends reasoning_effort: "low" and verbosity: "low". The default is medium, and medium is most of the wait; a coaching question over a week of numbers is not a reasoning problem, because the thinking that matters happened on the device when the digest was built. Low also spends fewer tokens, the same lever as the daily cap pulled from the other end. A 400 from the provider retries once with the two parameters lifted off, because a model that stops accepting one of them should cost a slower answer, never no answer.

Debit everything. The non-streaming path debits before it parses. A refusal or a malformed reply still consumed real tokens, and leaving those unmetered would let someone burn unlimited budget by asking off-topic questions in a loop. The debit's own failure is logged and never costs the user their answer. Logs carry ids, task names, token counts and latency; never the prompt, never the key.

lifo-nudge: rules decide, a model phrases

The proactive half. pg_cron calls it hourly with the service-role key as a bearer, and the function refuses any other caller. Each run selects the users whose local clock has just reached the send hour (8am, inside a 7am to 9pm quiet floor that widening the send hour can never breach), fetches 94 days of daily_metrics, workout_records and nudge_log for the whole batch in three queries, and evaluates four triggers per user in a fixed order:

  1. strongWeek: seven-day step mean at least 25 percent above the trailing three weeks, or a personal best in the last three days against 90 days of history. First on purpose: a channel that only carries bad news gets switched off.
  2. shortSleep: three nights each more than an hour under the person's own median over the prior four weeks, needing at least fourteen nights of baseline. Their own median, not seven hours, so a habitual six-hour sleeper is not told they are failing daily.
  3. stepsCollapsing: three-day mean under 60 percent of the trailing fortnight, with a baseline of at least 2,000 so someone who does not carry their phone is left alone.
  4. streakAtRisk: a workout streak of three or more days counted back from yesterday, because at 8am nobody has trained yet.

A trigger that fired inside the seven-day cooldown steps aside. Nothing firing is the common outcome and a valid one; it reaches no model. When one fires, the function first inserts the nudge_log row, so two overlapping cron runs both reach here and the unique key on (user_id, day) lets exactly one win. Only then does it ask the model to phrase, with a prompt of roughly 300 tokens carrying the trigger's figures and an instruction to use only those. Every fired trigger carries a fallback sentence, so an OpenAI outage delivers the observation plainly rather than swallowing it. A refusal is the one failure that sends nothing, the same distinction EscalationPolicy draws on the device between a transient fault and a safety decision. The phrasing spend debits the nudge kind against its own cap of 4,000 tokens, a runaway guard more than a budget.

A forced send exists for proving delivery: {"test_user_id": ...} bypasses the triggers, the cooldown and the send hour, writes no log row and spends no tokens, and reports how many tokens were found and how many sends succeeded. Silence being the design, there was otherwise no way to know the APNs half was wired without waiting days for a real trigger. 

-- supabase/functions/lifo-nudge/schedule.sql (NOT a migration, run once per project)
select cron.schedule('lifo-nudge-hourly', '0 * * * *', $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name = 'lifo_project_url')
           || '/functions/v1/lifo-nudge',
    headers := jsonb_build_object('Content-Type', 'application/json',
      'Authorization', 'Bearer ' ||
        (select decrypted_secret from vault.decrypted_secrets where name = 'lifo_nudge_key')),
    body := '{}'::jsonb, timeout_milliseconds := 55000);
$$);

The schedule is deliberately not a migration. It needs the project's own function URL, which differs per environment, and the service-role key, which must never be committed; both are read from Vault. Hourly rather than daily because the send hour is local and a single daily run would serve one time zone.

20.6Email templates

magic_link.html and confirmation.html are the same design: a card on the app's canvas colour with an accent band across the head, the dot grid drawn with table cells so it survives image blocking, and the six-digit {{ .Token }} in a 42-point monospaced span with 12 pixels of letter spacing. Tables and inline styles throughout, because email clients strip style blocks, ignore flexbox, and Outlook renders through Word. No images anywhere: nothing to host or have go missing in a year. The subject lines are set in config.toml, and supabase config push is what sends the templates to the hosted project.

20.7The static site

web/ is a two-file site deployed on Vercel at almanac.shivvyas.com. Its only job is to make Plaid's OAuth redirect land back inside the app. 

// web/.well-known/apple-app-site-association
{ "applinks": { "details": [ {

} ] } }

Banks that use OAuth hand the browser to the bank, and the bank redirects to a URI Plaid was told about in advance. On iOS that must be a universal link, because a custom scheme cannot be registered with Plaid and would not survive the hop through Safari. The association file claims the one path, vercel.json forces its content type to application/json (without which iOS ignores the file and every OAuth connection silently falls back to Safari), and plaid-oauth.html is the fallback page a person sees only when the link does not resolve. That page must not look like an error and must never claim the connection failed, because by then Plaid has usually already succeeded; it offers an almanac://plaid-oauth button back into the app. The README lists the four steps the repository cannot do: DNS, the Plaid dashboard's allowed redirect URIs, the PLAID_REDIRECT_URI secret, and the Associated Domains capability on the App ID.

Read in this order

  1. supabase/functions/_shared/supabase.ts, the door every function uses.
  2. supabase/migrations/20260811164841_initial_schema.sql for the policy shape, then 20260914090000_social_groups.sql for the definer-function shape.
  3. _shared/lifo.ts top to bottom, then lifo-agent/index.ts.
  4. _shared/nudge.ts, then lifo-nudge/index.ts, then schedule.sql.
  5. _shared/otp_guard.ts and otp_twilio.ts together.
  6. plaid-exchange/index.ts for the cleanup pattern.
  7. supabase/tests/social_groups.test.sql, to see RLS tested from three seats.

Check yourself

  • Why must resolveUser run before serviceClient in every function? The service role bypasses RLS. A user id taken from the request body would let any signed-in person read anyone's bank credential.
  • Which tables have RLS enabled with zero policies, and what does that mean? otp_events, plaid_items, lifo_usage, fitbit_connections, nudge_log, whoop_connections. Nobody but the service role can read or write them, including the row's own owner.
  • Why does the social groups migration grant only select to clients? Every write has a rule (friends only, 50 max, owner succession, idempotent sends) that a row policy cannot express, so writes go through definer functions that raise.
  • Why is the guardrail prompt on the server and not in the app? A client cannot strip what it never carries, and a client system message is refused so it cannot displace it.
  • What does the streamed path do that makes it not a free path through the cap? It asks for include_usage and debits in flush, which runs even when the client abandons the stream.
  • Why is schedule.sql not a migration? It needs the per-environment function URL and the service-role key, both read from Vault at run time.
  • What breaks if lifo-agent is deployed before the proactive_nudges migration? Its three-argument lifo_debit call fails until the migration creates that signature; deploy order is migration first, then both functions.
