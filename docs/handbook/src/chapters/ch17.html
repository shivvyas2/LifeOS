Chapter seventeen

17Profile and settings

A face in the corner of Today opens everything that used to be behind a gear: who you are, what your tracking adds up to, your friends, every connection with its own live state, the goals that decide a good day, and the account switcher. Settings is a page inside the profile, not a tab.

17.1Intent

Working backwards

Tap your photo on Today and the screen fills with it, fading into a gradient sampled from the picture itself. Under your name sit three figures that describe who you have been: day streak, days tracked, workouts. Then today's living numbers, then all-time totals, then three doors: Together, Connections, Settings. Edit the profile from a glass sheet that saves locally first and publishes after. Settings holds appearance, the five daily goals, the accounts signed in on this device, which engine the coach uses, whether it speaks, and a summary of every connection with a green dot for on and a hollow one for off.

Why a face instead of a gear?

A gear says "settings"; a face says "you", and everything that was behind the gear is about you. The button falls back to a person glyph rather than initials, because a single letter in a circle reads as an avatar that failed to load.

Why is the profile on the server now?

Because signing in on a second phone, or as a second account on this one, used to produce a profile with no name and no picture: both lived only on the device that typed them. The profiles row and the avatars bucket are the source of truth; the device keeps a per-account cache so the screen draws instantly and draws offline.

What does Settings do when Health access was denied?

It cannot know. HealthKit read authorisation is opaque by design, so the row says "No data yet. Check Almanac in Health > Sharing" rather than asserting a state it cannot verify.

Why can I edit the goals?

Because the dot grid is the app's central claim, and a claim you cannot calibrate is one you stop believing. Defaults are 8,000 steps, 7h sleep, 30 min exercise, 2,500 ml water, 3 of 4 required.

17.3Model

Three shapes of a profile

// LifeOSKit/Sources/Integrations/ProfileClient.swift
public struct RemoteProfile: Codable, Sendable, Equatable {
    public var firstName: String
    public var lastName: String
    public var country: String
    public var birthDate: Date?
    public var heightCM: Double?
    public var gender: String?        // nil is "prefer not to say"
    public var avatarPath: String?    // a path in the bucket, never a URL

    public var displayName: String { fullName.isEmpty ? "Someone" : fullName }

    public func payload(userID: String) -> [String: Any] {
        var row: [String: Any] = [ "user_id": userID, "display_name": displayName, ... ]
        row["birth_date"] = birthDate.map { SupabaseREST.day($0) } ?? NSNull()
        row["height_cm"] = heightCM ?? NSNull()
        row["gender"] = gender ?? NSNull()
        row["avatar_path"] = avatarPath ?? NSNull()
        return row
    }
}

RemoteProfile is the row as the server holds it. Two decisions are written into it. The avatar is stored as a path, {user_id}/avatar.jpg, never a URL, because a URL bakes in the project host and the signing scheme, both of which outlive their correctness. And cleared fields are sent as explicit nulls rather than omitted, because the save is an upsert of the whole row: an omitted key would leave the old value standing and make deleting a birthday impossible. displayName is never empty because the column is not nullable and a profile with no name is still a profile that friend search has to match.

LocalProfile, in ProfilePhotoStore.swift, is the per-account display cache, and ProfileStore.save(_ remote:) only ever writes it from what the server confirmed, so the two cannot drift. The profile used to live in auth.users.user_metadata with a copy in a single UserDefaults key. That payload rides inside the JWT on every authenticated request, which is the wrong place for anything that grows, and the copy was not keyed by account, so with two accounts on one device the second saw the first's name. 

// LifeOSKit/Sources/Integrations/ProfileClient.swift
public enum AvatarStamp: Sendable, Equatable {
    case missing           // no such object in the bucket
    case unknown           // the object exists, but the listing did not say when it changed
    case at(String)        // the object exists and last changed at this stamp
}

Three cases rather than an optional string, because "there is no object" and "the object is there but undated" want opposite answers. Collapsed into a single nil, the safe reading of nil is "do not download", and then a device with nothing cached downloads nothing, ever, and shows an empty circle for a profile that has a picture.

    let id: String
    let value: String

}

The draft is a separate type from UserGoals on purpose. Editing writes to the draft; committing validates it into the row. Binding steppers straight to the persisted model would write to the database on every increment and re-evaluate a month of history mid-drag. ProfileStat is a label and a pre-formatted string: the profile shows facts and never computes one.

AppConfig: what is public and why

AppConfig reads the bundle's Info.plist for the Supabase URL and anon key, the WHOOP, Fitbit and Plaid redirect URIs, the ElevenLabs key, and the function endpoints derived from the project URL. Everything here is public by design except the ElevenLabs key, which is gitignored but still extractable from a shipped .ipa and therefore never logged. Client secrets for WHOOP, Fitbit and Plaid are deliberately absent: they live only in Edge Function environments (Chapter 23). An unresolved build setting comes through as a literal $(…), so string(_:) treats that prefix as absent. The app answers to two URL schemes, almanac and the older lifeos, so the WHOOP redirect bridge can point at either without the app and the server having to ship together.

17.4ViewModel

SettingsViewModel

draft is the one mutable published property on this view model, and it is mutable because SwiftUI's @Bindable needs it to be. load() copies the goals row into it; save() writes the row back in one context.save(), which is what makes the dot grid re-evaluate. The rule is the user's, not hard-coded. SettingsScreen calls save() from onChange(of: model.draft), so each stepper commits once per change rather than once per dismissal.

Four connections, four shapes

Each provider has its own view model because each has a different relationship with credentials, and the differences are the point.

ProviderWhere the token livesSign-in surfaceWhat the view model owns
Apple HealthNowhere; it is a permissionThe system sheet, onceWhether it was asked, the sync cursor, the cycle switch, the foreground watch
WHOOPKeychain on the device, plus a server copy for restoreSafari, by UIApplication.openPKCE attempts, the manual desktop code, stalled sign-ins, sync with a staleness policy
FitbitA row on the server onlyASWebAuthenticationSession in-appPKCE attempts and a "connected" flag per account; the server is the authority

Health is deliberately the thinnest, because it has no OAuth, no tokens and no server, and the one thing it does have is a permission model that refuses to tell us anything. connect() asks once, records that it asked, decides the cycle-tracking default, syncs, and starts the watch. After that "Connect" becomes "Sync", because iOS shows the sheet exactly once and offering to connect again would be a button that visibly does nothing. The cycle-tracking switch is offered to everyone and defaulted from Health's own sex characteristic, not from the gender asked at signup: that field says how someone wants to be addressed, and using it here would get the answer wrong in both directions and strand everyone who chose "Prefer not to say". Turning the switch on asks for the extra permission there and then, so the prompt arrives with the tap that caused it.

WHOOP opens sign-in in Safari rather than an in-app web session because WHOOP's login sits behind a Cloudflare bot challenge that never clears inside ASWebAuthenticationSession. That decision creates two problems the view model then has to solve. Leaving for Safari looks identical whether or not the person comes back, so resolveStalledConnect() waits two seconds after the app becomes active and, if the card is still connecting with no token, returns it to disconnected. Two seconds is the whole subtlety: the redirect usually lands a moment after activation, so resolving immediately would cancel sign-ins about to succeed. And a challenge behind a VPN or Private Relay can hang forever, so beginManual() offers a desktop URL and a code field; the PKCE verifier never left this phone, so a transcribed code alone is not enough to impersonate it. Pending attempts are persisted, not held in memory, because iOS may terminate the app while Safari is up, and the callback is matched to the attempt whose state it carries because tapping Connect twice starts two valid authorisations.

Fitbit is thinner than WHOOP, and the missing half is the point. Fitbit rotates its refresh token on every use, so exactly one writer may hold it, and that writer is a row in the database. The view model hands a code to the fitbit-token function and asks fitbit-sync what the state is. A "connected" flag per account is remembered only so the card does not flash "Not connected" on every launch while the server is asked.

Plaid keeps LinkKit behind one seam. PlaidLinkPresenter is the only file that imports it, which is what lets the connection view model be tested against the PlaidClient alone. The presenter holds the live handler itself, because a bank using OAuth sends the person out to Safari and a handler released while they are away has nothing to hand the redirect back to. It also keeps the link token in the account's defaults, because the case that matters is the process not surviving: resume(from:) rebuilds a handler on the original token and calls resumeAfterTermination. The completion closure died with the old process, so PlaidConnectionViewModel.attach re-registers onResumedConnect every time. Sync runs the cursor loop up to twenty pages per pass and sets isFetchingHistory between connecting and the first transaction arriving, because Plaid fetches history asynchronously and an empty first sync must not render as "you spent nothing this month" (Chapter 11).

All four share three habits. A launch and a foreground arriving together coalesce into one sync through a held Task or an isSyncing flag. isConnected is false while connecting, so the summary dot never claims success while Safari is still open. And every failure is a sentence: "Whoop needs new permissions. Disconnect, then connect again" is a different problem from "Whoop sign-in expired", and collapsing them once sent people around the reconnect loop with no idea why it kept failing.

17.5View

The profile page

ProfileScreen is presented as a fullScreenCover from the avatar on Today. It owns a NavigationStack, the local profile and photo as state, the edit sheet, and a single destination enum for its four pushes: notifications, friends, connections, settings. Every push is a value, so the destination is a function of it. ProfileOverview is the presentation, shared with the DEBUG fixture, and is forced into the dark colour scheme with a hidden navigation bar because it is drawn over the photo. 

// LIfeOS/Features/Settings/View/ProfilePhotoBackdrop.swift
static func extract(from data: Data?) -> Self {
    guard let data, let image = UIImage(data: data) else { return fallback }
    let thumbnail = UIGraphicsImageRenderer(size: CGSize(width: 48, height: 48), format: format)
        .image { _ in image.draw(in: CGRect(x: 0, y: 0, width: 48, height: 48)) }
    guard let source = CIImage(image: thumbnail) else { return fallback }
    func average(_ y: CGFloat) -> Color {
        let bounds = CGRect(x: 0, y: y, width: 48, height: 16)
        let result = source.applyingFilter("CIAreaAverage",
            parameters: [kCIInputExtentKey: CIVector(cgRect: bounds)])
        ...
    }
    return Self(top: average(32), middle: average(16), bottom: average(0))
}

The gradient behind the profile is sampled from the photo: a 48 pixel thumbnail, three CIAreaAverage passes over its top, middle and bottom thirds, and the three colours become a diagonal gradient. It is recomputed only when the photo changes, through .task(id: photo). Over that sit a blurred copy of the whole photo at 35 percent, the portrait cropped 1.3 to 1 from the top and masked to fade out, and a dark wash that keeps white text readable. With no photo the backdrop is the fallback palette and a soft orange ellipse.

On a phone the portrait sits at the top and the page scrolls. At 760 points or wider the layout becomes a 340 point identity column beside a 540 point details column, the portrait becomes a rounded card, and the backdrop drops the portrait layer. Under the name are up to three parts of a subtitle: country, height, age. Then, in order, "Your rhythm" (three cumulative figures), "Today" (only the readings that exist), "Over time" (only totals above zero), and the three doors, all on clear Liquid Glass panels. An empty profile at accessibility sizes collapses every grid to one column.

The edit sheet

ProfileEditSheet is the same fields as signup, reachable at any time, because signup asks once and never again, which is fine for a name and wrong for a photo. It saves locally first and publishes after: the local copy is what the app displays, so writing it first means the change is visible immediately and survives a failed request. Dismissal, though, waits for the publish. The row is what friend search reads, so a save that only ever reached the device would leave someone invisible to everyone looking for them while their own screen said it worked. On failure the sheet stays open with the reason, Save becomes "Try again", and Cancel becomes "Close anyway", because the local copy is already written and trapping someone in a sheet they cannot satisfy is worse than letting them out informed. Removing a photo is a delete on the bucket rather than a null in the row; leaving the object behind would keep serving a face the person took down.

Settings and Connections

SettingsScreen is a page pushed from the profile with no inner stack and no Done: the back chevron is the way out, which is what makes it feel like a place rather than an overlay. Its cards, top to bottom: appearance (system, light, dark), the five goal steppers, the accounts signed in on this device with a radio to switch, the coach tier (automatic, cloud, on-device), the voice toggle and its three voices, "At a glance" with Notifications and Widgets & Watch, the connections summary, and Log out. Switching accounts does not sign anybody out: each account keeps its own store, cursors and connections, so moving between them is opening a different file rather than tearing one down (Chapter 4).

The connections summary used to be one row with a chain-link icon reading "Whoop, Health, banks" over WHOOP's status line, which said nothing about the other two. It now shows every source, one line each, with a green dot for on and a hollow one for off. Never red: not being connected is a choice someone is allowed to make, and an alarm dot next to WHOOP would nag every user who does not own one. While a sync runs the dot is replaced by a spinner, because the honest answer to "is it on" is "ask me in a second". ConnectionsSettingsScreen is the page it opens, one card per source with a chip whose colour is its meaning: orange asks for a tap, green reports one that already happened. The Fitbit card's "Sync" calls the forced refresh rather than reopening OAuth, and the Health card's "Sync" replaces "Connect" once the sheet has been shown.

Where the actions live

The calendar assistant, LIFO and Begin Activity are the app's three free-floating actions. They used to be laid flat on home and collapsed into a bottom-corner fan on every other tab, which put the control people reach for most in a different place depending on where they were and hid it behind a trigger on four of the five. They are now a [QuickAction] defined once in RootView, injected through the quickActions environment value, and drawn by .quickActionsToolbar() across the top of every tab as an ActionFan in its row arrangement: 34 point bare glyphs sized for a 44 point bar. The environment value is the mechanism because Notes and Life own their own NavigationStacks several levels below the root, and a toolbar has to be attached inside the stack it belongs to. The fan arrangement still exists in ActionFan, with its arc from 90 to 170 degrees and its 106 point radius chosen so three 52 point circles never overlap, but nothing in the app uses it today. The plus becomes a timer glyph labelled "Current activity" while a session is running.

17.6How it works

The avatar stamp, step by step

  1. AppShell's launch task restores the session and, if the person is signed in with a store open, calls ProfileSync.pull().
  2. The profiles row is loaded and mirrored into the per-account defaults. If the row says there is no picture, the local file is deleted, so a photo removed on one phone does not survive on another forever.
  3. The account's folder in the bucket is listed (one object, never the whole bucket) and the object's updated_at becomes an AvatarStamp.
  4. shouldDownloadAvatar decides: missing never downloads, unknown downloads only when there is no local copy, a dated stamp downloads when there is no copy or the stamp differs from the recorded one.
  5. After a download the stamp is recorded, and only when the listing gave one. Saving a photo clears the stamp first, because the stamp describes the bytes on disk; a photo taken on this device has no server stamp yet, and keeping the old one would make the next sync believe the copy it holds is the one already up there.

Every step re-checks that the signed-in account is still the one the pull started for, so an account switch mid-pull cannot write one person's face into another person's folder.

The photo maths

// LIfeOS/Components/Model/ProfilePhotoDownsizing.swift
static let side: CGFloat = 512
static let sizeLimit = 5_242_880          // the bucket's file_size_limit, kept in step by hand

static func jpeg(from image: UIImage) -> Data? {
    let ratio = min(side / image.size.width, side / image.size.height, 1)
    let size = CGSize(width: image.size.width * ratio, height: image.size.height * ratio)
    let format = UIGraphicsImageRendererFormat.default()
    format.scale = 1
    let resized = UIGraphicsImageRenderer(size: size, format: format).image { _ in
        image.draw(in: CGRect(origin: .zero, size: size))
    }
    var quality: CGFloat = 0.8
    var data = resized.jpegData(compressionQuality: quality)
    while let current = data, current.count > sizeLimit, quality > 0.3 {
        quality -= 0.1
        data = resized.jpegData(compressionQuality: quality)
    }
    return data
}

Scale 1 is the line that matters. The renderer otherwise draws at the device's scale, so a 512 point box becomes a 1536 pixel bitmap on a 3x phone: nine times the pixels asked for, which undoes most of the downsizing. The quality loop is a backstop against a pathological image, not the primary way the output is kept small. The limit is deliberately the bucket's real ceiling rather than something tighter, because a client-side constant below the server's would start rejecting uploads from installs running older code with nothing on screen to explain it.

The stats under the name

RootView computes the three panels from the store at the moment the profile opens. "Your rhythm" is the streak from Today's snapshot plus two fetchCount calls, which never materialise a row. "Today" lists only the readings that exist: a missing one is left out rather than dashed, so the panel always reads as facts, and money is deliberately absent because a sample-data default would put invented dollars on a person's face. "Over time" sums steps and sleep from one fetch of the daily rows, a few hundred small objects at most, and counts habit ticks, calendar events and scored sectors with fetchCount; zero-valued figures are left out.

17.7Performance and cost

  • Two small requests per launch, and the third only when needed. The profile pull is a row and a one-object listing; the picture downloads only on a changed stamp.
  • Reads are signed-in-only, not signed-URL-per-face. The bucket is private, but any signed-in user may read any avatar, which is what keeps a friend list from needing a signed URL per face on every refresh (Chapter 16).
  • Uploads replace in place. x-upsert: true rather than a delete and an insert, so a person changing their picture is never briefly without one.
  • The gradient is three 48-pixel averages, recomputed only when the photo changes. The CIContext is shared and built with intermediate caching off.
  • Goals commit once per change, not once per frame. The draft absorbs the stepper; the row is written on onChange.
  • Syncs coalesce. Every connection view model folds a launch and a foreground into one pass, and WHOOP, Fitbit and Plaid consult SyncStalenessPolicy before spending a request.
  • Provider secrets never reach the device. Fitbit tokens never even pass through it; Plaid access tokens sit behind service-role-only RLS.
  • Per-account defaults, per-account files. Cursors, "was Health asked", the cycle switch, the avatar and the profile cache all live in the account's own suite or directory, so an account switch is a lookup change, not a purge.

17.9Study notes

Read in this order

  1. LifeOSKit/Sources/Integrations/ProfileClient.swift: AvatarStamp and shouldDownloadAvatar.
  2. Features/Onboarding/Model/ProfilePhotoStore.swift: ProfileSync.pull(), then the stamp accessors.
  3. Features/Settings/View/ProfileEditSheet.swift: save().
  4. Features/Settings/ViewModel/HealthConnectionViewModel.swift: connect, decideCycleDefault, startWatching.
  5. Features/Settings/ViewModel/WhoopConnectionViewModel.swift: resolveStalledConnect and finish(callbackURL:).
  6. Features/Settings/View/PlaidLinkPresenter.swift: resume(from:).
  7. App/RootView.swift: quickActions, profileStats, profileAllTime.
  8. LifeOSKit/Sources/DesignSystem/ActionFan.swift: why the row and the fan are one component.

Check yourself

  • Why does AvatarStamp have three cases and not two? "Missing" must never download and "unknown" must download when nothing is cached; one nil cannot say both.
  • Why is the avatar stored as a path and not a URL? A URL bakes in the host and the signing scheme; both can change while the object stays where it is.
  • Why does ProfileEditSheet save locally first but wait for the publish before dismissing? Local first makes the change visible and durable; waiting makes a publish failure visible, because an unpublished profile is one nobody can find.
  • Why does the WHOOP stall check wait two seconds? The redirect usually lands just after the app activates; resolving at once would cancel sign-ins about to succeed.
  • Why is the cycle-tracking default read from Health rather than from the gender field? The gender field is a form of address, its own comment says so, and using it would be wrong both ways and strand the default answer.
  • Why is sizeLimit exactly the bucket's ceiling? A tighter client constant would reject uploads from older installs one release early, silently.
