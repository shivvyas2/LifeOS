Chapter one

1Architecture

Almanac is a local-first iOS app built on one bet: the value is in the join, not the collection. Seven sources of data now feed it, one table keyed by calendar day still receives all of the health signal, and every screen reads from the device before anything touches the network.

This chapter describes the system as it is on 15 September 2026, not the one the first edition planned. Since Revision D the package has grown from three targets to eight, the app has gained a watch, a bank, a second wearable, a calendar, a notes library, a nine-sector life board and a cloud tier for the coach. The architecture survived all of that because three early decisions held: one row per day, a compiler-enforced module graph, and a device that never waits for a server. Where the code and this handbook disagree, the code is right and this handbook is a bug.

1.1System context

Every source reaches the app through one of four doors: Apple Health, a vendor REST API behind a Supabase Edge Function, a system framework on the device itself, or a table in Supabase that the app reads directly over PostgREST. The Apple Watch is now both a source, through Health, and a second screen, through WatchConnectivity. Everything still converges on the local SwiftData store before a single pixel is drawn.

1.2Module map

LifeOSKit is a local Swift package providing compile-time boundaries. The app target contains only features and wiring, laid out per screen as described in Chapter 2. The dependency rules are enforced by the compiler, not by convention: a target that does not declare a dependency cannot import it, and the package manifest is the whole rule book.

That is why DailyMetrics.sourcesData stores a raw String rather than a MetricSource: the vocabulary of "who wrote this" lives one tier up, and the row only carries its name. The dependency arrow decided the type.

1.3The DailyMetrics spine

This is still the single most consequential decision in the system. One row per calendar day. Every health source writes into it; every health reader reads from it. The row has grown two bags since the first edition, and both exist to keep that sentence true as the number of sources went from two to four. 

// LifeOSKit/Sources/Persistence/DailyMetrics.swift
@Model
public final class DailyMetrics {
    #Unique<DailyMetrics>([\.date])

    /// Always `Calendar.startOfDay`. Never a timestamp.
    public var date: Date

    public var weightKg: Double?
    public var steps: Int?
    public var sleepMinutes: Int?
    // ... eleven named columns, all optional ...

    /// Everything Apple Health can supply that does not have a column of
    /// its own, as a JSON dictionary keyed by `HealthMetric.rawValue`.
    public var extrasData: Data?

    /// Who wrote each value, as a JSON dictionary keyed by `HealthMetric.rawValue`.
    public var sourcesData: Data?

    public var updatedAt: Date
    public var syncedAt: Date?
}

The named columns came first and are load-bearing: the sector scorers, the Whoop merge and the charts all read them by name. The extras bag is the long tail of Apple Health, more than thirty metrics most people have no data for, stored as [String: Double] so that adding a metric is one enum case and one mapping rather than a schema migration. The sources bag runs parallel to it and records provenance per metric per day.

Both bags decode to an empty dictionary rather than throwing when the bytes are unreadable. A day whose extras cannot be parsed still has its named columns, and losing the screen over the tail would be the worse failure. Both also treat writing nil as removing the key, never as storing a zero, for the reason the whole model is built on: absent and zero are different things, and a false zero is worse than a blank in a health app.

What the single-table choice still buys

  • Trends become a sort, not a multi-source asynchronous join. TodayViewModel.load fetches one bounded window of rows and derives the grid, the streak and today's figures in one pass.
  • The coach queries one table instead of orchestrating four network APIs mid-conversation, which is what makes an on-device model viable and what makes the cloud tier's context bundle small.
  • Offline works by default, because nothing renders from a live network call.
  • Adding a source means writing into the same row through the same arbiter. Fitbit shipped as a second wearable without a new pipeline; it is a loop around one function.
  • The widgets and the watch decode a SurfaceSnapshot that is a projection of one row, so the same steps figure appears on the lock screen, the wrist and the hub without three queries.

MetricsStore is the only way anything writes to the row. Its upsert fetches or creates the day and applies a closure, and it is a merge: fields the closure does not touch are preserved. upsertBatch exists because a save per row turned sixty days into sixty disk transactions on the main actor; a sync loop now makes one.

1.4The arbiter: merge by rank

With one wearable the merge rule was a boolean called fillGapsOnly: Health fills what Whoop left blank. With two straps that rule cannot tell a Whoop value from a typed one, which is exactly the distinction a second wearable forces. The replacement is a rank, and it is a pure function so every branch can be tested without a device, a permission prompt or a store. 

// LifeOSKit/Sources/Integrations/MetricArbiter.swift
public static func resolve(
    metric: HealthMetric,
    existing: Double?, existingSource: MetricSource?,
    incoming: Double?, incomingSource: MetricSource,
    ranking: SourceRanking
) -> (value: Double?, source: MetricSource?) {
    // A source having no reading is not evidence of zero.
    guard let incoming else { return (existing, existingSource) }
    guard existing != nil else { return (incoming, incomingSource) }

    let held = existingSource ?? MetricSource.legacy(for: metric)

    // Greater than or equal, not greater than. Equal rank means the same
    // source syncing again, which must be allowed to correct itself.
    guard ranking.rank(incomingSource, for: metric) >= ranking.rank(held, for: metric) else {
        return (existing, held)
    }
    return (incoming, incomingSource)
}

The ranks are decided per metric, because a source that is the authority on one number is a fallback on another:

RankWhoWhen
4manualAlways. A figure a person typed is never overwritten by a background sync.
3appleHealthFor metrics where healthIsAuthoritative: not claimed by a wearable and not typed, such as steps, active energy, weight from the scale. The latest reading is simply the truth, which is what lets an afternoon sync correct the morning's step count.
3the primary wearableFor metrics claimedByWearable: resting HR, HRV, SpO2, respiratory rate, every sleep stage. Whoop by default; Fitbit if the person named it primary.
2the other wearableFills a gap the primary left, never overwrites it.
1appleHealthFor wearable-claimed metrics: the fallback when no strap has spoken.
0unattributedA value written before provenance was recorded. The first sync after upgrade re-attributes it.

Rank 0 has one exception, and the exception matters. Weight and water are the two metrics a person can type. A figure typed before provenance existed is unattributed too, and reading it as unknown would let the next Health sync silently replace it. That is the one path that destroys data a person entered by hand, so MetricSource.legacy(for:) reads an unattributed value for a typed metric as typed. The test is named for the bug it prevents: anUnattributedWeightIsNotReplacedByASync.

HealthApply.write is the one place the HealthMetric vocabulary meets DailyMetrics columns. It loops the arbiter over a day's readings inside a single upsert, records the winning source in the bag as a side effect, and routes named metrics to their column and everything else to extras. The arbiter can be perfectly correct and still be wired into the wrong column; HealthApplyTests run against a real in-memory store precisely to catch that.

1.5Local first topology, and what syncs now

SwiftData on the device is the source of truth for the UI. Supabase is identity, backup for some models, the only place a secret may live, and the place to run jobs a sleeping phone cannot. The first edition had one thing syncing (nothing, in practice). This edition has a precise list, and the split is worth knowing because it decides what a second device sees.

DataWhere it livesHow it moves
Notes: folders, documents, blocksDevice and note_folders, note_documentsNoteSync pushes and pulls under a per-account cursor on every pass; the token is read per pass, never captured

Two mechanisms make this cheap. RootView reloads every snapshot on ModelContext.didSave, so a sync that lands repaints the screen without anyone polling. And SyncStalenessPolicy decides whether an automatic pull is due at all: data older than an hour, or from before today's midnight, is worth refreshing; anything fresher is not. The day boundary is the clock that matters most, because the first open of the morning must pull the night's sleep, and a sync from 23:50 is only minutes old while knowing nothing about the night.

1.6Conflict resolution

Within the health row, the arbiter above is the conflict rule: field-level, by rank, with a same-rank writer allowed to correct itself. It replaces the field-level last-write-wins the first edition described, and it is better for the same reason: a row-level overwrite would let the 04:00 Whoop pass discard the water you logged at 23:00, and a timestamp cannot tell a strap from a person.

Across devices, for the models that sync, the rule is simpler and per model. Notes carry an origin id and an updated_at; the pull applies rows newer than the cursor and the push sends rows changed since the last push, which is last-write-wins by row on a single-writer assumption that holds because one person edits one note at a time. The profile is an upsert of the whole row with explicit nulls, because an omitted key would leave the old value standing and make deleting a birthday impossible. Social rows never conflict because they are never edited locally; only status is updatable on a friendship, and the database says so.

Known limitation The notes cursor depends on server clocks, not device clocks, so the skew problem the first edition warned about is gone for notes. It remains for anything that compares updatedAt on the device with a server timestamp, and today nothing does. If a model starts syncing health rows, the arbiter's rank must travel with the row or the merge will regress to a timestamp race.

1.7One store per account

The first edition assumed a single user and said so. That assumption is gone: several people can sign in on one device, and the way that works is the most important structural change since Revision D. Isolation is by store file, not by an owner column. 

// LifeOSKit/Sources/Persistence/UserScope.swift
public struct UserScope: Hashable, Sendable, Codable {
    /// The signed-in Supabase user id.
    public let id: String

    public func storeURL(base: URL) -> URL {
        directory(base: base).appendingPathComponent("store.sqlite")
    }

    public func directory(base: URL) -> URL {
        base.appendingPathComponent("Accounts", isDirectory: true)
            .appendingPathComponent(safeDirectoryName, isDirectory: true)
    }

    /// A defaults suite of this account's own.
    public var defaultsSuiteName: String { "account.\(safeDirectoryName)" }
}

The reasoning in the file's own comment is the whole argument: a column means a predicate on every read across twenty models, and a predicate forgotten once is a leak that looks like working software. A separate file cannot leak, because the rows are not there to be read. LifeOSContainer.make(for:) opens Application Support/Accounts/<uid>/store.sqlite, and every account also gets its own UserDefaults suite for the things that turned out to be per account rather than per device: sync cursors, connection tokens, whether the tour has been seen. Appearance, the assistant's voice and which engine answers stay in standard on purpose, because they belong to the phone.

Three pieces cooperate. AccountStore keeps the roster of accounts in defaults (ids and labels are not secrets) and one keychain item per account for the session (a refresh token is a credential). AccountSession owns which scope is open and the ModelContainer for it, and tears down every cross-account surface, the widget snapshot, the Live Activity, the watch bridge, before adopting the next one. And LIfeOSApp re-roots the whole view tree with .id(scope.id) so no screen carries the previous account's view models or scroll position into the next; a stale snapshot on screen after a switch is the same class of leak as a stale row. Chapter 4 walks through the sequence.

The upgrade path is a file move. Every install before accounts kept one unscoped default.store. adoptLegacyStore moves that file, and its -wal and -shm companions, into the first account that signs in, once, and refuses when the destination already has a store. Moving the write-ahead log matters: the database alone would leave the most recent writes behind in a log the new file cannot find, and adoptionCarriesTheWriteAheadLog pins it. Signing out leaves the store on disk; removing an account from the device is a different, louder action that does not exist yet.

1.8The privacy boundary

Three things leave the device, and each crosses a boundary that is a type or a dependency edge rather than a code review promise.

  • Derived numbers to the coach's cloud tier. RemoteChatEngine takes a ContextBundle, which is assembled on the device from digests: aggregates, deltas, sector scores, the last thirty transactions as merchant, category and amount. DailyMetrics is a SwiftData class that is not Sendable, so the compiler prevents a raw row from crossing. Chapter 14 has the shape of the bundle.
  • Content, not numbers, to the calendar assistant. Event titles cannot be aggregated without destroying their use, so this is the one deliberate exception, and it is gated behind a confirmation broker before any write. Chapter 15.
  • Three figures to friends. Streak, days tracked and workouts, plus a wellness score, and only when the person has turned sharing on in a group. publishWellnessIfShared in RootView checks the group's flag before every publish. Chapter 16.

Everything with a vendor secret runs in an Edge Function: the Whoop client secret, the Fitbit client secret, the Plaid client id and secret, the Twilio credentials, the OpenAI key, the APNs key. The app bundle holds only what is public by OAuth design, and AppConfig says so in its comments. Chapter 23 has the three-tier table.

1.9Study notes

Read in this order

  1. LifeOSKit/Package.swift, for the graph. Twenty lines, and every rule in this chapter is one of its edges.
  2. LifeOSKit/Sources/Persistence/DailyMetrics.swift, for the row and the two bags.
  3. LifeOSKit/Sources/Persistence/MetricsStore.swift, for the only write path.
  4. LifeOSKit/Sources/Integrations/MetricSource.swift then MetricArbiter.swift, for the rank and the merge.
  5. LifeOSKit/Sources/Integrations/HealthApply.swift, for where the vocabulary meets the columns.
  6. LifeOSKit/Sources/Persistence/UserScope.swift and LifeOSContainer.swift, for one store per account.
  7. LifeOSKit/Tests/IntegrationsTests/MetricArbiterTests.swift, which reads as a list of the rules in plain English.

Check yourself

  • Why does the arbiter use greater-than-or-equal rather than greater-than? So that the same source syncing again can correct its own earlier value; an afternoon Health sync must be able to raise the morning's step count.
  • Why is sourcesData a string bag rather than a typed MetricSource? Because Persistence sits below Integrations in the package graph and cannot import the enum.
  • What does an unattributed weight become on the first sync after upgrade? It is read as typed, rank 4, so Health cannot overwrite it; every other unattributed metric is rank 0 and is re-attributed.
  • Why a store file per account rather than a userID column? A column needs a predicate on every read of every model and one omission leaks; a file cannot leak rows it does not contain.
  • Which health data reaches Supabase today? None of the rows. Notes, profile, social, connection credentials and coach usage sync; DailyMetrics, sleep, workouts, money and sectors stay on the device.
  • What must move with a store when it is adopted, and why? The -wal and -shm files, or the most recent writes are stranded in a log the moved database cannot find.
