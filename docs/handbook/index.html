Chapter one

1Architecture

Life OS is a local-first iOS app built on one bet: the value is in the join, not the collection. Every architectural decision below follows from it. Four devices produce data, all of it converges on a single table keyed by calendar day, and every screen reads from that table and nothing else.

This document describes a system that is designed but not finished — V1 is in active implementation. Where the code and this handbook disagree, the code is right and this handbook is a bug. The product reasoning that led here is in Appendix A; it is deliberately behind the engineering, not in front of it.

1.1System context

Four devices produce data, two of them reach the app through Apple Health, one through a REST API, and one — your MacBook — cannot reach it at all. Everything converges on a single local store before anything renders.

1.2Module map

LifeOSKit is a local Swift package providing compile-time boundaries. The app target contains only features and wiring, laid out per screen as described in Chapter 2. The dependency rules are enforced by the compiler, not by convention.

RuleEnforced howWhy
Nothing outside HealthData imports HealthKitPackage dependency graphHealthKit types never leak into views; the module is swappable and testable
Nothing outside WhoopKit knows Whoop existsPackage dependency graphA vendor change is contained to one target
Nothing outside SyncKit imports the Supabase SDKPackage dependency graphThe app works identically with sync disabled
Insights reads Persistence onlyPackage dependency graphThe coach cannot make network calls mid-conversation
DesignSystem depends on nothingPackage dependency graphComponents stay previewable and reusable across every module
No feature folder imports another feature folderReview; see 2.6Screens compose only through Components and DesignSystem

1.3The DailyMetrics spine

This is the single most consequential decision in the system. One row per calendar day. Every source writes into it; every reader reads from it.

What the single-table choice buys

  • Trends become a sort, not a multi-source asynchronous join.
  • The coach queries one table instead of orchestrating two network APIs mid-conversation — which is what makes a 3B on-device model viable.
  • Offline works by default, because nothing renders from a live network call.
  • Adding a source later means writing into the same row, not building a new pipeline.
  • Every ViewModel has the same dependency — one store protocol — so screens stay uniform and stubbable.

1.4Local first topology

SwiftData on-device is the source of truth for the UI. Supabase is backup, sync, and a place to run jobs that a sleeping phone cannot.

1.5Conflict resolution

Field-level last-write-wins, using updatedAt. Not row-level.

Row-level LWW would be a bug here. The nightly Whoop job writes recovery fields at 04:00; if you logged water at 23:00 the night before, a row-level overwrite silently discards it. Field-level merge means each writer touches only its own columns.

This is defensible only because there is exactly one human user and the writers rarely contest the same field: HealthKit owns the health columns, the Whoop job owns the Whoop columns, and you own the manual ones. If this app ever became multi-user, this strategy would need replacing outright.

Known limitation LWW depends on clock agreement between the device and the Edge Function. Device clock skew of more than a few minutes can cause a stale write to win. Accepted for a single-user personal app; documented so it isn't rediscovered as a mystery bug.

Chapter two

2MVVM and project structure

Every screen in Life OS is built the same way: a Model of value types, a ViewModel that owns all state and every decision, and a View that renders and forwards intent. The folder layout mirrors that exactly, one folder per screen, so a file's path tells you its layer before you open it.

2.1Why MVVM here

SwiftUI will happily let a view query the database. @Query in a View is one line and works immediately — and it is the reason this app does not do it. Three specific things break:

  • Nothing is testable without a simulator. Goal evaluation, streak arithmetic, and weekly deltas are the parts most likely to be wrong, and they would live inside a view body that only a running device can exercise.
  • Derivation gets re-run per render. Status-per-day, the month grid, the streak — computed in body, they recompute on every state change, including ones that have nothing to do with them.
  • Persistence types leak into layout code. Once a view knows what a @Model class is, changing the schema means editing views.

MVVM fixes all three for the price of one extra file per screen. The ViewModel does the fetching and all derivation once, hands the View a plain value type, and can be exercised in a unit test with a stub store in milliseconds.

The rule that makes it work A ViewModel never imports SwiftUI, and a View never imports SwiftData. Both are checkable by reading the first ten lines of a file, and between them they force everything else into place.

2.2What each layer owns

LayerLives inShapeMay import
Domain model LifeOSKit/Sources/Persistence @Model classes, store, pure logic Foundation, SwiftData
Feature model Features/<Screen>/Model struct, Sendable, Equatable — the screen's rendered state Foundation, Persistence value types
ViewModel Features/<Screen>/ViewModel @Observable @MainActor final class Foundation, Observation, Persistence — never SwiftUI
View Features/<Screen>/View struct: View, plus its private subviews SwiftUI, DesignSystem, its own ViewModel — never SwiftData
Shared component Components/{Model,ViewModel,View} Same three shapes, reused by two or more screens As above
Design primitive LifeOSKit/Sources/DesignSystem Stateless View structs and tokens SwiftUI only — knows nothing about the app

The distinction between the last two rows is the one people get wrong. DesignSystem holds things that would make sense in any app — HeroNumeral, DotGrid, GlassCard. Components holds things that are reusable but specifically about this app's data — the quick-log sheet, the connection row, the metric tile that knows a missing value renders as an em dash.

Why this works without touching the project file The app target uses a PBXFileSystemSynchronizedRootGroup. Any folder created under LIfeOS/ is picked up by Xcode automatically — the directory structure is the project structure, and no one has to remember to add files to a target. Moving a screen between folders is a git mv, with no project file to merge.
The corollary: don't put documentation in these folders Synchronised membership means every file is a build input. A README.md in each folder is copied into the app bundle as a resource, and twenty-three of them collide on the same destination path — Multiple commands produce …/LIfeOS.app/README.md. Empty folders are held open by a hidden .gitkeep, which Xcode ignores; the layer contracts are documented here instead.

2.4Anatomy of a feature folder

Every feature folder answers the same four questions in the same order. Chapters 4 to 9 are each one instance of this template.

FolderContainsTest
Model/ One snapshot struct per screen, plus any small enums it needs. Value types only. No methods that fetch, no dates computed from .now. Compiles without SwiftUI or SwiftData
ViewModel/ Exactly one class. Holds private(set) var snapshot, a loadState, the store dependency, and the funcs the view calls. Instantiable in a unit test with a stub store
View/ The screen struct and its private subviews. Reads only from its view model; owns @State for presentation concerns like sheet visibility and focus. Every subview has a #Preview in both schemes

The ViewModel shape is identical everywhere, which is the point:

@Observable
@MainActor
final class BodyViewModel {
    private(set) var snapshot: BodySnapshot = .empty
    private(set) var state: LoadState = .idle

    private let store: MetricsReading
    private let calendar: Calendar

    init(store: MetricsReading, calendar: Calendar = .current) {
        self.store = store
        self.calendar = calendar
    }

    func load() async { … }        // called from .task
    func refresh() async { … }     // called from .refreshable
}

LoadState is a four-case enum shared by every screen — .idle, .loading, .loaded, .failed(String) — and lives in Components/Model. One vocabulary for "what is this screen doing right now" is worth more than per-screen nuance.

2.5Shared components

Components/ is split into the same three folders, for the same reason: a shared piece of UI that owns state has a view model, and it belongs somewhere obvious.

ComponentModelViewModelUsed by
MetricTile MetricReading<Value> None — stateless Today, Activity, Recovery, Body
MetricValueLabel MetricReading<Value> None — stateless Every screen with a number on it
QuickLogSheet QuickLogDraft QuickLogViewModel — writes water and weight Root FAB, from any tab
ConnectionRow ConnectionStatus ConnectionRowViewModel — reconnect actions Settings; Recovery's empty state

A component earns its place in Components/ the second time it is needed, not the first. The first time, it is a private subview inside the feature that needs it. Promoting it is a file move between two folders that already exist.

Where the em-dash rule lives "A missing metric renders as an em dash at 35% opacity, never as 0" is the single most repeated rule in this app. It is implemented once, in Components/View/MetricValueLabel.swift, and every screen renders numbers through it. A rule stated in a handbook and implemented in nine places is a rule that will be broken in one of them.

Chapter three

3Design system

Ten modules have to read as one app. That happens because they share a small set of primitives and differ by exactly one variable — the module hue — rather than because each screen was designed carefully on its own.

3.1Principle

The hub is neutral; the domains are coloured. Today is a warm off-white canvas. Every domain screen is a saturated-at-top, near-white-at-bottom gradient in its own hue. This resolves two competing visual languages into one hierarchy instead of a collision, and it means adding a module later is a token, not a design exercise.

3.2Tokens

TokenValueMeaning
ModuleHue.bodyTealWeight and composition
ModuleHue.activityAmberMovement
ModuleHue.recoveryBlueWhoop, HRV, sleep quality
ModuleHue.nutritionPurpleV3
ModuleHue.moneyGreenV6
ModuleHue.habitsOrangeV4

The accent never varies by module. It marks the current day, the FAB, the selected tab, and alert states. Everything else on screen is the module hue or a neutral. Two colours competing for "this is important" is the fastest way to make neither mean anything.

Colours are AdaptiveColor pairs resolved explicitly by the consuming view rather than UIKit dynamic colours, because the package also builds for macOS so that swift test runs from the terminal without a simulator. Explicit resolution is the price of fast tests.

The tab bar is circular icons plus a floating dark FAB for logging. In V1 the FAB logs water and weight only — the two metrics with no automatic source. Both write to local DailyMetrics through QuickLogViewModel; the app requests no HealthKit write permissions in V1. The FAB's menu grows in later slices (meals in V3, habits in V4).

3.4Dark mode

Every hue has a dark variant: deep saturated top, near-black bottom, card materials inverted. These are defined as tokens in V1, before any screen exists, because retrofitting a gradient system to dark mode later is significantly harder than doing it once at the start.

No colour is defined only inside a scheme branch Every token has a light value and a dark value, always both. A colour that exists only in the dark branch renders as whatever the parent inherited in light mode — usually black on black, and usually discovered by a user rather than a preview.

Chapter four · Feature

4Today

The hub. Neutral canvas, oversized date, week strip, a month of dots, and four tiles. It answers "am I on track" before you have processed a single number.

4.1Intent

Working backwards · V1 feature

Today opens with the date at the size of a poster, a strip of the current week, and a grid of dots — one per day this month. Filled dots are days you hit your targets, hollow dots are days you didn't, and today is orange. Underneath, four tiles: steps, sleep, weight, recovery. You can read the whole month in about a second.

What makes a dot fill?

Meeting 3 of 4 daily goals: steps ≥ 8,000, sleep ≥ 7h, exercise ≥ 30 min, water ≥ 2,500 ml. All five values — the four goals and the required count — are editable in Settings. The rule is deliberately explicit; a vague definition makes the entire grid meaningless.

What happens on a day with no data at all?

It renders as no-data, not as a miss, and it is excluded from streak arithmetic entirely. Leaving your watch on the charger is not a moral failure, and a system that punishes it teaches you to distrust the streak.

And a day with some data?

Judged on what it has. If steps are logged at 500 and nothing else was recorded, that's a miss. The alternative — treating partial days as blank — would let forgetting to log water silently launder a bad day into a neutral one.

If I change a goal, does history change?

Yes. Status is computed on read, never stored, so past dots re-evaluate against the new target immediately. The grid answers "how am I doing against my current standard," not "how did I do against a standard I've since abandoned."

Screen anatomy

  • Header — day numeral at 92pt, month and year, weekday, all derived from the selected date.
  • WeekStrip — seven days, today filled orange, selection bound to the ViewModel.
  • Month card — month label, streak count in accent, DotGrid.
  • Tile grid — steps, sleep, weight, recovery; each a MetricTile.

4.3Model

struct TodaySnapshot: Equatable, Sendable {
    var selectedDate: Date
    var monthLabel: String
    var cells: [DotCell]                     // from MonthGridLayout
    var streak: Int
    var steps: MetricReading<Int>
    var sleepMinutes: MetricReading<Int>
    var weightKg: MetricReading<Double>
    var recoveryPct: MetricReading<Double>

    static let empty = TodaySnapshot(…)
}

MetricReading is the shared component model: a value that may be absent, and a goal that may not exist. It is what carries the missing-versus-zero distinction from the database all the way to the label without any screen having to remember it. 

struct MetricReading<Value: Equatable & Sendable>: Equatable, Sendable {
    var value: Value?          // nil renders an em dash — never 0
    var goal: Value?
    var unit: String?
}

4.4ViewModel

@Observable
@MainActor
final class TodayViewModel {
    private(set) var snapshot: TodaySnapshot = .empty
    private(set) var state: LoadState = .idle

    private let store: MetricsReading
    private let calendar: Calendar

    init(store: MetricsReading, calendar: Calendar = .current) { … }

    func load() async                  // .task
    func refresh() async               // .refreshable
    func select(_ date: Date) async    // WeekStrip binding
}

Inside load(), in order:

  1. Fetch the visible month plus enough history for the streak, most-recent-first.
  2. Fetch GoalTargets.
  3. evaluate each day once, into a date-keyed dictionary — not once per dot, which is what a view-body implementation ends up doing.
  4. Ask MonthGridLayout for the cells, mapping DayStatus to DotState. This mapping lives here because Persistence must not depend on DesignSystem.
  5. Compute currentStreak.
  6. Publish one TodaySnapshot. A single assignment means a single render.

4.5View

struct TodayScreen: View {
    @State private var vm: TodayViewModel
    @Environment(\.colorScheme) private var scheme

    init(store: MetricsReading) {
        _vm = State(initialValue: TodayViewModel(store: store))
    }

    var body: some View {
        ScrollView {
            VStack(alignment: .leading, spacing: 24) {
                TodayHeader(snapshot: vm.snapshot)
                WeekStrip(selection: Binding(
                    get: { vm.snapshot.selectedDate },
                    set: { date in Task { await vm.select(date) } }
                ))
                SolidCard { monthSection }
                TodayTileGrid(snapshot: vm.snapshot)
            }
            .padding(20)
            .padding(.bottom, 100)
        }
        .background(LifeOSTokens.canvas.resolve(scheme))
        .task { await vm.load() }
        .refreshable { await vm.refresh() }
    }
}

No @Query, no modelContext, no arithmetic. Every subview takes the snapshot or a slice of it, which is what makes previews trivial: construct a TodaySnapshot literal and render.

Chapter five · Feature

5Body

Teal. Your weight at 96 points and nothing competing with it, a weekly delta beneath, and a fourteen-day bar chart where the days you skipped are visibly gaps.

5.1Intent

Working backwards · V1 feature

Body is a teal screen with your weight as the hero. Below it, the week's change with direction, and a fourteen-day bar chart where each bar is a weigh-in. Days you didn't step on the scale are gaps, not interpolations.

Where does weight come from?

Your Renpho scale, via Apple Health. Renpho already syncs there, so Life OS never talks to Renpho directly — one less integration, one less thing to break, and no third-party credentials to store.

Why a weekly delta instead of a trend line?

Daily bodyweight is mostly water and noise. A seven-day delta is the shortest window where the signal beats the noise, and it's the number that actually changes behaviour.

What if I weigh myself twice in one day?

The row for that day holds one weight; the most recent write wins. For a daily-granularity app the second weigh-in is the better one anyway.

Screen anatomy

  • GradientCanvas(hue: .body) behind everything.
  • HeroNumeral — weight, one decimal, unit always shown.
  • Delta row — signed change over seven days, with direction.
  • 14-day bar chart — one bar per weigh-in, gaps preserved.

5.3Model

struct BodySnapshot: Equatable, Sendable {
    var current: MetricReading<Double>       // kg, nil when never weighed
    var weeklyDeltaKg: Double?               // nil when < 7 days of history
    var bars: [WeightBar]                    // oldest first, gaps included
}

struct WeightBar: Identifiable, Equatable, Sendable {
    var id: Date { date }
    var date: Date
    var weightKg: Double?                    // nil renders a gap, not a zero bar
}
The gap is the data WeightBar.weightKg is optional so the chart can render an absence. Filtering absent days out of the array instead would silently compress the x-axis and make a fortnight of two weigh-ins look like two consecutive days.

5.4ViewModel

@Observable @MainActor
final class BodyViewModel {
    private(set) var snapshot: BodySnapshot = .empty
    private(set) var state: LoadState = .idle
    private let store: MetricsReading

    func load() async
    func refresh() async
}

The delta rule, implemented once, here:

  • Take the most recent weight as the hero. If there is none, current.value stays nil and the hero renders an em dash with its unit.
  • Find the most recent weight at least seven days older than the hero's date. If there isn't one, the delta is suppressed entirely rather than computed over a shorter window — a "weekly change" measured over two days is a wrong number wearing a right label.
  • Build fourteen bars by walking the calendar backwards, not by iterating the fetched rows, so missing days become nil bars rather than disappearing.

7Recovery

Blue. Whoop's recovery percentage as the hero — the number you would otherwise open the Whoop app to see — with HRV, day strain, and sleep performance beneath it.

7.1Intent

Working backwards · V1 feature

Chapter nine · Feature V2

9The Coach

One card every morning: what you did well yesterday, what slipped, and one thing to fix today. Built from your actual numbers, on-device, and structurally unable to invent them.

9.1Intent

Working backwards · V2 feature

Every morning, one card: what you did well yesterday, what slipped, and one thing to fix today. Built from your actual weight, sleep, recovery, steps, calories, and water. Ask it anything — "why is my recovery tanking?" — and it queries your real records to answer rather than guessing.

Does my health data go to a server?

For the coach, no. It runs on Apple's on-device Foundation Models — free, private, offline, no API key. Only food photos leave the device, because the on-device model is text-only and cannot see an image.

How does it avoid making numbers up?

Tool calling. The model doesn't receive your data in a prompt; it calls Swift functions that query DailyMetrics and returns what they hand back. A number it had to look up is a number it cannot hallucinate — and the context stays small enough for a 3B on-device model.

What if the on-device model isn't available?

SystemLanguageModel.availability is checked at runtime. On a device without Apple Intelligence, or while the model is still downloading, the coach degrades to unavailable rather than silently shipping health data to a cloud provider without asking.

Freshness

  • HKAnchoredObjectQuery with a persisted anchor per type, so each sync fetches only what changed since last time.
  • enableBackgroundDelivery so iOS wakes the app when new samples land.
  • HKStatisticsCollectionQuery for daily aggregates — this de-duplicates across sources. Summing raw samples yourself double-counts steps on any day you carried both an iPhone and a Watch.
The authorization trap HealthKit read authorization is deliberately opaque. The API will not tell you whether the user denied a type — only whether you have asked. Branching on read authorization status is therefore always a bug. Query anyway, and treat an empty result as "no data," rendering an explicit empty state. Apple designed it this way so apps cannot detect that you are hiding a condition from them.

10.2Whoop

Base URL https://api.prod.whoop.com, API v2. v1 is deprecated. Note that v2 identifies sleep by UUID rather than integer ID, and recovery webhooks reference the associated sleep UUID, not the cycle ID — a migration footgun worth knowing before you read the payloads.

Scopes

offline is required to receive a refresh token. Without it, the integration breaks the first time the access token expires.

OAuth — and why the secret never ships

Whoop's token exchange requires a client secret. Embedding it in the app binary would make it extractable with strings. Supabase Edge Functions solve this cleanly: the app does PKCE and obtains a code; the function exchanges it.

Nightly job and webhooks

  • A scheduled Edge Function (pg_cron) pulls the previous day's cycle, recovery, and sleep overnight, so morning data exists before you open the app.
  • A whoop-webhook function receives push updates. Signature verified against WHOOP_WEBHOOK_SECRET; unverified requests are rejected outright.
  • Webhooks are only possible because a public HTTPS endpoint now exists. A phone alone cannot receive them.

10.3Supabase

Schema

Mirrors the local SwiftData models: daily_metrics, workout_records, sleep_records, whoop_raw, and sync_state.

whoop_raw stores unprocessed API payloads. This is deliberate: when Whoop's response shape differs from the documentation — and it will — you can re-derive every downstream value without re-fetching a month of history against a rate limit.

Row Level Security

RLS is enabled on every table, without exception Policies scope all access to auth.uid(). This is precisely what makes shipping the anon key inside the app safe. An RLS misconfiguration does not throw — it returns an empty result set, which looks exactly like "no data yet." Verify policies with a real query before trusting an empty screen.

11.5Store protocols

MetricsStore is the only path by which anything writes to DailyMetrics. It enforces the one-row-per-day invariant so callers cannot get it wrong. This is what ships today: 

public struct MetricsStore {
    public init(context: ModelContext, calendar: Calendar = .current)

    @discardableResult
    public func upsert(date: Date, apply: (DailyMetrics) -> Void) throws -> DailyMetrics
    public func upsertBatch(dates: [Date], apply: (Date, DailyMetrics) -> Void) throws
    public func metrics(from: Date, to: Date) throws -> [DailyMetrics]   // most-recent-first
    public func goals() throws -> UserGoals                              // defaults on first access
}

upsert normalises any timestamp to startOfDay and merges — fields the closure doesn't touch are preserved. That is what lets HealthKit and Whoop write the same row safely.

The protocols MVVM needs to be added

The concrete API above returns @Model instances, which a ViewModel must not hold — see 2.6. Two protocols close that gap, implemented by MetricsStore in an extension: 

public protocol MetricsReading: Sendable {
    func days(from: Date, to: Date) async throws -> [DayRecord]   // most-recent-first
    func targets() async throws -> GoalTargets
}

public protocol MetricsWriting: Sendable {
    func logWater(_ millilitres: Double, on date: Date) async throws
    func logWeight(_ kilograms: Double, on date: Date) async throws
    func updateTargets(_ targets: GoalTargets) async throws
}

DayRecord is a Sendable struct mirroring the columns of DailyMetrics. The store converts on the way out.

Why the protocols return value types Handing a @Model instance to a ViewModel would give every screen a live, mutable handle on the database and make each one require a ModelContainer to test. Returning DayRecord costs one map per fetch and buys back both.

The protocol methods are async while the store's are synchronous. That is deliberate: the store wraps trivially today, and when a fetch eventually moves off the main actor no ViewModel or test has to change.

Same row edited locally and by the nightly jobField-level LWW — the job's Whoop columns and your water column both survive
Supabase session expiresRefresh silently; on hard failure, sync pauses and Settings shows it. The app keeps working
RLS policy misconfiguredReturns empty, does not throw. Indistinguishable from "no data" — verify policies explicitly
Schema drift SwiftData ↔ PostgresDecoding failures logged per-row and skipped; one bad row never halts a sync

13.2Secrets

There is no runtime .env on iOS. The app is a signed bundle; anything shipped inside it is extractable. The governing rule is therefore: what must never leak, must live server-side.

TierLocationContentsIn git?
1 · Build config Config/Secrets.xcconfig Supabase URL, anon key, Whoop client ID Gitignored. Template committed
2 · Runtime Keychain Whoop access + refresh tokens, Supabase session Never
3 · Server Edge Function env WHOOP_CLIENT_SECRET, WHOOP_WEBHOOK_SECRET, ANTHROPIC_API_KEY, SERVICE_ROLE_KEY Never. Never on device either

Nothing in Tier 1 is truly secret. The Supabase anon key is designed to ship in clients — it is safe precisely because RLS gates every row — and the Whoop client ID is public by OAuth design. Tier 1 is gitignored for hygiene, not because a leak would be catastrophic.

service_role is the one that matters It bypasses RLS entirely. It belongs only in an Edge Function environment — never in an xcconfig, never in the app target, never in git. Every other secret in this system is recoverable by rotation; this one grants total read and write access to everything.

13.3Testing strategy

Logic that can be tested without a simulator lives in the package and is developed test-first. ViewModels are tested in the app's own test target against stub stores. SwiftUI view bodies are verified by previews and a build — asserting on view structure is ceremony that breaks on every layout change without catching real defects.

The package declares a macOS platform alongside iOS purely so swift test --package-path LifeOSKit runs from the terminal without booting a simulator. Integration modules guard platform-specific imports with #if canImport(HealthKit) to preserve this.

The one test that matters most For every screen: an empty store must produce a snapshot whose readings are all nil. It is a four-line test per feature and it is the regression guard against the single worst bug this app can have — a confident zero where there is no data.

Appendix A

AProduct thesis

A.1The thesis

Every health app you already have is a silo. Whoop knows your recovery but not that you skipped breakfast. Apple Health knows your steps but not that you blew the grocery budget and slept badly because of it. Each one gives advice that is correct in isolation and useless in context.

Life OS is built on a single bet: the value is in the join, not the collection. A coach that can see you missed meditation, logged 5 hours of sleep, journalled "low focus," and went 900 calories over can say something no single-purpose app can. That is the entire reason to build one app instead of using five.

Everything in the architecture follows from that bet. There is one table keyed by date that every source writes into and every reader reads from. Cheap manual modules ship early precisely because they make the coach smarter, not despite being simple.

A.2Product PR FAQ

Working backwards · Product

Life OS is a personal dashboard that pulls together everything your devices already know about you — weight from your scale, recovery from your strap, movement from your watch, and what you ate from a photo — and answers one question every morning: am I on track? Open it and a grid of dots shows the month at a glance. Filled means a good day. The app knows what a good day means because you told it.

Who is this for?

One person. This is a personal app, sideloaded on the author's own devices. There are no accounts, no other users, and no App Store distribution. That constraint removes an enormous amount of architecture and is load-bearing throughout this document.

Why not just use Apple Health?

Apple Health is an excellent store and a poor interpreter. It will show you a chart of anything and tell you the meaning of nothing. Life OS reads from it, then adds the layer Health deliberately doesn't: a definition of a good day, a streak that survives days you forgot to log, and eventually a coach that reads across domains.

What is explicitly not in this product?

Screen time analysis. It was requested and it cannot be built — see 10.5 for the technical reason. Rather than ship a hollow version, it is cut.

What's the hardest part?

Not the integrations. It's friction: any app that requires daily manual logging dies in about eleven days. Every product decision here is subordinate to keeping the daily cost near zero — which is why food logging is a photo, not a form.

A.3Roadmap

V1 is the only slice specified in detail. Each subsequent slice gets its own spec and plan, and adds one feature chapter to this handbook.
