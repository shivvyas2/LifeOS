Chapter one

1Architecture

Life OS is a local-first iOS app built on one bet: the value is in the join, not the collection. Every architectural decision below follows from it. Four devices produce data, all of it converges on a single table keyed by calendar day, and every screen reads from that table and nothing else.

This document describes a system that is designed but not finished. V1 is in active implementation. Where the code and this handbook disagree, the code is right and this handbook is a bug. The product reasoning that led here is in Appendix A; it is deliberately behind the engineering, not in front of it.

1.1System context

Four devices produce data, two of them reach the app through Apple Health, one through a REST API, and one (your MacBook) cannot reach it at all. Everything converges on a single local store before anything renders.

1.2Module map

LifeOSKit is a local Swift package providing compile-time boundaries. The app target contains only features and wiring, laid out per screen as described in Chapter 2. The dependency rules are enforced by the compiler, not by convention.

1.3The DailyMetrics spine

This is the single most consequential decision in the system. One row per calendar day. Every source writes into it; every reader reads from it.

What the single-table choice buys

  • Trends become a sort, not a multi-source asynchronous join.
  • The coach queries one table instead of orchestrating two network APIs mid-conversation, which is what makes a 3B on-device model viable.
  • Offline works by default, because nothing renders from a live network call.
  • Adding a source later means writing into the same row, not building a new pipeline.
  • Every ViewModel has the same dependency: one store protocol, so screens stay uniform and stubbable.

1.4Local first topology

SwiftData on-device is the source of truth for the UI. Supabase is backup, sync, and a place to run jobs that a sleeping phone cannot.

1.5Conflict resolution

Field-level last-write-wins, using updatedAt. Not row-level.

Row-level LWW would be a bug here. The nightly Whoop job writes recovery fields at 04:00; if you logged water at 23:00 the night before, a row-level overwrite silently discards it. Field-level merge means each writer touches only its own columns.

This is defensible only because there is exactly one human user and the writers rarely contest the same field: HealthKit owns the health columns, the Whoop job owns the Whoop columns, and you own the manual ones. If this app ever became multi-user, this strategy would need replacing outright.

Known limitation LWW depends on clock agreement between the device and the Edge Function. Device clock skew of more than a few minutes can cause a stale write to win. Accepted for a single-user personal app; documented so it isn't rediscovered as a mystery bug.

Chapter two

2MVVM and project structure

Every screen in Life OS is built the same way: a Model of value types, a ViewModel that owns all state and every decision, and a View that renders and forwards intent. The folder layout mirrors that exactly, one folder per screen, so a file's path tells you its layer before you open it.

2.1Why MVVM here

SwiftUI will happily let a view query the database. @Query in a View is one line and works immediately, and it is the reason this app does not do it. Three specific things break:

  • Nothing is testable without a simulator. Goal evaluation, streak arithmetic, and weekly deltas are the parts most likely to be wrong, and they would live inside a view body that only a running device can exercise.
  • Derivation gets re-run per render. Status-per-day, the month grid, the streak, computed in body, recompute on every state change, including ones that have nothing to do with them.
  • Persistence types leak into layout code. Once a view knows what a @Model class is, changing the schema means editing views.

MVVM fixes all three for the price of one extra file per screen. The ViewModel does the fetching and all derivation once, hands the View a plain value type, and can be exercised in a unit test with a stub store in milliseconds.

The rule that makes it work A ViewModel never imports SwiftUI, and a View never imports SwiftData. Both are checkable by reading the first ten lines of a file, and between them they force everything else into place.
Where are the view controllers? There are none, and that is not an omission. UIViewController is UIKit's unit of screen ownership: it exists to manage a view hierarchy's lifecycle by hand (viewDidLoad, viewWillAppear, manual reloads). SwiftUI replaces that whole job with declarative views that re-render from state, so the controller's two remaining responsibilities split cleanly: owning state and making decisions went to the ViewModel, and describing what is on screen went to the View struct. If you come looking for the controller layer, the ViewModel is where it went, minus the lifecycle boilerplate that SwiftUI made unnecessary.

Why this works without touching the project file The app target uses a PBXFileSystemSynchronizedRootGroup. Any folder created under LIfeOS/ is picked up by Xcode automatically, because the directory structure is the project structure, and no one has to remember to add files to a target. Moving a screen between folders is a git mv, with no project file to merge.
The corollary: don't put documentation in these folders Synchronised membership means every file is a build input. A README.md in each folder is copied into the app bundle as a resource, and twenty-three of them collide on the same destination path: Multiple commands produce …/LIfeOS.app/README.md. Empty folders are held open by a hidden .gitkeep, which Xcode ignores; the layer contracts are documented here instead.

2.4Anatomy of a feature folder

Every feature folder answers the same four questions in the same order. Chapters 4 to 9 are each one instance of this template.

FolderContainsTest
Model/ One snapshot struct per screen, plus any small enums it needs. Value types only. No methods that fetch, no dates computed from .now. Compiles without SwiftUI or SwiftData
ViewModel/ Exactly one class. Holds private(set) var snapshot, a loadState, the store dependency, and the funcs the view calls. Instantiable in a unit test with a stub store
View/ The screen struct and its private subviews. Reads only from its view model; owns @State for presentation concerns like sheet visibility and focus. Every subview has a #Preview in both schemes

The ViewModel shape is identical everywhere, which is the point:

@MainActor @Observable
final class BodyViewModel {
    private(set) var snapshot = BodySnapshot()
    var selectedDate: Date = .now

    private var context: ModelContext?
    private let calendar: Calendar

    init(calendar: Calendar = .current) { self.calendar = calendar }

    func attach(_ context: ModelContext) { self.context = context }
    func select(_ date: Date) { selectedDate = date; load() }
    func load() { … }
}

Nine view models follow this shape exactly. The context arrives through attach rather than the initialiser because RootView constructs them all as @State before the environment is available, and a snapshot with its empty default is a valid thing to render in the meantime.

Injection is by context today, not by protocol Every view model builds a concrete store from a ModelContext, so testing one means standing up an in-memory ModelContainer rather than passing a stub. The protocol surface that fixes this is specified in 12.5 and has not been built. It is why the package has 70 tests and the feature layer has none.

There is no shared LoadState. A load either replaces the snapshot or trips an assertionFailure and leaves the previous one in place: local SwiftData reads do not fail in ways a user can act on, and a spinner vocabulary for an operation that takes a millisecond would be ceremony. Network-backed state lives on the one view model that has any, in 9.4.

Chapter three

3Design system

Ten modules have to read as one app. That happens because they share a small set of primitives and differ by exactly one variable (the module hue) rather than because each screen was designed carefully on its own.

3.1Principle

The hub is neutral; the domains are coloured. Today is a warm off-white canvas. Every domain screen is a saturated-at-top, near-white-at-bottom gradient in its own hue. This resolves two competing visual languages into one hierarchy instead of a collision, and it means adding a module later is a token, not a design exercise.

Colours are AdaptiveColor pairs resolved explicitly by the consuming view rather than UIKit dynamic colours, because the package also builds for macOS so that swift test runs from the terminal without a simulator. Explicit resolution is the price of fast tests.

3.4Dark mode

Every hue has a dark variant: deep saturated top, near-black bottom, card materials inverted. These are defined as tokens in V1, before any screen exists, because retrofitting a gradient system to dark mode later is significantly harder than doing it once at the start.

No colour is defined only inside a scheme branch Every token has a light value and a dark value, always both. A colour that exists only in the dark branch renders as whatever the parent inherited in light mode, usually black on black, and usually discovered by a user rather than a preview.

Chapter four · Feature

4Onboarding

Four pages of pitch, then an identity, then a name, then the connections. Signup is mandatory and it is the only entry point, so this flow is the one screen every user sees before any other.

4.1Intent

Working backwards · V1 feature

Life OS opens on a four-page intro, one page per life domain in tab order. Signing in takes a phone number or an email address and a code, a first and last name, and then offers Whoop and Apple Health. Every connection is skippable. Nothing on the way in asks for a password.

Why is there an account at all in a personal app?

Because the data outlives the phone. The account is what lets Supabase hold a backup and run nightly jobs, and it is what Row Level Security keys every row to. Without it, a lost device is a lost year.

Why no password?

A password is a credential to lose, store and reset. A one-time code delivered to a channel the user already controls proves the same thing with no secret at rest and no reset flow to build.

Phone or email?

Phone, when the project can send SMS. The app asks Supabase which channels are actually enabled before it renders the choice, and falls back to email when SMS is not configured, rather than offering a button that silently fails.

Why can every connection be skipped?

Because a screen that blocks on a Whoop login is a screen people abandon. Everything Life OS shows degrades to a blank rather than a wrong number, so an unconnected app is honest, not broken. Connections are offered again in Settings.

Flow anatomy

  • IntroScreen: four pages, one per domain, each carrying its own hue.
  • IdentityScreen: channel switcher, dial-code picker, destination field.
  • CodeScreen (phone) or LinkSentScreen (email).
  • ProfileScreen: first name, last name, country.
  • ConnectionsScreen: Whoop now, Health and Plaid marked as next release.

4.3Model

enum OnboardingStep: Equatable {
    case intro
    case identity            // phone or email
    case code                // OTP (phone)
    case linkSent            // magic link (email)
    case profile             // name, country
    case connections         // Whoop and Health, all optional
}
One enum, not five booleans OnboardingStep is a single value because the alternative, hasSentCode && !hasVerified && isEmail, can represent states that do not exist. A user cannot be on the code screen and the profile screen at once, and the type should say so. 
struct SignupDraft: Equatable {
    var channel: SupabaseAuthChannel = .phone
    var phone = ""
    var dialCode = "+1"
    var email = ""
    var code = ""
    var firstName = ""
    var lastName = ""
    var country = Locale.current.region?.identifier ?? "US"

    var e164: String { dialCode + phone.filter(\.isNumber) }
    var destination: String {
        channel == .phone ? e164 : email.trimmingCharacters(in: .whitespaces)
    }

    var canSendCode: Bool
    var canVerify: Bool
    var canFinishProfile: Bool
}

The draft holds what the user typed, before any of it is trusted. The three can… properties are the only validation in the feature, and they live on the model rather than in a view so a disabled button and a rejected submit can never disagree.

DialCountries.all is built from Locale.Region.isoRegions rather than a hand-typed list, so it is complete and localised. A region with no known dial code is dropped rather than guessed at: offering the wrong prefix sends an SMS into the void, and the user has no way to tell that is what happened.

The rules that live here, and nowhere else:

  • Channel availability is asked, not assumed. loadChannels() reads auth/v1/settings and switches the default to email when SMS is off. The identity screen shows a note explaining why rather than leaving a dead button on screen.
  • Email uses a magic link, deliberately and temporarily. The free tier will not let the email template carry a six-digit token, so emailUsesMagicLink is true and the flow diverts to .linkSent. Flip that one constant once custom SMTP is configured and the OTP screen returns with no other change.
  • A failed profile write does not strand the user. The account already exists by then, so saveProfile() records the error and advances to .connections anyway. Blocking the last step of signup on a metadata write would trade a cosmetic failure for an unusable app.
  • Resend is rate-limited in the UI. A thirty-second countdown starts on every send, because the server's own limit answers with a 429 the user cannot interpret.
The tokens arrive in the fragment, not the query Supabase returns a magic-link session in the URL fragment. queryItems finds nothing there, so the callback looks empty until the fragment is parsed by hand. AuthSession(callback:) reads both, and AuthSession.errorDescription(in:) pulls error_description out of the same place so an expired link says so.

4.5View

Every signup step is the same shape: a back control, a title, a subtitle, one field group and one primary button. SignupScaffold owns that shape so the four screens differ only in their content, which is what keeps them from drifting apart visually as they are edited.

IntroScreen renders IntroPage.all in a TabView pager. The pages are data rather than four hand-written views for the same reason: a loop cannot let page three fall out of step with page one.

ConnectionsScreen is the only onboarding screen that reads live state. It takes the shared WhoopConnectionViewModel, so a connection made here is already made when Settings opens later, and it renders Health and Plaid as explicitly next-release rather than as buttons that do nothing.

Tests

None of these exist yet. Auth is the largest untested surface in the app, and the three below are the ones worth writing first, because each covers a parsing rule that fails silently.

  • SignupDraft validation: a six-digit code with spaces verifies, a five-digit one does not; an email without a dot does not send.

5Today

5.1Intent

Working backwards · V1 feature

What makes a dot fill?

Meeting 3 of 4 daily goals: steps ≥ 8,000, sleep ≥ 7h, exercise ≥ 30 min, water ≥ 2,500 ml. All five values (the four goals and the required count) are editable in Settings. The rule is deliberately explicit; a vague definition makes the entire grid meaningless.

What happens on a day with no data at all?

It renders as no-data, not as a miss, and it is excluded from streak arithmetic entirely. Leaving your watch on the charger is not a moral failure, and a system that punishes it teaches you to distrust the streak.

And a day with some data?

Judged on what it has. If steps are logged at 500 and nothing else was recorded, that's a miss. The alternative, treating partial days as blank, would let forgetting to log water silently launder a bad day into a neutral one.

If I change a goal, does history change?

Yes. Status is computed on read, never stored, so past dots re-evaluate against the new target immediately. The grid answers "how am I doing against my current standard," not "how did I do against a standard I've since abandoned."

ActivityViewModel and RecoveryViewModel read exactly one row: the selected day, no history. BodyViewModel is the one that derives anything:

  • Fetch sixty days ending at the selected date, most-recent-first.

7Money

What you kept this month as the hero, income and expenses and savings rate beneath it, and the recent transactions under that. Built for Plaid from the first line, fed by hand until Plaid lands.

7.1Intent

Working backwards · V1 feature

Money is green. The hero is this calendar month's net, with a one-word verdict beneath it: on track, tight, or overspending. Three tiles carry income, expenses and the share of income you kept. Why is the savings rate sometimes blank rather than 0%?

Because a savings rate against no income is not zero, it is undefined. Rendering 0% would tell you that you saved nothing, when what actually happened is that nothing was logged. The whole app draws that distinction and this is the sharpest case of it.

Because the model, the store, the rollup and the screen are the work, and none of it depends on where the rows come from. Manual entry exercises all of it now and becomes a permanent feature anyway: cash exists, and Plaid will never see it.

What happens to a pending charge?

It is stored and shown, greyed, but excluded from every rollup. Plaid re-issues a pending transaction with a new identifier when it settles, so counting it twice is the default failure here, and the rollup refusing to see pending rows is what prevents it.

public func streak(for entry: PlanEntry, endingOn end: Date = .now) throws -> Int {
    let ticks = try recentTicks(for: entry, days: 365, endingOn: end)
    var count = 0
    for (index, done) in ticks.reversed().enumerated() {
        if done { count += 1 }
        else if index == 0 { continue }   // today still open
        else { break }
    }
    return count
}

Walk backwards from today, counting until a gap. The index == 0 clause is the whole rule from the PR FAQ, in one line: an unticked today is skipped rather than treated as a break. Yesterday unticked still ends the streak.

10The Coach

One card every morning: what you did well yesterday, what slipped, and one thing to fix today. Built from your actual numbers, on-device, and structurally unable to invent them.

10.1Intent

Working backwards · V2 feature

Every morning, one card: what you did well yesterday, what slipped, and one thing to fix today. Built from your actual weight, sleep, recovery, steps, calories, and water. Ask it anything, "why is my recovery tanking?", and it queries your real records to answer rather than guessing.

Does my health data go to a server?

Usually not. The coach floors on Apple's on-device Foundation Models: free, private, offline, no API key. Some requests genuinely exceed what a small model can do, and those escalate to a cloud model. What escalates is a MetricsDigest: derived numbers only, never raw Whoop payloads, heart-rate series, or identifiers. Food photos always leave, because the on-device model is text-only and cannot see an image.

So what actually leaves the device, and when?

Only on an escalated request, and only aggregates. The privacy rule is enforced by a type rather than by review: Engine.run takes a MetricsDigest, and DailyMetrics is a SwiftData @Model class that is not Sendable, so the compiler prevents a raw row from crossing the boundary. The calendar assistant is the one exception, and it is called out in 15.2: event titles are content, not numbers, and cannot be aggregated without destroying their use.

How does it avoid making numbers up?

Tool calling. The model doesn't receive your data in a prompt; it calls Swift functions that query DailyMetrics and returns what they hand back. A number it had to look up is a number it cannot hallucinate, and the context stays small enough for a 3B on-device model.

What if the on-device model isn't available?

SystemLanguageModel.availability is checked at runtime, and the request escalates to the cloud tier. Three reasons are distinguished: .deviceNotEligible is permanent and resolved once at launch, .appleIntelligenceNotEnabled is user-fixable and re-checked on foreground, and .modelNotReady is transient while weights download and is re-checked per request.

What about devices below iOS 26?

They have no on-device tier at all. FoundationModels requires iOS 26, and the app's deployment floor was lowered to iOS 18 in 7d85604 so TestFlight is not restricted to testers who have already upgraded. OnDeviceEngine is therefore @available(iOS 26, *) and the router treats an older OS as a fourth unavailability reason. Every coach and assistant turn on such a device escalates. This is the dominant cost case for a TestFlight cohort, and it is why the projections in chapter fifteen are stated per escalated turn rather than per turn.

11.2Whoop

The only source of Recovery %, Strain, and sleep staging, which is why it gets a direct API integration when every other wearable arrives through HealthKit. Everything below is API v2 against base URL https://api.prod.whoop.com/developer/v2; v1 is deprecated, and v2 identifies sleep by UUID rather than integer ID. The whole integration lives in LifeOSKit/Sources/Integrations and runs on the device: WhoopClient fetches, WhoopSync orchestrates, every payload is archived raw into SwiftData, and WhoopDerivation turns the archive into the same DailyMetrics rows every screen already reads. No screen knows Whoop exists.

Collections and scopes, defined in one place

WhoopCollection is a five-case enum pairing each endpoint path with the scope that authorizes it, and both the client and the OAuth request are driven from it:

CollectionEndpointScopeFeeds
RecoveryGET /recoveryread:recoveryRecovery %, HRV, resting HR, SpO2, skin temp
SleepGET /activity/sleepread:sleepDuration, stages, performance / efficiency / consistency, sleep debt
CycleGET /cycleread:cyclesDay strain, calories, average and max HR

The scope string sent to Whoop is exactly WhoopCollection.allCases.map(\.scope) + ["offline"]. offline is what makes Whoop return a refresh token; without it the connection dies the first time the access token expires, about an hour in. read:profile is deliberately not requested and /user/profile/basic never called: name and email are identity, not signal.

Why path and scope live in the same enum They used to be listed separately, and drifted: workout and body were added to the client while the authorize request still asked for three scopes. Whoop then 401s a token it issued seconds earlier, and the sync read that 401 as a dead credential and deleted it, so connect → sync became an unbreakable loop. Colocating them makes a fetchable-but-unauthorized collection unrepresentable. The same incident is why a 401 from a collection endpoint no longer clears tokens (see below).

OAuth, and why the secret never ships

Whoop registers apps as confidential clients: the token exchange requires a client secret, and an .ipa is a zip file, so a secret in the binary is a secret published. The whoop-token Supabase Edge Function is the fix: the app runs the authorize step with PKCE (S256 challenge over a random 32-byte verifier) and obtains a code; the function holds WHOOP_CLIENT_SECRET and performs the exchange. PKCE is kept even though the exchange is server-side, because it binds the code to this app instance — a code intercepted in transit is useless without the verifier.

Two implementation details of the authorize step matter in practice. First, the redirect is two hops: Whoop requires an https redirect URI, so the registered URI points at the whoop-callback Edge Function, which immediately 302s to lifeos://whoop-callback with the code and state attached. The hop holds no secret and makes no decisions; PKCE and the state check both still happen in the app, so anyone who reaches the endpoint gets a redirect back to an app that rejects a state it did not issue. Second, sign-in opens in Safari via UIApplication.open, not ASWebAuthenticationSession: Whoop's login page sits behind a Cloudflare bot challenge that never clears inside the auth-session web view — it renders blank on device and simulator alike — while real Safari passes it.

Because Safari backgrounds the app and iOS may terminate it before the callback returns, the pending PKCE verifier and state are persisted to the Keychain rather than held in memory, and as a list (capped at five, fresh for fifteen minutes): tapping Connect twice creates two valid in-flight authorizations, and the callback matches whichever state it carries. A separate manual flow exists for signing in on another device: state is prefixed manual-, the callback function renders the code on an HTML page for transcription instead of redirecting, and the user pastes it into Settings.

Token lifecycle

Tokens live in the Keychain (kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, so never in a plist and never in iCloud backups) as {accessToken, refreshToken, expiresAt}. Refresh is proactive: WhoopSync treats a token as expired sixty seconds early and refreshes through the same Edge Function before fetching, rather than reacting to a 401 mid-sync. Whoop rotates the refresh token on every use, so the new pair is persisted before anything else happens.

Only a refresh 401 clears the credential A 401 from the refresh call means the grant itself is dead (revoked in Whoop's app, or the rotated token was lost), so tokens are cleared and Settings shows reconnect. A 401 from a collection endpoint throws accessDenied and keeps the tokens: it usually means the token's scopes predate the current scope list, and the fix is disconnect-and-reconnect, which the error message says in those words. Treating the two alike is what once deleted a credential granted seconds earlier.

Fetching: pagination, dates, and scoring states

  • Paged collections take start/end (plain ISO 8601, no fractional seconds) and limit=25, which is Whoop's maximum page size, not a choice. The response's next_token is passed back as nextToken until exhausted, with a cap of 20 pages per collection per sync; hitting the cap logs an error to OSLog and returns what it has.
  • Date decoding is custom. Whoop timestamps carry fractional seconds (2026-08-10T06:16:16.180Z), which Foundation's stock .iso8601 strategy rejects — with the default decoder, every record fails. The decoder tries fractional-seconds first, then plain internet date-time.
  • Unscored records are archived but not derived. Records arrive with a score_state of SCORED, PENDING_SCORE, or UNSCORABLE; only scored ones become samples. They still land in the raw archive, so a record that scores later is picked up by the next sync's re-derive.
  • No retry logic. A 429 surfaces immediately as "Rate limited by Whoop"; there is no backoff loop to write until something automated calls this code (see below).

The sync pipeline: archive first, derive second

WhoopSync.sync() is the whole ingestion story, and its order is the design:

  1. Load tokens (throw notConnected if absent), refresh proactively if expired.
  2. Fetch all five collections for a rolling trailing 14-day window, sequentially.
  3. Archive every raw payload into WhoopRawRecord, split per record, before any interpretation. A payload that was never stored cannot be re-derived from.
  4. Run WhoopDerivation over the fetched records to upsert DailyMetrics, SleepRecord, and WorkoutRecord rows.

There is no incremental cursor and no watermark: every sync re-fetches the same fourteen days, and idempotency comes entirely from upserts — the archive on (kind, externalID), DailyMetrics on the day, sleep and workout records on their provider IDs. Re-syncing is therefore always safe, and "which records are new" is a question that never needs answering. Sync runs on exactly three triggers, all user-visible: a successful connect, a successful manual code exchange, and the "Sync now" button in Settings. There is no background task and no timer yet; the nightly server-side job and the whoop-webhook receiver from 11.3 remain planned, and are what will eventually make morning data exist before the app opens.

The raw archive, and why it exists

WhoopRawRecord stores {kind, externalID, payload, receivedAt}, unique on (kind, externalID). kind is a plain string rather than an enum so an unseen collection lands as data, not as a failed insert. Two facts justify keeping every byte: Whoop rate-limits, and a derivation bug found six months from now must be fixable without asking for the data again. WhoopDerivation.rederive() rebuilds every derived row from the archive with zero network calls — and because every normal sync also derives from freshly archived payloads, the archive path is exercised on every sync and cannot rot. The columns deliberately mirror the Supabase whoop_raw table, so moving ingestion server-side later is a copy, not a redesign.

One splitting quirk worth knowing Recovery records carry no id of their own — a recovery is keyed by the cycle it scores, so WhoopRawSplit resolves id first and falls back to cycle_id. And because splitting re-serialises each record through JSONSerialization, the archive is semantically faithful but not byte-faithful (key order and number formatting may differ), a known and accepted limitation.

Derivation: from payloads to DailyMetrics

WhoopDerivation holds two invariants. Every write goes through MetricsStore.upsertBatch, which merges into the existing row for that day rather than replacing it — HealthKit owns steps on the same rows. And a nil field never overwrites a stored value: a sample that omits a field means "no reading," not "clear what you had."

upsert normalises any timestamp to startOfDay and merges: fields the closure doesn't touch are preserved. That is what lets HealthKit and Whoop write the same row safely.

The protocols MVVM needs to be added

The concrete API above returns @Model instances, which a ViewModel must not hold, see 2.6. Two protocols close that gap, implemented by MetricsStore in an extension: 

public protocol MetricsReading: Sendable {
    func days(from: Date, to: Date) async throws -> [DayRecord]   // most-recent-first
    func targets() async throws -> GoalTargets
}

public protocol MetricsWriting: Sendable {
    func logWater(_ millilitres: Double, on date: Date) async throws
    func logWeight(_ kilograms: Double, on date: Date) async throws
    func updateTargets(_ targets: GoalTargets) async throws
}

DayRecord is a Sendable struct mirroring the columns of DailyMetrics. The store converts on the way out.

Why the protocols return value types Handing a @Model instance to a ViewModel would give every screen a live, mutable handle on the database and make each one require a ModelContainer to test. Returning DayRecord costs one map per fetch and buys back both.

The protocol methods are async while the store's are synchronous. That is deliberate: the store wraps trivially today, and when a fetch eventually moves off the main actor no ViewModel or test has to change.

12.6Money and plan models

These sit beside the daily spine rather than on it. A transaction and a habit are both dated, but neither is a daily reading, and forcing them into DailyMetrics columns would mean one row per day could hold only one of each.

There is no runtime .env on iOS. The app is a signed bundle; anything shipped inside it is extractable. The governing rule is therefore: what must never leak, must live server-side.

TierLocationContentsIn git?

Chapter fifteen

15Cost and the allowance

Life OS ships free, so every user costs money and none of them pay it. That single fact caps the architecture, and it is enforced by a database constraint rather than by good intentions.

15.1The ceiling

Total running cost must stay under roughly two dollars per user per calendar month, covering cloud inference, the API backbone, Supabase, and notifications. There is no revenue per user, so this comes out of pocket and unit economics decide what can be built.

The requirement is that spending cannot exceed the allowance, not that it usually does not. Those are different engineering problems, and only the first survives concurrency.

The allowance is internal Users are never shown a balance, a meter, a percentage, or a dollar figure. It exists to bound what the app costs to run, not to be a feature. The only moment it becomes visible is when it runs out, and then it is one sentence.

15.2Where the money goes

The calendar assistant weakens the privacy boundary, and says so Every other workload escalates a MetricsDigest of derived numbers. The assistant escalates event titles and times, which are content rather than statistics and cannot be aggregated without destroying what makes them useful. This is a genuinely weaker guarantee than the rest of the system offers, it is disclosed once before first use, and it is the reason the assistant floors on-device rather than merely preferring to.

15.3Why the ceiling holds

The obvious approach does not work: 

read spend  ->  if under cap  ->  call  ->  add cost

Two concurrent requests both read $1.98 and both proceed. Any scheme that reads and writes in separate statements has this gap, and a ceiling that leaks under concurrency is not a ceiling.

So the proxy reserves worst-case cost before calling and settles against actual reported usage afterwards, with the invariant expressed as a check constraint in the schema. A request whose reservation does not fit is refused with budget_exceeded before any money is spent. Four properties follow:

PropertyHow
Concurrency-safeThe constraint is checked by the database, not by application code between two statements
Prices cannot drift from modelsRates are resolved from the provider catalog for whichever model is configured, never hardcoded beside it
Fails closedNo catalog and no cached price means the request is refused, not attempted at a guessed rate. Guessing low is the one path that breaches a ceiling
Bounded loopsEach round of a tool-calling loop reserves separately, so a runaway loop is stopped by the ceiling rather than by trusting its own round cap
An unavailable coach beats an unbounded bill Refusing on a missing price is deliberate. The refusal surfaces as unavailable rather than as budget exhausted, because they are different problems and deserve different messages.

On the current demo tier, one flash-class model serves both roles at $0.10 per million input tokens and $0.40 per million output.

The selection rule is not cheapest available but cheapest model meaningfully more capable than on-device, which in practice means a large context window, since exceeding the on-device context is the expected escalation trigger.

Appendix A

AProduct thesis

A.1The thesis

Every health app you already have is a silo. Whoop knows your recovery but not that you skipped breakfast. Apple Health knows your steps but not that you blew the grocery budget and slept badly because of it. Each one gives advice that is correct in isolation and useless in context.

Life OS is built on a single bet: the value is in the join, not the collection. A coach that can see you missed meditation, logged 5 hours of sleep, journalled "low focus," and went 900 calories over can say something no single-purpose app can. That is the entire reason to build one app instead of using five.

Everything in the architecture follows from that bet. There is one table keyed by date that every source writes into and every reader reads from. Cheap manual modules ship early precisely because they make the coach smarter, not despite being simple.

A.2Product PR FAQ

Working backwards · Product

Life OS is a personal dashboard that pulls together everything your devices already know about you: weight from your scale, recovery from your strap, movement from your watch, and what you ate from a photo. It answers one question every morning: am I on track? Open it and a grid of dots shows the month at a glance. Filled means a good day. The app knows what a good day means because you told it.

Who is this for?

One person. This is a personal app, sideloaded on the author's own devices. There are no accounts, no other users, and no App Store distribution. That constraint removes an enormous amount of architecture and is load-bearing throughout this document.

Why not just use Apple Health?

Apple Health is an excellent store and a poor interpreter. It will show you a chart of anything and tell you the meaning of nothing. Life OS reads from it, then adds the layer Health deliberately doesn't: a definition of a good day, a streak that survives days you forgot to log, and eventually a coach that reads across domains.

What is explicitly not in this product?

Screen time analysis. It was requested and it cannot be built; see 10.5 for the technical reason. Rather than ship a hollow version, it is cut.

What's the hardest part?

Not the integrations. It's friction: any app that requires daily manual logging dies in about eleven days. Every product decision here is subordinate to keeping the daily cost near zero, which is why food logging is a photo, not a form.
